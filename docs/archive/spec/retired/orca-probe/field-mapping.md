`--run`, `--dispatch`, `--task`, and `--retry-request` are CLI selectors. SteerLine's business IDs remain separate from Orca's Run, Task and Dispatch IDs. The adapter must validate the returned host/worktree/Dispatch identity before applying a message. The successful raw result probe contained test IDs and a sentinel; a full SteerLine v1 business envelope has not yet been exercised.

## Invocation constraints learned on the remote

Use `worker-start --on <environment> --worktree new-top-level --repo id:<remote-repo-id>` for a new remote worktree. Later `worker-show`, `worker-read`, mail, stop and release calls use the home Run and exact Dispatch ID without `--on`. An existing remote worktree can be selected by its full `id:<repo-id>::<remote-path>` selector; creation flags such as `--repo` and `--base-branch` are then omitted.

On the tested Windows host, PowerShell 5.1 stripped inner JSON quotes from native CLI arguments. PowerShell 7.6.6 preserved `ConvertTo-Json -Compress` output passed as one `--payload` argument. The successful worker calls used the live Orca preamble's `--from` and Dispatch capability directly on the Orca CLI invocation. An automatic approval review rejected a wrapper that copied the capability into an environment variable; that attempt was stopped and its temporary script removed. Do not encode or store that capability to work around the rejection.

`worker_done` accepted a raw JSON payload containing `taskId`, `dispatchId` and `outcome`; it also preserved the custom `resultId` and nested result. The agent must choose **either** raw `--payload` **or** structured payload flags. Both forms were tried; the mixed form returned `invalid_argument` before enqueueing. The coordinator should reject a result with missing or mismatched identity, revision, required checks or applied decisions even if Orca settles the Dispatch.

An 8,192-character custom string and an unknown payload field crossed from the remote worker to the home Run intact. This establishes a measured lower bound for this version pair, not the maximum accepted message size. The true limit and oversized rejection behavior remain open.

## Paired environment reconnection

The [controlled reconnect sample](samples/disconnect-reconnect-2026-09-23.json) shows a live Dispatch before an Orca UI disconnect. The home fleet then reported `projection.liveness={verdict:unverifiable, reason:host_unavailable}`. The client UI subsequently showed Connected and `orca status --environment` returned the **same** remote runtime ID, but home `worker-show --dispatch` still returned `runtime_error: Runtime environment was disconnected or replaced.` The original unacknowledged question Delivery replayed with the same IDs. A direct read against the remote runtime returned `dispatch_not_found`, because the Run and Dispatch are owned by the home runtime. The remote terminal created for the Dispatch remained connected and orphaned.

The installed Orca version marks an explicit UI disconnect as `runtime_manually_disconnected` and retires the old runtime binding. This probe therefore tested manual-disconnect behavior, not the transient transport outage required by P06. Do not convert the home `unverifiable` verdict into an exit, answer the question, start a replacement worker, or release resources on the basis of the remote terminal handle. The original Dispatch was later verified and settled after the remote machine powered on; see the [recovery observation](samples/restart-recovery-settled-2026-09-24.json).

A [fresh-start attempt](samples/manual-disconnect-start-blocked-2026-09-23.json) on a separate Run was refused with `Runtime environment is manually disconnected` while `orca status --environment` reported connected. The new Run had no workers. The old home-runtime context could not start the next probe; it was subsequently restarted without treating the old Dispatch as settled.

After an authorized home Orca restart, the [restart observation](samples/home-restart-remote-unavailable-2026-09-23.json) showed a new home runtime ID and retained Run/Task/Dispatch records. The remote machine was powered off at that time, so the execution host could not confirm the old Dispatch. When it powered on, that exact Dispatch recovered, the original question was answered, and the worker settled. Later [center restart probes](samples/p07-center-restarts-2026-09-24.json) covered dispatch, message and answer checkpoints, including an in-flight worker-start interruption.

The later [transient transport probe](samples/p06-transient-2026-09-24.json) used a fresh, verified Dispatch and an automatically removed 30-second block of the remote Orca port. The home fleet changed from `live` to `unverifiable/host_unavailable` while the same unacknowledged question Delivery replayed. After transport restoration, `worker-show` returned `live` from the execution host with `exactWorker=true` on the original Dispatch. The Run retained one worker; reply and worker_done used the original IDs, release archived the transcript, and the worktree HEAD remained unchanged. This verifies P06 on the tested version pair.

## Output cursor boundaries

The [P03 output probe](samples/p03-output-2026-09-24.json) read live output using a terminal cursor and then released the worker after an accepted completion. Reusing that cursor with `--source auto` returned `source_changed`; a fresh read selected the archived transcript. Five bounded archive pages yielded 50 unique message IDs, while `contentComplete=false`, `clipping`, and a warning explicitly described older omitted history. The fresh worker printed 100 numbered lines, all distinct markers survived in the transcript, and payload clipping was reported. Consumers must restart without a cursor after `source_changed` and treat incomplete archive metadata as a real gap.

## Mutation response recovery

The [P08 response-loss probe](samples/p08-response-loss-2026-09-24.json) separated two caller states. With a saved request ID, `request-show` returned `completed` for a reply and its exact retry replayed the original answer. When the home Orca runtime exited during worker-start, `request-show` returned `pending` with accepted Task/Dispatch IDs; exact retry returned `operation_unknown` naming the original Dispatch, and `worker-show` verified it live. With the entire worker-start response discarded before its request ID reached the caller, read-only `worker-list` and `task-list` on the known Run found one matching live attempt. No fresh start was issued. The in-flight request remained pending after worker settlement, so consumers must keep the Dispatch-based reconciliation record rather than infer completion from request state alone.

## Agentless script receipt

The [P11 file-backed probe](samples/p11-file-receipt-2026-09-24.json) passed JSON input through an encoded PowerShell command to an Orca terminal. `terminal wait` returned exit code 7, but `terminal read` after exit returned an empty tail. The script wrote a versioned JSON receipt in the remote user's temp directory. After the home Orca runtime restarted, a second agentless terminal read the file, emitted a framed base64 JSON value, and the caller decoded and checked nonce, commit, stdout and exit code. The temp file and both terminals were removed. An adapter must bind that file path to the exact host/worktree and use a fresh terminal after restart; it cannot rely on the exited terminal's stdout.

## Compatibility and payload size

The [same-version P10 probe](samples/p10-current-version-payload-2026-09-24.json) sent 16, 24 and 30 KiB blobs with an unknown JSON field from home to one remote Dispatch. The worker reported all three exact lengths and field values. A 33 KiB attempt failed in local PowerShell before Orca started, so it gives no Orca rejection threshold. Mixed versions and host permission prompts remain untested.

## Verify result guard

The [P13 unit probe](samples/p13-verify-gate-unit-2026-09-24.json) exercises `remoteprotocol.ValidateVerifyGate`. The caller supplies durable expected business and Orca IDs, the candidate commit, required check IDs and the execution-host observed HEAD. The worker supplies a versioned verify JSON result and an accepted worker_done identity. A succeeded summary cannot override a missing check, nonzero exit, missing evidence or commit mismatch. The function does not start workers or advance workflow state; Spec 03 must wire it into the center before P13 can be marked end-to-end verified.

## Workspace and stop boundaries

The [P12 committed probe](samples/p12-committed-step-reuse-2026-09-24.json) first caught an agent that created a second worktree and reported succeeded while its Orca-assigned worktree remained at the base commit. Orca settlement alone did not validate the business workspace. A later pair of distinct supervised Dispatches used the exact assigned worktree: one cherry-picked a test artifact commit and released; the next read-only step verified the same HEAD, marker, branch and clean status. Spec 03 must compare result workspace identity with execution-host observations before applying a step result.

The [remote-runtime restart probe](samples/remote-runtime-restart-2026-09-24.json) observed a new remote runtime ID and a live exact original Dispatch with the same question Delivery; the worker resumed and settled after an explicit coordinator follow-up. The [disconnected stop probe](samples/disconnected-stop-2026-09-24.json) observed `stop_unknown/processAction=unknown` during transport loss. Even after the execution host verified the original worker live, Orca refused another stop and a follow-up as `dispatch_inactive`. With explicit user authorization the exact terminal was manually closed, exit verified, and the Dispatch abandoned as failed. This remains a production cancellation blocker on the tested version pair; manual cleanup does not establish a supported automated route.
