# 执行架构 Spec：共同约束

本 Spec 固定执行后端、中心状态机与远程接入的共同执行约束，由各阶段 Spec/Plan 引用和验收；它不单独启动一个实现阶段。

新流程变更由 #36 [单 worker 持续执行与统一待决策](../completed/worker-flow.spec.md)独立交付。该任务范围内，本文关于中心五步编排、步骤更换 worker、项目验证/修复门槛及答案应用证明的旧要求由其 §2–§8 替代；任务/DAG、唯一写者、消息身份、当前格式恢复及真实 PR 合并仍保留。本文其余旧流程描述不能用于宣告新流程已实现，也不改写已创建任务的固定契约。

远程执行分为三个 Spec：[01 Orca 远程协议验证](01-orca-remote-protocol.md) → [02 执行模型、最小状态机与适配器](02-execution-model-and-adapter.md) → [03 分阶段远程执行与 viewer 闭环](03-remote-execution-and-viewer.md)。本机双链路接口与会话契约由 [4A](../completed/pr-04a-execution-backends.spec.md)、[4B](../completed/pr-04b-conversation-events.spec.md) 定义，先落地的权威接口由后续阶段复用。

本文与具体阶段 Spec 共同构成执行依据。自动派发保持单活动执行；不同任务的人工启动遵循 [人工并行启动任务](../completed/manual-parallel-start.spec.md)。共享部署、移动端和同任务多 agent 并行不因本 Spec 被隐式纳入当前阶段范围。

## 实施顺序与依赖

| 顺序 | Spec | 交付门槛 |
| --- | --- | --- |
| 1 | 01 Orca 远程协议验证 | 确定真实 Orca 能力、身份和恢复边界，交付可复现证据及协议映射 |
| 2 | 02 执行模型、最小状态机与适配器 | 完成中心状态机、事务存储和本地/替身验证；远程接口遵循 01 已核实的协议 |
| 3 | 03 分阶段远程执行与 viewer 闭环 | 依赖 01 必需能力验证通过、02 实现完成，进行远程接入及端到端验收 |

默认按 01 → 02 → 03 顺序交付。01 的真机探测期间，02 的领域模型、状态机和本地存储测试可以先行；外部协议映射仍以 01 的实测结论为准。远端尚未就绪时允许继续 02 的独立工作，但不能跳过 01 的验收门槛而启用 03 的生产远程路径。

## 中心服务与执行层

- SteerLine 是业务状态的唯一权威，负责流程、任务领取、派发策略、人工决策、恢复以及最终完成核验。先部署在个人电脑，后续可迁到共享服务。
- 远端仅需 Orca、agent 和仓库所需工具及脚本，不要求部署 SteerLine 服务。
- Orca 管理执行现场：worktree、分支、agent、执行身份、输出和跨机消息。SteerLine 通过执行适配器接入 Orca；产物可以保留在远端，仅回传状态、决策和必要结果元数据。
- 桌面 viewer 和未来移动端通过同一服务接口查看状态、提交人工操作。业务状态切换由中心服务持久化；共享部署时按用户或组织隔离项目、权限及 Orca 连接。
- Spec 02/03 实现最小中心流程（不扩入控制台 4A/4B 的交付范围）：准备、实现、验证、按配置审查、发布 PR、等待合并、结项。SteerLine 决定步骤顺序、通过条件和修复回路；目标项目提供步骤内的基础技能或脚本，例如特殊测试与 PR 流程。技能不能自行推进中心流程。脚本可以在 Orca 管理的远端 worktree 内运行，无需常驻 SteerLine 服务。

目标远程适配允许使用 Orca 的受监管 worker、Dispatch、消息和 ask/reply。Orca 执行记录与 SteerLine 业务任务建立映射，业务 DAG 和完成判定仍归 SteerLine；具体权威与生命周期边界见 [Hosting 红线](../../../hosting.md)。

## 长期支持的执行路径

local Codex 与 Orca 均为正式、长期维护的执行后端。backend、agent、execution target 和协议版本分开；Orca terminal v2 与未来 supervised 属于同一后端族的不同协议实现。远程演进不移除 local，不提供不确定情况下的跨后端自动 fallback。

Service 持有唯一业务状态机和存储写入权；后端适配器只执行固定意图并返回事实。启动、观察、输出、回答、停止执行、分离观察和资源结算使用共同契约，能力差异有版本与原生证据。UI/CLI 共用 Query/Command 和会话模型，不直接操作平台终端或 OS 进程。接口与验收见 [控制台 4A](../completed/pr-04a-execution-backends.spec.md)、[4B](../completed/pr-04b-conversation-events.spec.md)；后续 SQLite 与 remote 复用它们，不建立第二套抽象。

进度消息、最终回复、轮次结束与业务完成分开；过程折叠属于 UI 视图状态。完整输出先持久化再推进来源游标，缺口与未解决问题始终可见。单纯输入接受不能作为决策已应用的证明。

## 执行身份

Task、WorkflowRun、Execution 和 StepAttempt 分别标识任务、一次流程、执行现场和步骤尝试。每个 Task 只保留一个权威活动 WorkflowRun/Execution；不同 Task 可由操作者并行启动。重试产生新的 StepAttempt，并保留原尝试和迟到消息。Orca Task/Dispatch 是平台身份，不等同于业务 Task。worker 成功只提供步骤事实，任务交付仍由中心核验。

同任务多 agent 候选、比较、整合和并行调度留待相应产品阶段另行设计；本阶段不实现其状态、命令或验收矩阵。

## 恢复与状态切换

业务状态转换和外部执行分开持久化：先记录待派发意图，再记录 Orca 回执。消费消息时先落盘和去重，再确认接收；外部动作依赖 Orca 支持的请求恢复机制和具体脚本的幂等性，不能承诺跨系统天然恰好执行一次。

每次观察或决策回答都核验所属任务、执行、尝试及外部身份。对同一待处理决策，中心服务处理重复提交与并发回答；网络不确定时保留待核实状态，不从超时推断执行已退出，也不自动启动替代 worker。

本地服务停止时，已启动的远端 worker 可以继续执行；中心流程待服务恢复、读取消息并完成对账后再推进。未来共享服务可以部署多个进程，但同一业务状态转换必须有事务或等价的并发控制。

## 上线前数据边界与后续验证

项目尚未上线，不为旧 runtime v1–v4、旧 SQLite、旧 Beads 数据或旧客户端协议开发读取器、导入器与回退流程。新中心格式要求干净的状态目录；检测到不支持的旧状态时拒绝启动有副作用的服务并说明原因，由人先核实可能仍在运行的外部 worker、PR 和资源，再决定如何处置旧目录。此规则不减免当前格式的重启恢复、同一 Operation 对账和数据损坏时的保守阻断。

原生任务的 [共同约束](../../../spec/native-task-constraints.md) 固定身份、状态机和单写者边界；[任务模型](../completed/task-core.spec.md)、[固定 DAG](../completed/task-dag.spec.md)、[原生接入](../completed/beads-exit.spec.md)、[关系视图](../completed/dag-view.spec.md) 各有独立 Spec/Plan 和实现 PR，分别交付。这些任务不以全部远程闭环完成为前置。系统不提供任务拆分、交付回退或动态依赖修改流程，用户可在系统之外分析并人工处置；故障恢复与固定任务契约下的重试继续支持。

- 先完成单 Execution 的最小分阶段远程闭环：中心逐步派发、输出、人工决策、阶段结果、断线对账和服务重启恢复。新流程不以一次 `execute_workflow` 包办全部步骤。
- 当前 `Run` 同时承载任务、执行和交付信息。新增模型时直接建立新的身份和存储结构；不能仅改字段名称或直接提高并发数。
- 每个固定 attempt 的步骤结果和工作区事实须在远程契约中指定执行位置与传输方式；不能引用中心服务目录路径或额外任务来源/结项服务。
- 远端版本对 worker、消息、输出和脚本执行回执的支持，需要真实环境验证。共享服务器的 Orca 协调运行时部署、用户连接隔离与网络可达性也需单独验证。
- 多 agent 候选、移动端和共享部署在需要时另行形成 Spec，本阶段不实现对应状态或接口。
