# PR 4C Spec：执行控制台与轮次折叠

任务 ID：2；任务名称：执行控制台与轮次折叠。

状态：已实现并验收；[验证报告](../../../validation/pr-04c-console.md) 记录 U-A1–U-A15 的自动化、原生 Windows 服务窗口和 local/Orca 会话证据。验收范围为当前 Windows amd64 与 PR 4B 已测的本机 Codex/Orca 目标。依赖：PR 1–3、[4A](pr-04a-execution-backends.spec.md)、[4B](pr-04b-conversation-events.spec.md)。对应 [Plan](pr-04-console.plan.md)。保留原 PR4 文件路径；本文件现在对应交付阶段 4C。

## 目标

把现有查看器升级为日常执行入口。用户在一个终端界面中切换项目、查看服务窗口启动入口并连接服务、选择 ready 任务开始执行、控制派发并查看运行详情。UI 通过共享客户端发指令，业务校验和状态变更由服务完成。

local Codex 与 Orca 使用同一执行/会话读模型。每轮过程消息可折叠，明确轮次结束时自动收起过程，最终回复独立保留。UI 不按后端名称维护两套消息或业务状态逻辑，能力差异由 4A/4B 的版本化报告驱动。

## U1：入口与项目

- `steerline console` 枚举 `<STEERLINE_HOME>/etc/*.json`；`-config <path>` 只打开显式配置的项目，即使该配置不在 etc。
- `-run-id <run-id|task-id>` 在所选项目中定位已有运行；找不到时显示提示，不静默聚焦另一个任务并暗示匹配成功。
- 无配置时显示配置目录和建立配置的说明。某一配置损坏时保留项目行及错误，其他有效项目正常可用。
- 多项目切换只改变观察/操作目标；Windows 服务窗口独立于控制台运行。项目显示服务状态、当前执行、待决策数和需人工处理数。
- 控制台按配置路径和 run_dir 保存视图身份，控制指令按实际 repository identity 与实例定位。不同配置指向同一仓库时显示关联/冲突，不能借此绕过单仓库服务锁。
- 后台刷新、命令结果、决策弹窗都携带项目与目标身份；换项目后到达的响应不能更新新项目的视图。

## U2：信息布局

默认宽屏布局示意（精确颜色、边框不是契约）：

```text
SteerLine  项目 A | 服务已连接 | 手动 | 派发正常 | 最近更新 1s
项目          Ready / 运行中 / 待决策 / 待合并 / 需处理 / 历史
 A  1决策     任务/运行列表                  详情 / 活动 / 尝试记录
 B  离线      ID     标题       当前阶段     task、run、attempt 身份
              ...                           执行 / 交付 / 任务状态
                                            PR、工作目录、错误与摘要
                                            当前对象可用操作与原因
状态：开始 B 的请求已提交，等待服务确认
快捷键提示：随当前焦点、模式和对象变化
```

- Ready 是提供方候选，run 列表是执行记录，不能把从未启动的任务伪造为 pending run。
- 待决策、需处理和运行中有清晰计数。错误/unknown 不因为有旧的 succeeded 字段而显示完成。
- run 详情分别显示 execution、finish、任务状态与最后核验时间；缓存事实注明采样时间，不显示成实时状态。
- 展示 PR 状态、queried_at 和 query_error，保留 PR 链接；只有 completed 才显示整体完成。
- activity/会话展示所选 execution/attempt；较早尝试通过 QuerySource 读取当前格式记录。切换尝试不会改变当前执行目标；UI 不自行拼宿主日志路径。
- 无日志、服务离线、候选查询失败、没有 ready 任务和执行槽被保留使用不同空态。
- 窄屏采用可切换的单面板，能读完整详情和操作说明；不能像当前 viewer 一样只剩列表而失去详情入口。

## U3：动作与反馈

| UI 动作 | 请求/行为 | 可用条件 |
| --- | --- | --- |
| 查看服务窗口入口 | 展示 PR 3 的固定启动器与配置路径，由用户独立打开；UI 不创建服务子进程 | 明确离线/未启动，配置可解析 |
| 连接/刷新 | 只读连接和快照刷新 | 项目可读取 |
| 开始所选任务 | start_task | 服务就绪、manual、未暂停、无槽阻塞、选中 ready 候选 |
| 切换手动/自动 | set_dispatch_mode | 服务就绪，显示切到 auto 后可能开始领取 |
| 暂停/恢复派发 | pause_dispatch / resume_dispatch | 服务就绪；当前模式保留 |
| 停止服务 | stop_service | 有可定位实例，显示对当前 worker 的 shutdown 后果 |
| 退出控制台 | 仅退出 UI | 始终可用 |

- 开始、切自动和停止使用显式动作键/命令面板；Enter 默认打开详情。只有停止可能中断 worker 的动作需要展示影响并确认，普通选中/浏览不产生执行。
- 点击开始后立即显示 task_id 和 request_id，并禁止同一视图重复提交；直到确定结果前继续跟踪原请求，不能因为 UI 超时再生成新 ID。
- 展示 submitted、applying、applied、rejected、failed、indeterminate。start applied 时跳转/提供导航到对应 run；worker 随后失败时展示 run 的真实状态。
- 回执丢失或超时显示“结果待确认”，允许按原 ID 查询。stale_revision 说明状态已变化，刷新并让用户重新选择，不自动重发有副作用动作。
- 服务不在线时已有 runs/日志仍可看；Windows 显示服务窗口入口或不可用原因，Linux 按平台能力展示启动动作。重连后不自动提交离线期间尚未确认的任务动作。
- 键盘焦点明确：列表、详情、日志、动作面板各自处理按键。输入控件内字符不触发全局开始/停止快捷键。

## U4：刷新与性能

- 前台项目状态/回执目标刷新间隔约 700ms–1s，后台项目摘要约 5s；以可注入计时器实现，慢请求不得堆叠。
- 候选任务直接读服务的 tasks 快照；UI 不直接轮询任务提供方。实例不同、查询报错或距最后成功查询超过 `max(3 × task_poll, 30s)` 时视为不可操作的缓存，禁用依赖候选的操作并显示刷新原因。
- 使用 PR 1 的选择/cursor/generation 规则；各项目恢复自己上次选择、筛选和日志跟随状态。
- 错误不通过刷新被瞬间清空；区分当前持续错误和已经结束的动作结果。切换项目后仍能回到原项目查到原 request_id。
- UI 退出无需等待后台任务结束；它等待的只应是自身必要的终端清理。

## U5：决策展示

- 显示待决策问题、明确 decision_id 和执行身份；本阶段不通过旧答案文件提交回答。完整决策提交及恢复由 [人工介入 Spec](pr-05-intervention.spec.md) 通过唯一命令入口交付。
- 仅后端接受输入不能展示“答案已应用”；待决策卡片不因折叠或 UI 重开消失。

## U6：控制台入口

- 提供 `console` 命令和 Windows 启动入口；`projects` 菜单可进入同一控制台。旧 watch/viewer 的协议格式和别名不是本阶段交付门槛。
- Windows 服务窗口仍由用户从固定入口打开；进入控制台不改变服务派发模式。

## U7：会话分组与自动折叠

- 使用 4B 的 Session/Turn/MessagePhase 模型；按项目、execution、attempt、source segment、session、turn 标识分组。过程包括 commentary、工具活动和阶段 unknown 的消息；final_answer 独立可读，不能把最后一条 unknown 当作 final。
- 活跃轮次的过程默认展开，可手动折叠；明确 completed/failed/cancelled 后只自动折叠一次，保留最终回复和可见终态原因。失败/取消不能仅剩一条“已完成”的折叠标题。
- 轮次结束时若明确存在未补全 final，显示“最终回复待同步”；来源确认无 final 时显示“本轮已结束，未识别到最终回复”；无法对账时显示“最终回复状态未知”。迟到 final 补回原轮位置，不新建轮次、不再次折叠、不改任务完成状态。
- 等待用户/宿主授权、失联、静默均不自动结束轮次。未解决问题、权限等待、gap、采集错误在折叠区外保持可见；宿主等待只指引原平台处理，不伪造业务答案按钮。
- 下一轮建立新过程组，保留历轮 final 和展开状态；同会话多轮不能因共用 item ID 合并。turn 结束不会使 waiting_decision / waiting_pr_merge 变成业务 completed。
- 折叠行显示状态、耗时（缺时间则未知）、条目数与警告/错误数；键盘可展开/收起，焦点不被后台更新抢走。

## U8：视图状态与阅读位置

- 折叠状态保存到 UI 自有版本化视图文件，不能写 runtime、业务 Store 或平台会话。记录 auto/manual、保持展开、已处理的终态及稳定分组 ID；新客户端首次打开历史终态默认收起过程，已有手动展开优先。
- 当前轮可明确选择“保持展开”；普通手动折叠保持到用户再展开。历史轮手动展开后，刷新、重连、UI 重开和 late final 不重新收起。两个窗口采用各自的视图身份，不能互相覆盖展开意图；配置切换后仍隔离项目状态。
- 折叠状态无效或文件损坏只重置视图并提示，不阻断业务读取；原子保存，缓存不持有正文、凭证或业务控制权。
- 滚动锚点使用稳定 group/item/body revision 与行偏移；折叠隐藏了当前锚点时定位该组标题。用户在读历史不强制滚到底部；显式“跳到最新”恢复跟随。切页或正文更新时不拼接不同 revision。
- 最终回复通过有界正文分页完整阅读，显示 partial/truncated/missing 和加载错误；自动折叠不能删除或截断存储内容。正文按纯文本安全呈现，控制字符不得作为终端指令执行。

## U9：能力差异的展示

轮次/阶段可靠时提供精确折叠；有轮次但无 final 时如实显示未识别最终回复；只有原始输出/结果时使用“执行过程 / 执行摘要”，仅在权威执行结算确认后执行级折叠。显示能力原因与来源，不能宣称降级视图实现了精确轮次能力；UI 不通过文字或沉默猜测协议字段。

能力探测失败或来源变化时保留已有组的证据和视图状态，新区段明确来源/缺口，不能把历史已验证消息整体降格或接到错误轮次。查询是只读行为，展开/折叠不触发上游 Reply/Continue 或业务重试。

## 范围限制

本轮不添加任务创建/编辑、DAG 编辑、批量排队、终端自由发消息或 PR 合并。外部宿主终端可用于只读诊断；控制台的任务操作始终通过服务状态机。
