# PR 3 Spec：后台服务生命周期

状态：本分支已实现，待协调审核。依赖：PR 2。对应 [Plan](pr-03-service-lifecycle.plan.md)。

当前 Windows 宿主中的测试进程处于不允许脱离的 Job Object 环境。实现会检测并明确拒绝这种启动；因此本分支尚未取得“启动父进程退出后服务与 worker 仍存活”的成功实测证据。该验收门槛保留给协调审核/合并前在允许 breakaway 的 Windows 会话复测。

## 目标

提供可由控制台调用的服务连接、后台启动和停止能力。控制台与服务拥有独立生命周期，打开或关闭 UI 不等于开始或终止任务。

## L1：服务连接与实例探测

连接结果需同时包含最后快照、新鲜度、进程探测和控制协议能力，不压缩成一个模糊的 online 布尔值。

| 观察结果 | 展示与动作 |
| --- | --- |
| 新鲜快照、身份匹配、ready=true、协议兼容 | 已连接，允许提交相应能力支持的控制指令 |
| 身份匹配但 heartbeat 过期或 ready=false | 服务异常/初始化中，保留原实例；禁止自动另起一个服务 |
| 进程确定不存在，或 PID 已属于另一个进程 | 离线，旧运行状态按历史展示，可显式启动服务 |
| 权限不足或身份无法核验 | 存活未知，展示原因；不把它当成进程已死 |
| 无 runtime | 未启动/无记录；可发起启动，实际唯一性由仓库锁仲裁 |
| 状态文件损坏、版本不支持或身份不匹配 | 显示诊断；不能覆盖状态或假装启动成功 |

新进程探测 API 返回确定不存在、身份匹配、身份不匹配和不可核验四类。不能沿用目前把 absent 与 inaccessible 合在一起的字符串结果作为启动依据。

连接必须核对 repository identity、run_dir、remote/branch 与 claimant；配置和运行对象不匹配时禁止提交控制。当前配置文件摘要若与 service.config_digest 不同，提示配置已修改、需停服后重新启动才生效；此时保留观察和明确实例的 stop，禁用其他变更动作。旧 v1–v3 快照可观察，但缺少协议/实例证明时只提供明确的升级或原 CLI 处理说明。

## L2：显式后台启动

- 提供共享 `StartService` / `ConnectService` / `StopService` 客户端方法，以及便于验收的 `steerline start-service -config ...`。
- 控制台只在用户点击“启动服务”后调用 StartService。已存在兼容服务时连接它，保持它当前的 manual/auto 和暂停状态。
- 新服务使用稳定安装路径 `<STEERLINE_HOME>/bin/steerline.exe`，参数数组为 `run -config <绝对路径> -dispatch manual -console off -startup-id <id>`。开发/测试可注入明确的可执行文件；生产路径缺失时提示安装，不能静默挑选旧工作目录中的 exe。
- 启动参数包含唯一 startup_id。客户端先以运行目录内独立的 launch 锁串行化同配置启动，再检查已有实例。launch 锁不替代服务的 repository/run_dir 锁，也不能由父进程持有服务锁等待子进程。
- 两配置映射同仓库但不同 run_dir 时，服务仓库锁仍拒绝第二个实例。错误需指向冲突仓库，不能把另一个运行目录错误地当成自己的服务。
- stdin 与 TUI 脱离；stdout/stderr 写 `service/startups/<startup_id>/service.log`，后台进程不争用控制台屏幕。
- 使用独立启动函数。现有 worker 的 `startProcess` 会绑定 kill-on-close Job Object / 父进程死亡信号，不能直接用于后台服务。
- Windows 必须保证关闭启动它的 UI 后服务仍存活，包括处理父进程 Job 的继承限制；Linux 不使用 worker 的 Pdeathsig，并脱离终端会话。无法保证脱离时返回明确错误，不能显示为已托管。

## L3：启动握手

- `cmd.Start` 成功只表示进程创建，UI 显示“启动中”。只有看到匹配 startup_id、完整实例身份、ready=true 的新快照，才显示服务已连接。
- ready 在服务取得两把锁、读取/恢复快照、处理控制 checkpoint、初始化指令消费后发布。manual 启动不进入新任务 dispatch；初始化后的 PR 核验与既有答案应用继续。
- 子进程在 `service/startups/<startup_id>/startup.json` 记录 started/failed、实例身份及错误。该文件仅表示这次启动尝试，不是服务/任务状态权威；即使未取得服务锁，也可写自己 startup_id 下的失败诊断。
- 客户端最多同步等待 30 秒；超时显示“启动结果待确认”，保留 startup_id 继续观察。它不是再次启动授权，也不自动杀子进程。
- 若客户端在握手前退出，子进程仍能完成启动；下次打开通过 runtime 发现它。
- 在两个客户端竞争启动时，最多一个持锁服务 ready。另一个可在核对仓库、配置和协议兼容后连接获胜实例，否则报告冲突。

## L4：停止与退出

- `StopService` 提交 PR 2 的 stop_service，展示正在停止、请求结果以及进程是否已退出。
- stop applied 表示服务已持久化最终 stopped 状态；客户端还需核验原身份进程退出/锁已释放，才开放“重新启动”。短暂退出收尾期间显示“停止收尾中”。
- 异常退出时，允许展示“进程已退出，停止回执未确认”，不能把未收到回执等同于失败并重新发起其他动作。
- UI 退出、断开、换项目和读取超时都不发送 stop。服务停止必须由明确动作触发。
- 对停服造成的 worker 终止继续保留原有 failed/blocked、claim 和 worktree。暂停与停服的说明由 UI 显示，底层语义不随 UI 变化。

## L5：兼容与范围

- 前台 `run`、`stop` 和批处理入口继续可用。连接前台启动的 auto 服务时要展示实际模式。
- 本 PR 支持本机、当前登录会话中的后台运行，不引入 Windows 系统服务、开机自启或跨用户管理。
- 启动时沿用现有 preflight。工具、技能或 Orca 不可用时，提供启动日志与具体错误；不会降低检查或更换 host 来让服务显示在线。
- 旧二进制缺少控制能力时展示不兼容；不能靠直接编辑 runtime 升级活跃实例。

## 验收标准

| ID | 场景与结果 |
| --- | --- |
| L-A1 | 后台启动成功有匹配握手，手动模式下没有新任务 claim/start |
| L-A2 | 强制结束 UI 父进程，后台服务和其正在运行的 worker 保持同一身份存活 |
| L-A3 | 重开 UI 连接原实例，服务/worker 数量未增加 |
| L-A4 | 两客户端同时启动、同仓库不同配置启动，至多一个服务取得锁 |
| L-A5 | preflight 失败、子进程早退、握手超时均展示真实状态和日志，不显示假在线 |
| L-A6 | PID 复用、权限不足、stale heartbeat 分别正确分类；未知不触发替代启动 |
| L-A7 | stop 与退出 UI 的行为分开；stop 结果与进程退出均可核验 |
| L-A8 | 旧快照只读可看；协议/配置冲突不会向错误实例提交动作 |
