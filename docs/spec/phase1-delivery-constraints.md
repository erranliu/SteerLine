# 第一阶段交付共同约束

本文约束 #36 的持续 worker 基线，以及 #37–#42 的候选、版本和组合交付。每项任务各有独立 Spec/Plan 与一个实现 PR；本文不代替执行任务。

## 权威与执行边界

复用[持续 worker 流程](worker-flow.spec.md)、[原生任务共同约束](native-task-constraints.md)、[服务生命周期](pr-03-service-lifecycle.spec.md)和[会话契约](pr-04b-conversation-events.spec.md)中仍有效的身份、权限、消息与交付要求。SQLite 是 Task、执行、反馈和 TaskDelivery 的唯一权威；UI、运行选择文件及候选汇总不复制业务状态。

worker 依据任务 Spec/Plan 实现、提交和创建 PR。测试、修复、审查及文件提交要求来自该任务契约；中心不维护五步、验证/审查结果链、修复轮数或工作树 dirty 门槛。

#37 明确扩展 #36 的单候选边界：一个 multiple Task 可以有多个 WorkflowRun，每个候选内部仍保持一条原 worker 会话。一个 Task 只记录一个经真实 PR 合并核验的 Delivery；合并前的候选评价由用户完成。中心不能保证阻止在途独立 worker 发布，也不能把落选等同于资源停止。

## 操作与持久化

新的开始、反馈、候选或版本选择保存固定意图后再执行外部调用；回执和消息持久化后推进游标。相同请求重交复用原记录，未知外部动作先对账，不能改 ID 盲重发。主状态表达用户进度，传输/资源错误是事实，不衍生项目专用恢复状态机。

PR 真实存在、归属和实际合并由 provider 核验；唯一交付、Task.closed 和后继资格同一事务提交。任务丢弃沿现有未合并核验和资源保留规则，不把用户任意反馈当成直接修改中心状态。

## 格式与版本隔离

本组以 #36 实际发布的持续会话协议为基础。默认不兼容旧开发配置、数据库或执行记录，不保留旧 schema 5/legacy 摘要双模式；若独立任务要求跨格式保留，必须另行明确输入范围和受控转换。当前格式内的 Task/会话/消息/PR 重启恢复及原操作对账必须通过。

不支持的格式在外部副作用前拒绝，原库和外部绑定保留供人工核实，不清库升级、不恢复旧快照掩盖副作用。stable/dev 用不同 home 和测试仓库，同仓库跨 home 的单写锁继续生效。

#40 的构建 dirty 标志与目标项目文件改动是两种事实。stable 构建保持干净源码/固定摘要要求；worker 如何处理 `.meta` 等文件不由版本模块决定。

## 验证

各任务先验本范围，再运行所需 Go 完整回归、vet 和 Windows/Linux 构建。标准 Go 回归命令为 `go test ./... -count=1 -timeout=45m -p 1 -parallel 1`；不同任务复用前置真实能力证据，只重验自己的增量和受修改影响的边界。#36 验单会话，#39 验多候选，#42 验版本组合与24小时，#53 验原生规划/产品链。

真机使用隔离项目和当前已认证目标；模拟或编译通过不等于平台通过。测试 PR 由操作者合并，系统只核验；远端取消不支持的模式按实际能力展示。证据位于各任务 `docs/validation/` 目录。纯文档修改检查身份、依赖、链接和语义，不运行实现验收。
