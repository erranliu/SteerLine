# Spec：dev 隔离与 stable 提升

任务 ID：31；任务名称：dev 隔离与 stable 提升；目标：`PHASE1-RUNTIME`。配套 [Plan](runtime-isolation-promotion.plan.md)。状态：待实现与验收。一个独立实现 PR 交付。

## 范围与前置

硬前置：#30。依赖[固定版本与双入口](versioned-runtime.spec.md)，遵守[共同约束](phase1-delivery-constraints.md)。交付两个可同时使用的独立运行环境，以及从已发布版本选择 stable 的受控提升；不建立第二份生产 Task 权威或通用升级框架。

## 隔离

stable/dev 使用不同规范 home，配置、SQLite、日志、锁、发现/凭证、命令目录、工作树根及能力报告各自归属 home。生产仓库仅注册到 stable，dev 使用独立测试仓库；不复制可被两边派发的生产数据库。初始化和启动核验规范路径、仓库 origin/目标分支及现有项目锁，拒绝 home 别名或重叠写目录；Windows 大小写、分隔符与可解析链接不得绕过判等。同一仓库跨 home 启动依旧由既有仓库锁互斥。

dev 的构建、运行、崩溃和重生成入口只影响 dev。能力认证绑定实际后端/目标/平台/构建证据，dev 探测不能静默替换 stable 的报告。stable 能保持任务处理和日志积累；诊断中可核对实际 home/channel/build_id 与目标。

## 提升流程

提供显式提升命令，携带 request_id、expected selection version、目标 build_id/manifest 摘要、操作者及原因。只读预检先返回准确 blocker：版本完整性、格式支持、配置/项目归属，以及该 home 下所有注册项目的进程/Operation/执行状态。首版不支持在活动 worker、未知外部动作、未结算回答/派发或平台身份无法核实时提升；暂停派发和服务退出都不替代外部停止证明。等待合并且全部 worker 已精确结算的任务可提升，原 PR 与 claim 必须保留。

受理后持久化部署意图、原/新选择和固定项目清单，取得渠道维护 owner/request_id；阻止该渠道新服务启动、项目注册/配置变更、dev select 和并行提升。每个已运行项目在自己的中心事务中持久化维护屏障，暂停所有新增外部副作用的准入：自动/人工领取、新候选、步骤启动、回答续跑、重试、发布以及有外部动作的恢复命令。UI 按钮不是屏障。既有派发意图、平台消息和 PR 观测继续以原身份对账，不能因维护而丢回执。未在列表的项目不能在此次提升中被加入。

屏障提交与任务动作意图写入在同一项目事务权威上仲裁。动作先提交则提升重查发现活动/unknown，拒绝切换；屏障先提交则新动作返回 maintenance_in_progress。所有项目均确认屏障，且再次核验没有在途/未知副作用后，才允许调用停服并取得仓库/状态锁。不通过预检不得停服；多项目屏障部分取得后失败，只按本请求 owner 释放已取得屏障并恢复原派发设置。停服之前或期间出现身份不明时保留阻塞，不强制终止外部 worker。

进程/机器中断后屏障不靠超时自动释放；新启动、直接 exe 和离线写命令必须在取得锁后核验持久维护 owner，只允许本次恢复继续。旧服务若不支持屏障协议，在线提升返回 unsupported_source_maintenance；操作者自行停服后只能走离线入口，先取得全部项目锁并核验外部执行，再进行任何格式或选择写入。恢复须核选择、进程及全部项目状态，成功或确定未切换且无未知副作用时按原请求释放屏障，不能撤掉别人的维护状态。

备份是在锁内取得的一致 SQLite/配置/选择快照，包含必要 WAL 内容与校验摘要；不是复制一个正在写入的 db 文件。选择前核验目标代码对全部项目当前状态格式可读且可恢复；不同 schema 默认拒绝。#26 明确实现的特定受控转换只有在目标构建包含已验证入口且输入精确匹配时才可使用，不根据版本号猜迁移。转换或备份未知时阻止新写者，保留原库和诊断。

使用 #30 的原子选择提交后，从固定入口启动新服务并核验实际 build/home/channel、项目身份、当前 schema 和恢复结果；只有全部项目恢复完成且服务 ready 才报告 applied。选择已提交但启动/核验失败时报告 selection_applied_start_failed，维持阻塞并保留恢复意图，不能宣称提升完成、自动回退旧二进制或恢复旧数据库。

本次启动必须携带原维护 owner，允许新服务进入只恢复不派发的阶段；恢复核验完成后由同一提升请求解除各项目屏障并恢复原派发设置。不得为了启动新服务先无条件清空屏障，或把 recovery-ready 误报为已恢复业务派发。

部署记录只管理版本选择和本次操作进度，业务事实仍来自原 SQLite。相同请求重放从持久检查点继续，同 ID 不同目标拒绝；进程退出、响应丢失和机器重启后先核实际选择与进程身份，不重复启动另一个服务。人工处置后继续原请求；通用强制清库、自动回滚及任意历史版本降级不在范围。

## 验收

| 编号 | 通过条件 |
| --- | --- |
| RP1 | stable/dev 在独立仓库同时运行；任务、问题、配置、能力、日志与发现不串线；同 home/重叠路径/同仓库双写被代码阻止 |
| RP2 | dev 构建和退出不改变 stable exe/选择/进程/任务推进，误连请求没有业务副作用 |
| RP3 | 活跃 worker、unknown Operation、不可核身份及未认证 schema 阻止提升；错误预检不停止健康 stable 或改变选择 |
| RP4 | 静止可恢复状态提升成功，原 Task/DAG、等待合并 PR、Command/Decision/Operation 与精确外部身份完整；没有第二份生产库或重复动作 |
| RP5 | 备份、选择提交、启动及恢复前后中断均可按同 request 对账；不能恢复旧快照掩盖新副作用或误报 applied |
| RP6 | 新服务启动失败保持明确阻塞；并行提升/启动、旧选择版本、异内容重放及渠道写目录别名均拒绝 |
| RP7 | 维护屏障与自动/人工领取、新候选、步骤、回答、发布竞态分别注入，两方只有一个取得副作用准入；部分项目失败、重启和离线命令不能绕过屏障；旧源版本不支持时在线拒绝、离线按锁核验 |

在隔离 Windows home 和测试仓库原生验收，证据路径为 docs/validation/runtime-isolation-promotion/。#32 再验证组合构建的持续运行与提升。
