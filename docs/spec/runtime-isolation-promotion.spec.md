# Spec：dev 隔离与 stable 提升

任务 ID：41；任务名称：dev 隔离与 stable 提升；目标：`PHASE1-RUNTIME`。配套 [Plan](runtime-isolation-promotion.plan.md)。状态：待实现与验收，一个独立实现 PR 交付。

## 范围与前置

硬前置：#40 [固定版本与双入口](versioned-runtime.spec.md)、#36 [持续 worker 流程](worker-flow.spec.md)。遵守[第一阶段共同约束](phase1-delivery-constraints.md)。交付独立 stable/dev home 和可恢复的受控版本选择；不维护项目五步、自动回滚或通用迁移框架。

## 隔离与维护资格

stable/dev 使用不同规范 home、测试仓库及所有可写运行目录。生产任务库不复制成可由 dev 派发的第二来源。同一仓库跨 home 仍由原仓库锁互斥，路径别名/目录联接不能绕过。版本和能力证据分别归属实际 build/home/目标。

持续会话存在不等于正在工作。允许提升的事实是：没有活动工作轮次和未核实启动/发送动作；空闲会话、已保存未发送反馈及 PR 关联可持久恢复；目标构建已证明能按当前格式重接这些原会话。不能确认轮次或投递结果时拒绝切换，不以暂停派发或中心停服代替核验。该规则也用于 #40 的 dev select 在本组合版本中的维护准入。

## 提升流程

操作者提交 request_id、选择版本、目标 build/manifest 摘要及原因。中心先只读检查版本完整性、项目/home 归属、状态格式和原会话的恢复条件，再记录本次维护意图及项目清单。

使用原中心事务建立短范围的维护屏障，禁止新任务/候选启动、会话新增反馈投递、配置/项目集合变更及并行版本选择。既有消息、PR 查询和外部操作回执继续按原身份对账。屏障只作用于中心拥有的入口，不宣称阻止已经运行的 worker 自行提交或创建 PR；发现活动轮次则本次提升不进入选择提交。

取得各项目屏障后复核空闲/可恢复条件，再停中心服务并在项目/状态锁内取得一致快照。任务动作与屏障竞争时按同一事务权威只允许一方提交；部分取得屏障后拒绝提升，只释放本请求拥有的屏障，保留输入和原任务状态。

目标代码必须支持当前状态格式；不同格式默认拒绝，不继续保留老 schema 5 的专项迁移例外。快照包含必要 WAL/配置/选择及摘要，不能复制正在写入的裸 db 冒充备份。切换使用 #40 的原子选择接口；版本未完整发布或原选择不匹配时拒绝。

新服务携带原维护请求启动，先重接原会话、对账未完成消息、查询 PR，再由同一请求解除屏障并恢复原派发设置。只有实际 build/home/格式及恢复结果均一致才报告完成；选择已提交但启动失败保留原请求和明确诊断，不自动回滚二进制/数据库，不清空 owner 以强行启动。

重启恢复使用同一个请求和选择记录，不重复启动服务或重发用户反馈。空闲会话重接失败时保留反馈和原绑定，不能创建替代 worker。维护记录只表达部署进度，Task/Decision/PR 仍来自原 SQLite 权威。

## 验收

| 编号 | 通过条件 |
| --- | --- |
| RP1 | 独立 stable/dev 同时运行无目录、任务、凭证、日志或能力串线；同仓库双写被拒绝 |
| RP2 | dev 构建/退出不改变 stable 的实际 exe、选择和任务状态 |
| RP3 | 活动轮次、未知启动/发送、无恢复能力或不支持格式阻止选择提交，失败预检不停止健康服务 |
| RP4 | 有空闲原会话、未发送反馈和待合并 PR 的当前格式成功提升，原 session/请求/Delivery 保持，无第二 worker |
| RP5 | 屏障、备份、选择、启动与解除屏障边界中断，沿原请求恢复，无盲重发或回滚掩盖 |
| RP6 | 错版本/home、并行提升、部分项目失败及选择后启动失败明确记录，只结算本请求 |
| RP7 | 屏障与启动/发送/配置变更竞争按真实中心入口核验；既有消息/PR 观察不丢失，不虚构项目步骤或发布锁 |

使用隔离 Windows home、测试仓库和已支持的原会话模式，保存 `docs/validation/runtime-isolation-promotion/` 证据；#42 验组合版本及持续运行。
