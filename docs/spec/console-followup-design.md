# 控制台后续交付提案：长期双后端与按轮次折叠

日期：2026-09-24。状态：方案提案，尚未实施。

依据：[控制台总览](console-upgrade.md)、[原 PR4 Spec](pr-04-console.spec.md)、[原 PR5 Spec](pr-05-intervention.spec.md)、[执行模型与适配器 Spec 02](02-execution-model-and-adapter.md)。

本提案重新划分控制台升级第 3 阶段之后的交付。这里的 4A/4B/4C 是交付阶段名，不是 GitHub PR 编号；第 3 阶段对应 GitHub PR #14，其内容、验收和分支不变。现有定时协调任务保持暂停，本提案不启动实现任务。

## 1. 目标与现状

local Codex 和 Orca 是长期正式支持的执行后端。新增功能通过明确的公共契约集成；平台存在能力差异时，展示真实支持范围，不把 local 视为将来要删除的临时回退。

目前只有 process/Worker 等局部公共类型。Spawner 实际只服务 local；Orca 在 Service 中另行建 worktree、启动 agent 并观察结果文件。local 采集 Codex JSONL，Orca 的监督器没有发布完整的 agent 消息；retry、决策续跑、停止和预检也存在宿主分支。因此消息折叠不能仅作为 viewer 的字符串处理功能实现。

本轮交付目标：

1. 两个后端共用启动、观察、停止、输出和恢复的行为契约，由同一业务状态机管理。
2. 控制台共用一种会话读模型；有可靠轮次信息时，按 turn 展示过程和最终回复，并在本轮结束后自动折叠过程。
3. 原始输出不足时提供明确的执行级展示；输出缺口、未知状态和未回答问题始终可见。
4. 后续中心状态机与 SQLite 工作复用这些接口，不建立第二套执行或消息抽象。

## 2. 交付顺序

```text

  → PR4B 统一会话事件、完整回复与持久读取
  → PR4C 执行控制台与按轮次折叠（扩展原 PR4）
  → PR5 人工决策与恢复（修订原 PR5）
```

| --- | --- | --- |
| 4A | local 与 Orca 都通过正式适配器运行，平台差异从业务代码中收敛，公共契约测试覆盖两边 | 新 UI、SQLite、远程生产路径、多执行并行 |
| 4B | 两边输出进入同一会话模型；阶段、轮次、最终回复、缺口与能力状态可查询和重放 | TUI 交互布局、任务创建、自动业务重试 |

## 3. PR4A：双执行后端契约

### Spec

执行后端与 agent 是两个配置维度：backend 为 local 或 Orca，agent 为 Codex 或平台实际支持的 agent。第一版 local 仅需实现 Codex；不要求为尚无需求的 agent 编写通用插件框架。当前配置继续兼容读取，历史运行的路由以派发时保存的绑定为准。

适配器接受不可变的执行输入，返回事实和回执，不接收可随意修改的 Run 指针。任务领取、派发许可、业务重试、PR 核验、结项及业务状态持久化归 Service。

| 契约 | 必须表达的语义 |
| --- | --- |
| Probe / Preflight | 当前后端、目标、agent、版本与配置下的能力和前置检查；未使用的本机工具不成为另一个后端的隐式依赖 |
| Prepare / Start | 输入固定工作区要求与执行意图；返回实际工作区/外部身份，以及 accepted、rejected、outcome_unknown；记录残留资源 |
| Observe | 原执行身份的存活、连接、新鲜度和宿主等待事实；不可达不等于已退出 |
| ReadOutput | 绑定来源的不透明 cursor、有界记录、历史保留范围及 gap/source_changed |
| Reply / Continue | 精确问题或原会话、固定答案和操作身份；区分收到输入、轮次开始、答案应用，不把 send accepted 等同应用 |
| StopExecution | 明确取消目标执行；返回接受/确认/拒绝/未知，确认需有停止证据 |
| DetachObservation | 仅结束中心侧监听，不隐式取消执行 |
| SettleResources | 在已结算的执行上释放或保留平台资源；默认保留 worktree 与产物 |
| ReconcileOperation | 查询已有外部动作或按已验证平台协议恢复原请求；不重新启动替代执行 |

不是所有后端都支持每个可选操作。能力返回 verified、unsupported、not_tested，并附原因、版本和目标；同一种能力在不同 agent/host 组合中可以不同。UI 和业务入口共用能力判断，不能只靠隐藏按钮保证安全。

当前 local 的受限 retry 和 Orca 的原终端 continuation 保持现有资格；未实现的 local continuation、Orca retry 继续明确不支持。长期正式支持要求两边的已支持行为均有测试和维护责任，不要求用不可靠的替代操作伪造能力相同。

StopService 的现有本机关闭策略由 Service 调用 StopExecution 实现；这次接口提取不改变 PR3 的本机服务/worker 生命周期。未来远程中心退出是否取消远端执行，由显式策略与 Spec 03 决定，不能由 DetachObservation 或析构行为暗中决定。

持久绑定至少能区分后端、固定目标与连接、agent、OS 或 Orca 外部身份及其代次。优先复用已有字段与同一存储入口；新增记录必须版本化。不得在严格解码的 runtime v4 中静默加入旧程序无法读取的字段，也不能把新绑定只留在内存。没有足够历史证据的旧运行保持 legacy/incomplete；不从当前配置猜测历史目标。

### Plan 与验收

1. 从 Service 中提取 local 准备/启动与 Orca 准备/启动，把共享的状态推进留在 Service；消除重复的启动后状态写入。
2. 用明确的后端注册/选择替代恒定返回 LocalSpawner 的 SpawnerFor；backend-specific 代码集中到适配器实现。
3. 接入观察、停止与错误分类，再把决策续跑/恢复的后端调用接到契约；业务资格仍由原规则校验。
4. 固定执行绑定、能力结果及不确定动作恢复行为；按实际后端拆分预检。
5. 两个适配器运行同一套契约测试，再补各平台的原生回归。

必需覆盖：成功/明确失败/启动结果未知、停止失败与超时、身份替换、修改默认 host 后操作旧运行、配置能力缺失、Detach 不取消执行、旧结果迟到和残留资源保留。Orca 的调用错误不能被吞掉后显示成功；local 的 OS 退出结果不能直接关闭业务任务。新旧后端的既有工作区、claim、PR 与决策回归均通过。

## 4. PR4B：统一会话事件和完整最终回复

### Spec

消息模型区分四个概念：

- Session：agent 的持续会话。
- Turn：该会话的一轮交互；一轮结束不代表会话或业务任务结束。
- Assistant message：进度消息 commentary、最终回复 final_answer，或明确标记的 unknown 阶段。
- Execution result：供 SteerLine 核验的结构化结果；它与面向人的最终回复分开保存与展示。

每条规范事件保留项目、run/执行、attempt、后端/来源、session、turn、item/event 身份及顺序信息。未来 Execution/StepAttempt 模型通过同一映射扩展；当前一个 Run 只有单执行不成为外部 API 的唯一性假设。没有原生 turn ID 的来源，仅在可靠的轮次边界下生成可重放的本地轮次键，并标记身份由适配器派生；来源发生变化时不能继续复用旧键。

消息完成与轮次结束是两个事件。收到某条 message 的 completed 不能关闭整个 turn；收到 turn.completed 也不能把已有进度消息改标为最终回复。失败、取消、等待输入、失联和正常结束分别表示。

输出能力按独立字段声明，例如：轮次边界、消息阶段、最终回复、稳定 item ID、增量读取、保留历史回放。不能因为后端提供文本或声明 structured-read，就假定全部能力已验证。

| 实际证据 | 展示契约 |
| --- | --- |
| 轮次边界和最终回复阶段均可靠 | 逐轮会话、过程分组、最终回复独立显示 |
| 轮次边界可靠，但没有最终回复阶段 | 可按轮折叠；标注“本轮已结束，未识别到最终回复”，保留可展开的全部输出 |
| 只有终端文本或执行结果 | 展示“执行过程”和“执行摘要”；仅在执行结算被确认后做执行级折叠，不宣称识别了 agent turn |
| 来源切换、历史淘汰或连接中断 | 明示缺口或观察未知；保留已存消息，不推断轮次/执行成功 |

本地 Codex 首先验证当前版本的 JSONL/记录出口是否保留 phase 与轮次结束事实。当前 --output-schema 的最终内容可能是任务结果 JSON；此时可以渲染其 summary 为“执行摘要”，不能把结构化结果伪装成独立的自然语言最终回复。

Orca 优先使用经过验证的结构化 transcript/输出接口，按原 Dispatch、session 与来源定位。terminal 输出可以作为明确标注的降级来源；不解析 TUI 屏幕中的标题、颜色、“完成”文字或静默时间来认定 final。若上游公开接口缺少阶段或轮次字段，记录能力缺口；需要精确同等体验时，以 Orca 协议补充作为前置依赖，不能仅靠提示词约定“最后一条就是 final”。

所有后端事件经过同一归一化与持久化入口。先保存内容再推进读取 cursor，崩溃后根据来源 ID/游标范围幂等重放；没有外部稳定身份时明确相应去重边界。source_changed 创建新的来源区段并记录 gap。已存历史不因切换项目、重连或 UI 重启而消失。

最终回复必须能完整阅读，不能沿用当前 activity Detail 的 4096 字符裁剪而无提示。采用有界分页或受管正文引用；保存内容摘要、大小、来源和截断状态。raw 和 CLI 流式输出保持兼容，UI 折叠不删日志。SQLite 尚未落地时使用既有持锁服务与版本化文件/日志接口；SQLite 落地后同一查询契约切换存储实现，不增加另一个业务写者。

### Plan 与验收

1. 保存本地 Codex 和本机 Orca 的脱敏原生样本，逐字段确认 session/turn/item/phase、失败/取消、等待和重放语义；记录版本组合与 verified/unsupported/not_tested。
2. 与现有 Orca Spec 01 的探测工作共用输出映射与证据格式；本机 Orca 能力不因远端未就绪而被标成已验证的远程能力。
3. 定义会话事件、能力与分页 DTO；扩展现有 Normalizer 和 Orca 输出适配，保留 unknown 与原始证据。
4. 实现正文持久化、增量合并、来源绑定、去重与 gap；查询层返回按轮次分组所需事实，不在读取时修改业务状态。
5. 两个后端运行同一会话契约测试；旧 activity 缺字段时使用明确的 legacy 展示。

必需覆盖：进度/工具/最终回复交错、流式更新与最终全文去重、同 session 多轮、同 item ID 跨轮重复、final 晚于轮次结束到达、完成但无 final、失败/取消无 final、等待授权/业务问题、重放/重复事件、来源切换、UI 重开与长最终回复。真实 Orca 样本不足时，精确轮次能力保持 not_tested；已验证的执行级展示可独立使用，但不得把降级当作精确能力的验收通过。

## 5. PR4C：控制台与轮次折叠

### Spec

保留原 PR4 的多项目、服务生命周期、任务开始、派发控制、运行详情、窄屏及 CLI/launcher 兼容范围，并增加统一会话页。该页面只消费 PR4B 的规范模型和能力结果，不直接调用 Codex/Orca，不因后端名称实现两套折叠逻辑。

默认交互：

1. 活跃轮次的过程区默认展开；进度消息与工具步骤按稳定身份更新，可继续手动折叠。
2. 正常结束、失败或取消被明确确认时，自动折叠该轮过程一次；最终回复独立保持展开，失败/取消原因留在可见区域。
3. 如终态先到、final 全文后到，且有明确 final item 引用或来源确认仍在补传，显示“最终回复待同步”；完成来源对账/分页后确认无 final 则显示“本轮已结束，未识别到最终回复”，不无限等待。后到的同轮回复补入原位置，不开启新轮或重复折叠。
4. 活跃问题、权限等待和业务决策卡片始终可见；等待输入本身不触发轮次结束。
5. 已手动展开的历史过程不会被后续刷新重新折叠；当前轮的“保持展开”选择也优先于自动折叠。
6. 下一轮新建过程区，上一轮的最终回复和折叠状态保留。折叠状态按项目/执行/attempt/session/turn 保存到 UI 自有视图状态，不能写入业务 runtime。
7. 自动折叠尽量保留用户当前阅读对象与滚动锚点；用户正在查看历史时不强制滚到底部。跳到最新内容使用显式动作。

折叠行显示状态、耗时、过程条目数和警告/错误数量，支持键盘展开与收起。缺口提示不藏进折叠区。执行级降级使用“执行过程/执行摘要”标签，不显示虚构轮次数。

示意：

```text
第 3 轮 · 已结束
▶ 过程 18 项 · 2分14秒 · 1条警告

最终回复
已完成修改，测试结果……

第 4 轮 · 等待你的答复
▼ 过程 5 项
  正在核对……
! 待处理问题：……
```

### Plan 与验收

1. 把原 PR4 的 QuerySource 改为消费统一执行/会话 DTO，完成项目切换和 generation 隔离。
2. 先接原 PR4 控制动作，再实现 turn 分组、过程折叠和最终回复完整滚动页。
3. 折叠状态采用明确的 auto/manual 状态和终态已处理标记，避免每次快照重建都重新折叠。
4. 实现阅读锚点、长回复分页、错误/问题置顶及旧日志/终端输出降级。
5. 复用原 PR4 UI/协议端到端与 Windows TTY 验收，增加同一交互脚本分别运行 local 和 Orca 的展示验证。

验收除原 U-A1～U-A9 外，须验证只折叠所属轮次、无 final 不猜测、晚到 final 补入原轮、多项目不串消息、等待问题可见、手动展开不被刷新覆盖、重开恢复与窄屏键盘可达。轮次结束不能把 waiting_pr_merge 或 waiting_decision 的业务任务显示为已完成。

## 6. PR5：人工决策与恢复接入同一契约

保留原 H1～H6 的答案身份、first-wins、留档、恢复资格和冻结结果内容要求。把其中直接使用 Orca terminal send/inspect 的调用替换为 PR4A 的后端操作；页面展示和历史关联使用 PR4B 的 session/turn/attempt 绑定。

答案保存、服务接受、后端接受、轮次开始和答案实际应用分别记载。现有 terminal send 只证明输入接受时，Decision 不能立刻变为 applied；原 H3 的成功文案及状态迁移按实际回执能力修订。应用证据可以是已验证的平台事件，或严格绑定原问题的 worker 确认；只出现新文本不足以确认。

能力矩阵代替业务函数中的硬编码 host 条件，但现有安全资格不扩大：首版 local continuation、Orca retry 仍可明确不支持。若决定补齐这些能力，应有单独的实现与原生恢复验收，不能借抽象重构偷偷把“重起一次执行”当作“恢复原会话”。

新增验收：两后端对相同业务动作共享资格判定；unsupported 明确拒绝；超时不重复回答/续跑；旧 attempt 的应用回执不会解锁新问题；折叠不会隐藏未解决决策；人工恢复只影响所选执行。原 H-A1～H-A12、整仓测试和真实 TTY 验收继续适用。

## 7. 与现有中心状态机计划的合并边界

- 从 Spec 02 提前提取执行适配器和稳定输出契约；4A/4B 不同时引入 Task/WorkflowRun/Execution 新持久模型、SQLite、多执行调度和 minimal-v1 流程。
- Spec 02 后续复用这些类型、适配器、能力定义和契约测试，负责新的模型/事务存储与旧记录迁移。将 local_process 明确列为长期正式后端，Orca terminal v2 和未来 supervised 模式可作为同一 Orca 后端族中的不同协议实现。
- Spec 03 的远端接入继续以真实远端验证为门槛；同一契约允许其实现不同的生命周期策略，不强迫中心停机时杀远端 worker。
- 如 Spec 02 已先合并，4A/4B 在其权威接口上补齐能力和事件，不重新建立文件权威或并行适配层。
- Spec 02 目前计划复用 runtime v4 表达全新的投影结构，与已合并控制协议 v4 存在版本冲突。正式更新 Spec 02 时必须为不兼容的投影选择新版本，并覆盖现有 v4 记录迁移；该调整属于 Spec 02，不修改 PR3。

## 8. 需要显式保留的边界

本方案可以保证公共模型与 UI 行为确定；它不能制造上游没有提供的 turn 或 phase。Orca 精确轮次功能以真实输出协议验证为门槛，缺口通过能力与展示降级公开。业务完成仍由 SteerLine 的结果、PR 和任务来源核验决定。

本轮不以取消原始输出、读取私有桌面数据库、屏幕文字猜测或模型自报来获得“看似一致”的消息体验。长远演进以两个正式后端、一个状态机、一种会话读模型和共同契约测试为基础。
