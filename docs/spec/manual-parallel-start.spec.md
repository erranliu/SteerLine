# 人工并行启动任务 Spec

## 目标

操作者在控制台逐个选择 Ready 任务并确认执行配置后，可以让同一项目的多个不同任务同时执行。人工启动不设置项目级并行数量上限。自动派发继续一次只启动一个任务，并在项目存在未结算的活动执行时等待。

本需求只允许**不同任务**并行。一个任务仍只允许一个权威活动 WorkflowRun；重试沿用该任务的既有 WorkflowRun 和固定执行身份。任务 DAG 的硬前置、任务领取 CAS、固定契约、执行配置冻结、步骤门槛与真实 PR 合并核验保持权威。

## 行为

1. 手动派发模式下，其他任务正在准备、执行、等待人工决策、等待 PR 合并或结果未知，不构成当前 Ready 任务的项目级启动阻塞。暂停派发、服务未就绪、当前任务不 Ready、任务已被领取、配置或能力不合格，仍拒绝开始。
2. 同一任务的重复开始请求按原 request ID 幂等对账；另一 request ID 不得创建第二个活动 WorkflowRun。不同任务的领取在同一个 SQLite 权威事务中各自 CAS。控制请求可以串行受理；受理后各任务的 worker 可以并行运行。
3. 自动派发保持单活动执行策略。切到自动模式时，已有人工执行继续运行；自动派发等所有活动或未核实执行结算后再领取下一项。自动模式不改变人工运行的固定配置。
4. 服务以 WorkflowRun/Execution/Attempt 身份管理 worker、步骤和执行配置。事件、输出、人工问题、停止、重试、资源结算与 PR 核验只作用于所属运行。一个任务的未知结果或待人工决策不停止其他任务的监督，也不授权重复派发该任务。
5. 服务重启逐一核对所有未结算执行。可精确重接的原 Orca 执行继续监督；不能证明停止或重接的执行保持原身份和未知状态。对账期间不创建替代 worker。新手动启动只在服务完成项目级恢复后受理，随后按目标任务独立核验。
6. 控制台显示所有活动运行和各自阶段；Ready 列表在一个任务开始后仅移除该任务，不因其他执行而整体消失。详情中的“开始不可用”报告目标任务的实际原因，不把其他任务的执行显示成槽忙。自动派发状态显示其单活动限制。
7. 系统不配置人工并行数量上限，也不以主机资源估算结果隐式设置数量上限。底层启动失败须针对相应任务记录失败或未知证据，不影响已在执行的其他任务。

## 边界和验收

- 两个无依赖的 Ready 任务使用不同执行配置依次人工启动；两者同时拥有独立 worker/工作区/尝试身份，步骤事件与结果不串线。第三个任务仍可人工启动。
- 自动模式下同一场景仅领取一个任务；已有人工运行存在时不自动领取。切回手动模式不停止已有运行。
- 并行任务中的一个进入等待人工决策、结果未知、失败、PR 等待或被丢弃时，另一任务仍能推进；前者本身的重试和清理遵循其固定身份及恢复门槛。
- 服务在两个任务同时执行时重启；恢复各自原始身份，不重发步骤，不因其中一个未知而覆盖另一个的状态。关闭服务按每个活动执行实施既有停止与未知结果保护。
- 同时提交同一任务的两个开始请求，至多一个取得任务 CAS；并行提交不同任务的请求均可按各自身份结算。
- 本 Spec 改变现有单项目执行槽策略。既有文档中关于单槽的阶段性描述应随实现更新；不借此加入同任务多 agent 候选、自动并行调度、资源锁系统或配置兼容路径。
