# Spec：worker 环境就绪与宿主阻断恢复

目标：`WORKER-ENVIRONMENT-READINESS`。配套 [Plan](worker-environment-readiness.plan.md)。状态：待实施。日期：2026-09-30。未分配原生 Task ID；一个实现 PR 交付。最终权限接线及交付前置：[#59 项目执行权限策略](execution-isolation-06-policy.spec.md) 合入；原会话探针和宿主观察可先独立准备。

## 1. 问题与目标

本机 Orca + Codex worker 能完成 terminal 创建和原生 Dispatch 接受，但实际工具执行可能失败。2026-09-30 测试任务 101 的现场显示：工具报告 `helper_unknown_error: setup refresh had errors`，随后写失败回传文件也进入宿主审批菜单；Orca 已报告 `agentWait`，中心仍停留在 `queued`，没有形成可操作的待决策。这证明启动接受、terminal 存活和宿主能执行 Git 都不能证明 worker 沙箱可用。具体 Windows 账户、ACL 或安装损坏原因尚未证实，不作为本 Spec 的根因结论。

修复目标是由 SteerLine 完整管理“检查、原会话准备、实际就绪、业务派发、宿主阻断观察、原身份恢复”流程。worker 无法执行工具、无法写回传文件或正在等待宿主审批时，中心仍能给出有证据的阻断原因和恢复入口，不能无限显示正在开始。

本期覆盖 Windows 本机 `host=orca`、`agent=codex`、`sandbox=workspace-write` 的固定执行配置。无论是否显式指定 model/effort，都必须使用能落实本 Spec 权限设置的受管启动命令；不能因 model 为空而走无法冻结权限的 `worktree create --agent` 分支。不增加新 agent、远端后端、候选 worker、通用修复框架或自动操作 Windows 账户/ACL/防火墙的安装器。操作系统确需管理员授权时，由用户在原生系统入口处理；SteerLine 负责诊断、定位原会话、重新核验和安全续行。

沿用 [项目规则](../../AGENTS.md)、[worker-flow](worker-flow.spec.md)、[本机 Orca 原生编排](worker-flow-orca-native.spec.md)和[原生任务约束](native-task-constraints.md)。不引入旧数据迁移、双写、旧启动路径兼容、自动降级沙箱或运行中更换 Profile。本 Spec 补充就绪与宿主恢复语义，不改既有 PR 合并交付规则。

针对本期 Windows Orca Codex 路径，本 Spec 的受管启动/CLI 能力检查替代原生 Orca Spec §4 中“仅依赖 opaque agent 启动设置、不调用中心 Codex CLI、不固定 Codex 参数”的限制；这是已知 agent 的明确权限契约，不改变其他 agent 路径。原生 Orca Spec §5 的首轮业务派发改为准备成功后的业务派发。worker-flow §5 的业务文字反馈语义保持，仅本 Spec 明确绑定受理方的宿主选项由中心处理，不新增专用恢复 API。

## 2. 主流程与状态边界

```text
选择 Profile 并取得配置快照
  → 领取前静态检查（配置、CLI 能力、Orca 连通性）
  → 核对 Profile digest，原子领取并冻结 Task / WorkflowRun / Execution
  → 创建或核实原 worktree、agent terminal、coordinator、Orca Run
  → 在原 agent 会话运行就绪准备轮次
  → 核验工具探针与原生准备轮次结算
  → 业务 Dispatch
  → 正常 worker-flow / PR 观察

准备或执行中出现宿主阻断
  → waiting_decision，保留原资源及未结算事实
  → 打开原 terminal / 重新检查
  → 原身份与原操作对账
  → 条件满足后继续原流程
```

继续使用 `queued / executing / waiting_decision / waiting_pr_merge / completed` 五个主阶段。准备轮次属于 Execution 内部准备事实，不是项目验证阶段，也不新增 Task 的执行步骤。静态检查只调用无启动副作用的配置/版本/能力和连通性查询，不借此初始化沙箱或启动测试会话。失败发生在领取前，任务保持 ready，执行配置可用性展示原因；自动派发不得改选其他配置。领取时再次核对所选 digest，防止检查与领取之间配置变化。

领取后从资源准备开始就保存一次有界准备意图；即使尚未绑定 terminal 或 Dispatch，资源创建失败、回执不明、agent 无法识别及准备超时也进入 `waiting_decision`。保留已取得的部分身份和原操作，不自动释放后再次领取。因停止服务产生的 context cancellation 只保留待对账事实，不记录为新的 worker 故障。

准备轮次的 status、question、worker_done 不调用业务轮次的“开始执行”、PR 候选绑定或业务完成逻辑。question 仍持久化原 message ID 并通过原问题回答，展示为准备轮次问题；宿主等待未解除时不发送回答。只有工具检查通过、原准备 Dispatch 已核实成功结算且无当前宿主阻断，才允许创建首个业务 Dispatch；失败结算、输入已接受、模型口头表示成功和 terminal 有输出均不能放行业务。

原生当前轮定位须区分准备轮与业务轮：准备可以拥有自己的活动/结算关联，但不能成为业务的 CurrentTurn/LastStoppedTurn、增加业务轮计数或重绑待投递业务反馈的目标。整个原 agent 会话同时最多一个活动或结果未知的原生 Dispatch；新增准备类型不能绕过这一限制。

## 3. 冻结执行权限

[项目执行权限策略 #59](execution-isolation-06-policy.spec.md) 统一交付项目授权、Codex 参数编译、安全 args 检查、两阶段冻结及必要展示。本文复用其已落实的策略、配置与资源绑定，不再单独扩充 Profile 顶层 sandbox 或另一套权限快照。权限接线与本任务最终交付以前置 #59 合入为条件；原会话探针、宿主观察和准备 fixture 可先独立开展，不以实验完成绕过前置。

1. 本期 Orca Codex 使用 #59 支持的 workspace 写入、固定 Git 元数据、network allow 与 escalation deny 项目策略，以及显式 `codex.windows_sandbox=elevated|unelevated`。实际 CLI/approval policy 由 Codex 适配器生成，不依赖用户配置或历史批准，不在故障后降级。
2. 领取时复用固定项目策略和方案，资源绑定时复用实际根目录、Orca runtime 和启动证据；model/effort 未配置的语义保持。准备轮和业务轮使用同一权限，不通过探针增加业务根目录。
3. 参数冲突与版本能力拒绝由 #59 的同一编译器处理。静态检查只证明设置受支持，本文的原会话工具探针证明实际就绪；两种事实独立记录。
4. 配置变化只影响新 Execution。本文的重新检查或宿主恢复不能重写旧快照；UI 复用冻结值，补充本任务实际准备/阻断状态。

本期不改变 local 后端的启动/恢复语义。必要的共享 DTO 和固定配置字段可复用，但不能为满足 Orca 探针而重启 local worker。

## 4. 原 worker 的实际就绪检查

### 4.1 就绪准备轮次

使用现有低层原生 Orca Task/Dispatch 在原 agent terminal 上执行一个明确标记为 `readiness` 的准备轮次，与业务轮次使用不同中心 turn 和原生 Task/Dispatch 身份。不创建第二个 agent 会话或测试 worktree，不自制 Orca preamble。准备提示只包含受控探针和准备轮次的结算要求，不包含业务实现指令。

探针由真实 agent 的命令执行工具，在该会话的冻结沙箱内完成以下最小操作：

- 读取原 worktree 中由中心准备的固定探针输入，确认当前目录、Execution/turn 和一次性 nonce；用只读 Git 查询确认 linked worktree 元数据可访问，不修改索引或分支。
- 在 worktree 内的专用、Git exclude 的准备目录创建文件，读回并删除；仅删除本轮自建的精确文件。
- 将本次命令的结果原子写入准备收据，包含绑定身份、nonce、输入摘要及读写删除结果。收据不含 Dispatch capability。

中心校验收据来源路径、大小、字段、身份及输入摘要，并对照本轮工具输出和原生轮次事实。接受证据必须包含平台来源中可区分于 assistant 正文的命令工具调用及成功返回，能关联固定探针命令/摘要和本轮 nonce；原生身份仍使用 Orca 身份，不要求 Codex thread UUID。普通 terminal 屏幕文本或未经解码的 transcript JSON 本身不是已核实工具事件。平台适配层负责解析、关联和可信程度，中心消费类型化事实，不在 Service 里解析屏幕关键字来宣告就绪。

不能由中心在宿主运行探针或代写成功收据；`apply_patch` 单独写出的收据、旧收据和口头 `OK` 不证明命令执行工具可用。现有平台若不能提供上述执行证据，准备保持未核实并给出明确诊断。此能力是实施前必须补证的门槛，不得仅实现“永远阻断”的探针后宣称本功能交付。探针用于操作能力检查，不提供对任意恶意 worker 的安全认证。

准备输入、临时文件、收据和 relay 使用不同精确路径。中心读写/清理先核验归属与最终路径在原 worktree 内，拒绝符号链接/junction/reparse point 将路径导向外部；不递归删除准备目录。收据和必要证据经权威存储确认后才清理原文件，崩溃后的同一收据重读幂等。不同准备意图不复用 nonce，同一意图重启保留原值；旧收据只保留历史，不放行新准备轮次。

准备完成仍须收到原生协议产生的成功结算并确认原准备 Dispatch 已结束。可复用已存在的、经身份校验的 worker 结果 relay；成功收据不代替 worker_done，worker_done 也不代替工具证据。整批 Delivery、收据证据及轮次结果先持久化，再 ack 和清理。准备探针、准备轮次结算、业务派发各自保存事实，崩溃后先对账，不重新注入一次“试试看”。

### 4.2 有界观察

首次准备从领取后保存准备意图时计时，包含资源创建、agent 识别、探针及结算；预算取冻结的 `orca.wait_timeout`，每次平台查询另受现有 `command_timeout` 和剩余预算约束。以持久化的开始/截止时间驱动多次有界轮询，不在 Service 主循环内等完整预算，也不每个步骤重新领取一份预算；重启不重置截止时间。

明确工具初始化失败或宿主等待立即阻断，不等待整个超时。截止后没有足够证据则进入 `waiting_decision`，原因标记为准备未核实；超时不证明进程退出或原 Dispatch 结算。截止后的晚到成功证据可以补齐原准备历史，但不能自动清除超时 blocker 并派发业务；需要一次新的、目标仍有效的“重新检查”请求确认原操作、当前身份和无宿主等待，再决定是否接纳原轮的完整成功事实。新准备轮只在原轮已核实结束后创建，并拥有自己的预算；不是延长旧轮预算。

worker 明确未收到输入、且原请求已证明没有副作用时，沿用现有有界注入重试。输入接受、响应丢失或轮次状态不明时只核对原操作；不得自动创建新的准备轮次。就绪结果绑定原 Execution、Profile digest、runtime、worktree、terminal/incarnation，不作为其他会话的共享成功缓存。

## 5. 中心独立观察宿主阻断

原生准备和 `pollNativeOrcaWorker` 使用同一宿主观察规则，读取已绑定的原 Run inbox、原 Dispatch、原 terminal 的 `agentWait`、退出事实和有界输出；某渠道不可用时仍收集其他可用事实。没有 Dispatch、绑定尚不完整或上轮已结算的 early return 不能遮蔽仍可核验的原 terminal 事实。只有已核实的身份才能作为发送/关闭目标；部分绑定或未知原请求只用于展示和对账，不猜测不存在的身份。

每次观察均有单次查询超时，不因一个不可用渠道阻塞其他渠道整轮等待。平台适配层负责身份核验和原始协议解码，中心按类型化事实及当前业务关联决定转换，保持现有单写者边界。worker 结果 relay 继续承载 worker 声明的业务结果，不是基础设施失败的唯一入口。

| 观察事实 | 中心处理 | 证据限制 |
| --- | --- | --- |
| 当前身份下的沙箱/工具初始化错误 | 保存环境阻断，进入 `waiting_decision` | 不把一般命令非零退出、项目测试失败认作沙箱故障；不证明 worker 已退出 |
| 原 terminal 的可信结构化审批等待 | 保存宿主等待，提示原生处理入口 | 普通业务反馈不能当作授权 |
| `agentWait.source=prompt-text` 等文本推测 | 保存“疑似宿主等待”、来源与时间，进入待核实决策 | 不宣称已确认具体审批类型，也不自动按键 |
| terminal 退出或身份不匹配 | 保存对应平台事实，阻止后续发送 | 退出不伪造原生业务结算；身份无法核实不另建替代会话 |
| 输出截断、来源切换或单次观察断线 | 保存观察缺口，继续可行的有界对账 | 不是宿主故障；其他渠道仍足以证明进展时不转 waiting_decision |
| 准备期限或首次业务启动观察期限到期仍未核实 | 进入 waiting_decision，保留原操作等待对账 | 不依据超时宣称命令失败、进程退出或 Dispatch 结束 |

优先使用平台结构化事实；只有当前绑定轮次的可定位输出时，保留明确错误片段及其来源作为诊断，以“疑似”标记，不能从模型引用的错误字符串认定真实工具故障。输出 source/cursor 只证明观测位置，不自动证明内容属于当前轮；无法可靠关联的 terminal tail 只展示，不改变当前轮状态。`agentWait` 是当前原 terminal 的平台等待提示，在无法归属轮次时标记会话级疑似等待；可以阻止向该会话新增输入，但不把它记成当前业务轮的已确认失败。

文本识别不得成为结算、释放资源或自动重试的依据；无法确定具体原因时在有界观察后形成可操作的“环境未核实”，避免无限 `queued`。业务 Dispatch 已接受但尚无可信开始事实时，以该派发意图的持久化时间加冻结的 `orca.wait_timeout` 观察首次启动；到期进入待核实决策，不再注入任务。此期限只用于启动观察，不给已经正常执行的业务轮增加总执行时限。

通过既有中心写者记录 blocker、Decision 与会话事件，UI 只读投影，不新建独立状态机。主阶段变为 `waiting_decision` 与 Execution 的未结算状态可以同时成立。保存最少的原因代码、可信程度、证据来源/时间、身份、可用动作及原生轮次事实；禁止记录 capability、凭据或完整无界屏幕内容。

重复轮询相同等待不重复生成 Decision 或日志；晚到的旧 terminal/turn 观察不能阻断或恢复新轮次。宿主 blocker 是 Execution 的附加事实，通过既有待决策记录呈现；保存 worker question 的原 message ID、答案及投递事实，不用一个宿主提示覆盖或清空它们。解除宿主阻断时，原 question 仍属于活跃 Dispatch 且未回答才恢复为待回答；原轮已结算的未回答问题按既有规则标记过期，已保存但投递未知的答案继续对账，不改投新问题。

宿主 blocker 不停止 inbox 消费、Delivery ack、原生结算或 PR provider 观察。新状态提交核对当前 WorkflowRun revision、turn 和 Decision 版本：有效业务结算按既有 PR 规则收敛；已核实交付/已结束任务优先，不能被迟到 blocker 重开。在仅等待 PR 合并且没有待投递反馈时，保留 terminal 故障诊断，不因此把 `waiting_pr_merge` 回退成 `waiting_decision`。本 Spec 的 readiness 成功只解除准备限制，不自行恢复 executing；业务开始仍需原业务轮的可信开始事实。

## 6. 恢复动作与原身份约束

统一待决策界面在既有反馈命令中增加有类型的中心动作，复用 CommandService、Operation/outbox 与写者，不新增 `retry_run / mark_stopped / resolve_command` 等恢复命令族。选项的受理方、Execution、turn/准备意图及 Decision 版本由中心记录明确绑定，不依靠解析自由文本“重试”触发操作，也不把选项当 worker 消息注入审批菜单。文字及选项附带备注原样保存；给 worker 的文字在宿主等待期间保持待投递，恢复后按原目标核验，目标过期时保留并提示，不自动转发给新轮：

- **打开原 terminal**：精确定位保存的 Orca runtime、handle/incarnation；提示用户按原生界面处理必要授权。未绑定 terminal 时该动作不可用，并显示原准备操作状态。此动作不声称完成修复。
- **重新检查环境**：先核验原身份、当前 agentWait、原 Dispatch 和未完成 Operation，再继续观察或执行允许的准备检查。重复请求幂等，同一未知结果操作先对账。

命令受理及结果提交核对所绑定的准备意图/轮次和 Decision 版本；同一 blocker 只有一个未完成重新检查意图，不因第二次点击使用新 command ID 就重复外部操作。旧动作在新轮次已经生效后只返回过期/已有结果，不恢复旧阶段。打开 terminal 是界面定位动作，不持久化为已批准或已修复；“重新检查”成功也只保存已经证实的环境与投递事实。

重新检查在 readiness 尚未注入时，只能对账/继续原准备意图；原准备轮次已经注入时，只有已证明其结束，才允许在同一会话创建新的准备轮次。当前原轮仍活动/未知时不得注入第二次探针。原轮恢复后可继续完成已注入的探针，不因界面点击重复执行。因已确认环境故障失效的就绪事实不能由一次 terminal 查询清除；原轮结束后必须做新的工具探针。仅观察断线且没有确认环境故障时，可对账原轮而不额外插入探针。若原会话无法结束阻塞或已丢失，本期保留现场并明确告知无法自动续行，沿用已有人工接管/丢弃边界。

业务未派发时：原身份可用、准备通过、成功结算均已核实且无 blocker 后，仅派发一次业务任务。业务已派发时：先恢复观察原业务 Dispatch；仍在执行就继续观察，不能再发送完整业务任务，也不向活动轮次插入 readiness Dispatch。只有原轮真实结算且符合现有反馈规则，才能创建后续业务轮次；确认环境故障后须重新验证时，先在原会话完成准备轮次，再按原反馈操作创建一次业务续聊轮次。准备轮不消费或更换待投递反馈的业务目标身份。

清除 `agentWait`、关闭审批菜单或新出现一个进程 PID 都不足以证明环境已就绪。恢复不能改 Task/WorkflowRun/Execution/worktree/逻辑会话身份，不能 reset 用户工作区，不能自动放宽权限。原 terminal/incarnation 丢失时不得用新会话冒充恢复。

服务重启恢复准备阶段、blocker、截止时间、探针身份、原 Operation 和原生轮次；不再次领取，不重复创建资源、probe 或 Dispatch。当前持久格式变更时按项目规则更新格式，在副作用前拒绝不支持的记录；本 Spec 不承诺将现存测试任务 101 的旧 Execution 自动迁入新格式。

## 7. 最小必要验收

复用现有固定身份、原生轮次与 Operation 回归，仅补测本次变化。四组场景覆盖新增故障边界，不要求全量测试或多 agent 真机认证：

| 编号 | 场景与最小断言 |
| --- | --- |
| ER1 | 沙箱初始化失败且 worker 无法写失败 relay，或失败发生在 Dispatch 绑定前：中心仍进入 `waiting_decision`、保存有来源的原因，无业务派发或释放重领。正向验证真实工具探针和成功结算后只派发一次；口头成功/旧收据/失败结算不能绕过检查 |
| ER2 | 业务执行中报告 `agentWait`：来源可信程度分别显示，普通反馈不注入菜单，原 question/答案不丢失。合并在同一轮询的负向断言：一般命令失败、无关旧屏幕文本和单次输出截断不误报；inbox 不可用仍观察宿主；有效 PR 交付不被迟到等待重开 |
| ER3 | 用户处理原生等待后重新检查：保留同一身份，活跃/未知 Dispatch 不重复注入；确认环境故障失效的准备须在原轮结算后重验。重复点击和晚到旧收据幂等；过期 question 不恢复，原目标未知答案只对账；身份丢失不创建替代会话 |
| ER4 | 准备或宿主等待期间重启中心，含派发响应丢失：恢复原记录、截止时间和原 Operation，不重复领取/资源创建/派发。准备/首次业务启动到期均进入可操作决策；晚到准备成功不自动放行业务，明确重新检查可接纳完整原事实 |

配置断言并入 ER1/ER2：有/无显式 model 均落实冻结权限、冲突参数被拒绝、配置变更不影响既有 Execution、无隐式 sandbox 回退。收据字段/路径拒绝断言复用就绪校验的表驱动用例；每组复用 fixture，不为每个断言创建一套端到端实验。UI 验证只覆盖原因、冻结配置和两项宿主动作，不扩展完整交互矩阵。

用一个隔离测试项目完成一次本机 Orca + Codex 的真实探针到业务派发闭环，确认原 terminal/incarnation 和实际工具执行。宿主等待/无法写 relay/回执丢失用受控故障覆盖，不人为破坏 Windows 沙箱。若真实探针或可核对的工具执行证据尚未可用，明确标记未验证，不用 fake 或宿主命令结果替代真机通过。

## 8. 交付边界

一个实现 PR 包含冻结权限、原会话准备、独立宿主观察、统一待决策恢复、持久化恢复和最小文档/UI 更新；不拆成会长期只诊断却无法安全续行的半成品。交付须 ER1–ER4 及真实成功链路通过；若平台缺少所需工具证据，只能报告实施阻塞/未验证，不能以“保持阻断”作为完成条件。更新相关实际支持状态和运行配置示例，说明本期能够自动对账的范围及仍需原生处理的原因。

本次 Spec/Plan 编写只检查文档链接和语义一致性，不实施上述功能、不创建生产任务、不改运行中 Execution，也不部署到 `C:\SteerlineRuntime`。实施验证采用快速入口及受影响用例，详见 Plan。
