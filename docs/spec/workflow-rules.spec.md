# Spec：执行规则包提取

任务 ID：33；任务名称：执行规则包提取；目标：`PHASE1-MODULARITY`。配套 [Plan](workflow-rules.plan.md)。状态：待实现与验收，一个独立实现 PR 交付。

规格协调：#36 [持续 worker 流程](worker-flow.spec.md)计划移除本任务当前要求保持的五步和项目验证门槛。二者共享改动串行集成；#36 先交付时，本任务须先完成固定执行契约的协调，不能按旧 WR2/WR3 重新引入被删除行为。本说明不更新已创建 TaskContract 的 Git 引用。

## 范围与前置

无未完成硬前置，遵守[模块重构共同约束](modular-refactoring-constraints.md)。以当前已交付 minimal-v1 为基线，把散布于步骤推进与交付核验的纯业务判断收敛到 `internal/steerline/workflow`。本任务不改任务策略、运行并发、数据库格式或平台能力。

## 包边界与规则

新包拥有以下三组规则：步骤结果与固定输入/候选 revision/必需检查的匹配；prepare/implement/verify/review/publish_pr 的合法推进与原修复轮次限制；交付所需的验证、审查、发布和精确 PR 合并证据匹配。输入携带判断所需的固定身份、工作流定义、步骤证据和状态值；输出是可接受结果、下一步建议或结构化拒绝原因，不能写状态或发起动作。

平台解析和证据可信度仍归原适配器及中心。Orca 消息尺寸、协议版本、worker_done 身份与平台字段检查保留在协议层；协议层形成已校验事实后消费同一业务规则，不复制另一份 verify/交付算法。依赖图算法继续复用 taskgraph，规范 JSON/文件摘要仍沿用原实现。

规则包不接收 Config、Service、Worker、数据库句柄、任意回调或可变全局状态。只定义必需的值类型，输入中的缺失、unknown、unsupported 与已证实失败继续区分；相同输入得到相同结果，时间或能力信息由调用方明确传入。内部错误需映射回既有命令/协议错误码，不迫使 UI 解析字符串。

## 接线与权威

迁移 `minimal_step.go` 的结果/转换判断、`task_execution.go` 的交付证据判断及相关重复调用点。既有 Service、CommandService 和协议适配通过明确转换函数调用新包，转换不得省略身份、revision、必需检查或审查要求。中心仍在事务内重读状态、复核版本并作最终提交；规则通过不等于获得派发或结项许可。

替换后删除被替代的规则实现及无用途包装。事务前预检和事务内复核可各调用同一规则；不为消除重复调用而取消并发检查。历史测试中的关键反例迁为规则测试，并保留少量真实中心接线测试，证明新包确实用于生产路径。
