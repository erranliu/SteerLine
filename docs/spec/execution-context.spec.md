任务 ID：34；任务名称：执行上下文封装与服务职责收缩；目标：`PHASE1-MODULARITY`。配套 [Plan](execution-context.plan.md)。状态：待实现与验收，一个独立实现 PR 交付。

规格协调：#36 [持续 worker 流程](worker-flow.spec.md)改变本任务涉及的步骤派发、决策续跑及五步验收语义。二者共享接线串行集成；#36 先交付时须先协调本任务固定执行契约，再按原会话和单一主阶段定义上下文，不能只凭本文修改重绑定已创建 TaskContract。

## 范围与前置

硬前置：#33。消费[执行规则包](workflow-rules.spec.md)，遵守[模块重构共同约束](modular-refactoring-constraints.md)。交付显式执行上下文和 Service 职责分工，作为 #26 的拟追加前置；本任务本身不实现同任务多候选。

## 所有权与封装

固定上下文以 project/workflow_run/execution/attempt 身份定位，携带该次运行冻结的执行配置、后端/目标、工作区及步骤输入所需事实。创建时从权威记录核验从属关系，重启从同一记录重建；重试形成新 attempt 的上下文，旧上下文只用于原事件/Operation 对账。配置中的 slice/map 按所有权复制，不能通过别名修改其他执行或项目默认值。

固定上下文、worker 观察者句柄和可变业务状态分别管理。上下文不拥有第二份可写 Runtime；worker 登记仍按 WorkflowRun，并绑定 Execution/Attempt 及观察者代次。业务状态只由现有服务事件循环调用中心操作更新，观察 goroutine 仅传递带身份的事实。消息正文持久化后才推进游标/确认接收的顺序保持。

执行相关方法显式接收固定上下文或由精确 ID 在方法入口解析，不依赖事先调用 selectWorker 改写 `s.Config/s.active/s.worker`。项目级配置只表达项目默认值；步骤、回答续跑、重试、停止、资源结算、输出/会话和恢复均从所属执行取配置。保留必要的生命周期登记，但不能以一个跨方法的“当前执行”槽隐式选择目标。

## Service 与组件边界

Service 保留启动/恢复顺序、串行事件循环和组件协调。将执行操作、worker 观察生命周期、会话/活动输出的处理集中到各自职责明确的内部组件；组件只取得所需上下文、窄能力和提交入口，不能反向持有整个 Service 或直接修改全部 Runtime。可先使用根包内封装类型完成分工，不以强行搬包或公开字段解决循环依赖。

组件消费 #33 的规则与现有 ExecutionBackend，不建立新的调度器、事件总线或通用依赖注入框架。中心提交、平台事实和 UI 投影的先后顺序与失败语义保持。不同任务并行、自动派发的现行单活动策略以及远端取消 unsupported 均保留；关闭观察者不代表执行退出。

## 验收

| 编号 | 通过条件 |
| --- | --- |
| EC1 | 代码及调用点检查确认执行操作不再依赖临时改写 Service 当前配置/执行；组件不借整个 Service/Runtime 绕过边界 |
| EC2 | 两个不同任务、不同配置/后端的事件交错处理，步骤输入、回答、日志、停止和资源结算始终属于原执行；错误返回也无需恢复“当前执行” |
| EC3 | 重试后的旧 Attempt/旧观察者消息保留原事实且不推进新执行；上下文 map/slice 不共享可变别名，项目配置变化不改已有运行 |
| EC4 | 单写者与消息持久化顺序保持；停止中心、观察断开、回执丢失和重启沿原身份恢复，unknown 不重派、不释放占用 |
| EC5 | 不同任务人工并行、单任务正常五步、决策 applied 门槛、自动派发与真实交付核验回归通过；已改变的本机/Orca 接线完成隔离原生复验 |

证据保存于 `docs/validation/execution-context/`。EC2–EC4 使用可控后端和真实中心注入顺序/错误，EC5 的真实路径按共同约束记录实际支持范围；不能借重构放宽 #3/#4/#6 剩余门槛。
