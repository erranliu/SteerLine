# 架构决策：中心状态机与 Orca 远程执行

确认日期：2026-09-23。状态：目标架构已确认，尚未实现。

实施分为三个 Spec：[01 Orca 远程协议验证](spec/01-orca-remote-protocol.md) → [02 执行模型、最小状态机与适配器](spec/02-execution-model-and-adapter.md) → [03 分阶段远程执行与 viewer 闭环](spec/03-remote-execution-and-viewer.md)。

本文约束后续设计。现有单执行槽、文件结果协议和技能流程仍是当前实现；远程接入、共享服务、移动端和同任务多 agent 并行需分别实施。

## 实施顺序与依赖

| 顺序 | Spec | 交付门槛 |
| --- | --- | --- |
| 1 | 01 Orca 远程协议验证 | 确定真实 Orca 能力、身份和恢复边界，交付可复现证据及协议映射 |
| 2 | 02 执行模型、最小状态机与适配器 | 完成中心状态机、事务存储、旧数据迁移和本地/替身验证；远程接口遵循 01 已核实的协议 |
| 3 | 03 分阶段远程执行与 viewer 闭环 | 依赖 01 必需能力验证通过、02 实现完成，进行远程接入及端到端验收 |

默认按 01 → 02 → 03 顺序交付。01 的真机探测期间，02 的领域模型、状态机和本地存储测试可以先行；外部协议映射仍以 01 的实测结论为准。远端尚未就绪时允许继续 02 的独立工作，但不能跳过 01 的验收门槛而启用 03 的生产远程路径。

## 中心服务与执行层

- SteerLine 是业务状态的唯一权威，负责流程、任务领取、派发策略、人工决策、恢复以及最终完成核验。先部署在个人电脑，后续可迁到共享服务。
- 远端仅需 Orca、agent 和仓库所需工具及脚本，不要求部署 SteerLine 服务。
- Orca 管理执行现场：worktree、分支、agent、执行身份、输出和跨机消息。SteerLine 通过执行适配器接入 Orca；产物可以保留在远端，仅回传状态、决策和必要结果元数据。
- 桌面 viewer 和未来移动端通过同一服务接口查看状态、提交人工操作。业务状态切换由中心服务持久化；共享部署时按用户或组织隔离项目、权限及 Orca 连接。
- 本轮即实现最小中心流程：准备、实现、验证、按配置审查、发布 PR、等待合并、结项。SteerLine 决定步骤顺序、通过条件和修复回路；目标项目提供步骤内的基础技能或脚本，例如特殊测试与 PR 流程。技能不能自行推进中心流程。脚本可以在 Orca 管理的远端 worktree 内运行，无需常驻 SteerLine 服务。

目标远程适配允许使用 Orca 的受监管 worker、Dispatch、消息和 ask/reply。Orca 执行记录与 SteerLine 业务任务建立映射，业务 DAG 和完成判定仍归 SteerLine。当前 hosting v2 对 `orca orchestration *` 的全面禁用不作为目标远程架构的约束；迁移时应明确替换其结果、交互和恢复契约。

## 长期支持的执行路径

local Codex 与 Orca 均为正式、长期维护的执行后端。backend、agent、execution target 和协议版本分开；Orca terminal v2 与未来 supervised 属于同一后端族的不同协议实现。远程演进不移除 local，不提供不确定情况下的跨后端自动 fallback。

Service 持有唯一业务状态机和存储写入权；后端适配器只执行固定意图并返回事实。启动、观察、输出、回答、停止执行、分离观察和资源结算使用共同契约，能力差异有版本与原生证据。UI/CLI 共用 Query/Command 和会话模型，不直接操作平台终端或 OS 进程。接口与验收见 [控制台 4A](spec/pr-04a-execution-backends.spec.md)、[4B](spec/pr-04b-conversation-events.spec.md)；后续 SQLite 与 remote 复用它们，不建立第二套抽象。

进度消息、最终回复、轮次结束与业务完成分开；过程折叠属于 UI 视图状态。完整输出先持久化再推进来源游标，缺口与未解决问题始终可见。单纯输入接受不能作为决策已应用的证明。

## 为同任务多 agent 保留的模型

必须允许同一个业务任务由不同 agent 在独立 worktree 上并行执行。当前不实现并行调度，但后续远程协议和状态机不能固化任务与 agent、worktree 或 Dispatch 的一对一关系。

```text
Task                         业务任务、领取、最终完成
└─ WorkflowRun               一次流程及结果汇总
   ├─ Execution A            agent A、独立 worktree / 分支、阶段状态
   │  └─ StepAttempt(s)      步骤尝试、执行身份、Orca Dispatch、回执
   └─ Execution B            agent B、独立 worktree / 分支、阶段状态
      └─ StepAttempt(s)      步骤尝试、执行身份、Orca Dispatch、回执
```

以上是概念关系，字段名和数据库结构留给实施规范确定：

1. **任务与执行分离。** agent、host、worktree、日志游标和执行结果属于 Execution 或具体步骤尝试。当前仅派发一个 Execution 是调度策略，不能成为存储/API 的唯一性约束。
2. **并行与重试分离。** A、B 是同一任务的两个独立执行，不是互相替代的重试。步骤重试有新的尝试身份，保留旧尝试记录；旧尝试迟到的消息不能推进新尝试。
3. **Orca 身份正确映射。** SteerLine Task 不等同于 Orca Task。同任务的并行执行不得争用同一个只允许一个权威 Dispatch 的 Orca Task；由适配器分配各自的执行记录。每条消息绑定具体 Execution、步骤尝试及对应 Orca 身份。
4. **工作区隔离。** 同时运行的不同 Execution 使用不同 worktree 和分支。记录各自 host、Orca worktree 身份和实际 base commit；远端路径作为远端事实，不能默认在中心服务上可访问。比较候选实现时可固定共同起点。
5. **决策有明确作用域。** agent 的问题绑定所属 Execution、尝试和 decision ID，回答只送往对应 worker；需要影响整个流程的决策显式标记流程作用域。一个 Execution 等待用户，不能隐式暂停所有其他执行。允许存在多个待回答问题。
6. **完成由中心汇总。** 单个 worker 成功只表示其执行完成。任务级策略决定选用哪个候选结果、是否等待其他执行、如何整合以及哪些 PR 需要核验；不能默认首个 `worker_done` 就关闭业务任务。选择、比较和整合策略暂不实现。
7. **领取与结项只做一次。** 任务级领取由中心服务持有，各 agent 不分别 claim/close 同一个业务任务。最终交付引用已选用的执行结果；一个候选执行失败不会直接把整个任务判为失败。
8. **客户端按任务汇总、按执行展开。** viewer/API 保留执行身份与来源，可显示同任务多个 agent 的活动、问题和结果。调度器内部的单个 `CurrentTask`、`worker` 或任务上的单个 PR/Decision 字段不能作为未来并行模型的对外契约。

## 恢复与状态切换

业务状态转换和外部执行分开持久化：先记录待派发意图，再记录 Orca 回执。消费消息时先落盘和去重，再确认接收；外部动作依赖 Orca 支持的请求恢复机制和具体脚本的幂等性，不能承诺跨系统天然恰好执行一次。

每次观察或决策回答都核验所属任务、执行、尝试及外部身份。对同一待处理决策，中心服务处理重复提交与并发回答；网络不确定时保留待核实状态，不从超时推断执行已退出，也不自动启动替代 worker。

本地服务停止时，已启动的远端 worker 可以继续执行；中心流程待服务恢复、读取消息并完成对账后再推进。未来共享服务可以部署多个进程，但同一业务状态转换必须有事务或等价的并发控制。

## 迁移边界与后续验证

- 先完成单 Execution 的最小分阶段远程闭环：中心逐步派发、输出、人工决策、阶段结果、断线对账和服务重启恢复。现有完整 start/finish 技能仅留作旧流程兼容，新的远程流程不以一次 `execute_workflow` 包办全部步骤。
- 当前 `Run` 同时承载任务、执行和交付信息。新增模型时需要显式版本迁移，把旧记录映射为单执行历史，并保留原 run ID 的关联；不能仅改字段名称或直接提高并发数。
- 当前本地结果文件、绝对 worktree 路径、Beads 目录及结项命令的本地访问假设，需在远程契约中逐项消除或指定执行位置。
- 远端版本对 worker、消息、输出和脚本执行回执的支持，需要真实环境验证。共享服务器的 Orca 协调运行时部署、用户连接隔离与网络可达性也需单独验证。
- 多 agent 并行调度、候选结果比较/整合、移动端界面和共享部署均为后续工作；本阶段仅固定能够容纳这些能力的架构约束。
