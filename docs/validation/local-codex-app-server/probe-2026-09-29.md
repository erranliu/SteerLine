# Windows app-server 能力探针（2026-09-29）

环境：Windows；`codex --version` 为 `codex-cli 0.157.1`，`initialize.userAgent` 报 `Codex Desktop/0.158.0-alpha.2.1`。使用当前登录凭据、临时工作目录和只读 sandbox；此记录不是完整迁移验收。

1. stdio 探针：`thread/start` 返回原生 thread ID；`turn/start` 返回不同的原生 turn ID，`clientUserMessageId` 出现在完成的用户消息中。原生身份不能用 SteerLine Command ID 代替。
2. 独立 WebSocket 探针：首次连接启动 turn 后断开；20 秒后重新 `initialize`，`thread/read` 返回同一 thread，状态 `active`，同一 turn 状态 `inProgress`。
3. Default 模式内置提问探针：模型最终回复无法使用 `request_user_input`，没有 `item/tool/requestUserInput`。官方文档虽列出协议事件，不能据此推断此模式可用。
4. Default 模式注册最终的多题 `steerline_ask` 结构后，模型发出 `item/tool/call`，包含 JSON-RPC 请求 ID、thread ID、turn ID、call ID 和按 question ID 编排的参数。断开连接，再次 `initialize`、`thread/resume`，由第三条连接按原请求 ID 回复；观察连接收到匹配 call ID、`status=completed`、`success=true`、完整答案正文的 `item/completed`，同一 turn 随后 `turn/completed`，最终回复为 `A`。
5. 第一条 turn 待答期间，第二个独立 app-server/thread/turn 完成；再次读取第一条 thread 时，其原 turn 仍为 `inProgress`，随后再回复并完成。运行中的问题没有阻塞第二个原生执行。
6. npm `codex` 包装器会启动 Node 和实际原生 Codex 子进程。worker 现解析并核对同版本原生可执行文件，进程身份直接绑定后者。探针遗留的包装器/子进程已按确切 PID 与 loopback 端口核验后清理。
7. 扩展后的真机用例在首轮 `turn/completed` 后，提交结束后反馈；原 thread 上产生不同的 turn ID，且第二轮返回 `status=completed`。本次完整探针耗时约 239 秒。

以上是真实 Codex 协议探针；当前 Windows 测试宿主的 Job Object 不允许验证“SteerLine 服务退出后独立 worker 继续存活”，因此尚未构成 Spec 验收 A 的 SteerLine 双任务闭环。发送回执丢失与服务级双任务隔离仍待可脱离 Job Object 的宿主执行故障注入和闭环验收。

依赖的官方协议：[Codex App Server](https://learn.chatgpt.com/docs/app-server)。动态工具及其 `item/tool/call` 是实验接口，执行前必须启用 `capabilities.experimentalApi` 并做目标版本能力探测。
