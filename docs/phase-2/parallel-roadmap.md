## 并行推进原则

#14 能力验证与 #15 WinUI 基座可使用隔离资源同步准备。本机 API 的后继规格等待 #36，之后规划草稿消费其传输，执行 UI 消费其原会话反馈并等待 WinUI 基座。规划草稿交付后，文档发布与规划会话仍可按各自前置分头准备，再由文档浏览/审阅和规划对话页面消费。规划权限和正式文档发布核验仍保留，不被 #36 取消目标项目 verify 的决定覆盖。

上述是目标安排，现有任务领取仍服从当前中心图，包括旧 #16 的 #26/#35 前置。更换 API 任务还影响后继的固定依赖，正式重规划必须完整覆盖。不同任务人工并行、共享文件/宿主/构建串行集成规则保持。

## 完整用户路径

人讨论目标 → 同意编写规格并预留 ID → 受控草稿 → 人审阅固定版本 → 正式文档发布 → 用户将规格集成到执行目标分支 → 中心核验并创建 DAG → worker 实现/提交/PR 与用户同会话反馈 → 人合并任务 PR → 中心核验交付 → 主 agent 据真实交付提出新草稿，由人确认。

仅更新产品方向时走 documents_only，没有 ID 预留和 DAG 创建。规划分支提交不自动改变执行目标分支；任务规格尚未通过提交祖先及文件内容核验时，UI 显示等待保留原 commit 的 merge/fast-forward 集成，不宣布任务已创建，也不自动合并。中心创建尚未开始时可受控结束等待、保留文档与数字并重新审阅，避免永久占用规划写入。

#24 独立承担这条链路的最终原生验收，现有 DAG 汇合 #20/#21/#22/#23、第一阶段 #3/#4/#6 和新增 #32 整体版本门槛。正式 Windows 安装/升级、未来平台 UI 与有限自主推进仍属于后续产品节点。
