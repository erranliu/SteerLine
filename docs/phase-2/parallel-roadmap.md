# 第二阶段推进边界

第二阶段已按独立任务形成 Spec/Plan，`#14–#24` 已进入中心固定 DAG；任务清单、数字身份及剩余范围见[主 roadmap](../roadmap/roadmap.md)，真实硬前置、并行条件与最终汇合见[执行依赖图](../roadmap/execution-map.md)。本文件解释产品阶段的边界，不代替执行规格。

第一阶段交付目标现包括[同任务多候选与 stable/dev 双入口](../roadmap/phase-1-delivery.md)。这些新增范围尚未进入中心 DAG；保留现有第二阶段任务身份和硬前置，人工优先派发第一阶段。第二阶段没有新的执行状态机、并行调度器或取消后端，实际能力仍由已有执行权威提供。

## 并行推进原则

#14 能力验证与 #15 WinUI 基座可使用隔离资源同步准备。#16 在现有 DAG 中没有新增硬前置，但执行 Query/Command 消费多候选身份，先核接口、待其契约固定后集成。#16 完成交付后，#17 建立统一规划权威；#15 同时完成时，#21 已可交付执行界面。#17 后的 #19 发布与 #14 已通过时的 #18 会话服务可以分头实现。之后 #20/#23 接真实文档查询，#22 接真实会话，不让对话 UI 等待文档发布 UI 完成。

并行指不存在业务硬依赖的研发工作可独立推进。不同任务人工并行已交付，但没有把新增第一阶段优先级编码为 #14–#24 的依赖边。任务一旦进入 DAG，只有图中的前置整体交付后才可领取；不存在“接口已写好”提前放行。公共契约随规格固定，涉及共享文件、宿主与构建的集成仍串行协调。

## 完整用户路径

人讨论目标 → 同意编写规格并预留 ID → 受控草稿 → 人审阅固定版本 → 正式文档发布 → 用户将规格提交集成到执行目标分支 → 中心核验并创建 DAG → 执行与人工决策 → 人合并任务 PR → 中心核验交付 → 主 agent 据真实交付提出新的文档草稿，由人确认。

仅更新产品方向时走 documents_only，没有 ID 预留和 DAG 创建。规划分支提交不自动改变执行目标分支；任务规格尚未通过提交祖先及文件内容核验时，UI 显示等待保留原 commit 的 merge/fast-forward 集成，不宣布任务已创建，也不自动合并。中心创建尚未开始时可受控结束等待、保留文档与数字并重新审阅，避免永久占用规划写入。

#24 独立承担这条链路的最终原生验收，现有 DAG 汇合 #20/#21/#22/#23 与第一阶段 #3/#4/#6；新增第一阶段整体版本门槛在产品验收时另行核对。正式 Windows 安装/升级、未来平台 UI 与有限自主推进仍属于后续产品节点。
