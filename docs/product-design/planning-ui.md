## 2.1 DAG与执行UI

下述 DAG/执行页面保留为未来 WebUI 参考，TUI 长期保留。本轮先交付 TUI 经 HTTP 接入 Go 后端，不准入旧 #49/#50。

#45 是已有 HTTP 查询/命令基线；#44 实现删除由 #91 完成。未来 WebUI 消费公开 API，当前不固定页面任务与依赖。

执行页沿当前精简范围：近期有界活动摘要、完整final和问题背景；不恢复完整transcript时间线、工具过程正文与阅读偏好体系。中文IME组词不能误发；显式提交与目标/版本清晰。回执区分保存、接受、开始和结果待核实；未知查询原请求，切项目不重定向原输入。UI关闭不停止服务/worker，离线与错实例禁写。已有环境/权限阻断显示真实原因和核验入口，不给通用“已完成即放行”。

### 本轮原型交互方向

DAG 节点与任务列表按 Task 汇总候选数量、运行/待回答/待合并状态。全局默认候选参数在一级导航底部“设置 → 执行”独立管理，依次选择执行路径、机器、Agent、模型和推理强度，显式保存后影响以后启动的默认候选，不选择预先成组的方案。项目自动派发开关放在 DAG 页头，明确作用于当前项目。

本机 Codex 路径固定使用本机与 Codex。Orca 路径先选择机器（如本机、远端电脑 A），再选择该机器支持的 Agent、模型和推理强度。选项来源为 Orca 返回的能力或提前检测的配置，按所选机器/Agent/模型约束下级；切换上级清空受影响的下级选择，不保留不支持的旧值。没有完整且受支持的参数组合时禁用保存/启动。原型显示能力来源与采样时间，但当前来源和远端目标仅为演示数据，不宣称真实发现、连接或远端执行已实现；真实来源校验、失败/过期与派发前再核验留待接入契约固定。

自动派发只为尚无候选的就绪任务启动一个默认候选，已有候选不自动补位。未执行任务可从 DAG “手动启动”首次创建一个候选，预填已保存的全局默认参数；本次调整不改全局默认。只有“执行与待处理”中已执行且未合并任务提供“新增并行候选”，DAG 对已有执行只提供查看执行入口，已合并任务不提供新增入口。并行只能手动派发；任务面板仅包含本次新增数量，每个候选分别按路径、机器、Agent、模型、推理强度依次选择，未提交选择与冻结参数各自独立，完整组合重复仍按现有候选约束拒绝。任务面板绑定当前 Task，不承接全局配置。关闭自动派发不停止现有执行，Task 资格、候选允许范围和交付规则仍由服务校验。

执行页先展示任务汇总，再以候选卡片选择独立会话、冻结方案、工作区、PR 和问题。回答与未发送草稿绑定原候选及问题，切换不重定向；新问题不抢焦点。候选完成/放弃、外部停止事实和中心唯一交付分别表达，真实交付后才释放后继，其余候选保持准确状态。

新增方向是当前执行的实时输出：增量文字、工具活动及按需展开的命令输出，支持跟随最新、滚动时暂停跟随、新输出提示与最后观察时间。断线不判断 worker 停止，也不把部分文字当作完整 final。当前原型仅模拟这些数据；真实服务的增量读取、来源能力、缺口和重连行为需要后续契约固定，不改变现有近期接口交付范围，不以该演示宣称完整过程采集已实现。

实时输出区提供原生对话入口，按执行路径路由：本机 Codex 在 Codex 中打开原 thread / 工作区；Orca 在 Orca 中打开原机器 / terminal，不按 Orca 内部所选 Agent 改选工具。入口与定位回执绑定当前 Task / 候选 / Execution / Attempt 及原会话，切换不重定向；离线或缺少可核实绑定时显示原因并禁用。原型只显示打开目标，不调用真实工具，不使用未确认的 URI 或同名会话替代原会话。

规划 session 的列表、新建和历史切换仅在规划工作台内部；一级导航只切功能页面。不同 session 保留独立对话与输入草稿，切到 DAG/执行页再返回保留原 session。规划 session 的切换不改变执行页当前任务或候选。

## 2.2 草稿、artifact与人工事项

### 版本蓝图与项目愿景

版本蓝图是 AI 维护的版本目标文档，内容包括价值、能力范围与优先级、非目标、版本完成标准及未决取舍。一级“版本蓝图”只读展示文档列表、来源和正文，不提供新建、编辑、保存或确认工作流。页头保留“项目愿景”入口，在可关闭的文档面板查看仓库愿景快照并返回原蓝图；愿景同样只读。

当前不建立蓝图与 Roadmap 的关联，不展示 Roadmap / Task / PR 映射或任务执行进度，不修改 execution-map 与 DAG。蓝图的目标版本与体验版本编号分别管理。原型只内嵌示例蓝图快照，不模拟 AI 写入或文档维护操作。

### 长期技术文档与结构约定

一级“长期文档”为 AI 维护的技术资料提供只读入口，分为固定文档与设计目录。固定默认路径为 `docs/architecture.md`、`docs/architecture/parallel-development.md`、`docs/testing.md`、`docs/spec/SpecGuide.md`，分别维护架构、并行边界、长期测试方法及正式文档生成规则；SteerLine 识别命名、用途与必要内容。目录 `docs/design/` 可按主题包含多篇设计文档，文件名自由，不要求每篇注册固定角色。

2026-10-15 的[项目结构方案](project-structure.md)将这四类角色与设计目录作为项目准备要求，通过显式清单采用现有文件，避免复制正文。配套[准备提示词](project-onboarding-prompt.md)交给用户在 Codex 执行，服务核验通过并经用户确认后才纳管/建库；主界面的项目切换与职责归[项目管理方案](project-management.md)。这些仍是设计，原型和当前产品尚未实现该准入流程。

页面展示正文快照、待合入更新预览、更新状态、已记录代码覆盖、更新时间、触发依据和维护记录，不提供手动新建 / 编辑 / 更新工作流。“查看结构约定”说明固定路径、目录范围与更新时机。状态分已同步、待更新、更新中、变更待合入、更新失败；草稿生成 / PR 创建不算已同步，失败保留原正文。规范正文与明确维护产生的新规则分别预览，生成仍固定原输入版本。

项目接入时调查结构与缺失内容；正式 Spec / Plan 生成前读取共同文档，检查覆盖并记录待维护提示。代码 PR 合入后只维护受影响文档，任务和 Bug 修复同样适用；长期测试入口在候选提交登记时先记录候选事实，主分支合入后才整理主分支说明。多个输入可合并维护，以最新固定 SHA 更新同一文档 PR；事实更新反映实际实现，规范变化需要明确规划依据。纯文档 PR 不触发自身循环更新，文档维护失败不回退代码交付。

原型固定正文取本地仓库快照，设计目录与覆盖 / 更新 / PR 事实为演示；代码模拟合入、长期入口登记、明确规范维护与转正必读共同文档均有页面内状态演示。AI 草稿停在待合入状态，不写入真实技术文档或 Git，不新增 DAG 任务。

### 长期分级测试管理

一级“测试管理”提供长期目录与不可变运行记录两个视图，按稳定入口 / 场景 ID 和定义版本管理。目录仅展示测试内容、命令、环境要求与入口状态，不反向列出关联任务或 Plan；任务的测试要求在草稿任务与 DAG 详情中查看。产品原型中 L1 是每次 PR 必须验证的最小脚本 / 纯代码单元测试集；L2 包含实际程序运行的 smoke；L3 按功能维护，可独立选择多个实际功能场景；L4 是全部脚本 / 纯代码测试，包含 L1，不包含实际运行的 L2 / L3。开发过程临时创建的测试不属于该目录，不以临时脚本结果替代长期入口证据；未纳入长期分级体系的内容按 Plan 安排清理，不提供通用自动删除操作。

任务 Plan 明确提交 / 更新 PR 前的测试级别、长期入口与场景、所需环境、验证时点和证据位置，也安排需要扩展的稳定流程。草稿记录测试约束，L1 为必选最小集；约束变化产生新草稿约束版本，不直接生成正式 Plan。转正固定流程读取规范、调查代码后生成正式 Plan，复核测试引用、定义 / 场景版本与扩展所有者，固定生成结果后写入正式 Task 关联；需要新增入口时，必须在实施中完成并纳入分级体系，在 PR 前落实可用入口。DAG 始终展示正式任务关联的测试，不使用最新草稿动态覆盖固定要求。

实现提交后固定候选 SHA，先进入 PR 前测试检查；要求未满足时不模拟提交 / 更新 PR。相同提交与定义下，完整 L4 可提供 L1 最小集证据，不能替代 L2 / L3。L3 的多个场景可以独立验证，匹配的成功报告覆盖所需场景才满足 Plan；最新失败、未知观察、未完整范围、其他候选或旧提交不放行。未知结果查询原测试请求，结果始终归属原提交 / 候选 / 定义。既有真实交付事实不会因后续测试失败被回退。

L1 / L4 只验证脚本与纯代码，不要求调试运行现场；L2 / L3 选择与测试来源完整 SHA 一致、具备对应长期入口版本的独立调试环境。环境准备或入口登记不等于测试通过。新入口先以专属 Plan 扩展安排显示，取得实现提交并登记后才能运行，合并后继续长期维护；旧代码 / 旧环境不能因目录更新自动取得新入口。

当前原型模拟测试目录、运行、扩展登记及 PR 门槛，未修改本仓库现有测试 CLI 或 Full / E2E 分级入口，也不执行真实测试、创建 PR 或清理文件。代码提交的版本覆盖同样为演示元数据，真实接入应从 Git / 项目测试注册表和执行报告核验。

### 体验版本管理

一级“体验版本”包含版本列表与项目 PR 记录。PR 记录覆盖已合并、未合并、关闭未合并及合入其他分支的 PR，默认只看已合入当前项目主分支。新版本必须选择已合入当前主分支、且实际落点是上一编号版本提交之后的 PR；以 Git 提交关系核对，不能按 PR 编号、创建时间或合入时间单独推断。相同或更早节点不允许新建，旧版通过原记录重建。主分支设置改变后，须仍能核实上一版与目标的提交关系才能创建。

确认创建时分配项目内递增编号，固定所选 PR、实际合入后完整 SHA（非 PR head）、主分支、上一编号版本及其 SHA、新增 PR 清单与体验根目录。失败、删除与重建不回收编号，也不改比较基线。每版建议保留稳定 Git 引用，以便从原提交重复取得旧版；实际接入需核验引用与提交可取得。

Agent 按固定提交差异、PR 描述和代码生成新增 PR 介绍、综合行为变化及建议体验步骤，首版为初始功能介绍。重新生成保留此前介绍快照；重建目录沿用原编号和原介绍，不产生新版本。目录准备与介绍生成各有进度、失败和重试状态，介绍失败不阻止已准备版本启动。版本记录一旦存在即作为下一版本的比较基线，不因目录准备失败或删除而回退。

项目设置提供体验版本根目录，如 `C:\SteerLineExperience\DemoProject`，独立目录命名为 `exp-递增编号-短SHA`。版本记录、PR 清单、介绍与 Git 引用独立于可删除的目录保存；运行数据、配置与端口按版本隔离。目录准备包括取得固定提交、构建、独立资源准备和启动核对。目录删除需确认实际路径与运行数据影响，运行中先停止；外部删除检测为目录缺失。从 Git 重建使用原记录路径、编号与 SHA，准备新的运行数据。修改根目录仅影响新版本。

原型提供已合入节点、PR 编号与合入先后不一致、未合并 / 关闭 / 其他分支、失败重试、目录删除 / 外部缺失 / 原版重建以及介绍历史演示。任务模拟提交 / 更新 PR 与草稿转正文档 PR 均同步 PR 记录，合并后固定主分支落点。当前页面不读写真实 Git 引用，不取真实 PR、不构建、不启动、不删除真实目录；版本准备不创建 DAG 任务或登记验收通过。

### Bug 管理与独立修复

一级“Bug 管理”直接同步项目 Git Issue，保留编号、标题、标签、正文版本、更新时间及外部打开 / 关闭状态；Issue 状态、修复阶段与 PR 合并事实分别表达。列表按待审计 / 排队、修复与测试、待人工、待 PR 与合并筛选，详情展示问题、两道审计判断、实时输出、原生对话、固定修复成果、自动 / 人工验证与 PR。修复记录使用独立身份，不占 Task ID，不进 DAG，不修改 execution-map。

项目自动开关按 bug 或 bug + auto-fix 标签纳入，手动入口可审计单个打开 Issue。每个 Issue 同时仅一个进行中流程，已有待提交 / 待合并 / 已合并结果不重复纳入；人工交接不自动重跑，显式重新审计创建新记录并保留历史。修复与任务执行共用项目并行额度，排队不启动 Agent，观察中断的在途操作仍计入占用。关闭自动修复停止新纳入与未启动的自动队列，已经开始的流程继续。执行参数沿用已保存全局默认，启动记录固定 Issue 正文 / 补充 / 版本、主分支完整 SHA、执行路径 / 机器 / Agent / 模型 / 推理强度。

第一道判断先只读审计：问题是否清晰，是否找到根因与覆盖同类问题的系统性方法，是否可避免大规模重构。描述不清进入待补充，方案不满足进入待决策；满足后在独立分支修复。实施时发现范围扩大则停止自动修改，将已有检查与部分成果交给人工。人工补充供下一次审计使用，不覆盖原 Issue 或历史快照。Issue 外部版本变化后停止继续旧依据操作，PR 提交 / 合并入口再次核对；已经存在的 PR 与真实合并事实仍保留。

修复提交后第二道判断能否自动复现原问题并可靠断言效果。可自动验证时，复用或小范围扩展长期 L1–L4 场景，绑定本轮 SHA、测试定义 / 场景和证据；需要实际运行时准备独立环境，固定 SHA 与运行资源。自动失败可返回修复，最多 2 轮，再交人工；旧提交的通过不放行新提交。不适合自动化时保留修复分支 / 草稿 PR，生成固定提交与独立环境的人工指南。人工结果须记录参与人、实际步骤 / 结果与证据，失败仍待人工；通过后核对同一提交的 PR 前 L1，才能提交 / 更新已验证 PR。Bug 已验证与通用基线通过分别表达，临时开发测试不作为长期证据。

同一提交验证通过后自动提交 / 更新 PR，已验证 PR 待合并是自动流程终点，不自动合并或关闭 Issue。模拟合并核实后更新体验版本页 PR 记录与主分支落点。修复自动测试报告也显示在测试管理运行记录中，不向测试目录添加反向关联任务列表。断线不生成测试通过，原步骤与修复身份保留，重连通过原记录查询 / 继续。当前 Issue / Agent / Git / 环境 / 测试 / PR / 原生工具操作均为原型模拟，无外部消息或真实代码执行。

### 本轮验收管理交互

一级“验收管理”集中展示任务 Plan 的验收安排与结果，按 Task / 固定 Plan 分组，显示稳定验收项 ID、Plan 路径 / 版本、通过 / 失败 / 待验数量及办理入口。方式（自动 / 人工）、时点（任务前置 / 后置）、阻塞性质、影响范围分别表达；默认前置阻塞、后置非阻塞，明确例外由 Plan 固定。范围至少区分当前任务启动、项目后续派发和项目交付。计划归 Plan，通过条件由关联要求定义，真实结果与证据归任务专属 acceptance，不把实时状态写回 Plan。Plan 未关联不表示零验收项或全部通过。

自动项按可用场景 / 命令及环境核验，执行过程中能完成的检查归入对应候选 / turn / 构建证据。只有匹配当前 Plan 版本和目标的报告计入通过，旧目标和历史失败仍保留；PR 合并、Agent 自述或工具启动不代替通过。缺环境 / 能力保留等待原因，不静默改为人工；自动失败不得用人工确认覆盖。未知观察保存原操作身份，重连核对原结果。原型中命令、环境及报告均为演示，不运行真实检查或改写文件。

人工项显示参与人、窗口或待安排、通过条件和具体操作，执行时点达到后允许逐项登记通过 / 失败、参与人、证据及结果说明。同一场景的自动检查和人工判断分别记录，不混成一个已通过结果；界面不提供更改已固定阻塞性质或通用勾选放行。

手动与自动派发均检查生效的验收门槛。前置项目范围门槛暂停后续派发，已有执行保持原状态；任务范围门槛只影响对应启动。DAG 只展示当前真正造成阻塞的验收项与办理链接，前置依赖未就绪、后置尚未到时点、非阻塞或已解除项不铺入 DAG。项目范围阻塞集中展示，任务节点 / 详情只展示当前任务实际启动阻塞。

项目交付门槛在项目交付检查时生效，与已有代码合并 / TaskDelivery 分开：可以显示“代码交付已核实，项目交付被某验收项阻塞”，不回退真实合并事实。门槛解除也不自动宣布项目交付，仍核对未交付任务与项目交付事实。非阻塞后置项允许保留待验，草稿按已有任务交付 / 同步规则归档后，未验记录继续在验收管理中可查。

### 独立调试环境与人工验收指南

目标项目须提供可独立并行的调试环境准备入口，每个环境由一个独立目录表示，置于项目公共调试根目录下。项目设置维护根目录，例 `C:\SteerLineDebug\DemoProject`；目录用 `dev-短commitSHA-YYYYMMDD-HHmmss` 命名，同秒重复创建保证不重名。目录、数据、配置和端口按环境独立绑定，不因主分支 / worker 推送 / 根目录配置变化而改写已有环境。

验收管理增加“验收项 / 调试环境”视图，创建入口始终位于页头，不依赖任务派发资格或当前待验数量。来源为当前项目主分支，或未合并任务 → 指定候选 → 已提交版本；无可用提交时不可创建。确认时核对并固定完整 SHA、源分支 / PR / 候选、根目录、创建时间和准备操作。准备分别显示目录、构建、独立资源、启动核对，只有项目声明的准备完成才标为可用；失败保留原环境身份继续，环境准备不创建执行 Task 或 DAG 节点。

环境可用后，固定流程 Agent 按该环境版本和 Plan 为待人工项生成逐项操作指南，包括启动方式、具体步骤、预期 / 通过条件及证据要求。指南绑定 Plan 版本、环境 SHA 和验收目标，生成中、失败和可用分别显示；指南失败可重生，目标变化需生成新匹配指南。未到时点、版本不覆盖或要求主分支的项继续列出等待原因，不把准备完成或指南生成当作验收通过。

登记人工结果必须选择适用环境和匹配指南，结果自动关联环境 ID / 目录 / 完整 SHA / 源候选 / Plan 版本 / 指南版本及不可变指南快照。不同环境的输入说明分别保存。Plan 明确允许候选验收时可在已提交未合并候选上执行，但结果只验证原版本；后续合并时核对目标与版本，不自动搬用为主分支通过。要求主分支版本的项保持等待；旧主分支环境不自动包含后来的交付，必要时另建环境。当前原型仅模拟版本覆盖与准备、指南生成、目录打开，不证明实际 Git 内容、隔离资源、构建或人工验收。

### 正式文档受控生成与项目规范

正式 Spec + Plan 只有 Roadmap 草稿转正固定流程可以生成。生成页始终显示本次规范路径 / 版本 / 读取状态，并提供查看本次快照、查看最新版、维护规范三个入口。设置维护规范路径，默认 [`docs/spec/SpecGuide.md`](../spec/SpecGuide.md)。规范强调简洁设计、先查现有实现再整合、跨任务整体安排、禁止隐式多执行链路及无必要桥接，并落实最小测试与验收覆盖。

生成前固定规范内容；文件缺失或读取失败不能生成，失败可重试本次快照。规范维护后，新旧版本分别显示，已有结果仍使用原规范；采用最新规范需显式重新生成并形成新的操作记录。代码调查与规范判断在当前原型中为模拟证据，不证明 Agent 已读取真实 Git 文件。页面规范编辑仅保存演示版本；真实维护编辑仓库 Markdown，生成真实接入需固定实际 Git 版本与读取内容。

生成页按任务列出 Spec / Plan 正文，展示现有代码调查、复用整合、执行路径 / 桥接与跨任务安排。关键需求矛盾停在待补充，不发布或入图。正文可在转正流程内受控修改，保存后重新核对并取消此前确认；Plan 的测试要求固定到实际生成结果。进入文档 PR 后锁定生成输入与正文，后续规范 / 草稿变化不改写原 PR；已合并文档的部分 DAG 继续原步骤，不重新生成、提 PR 或重建已有任务。

### 本轮多草稿与转正交互

一级“Roadmap”改为“Roadmap 草稿”，按项目的多个 roadmap 目录展示多份草稿，左侧目录 / 文档列表、中部 Markdown / JSON 预览与编辑、右侧关联任务和整体进度。每份 Markdown 配同名 JSON，JSON 保存格式版本、稳定 draft_id、文档位置、已占任务编号、名称、可空 Spec 和拟议依赖。编号由统一入口取得，改名 / 移动不改变草稿和任务身份；页面内原型只模拟占号，不消耗仓库计数器。

草稿任务可以没有 Spec，不因编号进入 DAG；转正流程生成并审阅正式 Spec + Plan、核对依赖，文档合并后才入 DAG，并沿用原编号。缺少 Spec 不是草稿进入生成流程的阻塞条件。JSON 维护草稿结构化关联，正式任务的运行 / 交付状态从中心读取，execution-map 维护正式执行汇总，转正 Operation 保存快照 / PR / 合并 / 入图恢复事实，不在草稿 JSON 复制实时状态。

规划工作台直接操作关联草稿文档，一个项目可有多个 session、多个草稿，同一草稿可由不同 session 继续讨论。创建 session 时选择已有草稿或新建草稿，切换仍在工作台内部。工作台仅维护 Roadmap 正文、草稿任务、依赖及测试约束，不能直接生成或写入正式 Spec / Plan，也没有转正工具权限；自然语言请求正式文档生成或转正只给出办理入口，不启动固定流程。正式文档路径不在草稿任务表单中手工填写。

设置中的项目 / 仓库区域配置主分支，默认 main；与全局默认执行参数分开。转正从草稿页独立启动，固定 Markdown / JSON、草稿版本、代码完整 SHA、目标分支与规范内容版本。生成按钮启动必读规范 → 现有代码调查 / 整体整合 → 正式 Spec + Plan 生成 → 规范 / 测试 / 依赖核对。人审阅正文、设计依据及 execution-map 差异后确认，流程负责提正式文档 PR、合并到固定主分支并核实，再依据已合并 execution-map 与生成的固定文档创建正式 Task / DAG；实际入图才显示正式任务。文档已合并而 DAG 部分创建时保留精确完成明细，继续原操作，不重复提 PR 或创建已有任务。当前原型只验证演示字段与状态，不证明真实文件、Git / provider 或中心准入验证。

转正后原草稿文档和 JSON 可以保留，继续编辑新版本不改变固定快照或正式任务契约。项目唯一 execution-map 汇总多份草稿，DAG 的图 / 清单双视图与任务来源链接承接追溯。任务核实交付后刷新 DAG 并同步 execution-map，分别展示同步中、已同步或失败待处理；清单同步失败不伪造交付失败。全部草稿关联任务真实交付且完成同步后，才允许固定归档步骤成对归档 Markdown 与 JSON，保留稳定身份；仍有未正式任务或未完成任务时不归档。

流程、模型与原型仍迭代。没有主agent也能人工维护草稿、查看精确关联文档/成果、办理任务后验收及启动前必要操作。草稿/送审快照/正式任务各自明确来源和版本；修改草稿不直接改DAG。

先推导两条代表流程：任务交付后打开待验项与产物、按步骤登记结果/证据；任务开工前查看具体必须操作、办理后由服务核验对应条件。验收结果不等于TaskDelivery；前置操作完成不等于所有启动条件满足。失败、过期、错对象和未知执行需清楚显示实际影响，不能用通用确认覆盖。

人工项显示参与人/窗口或待安排、截止节点和实际阻塞范围；允许后验收不锁住无关任务。artifact以真实任务/交付/文档版本定位，缺失关联如实显示。具体编辑器、布局、登记命令、状态/存储和授权留到原型成熟时固定，不提前搭通用artifact/待办/审批/提醒平台。

## 2.3 主agent接入

以下会话与工具内容仅保留旧原型设想，未来需要时重新规划，不表示2.2已有交付或仍在安排接入任务。原设想的主agent仅Codex，固定审核角色由服务调度；模型建议不是正式准入或任务启动，权限仍需实际接入验证。

固定送审快照后允许继续编辑新草稿，报告/授权绑定原快照；需修改或等待前置的内容留草稿。审核和人工集成等待不默认锁住全部草稿。新session/历史/草稿输入、中断、审批和固定审核界面在实际能力与原型确认后定稿；不提供未证实的已发送输入编辑重跑。
