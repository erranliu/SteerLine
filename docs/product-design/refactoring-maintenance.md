# 重构与维护

本文维护 SteerAgent 持续维护（maintenance）能力的产品设计。用户选择维护方向、执行配置、预算和决策策略，SteerAgent 只读观察项目、理解反馈并生成提示词，驱动 Runner 从项目远端 HEAD 创建独立 worktree，分轮执行重构与审计，交付一个 PR 和PR 合入评审。最小界面与后台流程已实现，实际验证范围和未验边界见[专属验收](../../SteerlineFlow/testing/acceptance/refactoring-agent-delivery.md)。

能力分类与协作原则见 [SteerAgent](steer-agent.md)，项目同步与就绪归[项目维护](project-maintenance.md)。本文只确定产品行为，不规定接口、存储格式或 Runner 内部执行步骤。

## 产品入口与启动

项目导航新增“重构与维护”分页，承接维护行动的创建、观察、人工决策及成果审阅。现有“项目维护”继续负责项目同步、材料与就绪，两者分别展示。

用户发起一次维护行动时选择重构方向、已就绪的 Runner 执行配置、预算和决策策略，可以补充目标、范围和排除项。只读调查、决策和审计使用全局 SteerAgent 配置，代码修改、验证和交付使用所选 Runner 执行配置。行动创建时冻结两套值。首版使用下文“最小界面与流程”确定的单方向表单；多方向选择作为后续扩展。

启动基线是配置远端目标分支的当前 HEAD。正常项目维护状态已就绪时，本地主工作区与远端 HEAD 一致；页面展示远端分支和启动提交，执行绑定该提交。未就绪时提供原因与项目维护入口，不以本地领先、落后或未经核实的 HEAD 替代远端基线。

一次维护行动由 Runner 创建并使用独立 worktree 和维护分支，多轮成果累计到同一个 PR。用户不必先手工拆成普通开发 Task；原有开发任务与依赖仍由其自身流程管理。

## 维护方向

SteerLine 提供一系列基础方向提示词，帮助用户表达维护目标。初始方向包括：

| 方向 | 关注的收益 |
| --- | --- |
| 简化设计 | 减少不必要的抽象、分支和间接调用 |
| 清理冗余 | 删除无用代码、重复实现和过期配置 |
| 理顺职责 | 改善模块边界、依赖关系和职责分配 |
| 提升可维护性 | 改善命名、错误处理和复杂控制流 |
| 整理文档与测试 | 减少重复维护，使文档、测试与实现一致 |

部署管理员可以在安装目录添加自定义方向，同一安装中的项目均可选择。内置与自定义方向共用单选框，选中即展示完整的方向提示词；一次性的目标、范围和排除项填写在“补充要求”。[安装维护说明](../integration/install-deploy.md#自定义重构方向)

SteerAgent 根据所选方向与实际代码选择切片、评估收益和处理反馈。启动时核对页面所预览的版本，正文发生变化时提示重新查看。行动详情保留启动时的名称和完整正文，后续轮次与冲突续作沿用该版本。内置提示词按[提示词治理](../prompt-governance.md)维护。

默认保持现有业务行为。需要改变产品行为、公共接口或其他任务范围时，SteerAgent 判断是否超出原授权；超出时提出人工决策，不将变化混入普通重构。

## 多轮推进与预算

一轮是围绕所选方向开展的一次有限重构或审计尝试，包括选题、调查、必要修改、验证及结果判断。审计可以得出无需修改的结论；失败或放弃的尝试也保留记录并计入轮次。Runner 内部的工具调用和修复步骤不分别算作新的维护轮次。

每轮结束后，SteerAgent 根据已核实成果、剩余问题和预算，决定是否在相同维护方向与授权范围内发起下一轮重构或审计。有剩余预算即可发起下一轮，不要求先预留足以完成下一轮或最终交付的预算。没有值得继续的工作时，也可以提前收尾，无需用完预算。

| 预算 | 产品含义 |
| --- | --- |
| 美元 | 按约定配置模型估算的已覆盖参考费用，汇总 SteerAgent 决策、Runner 执行、审计和修复的主会话与已登记内部调用；未结算或未覆盖部分明确展示 |
| 时间 | 行动实际运行时间，包含执行、验证和审计；排队、等待共享容量、显式停止后待结算与等待人工决定不计入，页面另展示总历时 |
| 重构轮次 | 可发起的维护轮次，包含重构与审计尝试；失败或放弃不返还已使用轮次 |

组合设置时，任一预算耗尽就停止发起新的维护轮次。预算控制继续探索与改善的机会，耗尽后行动自动进入收尾：完成当前轮次的必要处理，将已有成果推进至 PR 和报告，包括必要验证、修复、冲突处理、收益复核与发布。

预算耗尽不会中断现有成果的交付，不会因预算本身进入等待人工，也不要求追加预算才能完成收尾。收尾期间不再借机开启无关改善或新切片。必要工作仍按真实消耗计入总额，页面分别展示轮次推进和收尾的消耗，允许总额超过最初预算；预算不表示整个行动费用或历时的绝对上限。

美元预算按用户已确认的“主会话 + 已登记内部调用的参考费用”控制，持续披露子 Agent、工具内部模型和不可观测供应商调用等未覆盖范围，不宣称完整账单。已登记但待采集或未取得可信用量的调用不算零；有界核实后仍不能判断美元新轮次资格时自动收尾，不要求人工追加预算。范围外来源的公开披露本身不等于计量失败。

没有有效改动时，保存调查结论和结束原因，不制造空 PR。部分切片无法通过验证时，SteerAgent 可以生成修复或撤销该切片的提示词，由 Runner 执行，保留可交付成果；不能把未通过验证的修改描述为已验证收益。确有授权、环境或产品取舍阻断时仍可等待人工，但须说明具体问题，不能仅归因为预算耗尽。

## 主动决策与人工参与

SteerAgent 主动组织“只读检查现状 → 选择切片并生成提示词 → Runner 执行 → 理解反馈与审计结果 → 生成后续提示词或请求人工决定 → 后续轮次”。方向提示词支撑这一过程，不能用一次固定提示词执行代替 maintenance 的主动判断能力。

SteerAgent 的维护能力对项目只读，可以调用工具读取代码、差异、项目状态以及 Runner 公开反馈，用于调查、选题和判断。它面向执行的产物只能是提示词：回答范围内问题、调整方法、修复、撤销、审计和收尾等决定，都通过提示词驱动 Runner 落实。SteerAgent 不直接写项目，也不直接执行创建工作区、运行会写入产物的验证、修改文件、解决冲突、Git 提交、推送或创建和更新 PR 等操作。

首轮调查使用固定在启动提交的只读目录。后续决策读取行动上下文。PR 合入评审读取平台核验版本的差异及可取得的检查。

| 参与者 | 维护行动中的职责 |
| --- | --- |
| SteerAgent | 只读调查、理解反馈、评估方向和收益，生成下一步提示词，提出结构化人工问题，撰写最终报告 |
| SteerLine 维护业务 | 保存预算、策略、决策和行动记录，按有效授权将提示词交给 Runner，展示 PR 和报告 |
| Runner | 根据提示词及授权创建工作区，执行修改、验证、修复、撤销、冲突解决，提交并发布 PR，回传已验证最终回复 |

Runner 提供执行进展、问题和结果，并管理受托执行及内部流程。SteerAgent 的决策也通过 Runner 承载模型执行，但其只读决策与项目写入执行的权限边界保持独立，不能因都经过 Runner 而混用。具体协作与恢复遵循 [Runner 调用生命周期](runner-lifecycle.md)。

| 策略 | 决策倾向 |
| --- | --- |
| 完全自主 | 在授权范围内自行取舍并完成闭环，对超出授权或无法核实的关键事项请求人工决定 |
| 激进决策 | 更愿意接受较大结构调整和较高冲突成本，追求更大重构收益 |
| 谨慎决策（默认） | 优先局部、易验证、易审阅的改动，关键收益或影响不确定时更早请求人工决定 |

三种策略都受相同范围、验证和交付要求约束，都可以主动处理常规反馈。谨慎决策不要求每轮由人工批准，完全自主也不赋予超出原授权的权限。

需要人工时，页面说明事实、已尝试的处理、可选方案、推荐选项，以及对收益和交付的影响。等待人工保留已有成果和当前上下文；回答后继续原行动。策略与人工决定均保留记录，方便理解和调试 Agent 的行为。

## 与任务开发并行及冲突处理

维护默认与任务开发并行推进，使用独立工作区。开发任务可以持续改变目标分支，维护不通过冻结主线或大范围文件锁来避免冲突。

SteerAgent 在推进和交付时只读关注目标分支变化，需要同步时生成提示词，驱动 Runner 同步、解决冲突并复核成果。冲突处理属于原维护成果的必要推进，预算耗尽后仍可进行。能够在原授权内解决的冲突，由 SteerAgent 决策并通过提示词交给 Runner 执行；涉及行为取舍、范围变化或无法判断的重要收益损失时，按决策策略决定是否交由人工。

PR 合入评审出现冲突时附带冲突审计，回答“解决后的成果是否仍然值得保留”，至少说明：

- 目标分支变化与冲突来源，双方需要保留的行为或设计意图。
- 采取的解决方案与重新验证结果。
- 原重构收益保持、部分损失、已被抵消或尚无法判断，以及判断依据。
- 是否撤销部分重构、接受收益下降或请求人工决定。

Git 自动合并成功不表示收益仍然成立。主线变化即使没有文本冲突，只要影响重构依据，也需要复核。无法经济地保留收益时，SteerAgent 可以要求 Runner 撤销对应切片，并在报告中解释。

报告绑定明确的 PR 提交与目标分支提交。相关代码变化后，旧结论标记为待复核，不能继续作为新版本的有效审计。交付后若继续处理该 PR 的冲突，沿原维护记录更新报告，保留此前结论与变化原因。

## 成果与审计报告

有有效改动的维护行动最终交付一个 PR 和一份可阅读、可追溯的PR 合入评审。PR 就绪与报告完成是本次产品交付目标，PR 合并是后续事实；创建 PR 不表示已合并，也不授予自动合并权限。

Runner 发布或更新原 PR 后，SteerLine 独立核验原 PR 及 head/base，从绑定的远端读取该版本的差异及可取得的检查。SteerAgent 独立评估收益、风险、证据缺口和新增结构债，给出合入、修改后再审或证据不足的建议。评审保存在原行动，PR 正文保持原样。PR 版本变化时保留旧评审并评审新版本。由人作出合入决定。

## 最小界面与流程

项目页默认展示进行中、待答复与历史行动。桌面并排显示列表和详情，窄屏从列表进入详情。新建使用右侧栏，窄屏使用全屏表单。每项目默认同时推进三条行动，后续提交进入队列。原 Run 未结算时继续占用名额，待答复的行动在原 Run 结算后让位。详细边界见[并发与运行环境选择 Spec](../../SteerlineFlow/spec/refactoring-maintenance-concurrency.spec.md)。

### 启动表单

| 字段 | 首版行为 |
| --- | --- |
| 重构方向 | 从内置和自定义方向中单选，并预览完整的方向提示词 |
| 补充要求 | 可选文本，填写目标、关注范围和排除项 |
| 运行环境与 Runner 执行方案 | 先选已就绪的环境，再选其支持维护的方案。项目默认方案仍可用时预选对应环境和方案 |
| 预算 | 美元、分钟、轮次三个可选数字，至少填写一项，可组合设置；默认只填写 1 轮 |
| 决策策略 | 谨慎决策、完全自主、激进决策，默认谨慎决策 |

表单下方展示远端分支、已核实的 HEAD、项目基线与所选运行环境状态。两项均就绪时才可提交“开始维护”。未就绪或待核实时禁用提交，显示原因并提供对应的项目维护或运行环境入口。开发者关闭环境门禁时，维护启动仍要求已就绪资格。提交时重新核验资格，若已失效则保留草稿并显示原因。受理后进入行动详情，可继续新建其他行动。

### 行动详情

详情直接展示运行环境、方案、方向与策略、当前轮次与阶段、运行时间、已计费用、当前工作和最近判断。费用尚未取得时显示未知或待结算，不显示为零。

轮次记录默认只展示“做什么、为什么、结果、下一步”，可以展开查看本轮提示词和 Runner 反馈，方便调试。无需切换详情子页或打开终端来理解基本进展。

运行时提供两个操作：

- “结束并交付”：不再发起下一轮，自动完成已有成果的必要处理、PR 和报告。
- “立即停止”：停止当前执行并保留成果，不自动开始收尾；停止后保留“结束并交付”入口。

页面区分准备中、执行中、等待人工、收尾中、已停止、已交付及异常状态。预算耗尽展示“收尾中”及当前交付工作，避免显示为等待追加预算。停止执行和资源结算分别反映，关闭或刷新页面不等于停止或重新发起行动。

### 最小推进流程

1. 用户开始维护，固定远端 HEAD、所选方向、配置、预算和策略。
2. SteerAgent 在固定于启动提交的目录只读调查并生成首轮提示词。Runner 在首次执行时从固定提交创建独立 worktree。
3. Runner 执行；SteerAgent 阅读反馈，按需生成审计、修复或补充调查提示词，再由 Runner 执行。
4. SteerAgent 评估本轮结果，有剩余预算且仍有值得处理的工作时，在同方向开启下一轮。
5. 预算耗尽、没有值得继续的工作或用户选择结束时，自动收尾。Runner 完成必要验证、目标分支变化检查、冲突处理和 PR 发布。SteerLine 核验 PR 后，由 SteerAgent 独立生成合入评审。

整个流程中 SteerAgent 始终只读，所有项目写入均由 Runner 完成。停止后再选择“结束并交付”仍使用原行动和已有成果；无法核实原执行或无法继续使用原资源时，明确说明原因，不重新创建工作区冒充续作。

### 人工决策

需要人工时，当前卡片内直接展示问题、影响和推荐方案，提供结构化选项、推荐依据、可选补充说明和“答复并继续”按钮，不另建聊天界面。提交后由 SteerAgent 根据决定生成后续提示词，驱动 Runner 继续。预算耗尽不会触发人工决策。

### 交付与冲突续作

完成后在同一页展示 PR 链接、PR 合入评审、实际轮次与时间费用、收尾消耗、遗留问题和验证限制。评审保存在本页。没有有效改动时展示结束原因。

交付前检查目标分支变化。交付后提供“处理冲突并重新评审”按钮，手动触发原成果的同步与冲突处理，继续使用原行动、分支和 PR，重新核验版本，生成新版评审，保留前次报告。该操作属于已有成果的推进，不开启新的方向或因原预算耗尽要求追加预算；同一项目仍只允许一个在途维护行动。已合并或关闭的 PR 不再提供此操作。

首版不自动持续监控 PR 到合并。多方向选择、暂停后续轮次、在途预算或策略编辑、定时触发和自动合并留作后续扩展。

## 设计范围

本设计确定手动启动、同方向多轮维护、默认并行、三种决策策略、预算控制新轮次，以及 PR、重构审计和冲突审计。定时触发、自动合并、自动跟踪到合并等后续能力另行确定。

本文维护长期产品规则；实际实现范围、执行能力缺口及验收证据在对应 Spec、Plan 和验收材料中确定。本文的设计状态不表示现有 Runner 或已安装版本已具备完整能力。

拟议模块拆分、Runner 接入缺口与实施顺序见[实现方案与解耦边界](../architecture/refactoring-maintenance.md)，不作为已实现架构。

本期实现范围见[决策与交付 Spec](../../SteerlineFlow/spec/refactoring-agent-delivery.spec.md)与[Plan](../../SteerlineFlow/plans/refactoring-agent-delivery.plan.md)。
