# 重构与维护

本文维护 SteerAgent 持续维护（maintenance）能力的产品设计。用户选择维护方向、执行配置、预算和决策策略，SteerAgent 只读观察项目、理解反馈并生成执行指令，驱动 Runner 从项目远端 HEAD 创建独立 worktree，按目标推进重构与审计，交付一个 PR 和PR 合入评审。最小界面与后台流程已实现，实际验证范围和未验边界见[专属验收](../../SteerlineFlow/testing/acceptance/refactoring-agent-delivery.md)。

能力分类与协作原则见 [SteerAgent](steer-agent.md)，项目同步与就绪归[项目维护](project-maintenance.md)。本文只确定产品行为，不规定接口、存储格式或 Runner 内部执行步骤。

## 产品入口与启动

项目导航新增“重构与维护”分页，承接维护行动的创建、观察、人工决策及成果审阅。现有“项目维护”继续负责项目同步、材料与就绪，两者分别展示。

用户发起一次维护行动时选择并编辑本次重构方向，再选择已就绪的 Runner 执行配置、预算和决策策略。目标、范围和排除项都写入方向正文。只读调查、决策和审计使用全局 SteerAgent 配置，代码修改、验证和交付使用所选 Runner 执行配置。

启动基线是配置远端目标分支的当前 HEAD。正常项目维护状态已就绪时，本地主工作区与远端 HEAD 一致；页面展示远端分支和启动提交，执行绑定该提交。未就绪时提供原因与项目维护入口，不以本地领先、落后或未经核实的 HEAD 替代远端基线。

一次维护行动由 Runner 创建并使用独立 worktree 和维护分支，多项目标的成果累计到同一个 PR。用户不必先手工拆成普通开发 Task；原有开发任务与依赖仍由其自身流程管理。

## 维护方向

「更新过期文档」是唯一内置方向，始终可选并在新建时默认选中。自定义方向由同一安装下的项目共享，可在「管理重构方向」新增、改名、编辑和删除。名称去掉首尾空白后须唯一，英文大小写视为相同，内置名称保留。[安装维护说明](../integration/install-deploy.md#自定义重构方向)

新建任务时可编辑所选方向的完整正文。直接启动时只用于本次任务。点「保存到方向」可覆盖自定义方向，点「另存为新方向」可用当前正文新建模板。服务受理任务前校验所选模板版本，并在受理时冻结其名称和实际提交的正文。排队、后续操作、评审和冲突续作均沿用任务快照。内置正文按[提示词治理](../prompt-governance.md)维护。

默认保持现有业务行为。需要改变产品行为、公共接口或其他任务范围时，SteerAgent 判断是否超出原授权；超出时提出人工决策，不将变化混入普通重构。

## 推进与预算

用户可填写金额、分钟或两者组合，任一耗尽后由 SteerLine 转入收尾。全部留空时，默认完成一个选定目标后交付。目标可以经历调查、实施、多次修复、补证和人工答复。维护任务通过操作关联保留目标和成果，通过目标引用保存历史。

SteerLine 计算预算及用量完整性，仅向 SteerAgent 发送“可继续改进”或“收尾交付”的决策条款。预算、金额和剩余时间由页面展示。费用待采集时暂停开启新目标，有界核实后仍无法判断资格则收尾，并展示原因。进入收尾后，迟到用量更正不会重新开启探索。

收尾允许完成当前成果的必要验证、修复、冲突处理、评审和发布，消耗仍计入总额并单列。预算控制探索机会，必要收尾可以超出初始预算。排队、启动核验和等待人工不计有效时间。

参考费用包括主会话与已登记内部调用，页面披露子 Agent、工具内部模型和不可观测供应商调用等未覆盖范围。没有有效成果时保存结论，已有成果累计至同一个 PR。未通过审计的改动须由 Runner 修复或处理后再交付。

## 主动决策与人工参与

SteerAgent 在启动提交的只读目录调查并选定目标，Runner 执行自然语言指令并汇报，SteerAgent 根据对话和系统事实审计，决定接受、最小修复、补证或人工决定。SteerLine 根据推进许可安排后续选题或交付。

SteerAgent 首个调查只读访问固定启动目录，后续选题和审计只依据提供的对话上下文及已有公开事实，无法访问修改后的远端工作区。SteerAgent 为实施、修复或补证生成执行指令，写明改动、需要保留的行为和验证。SteerLine 决定何时收尾，并派发固定的 Runner 执行指令。SteerAgent 不直接写项目，也不直接执行创建工作区、运行会写入产物的验证、修改文件、解决冲突、Git 提交、推送或创建和更新 PR 等操作。

SteerLine 发送共用规则和当前阶段的判断标准。首次在固定启动提交的只读目录调查，后续决策依据行动上下文。PR 合入评审使用平台核验版本的差异及可取得的检查。

| 参与者 | 维护行动中的职责 |
| --- | --- |
| SteerAgent | 只读调查、理解反馈、评估方向和收益，生成下一步提示词，提出结构化人工问题，撰写最终报告 |
| SteerLine 维护业务 | 保存预算、策略、决策和行动记录，按有效授权将提示词交给 Runner，展示 PR 和报告 |
| Runner | 根据提示词及授权创建工作区，执行修改、验证、修复、撤销、冲突解决，提交并发布 PR，回传已验证最终回复 |

Runner 提供执行进展、问题和结果，并管理受托执行及内部流程。SteerAgent 的决策也通过 Runner 承载模型执行，但其只读决策与项目写入执行的权限边界保持独立，不能因都经过 Runner 而混用。具体协作与恢复遵循 [Runner 调用生命周期](runner-lifecycle.md)。

| 策略 | 决策倾向 |
| --- | --- |
| 完全自主 | 在授权范围内自行取舍并完成闭环，对超出授权或无法核实的关键事项请求人工决定 |
| 激进决策 | 更愿意接受较大结构调整和较高冲突成本，追求更大重构收益 |
| 谨慎决策（默认） | 优先局部、易验证、易审阅的改动，关键收益或影响不确定时更早请求人工决定 |

三种策略都受相同范围、验证和交付要求约束，都可以主动处理常规反馈。谨慎决策按既有授权自动推进，完全自主也不赋予超出原授权的权限。

需要人工时，页面说明事实、已尝试的处理、可选方案、推荐选项，以及对收益和交付的影响。等待人工保留已有成果和当前上下文；回答后继续原行动。策略与人工决定均保留记录，方便理解和调试 Agent 的行为。

## 与任务开发并行及冲突处理

维护默认与任务开发并行推进，使用独立工作区。开发任务可以持续改变目标分支，维护不通过冻结主线或大范围文件锁来避免冲突。

收尾时，SteerLine 派发固定执行指令，由 Runner 整合目标分支并验证已接受成果。用户发起的冲突续作绑定原 PR 和版本。无法安全完成时保存阻断原因。

PR 合入评审出现冲突时附带冲突审计，回答“解决后的成果是否仍然值得保留”，至少说明：

- 目标分支变化与冲突来源，双方需要保留的行为或设计意图。
- 采取的解决方案与重新验证结果。
- 原重构收益保持、部分损失、已被抵消或尚无法判断，以及判断依据。
- 是否撤销部分重构、接受收益下降或请求人工决定。

Git 自动合并成功不表示收益仍然成立。主线变化即使没有文本冲突，只要影响重构依据，也需要复核。无法经济地保留收益时，SteerAgent 可以要求 Runner 撤销对应切片，并在报告中解释。

报告绑定明确的 PR 提交与目标分支提交。相关代码变化后，旧结论标记为待复核，不能继续作为新版本的有效审计。交付后若继续处理该 PR 的冲突，沿原维护记录更新报告，保留此前结论与变化原因。

## 成果与审计报告

有有效改动的维护行动最终交付一个 PR 和一份可阅读、可追溯的PR 合入评审。PR 就绪与报告完成是本次产品交付目标，PR 合并是后续事实；创建 PR 不表示已合并，也不授予自动合并权限。

Runner 发布或更新原 PR 后，SteerLine 独立核验原 PR 及 head/base，从绑定的远端读取该版本的差异及可取得的检查，并提供该 head 的只读源码快照供 SteerAgent 核验实现、路径和符号。已接受且提交匹配 head 的执行记录随上下文提供，执行者陈述和 Git 事实不代替实际测试结果。SteerAgent 独立评估收益、风险、证据缺口和新增结构债，给出合入、修改后再审或证据不足的建议。评审保存在原行动，PR 正文保持原样。PR 版本变化时保留旧评审并评审新版本。由人作出合入决定。

## 最小界面与流程

项目页默认展示进行中、待答复与历史行动。桌面并排显示列表和详情，窄屏从列表进入详情。新建使用右侧栏，窄屏使用全屏表单。每项目默认同时推进三条行动，后续提交进入队列。原 Run 未结算时继续占用名额，待答复的行动在原 Run 结算后让位。详细边界见[并发与运行环境选择 Spec](../../SteerlineFlow/spec/refactoring-maintenance-concurrency.spec.md)。

### 启动表单

| 字段 | 首版行为 |
| --- | --- |
| 重构方向 | 单选内置或自定义方向并编辑本次使用的完整正文，可将编辑结果存为模板 |
| 运行环境与 Runner 执行方案 | 先选已就绪的环境，再选其支持维护的方案。项目默认方案仍可用时预选对应环境和方案 |
| 预算 | 美元与分钟均可选，可组合设置；均留空时完成一项改进后交付 |
| 决策策略 | 谨慎决策、完全自主、激进决策，默认谨慎决策 |

表单下方展示远端分支、已核实的 HEAD、项目基线与所选运行环境状态。两项均就绪时才可提交“开始维护”。未就绪或待核实时禁用提交，显示原因并提供对应的项目维护或运行环境入口。开发者关闭环境门禁时，维护启动仍要求已就绪资格。

表单校验通过后，点击“开始维护”立即关闭表单，在“进行中”打开对应详情。服务受理前显示“提交待确认”，沿原请求核对；受理后显示“正在核验启动条件”。后台核验通过后按现有名额规则排队推进，核验期间不占推进名额、不扣时间预算。核验失败的行动进入“已阻断”，详情保留所填写的内容和原因，并提供处理入口及“带入新建”。

### 行动详情

详情顶部显示「剩余重构预算」，仅列出本次设置的金额和时间。未设置时说明完成一项改进后交付。费用尚未取得时显示待结算，收尾展示具体原因。详情显示 Runner 执行次数，运行信息提供环境、方案、方向与策略、阶段、运行时间、已计费用、当前工作和最近判断。

执行对话顶部直接显示冻结的重构方向正文。时间线按顺序直接显示每次执行的完整执行指令和 Runner 执行反馈。展开「决策指令」可读阶段规则；展开「发送给 Runner 的请求」可读保存的出站正文、材料清单及决策 schema。任务原文和实际出站请求分别展示。审计结论和 PR 合入评审默认显示摘要，可展开阅读全文。

目标审计结束并进入收尾后自动验证、发布 PR 和评审。PR 一经核验便在详情顶部提供「查看 PR」，结果卡展示编号、平台标题、交付摘要和当前版本的评审建议。列表区分「已创建 PR」与「已完成 · 无需修改」。无有效改动时展示调查结论。

操作入口按任务状态展示。

| 状态 | 操作 |
| --- | --- |
| 重构推进中 | 「提前结束并创建 PR」停止开启新目标，完成已有成果的验证和发布 |
| 执行或收尾中 | 「立即停止」停止执行并保存成果 |
| 已停止且有可交付成果 | 「继续交付 PR」恢复原任务的交付 |
| 发布请求明确被拒绝 | 「重试创建 PR」使用已接受成果重试发布 |
| 发布结果尚未核实或核验失败 | 「重新核验 PR」读取原发布结果，或核验已返回的 PR |
| PR 评审失败 | 「重试评审」核对当前 PR 版本并重新评审 |
| 原 PR 冲突续作失败 | 「重试更新 PR」继续原 PR 的更新 |

没有已接受成果的停止或失败任务展示原状态与原因。交付核验或评审失败展示「交付失败」，已有 PR 仍可查看。收尾时展示「正在验证并创建 PR」，PR 已存在时展示评审进度。停止执行和资源结算分别反映，关闭或刷新页面不等于停止或重新发起行动。

### 最小推进流程

1. 用户开始维护，服务保存所选输入。后台复核远端 HEAD、方向与配置等启动条件，通过后冻结执行所需事实并排队。
2. SteerAgent 在固定于启动提交的目录只读调查并生成初始提示词。Runner 在首次执行时从固定提交创建独立 worktree。
3. Runner 执行；SteerAgent 阅读反馈，按需生成审计、修复或补充调查提示词，再由 Runner 执行。
4. SteerAgent 根据上下文评估当前目标。接受后，SteerLine 在预算允许时安排后续选题，否则收尾。
5. 预算耗尽、没有值得继续的工作或用户选择结束时，自动收尾。Runner 完成必要验证、目标分支变化检查、冲突处理和 PR 发布。SteerLine 核验 PR 后，由 SteerAgent 独立生成合入评审。

整个流程中 SteerAgent 始终只读，所有项目写入均由 Runner 完成。停止后选择「继续交付 PR」沿用原行动和已有成果。发布结果不明时先核验原执行；PR 已取得时核验和评审该 PR。

### 人工决策

需要人工时，当前卡片内直接展示问题、影响和推荐方案，提供结构化选项、推荐依据、可选补充说明和“答复并继续”按钮，不另建聊天界面。提交后由 SteerAgent 根据决定生成后续执行指令，驱动 Runner 继续。预算耗尽不会触发人工决策。

### 交付与冲突续作

完成后在同一页展示 PR 链接、PR 合入评审、实际执行记录与时间费用、收尾消耗、遗留问题和验证限制。评审保存在本页。没有有效改动时展示结束原因。

交付前检查目标分支变化。交付后提供“处理冲突并重新评审”按钮，手动触发原成果的同步与冲突处理，继续使用原行动、分支和 PR，重新核验版本，生成新版评审，保留前次报告。该操作属于已有成果的推进，不开启新的方向或因原预算耗尽要求追加预算；同一项目仍只允许一个在途维护行动。已合并或关闭的 PR 不再提供此操作。

首版不自动持续监控 PR 到合并。多方向选择、暂停后续操作、在途预算或策略编辑、定时触发和自动合并留作后续扩展。

## 设计范围

本设计确定手动启动、同方向连续维护、默认并行、三种决策策略、预算控制新目标，以及 PR、重构审计和冲突审计。定时触发、自动合并、自动跟踪到合并等后续能力另行确定。

本文维护长期产品规则；实际实现范围、执行能力缺口及验收证据在对应 Spec、Plan 和验收材料中确定。本文的设计状态不表示现有 Runner 或已安装版本已具备完整能力。

拟议模块拆分、Runner 接入缺口与实施顺序见[实现方案与解耦边界](../architecture/refactoring-maintenance.md)，不作为已实现架构。

本期实现范围见[决策与交付 Spec](../../SteerlineFlow/spec/refactoring-agent-delivery.spec.md)与[Plan](../../SteerlineFlow/plans/refactoring-agent-delivery.plan.md)。

完整状态、自然语言执行和预算规则见[Spec](../../SteerlineFlow/spec/maintenance-conversation-budget.spec.md)，本次验证状态见[验收记录](../../SteerlineFlow/testing/acceptance/maintenance-conversation-budget.md)。
