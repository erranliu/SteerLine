# SteerAgent：能力分类与协作边界

SteerAgent 是 SteerLine 提供的智能工作能力体系，负责材料生成、对话续作、Roadmap 规划和持续维护；具体模型交互与执行由 SteerRunner（下称 Runner）承载。

本文维护长期能力边界、职责归属和 Runner 协作原则。当前已完成分类收敛：待答提示词建议、原 Run 冲突处理、Roadmap 解析和文档生成按实际用途归类，继续使用各自既有业务入口与执行契约。四类是职责分类，不表示已经建成统一执行服务；多轮规划已接入本机 Codex，通用材料服务和持续维护仍属后续能力。各项实际支持及验证范围以领域设计、所选 Runner 构建和专属验收为准。

## 定位与分类原则

SteerAgent 按业务职责分类。每类再按具体操作区分输入、产物、允许效果和完成条件；模型、执行后端、工具权限及自动化策略分别选择，不由类型名称推导。

这些选择在相应请求创建时固定。实际续作沿用原 Run 的模型、权限和资源绑定；修改新请求的默认配置不改变已有执行，也不隐含换模型或新建会话的能力。

一次材料生成可以是独立请求，一次续作可以沿已有会话执行，一项持续维护可以包含多个独立轮次。SteerAgent 不要求每种能力都有常驻会话，也不要求所有工作都创建新 Run。普通开发继续使用现有 Task、候选和交付体系。

能力归类与业务记录归属分别维护。例如，Roadmap 文档生成归材料生成能力，但原文档记录、规划关联、发布和入图仍归 Roadmap 业务所有者；分类不复制记录或增加第二套状态。

产品类型不强制对应代码包、配置层级或独立服务。模块按实际职责与产物组织，共享定义只服务当前真实消费者，不为覆盖分类清单给已有执行链增加包装或依赖。当前建议能力只承接提示词产物；冲突处理仍归原执行，Roadmap 记录、文档和任务图仍归原业务。

分类标签从已确认的工作来源推导，未知用途不猜测分类，也不通过标签选择执行或授予权限。分类缺失不改变原工作的观察、取消或停止资格。分类标签说明生成或续作的业务用途，不替代当前阶段和执行事实。Roadmap 文档发布、正式入图等本地或平台操作不会因同属一条记录而成为模型生成；原问题回答、取消、观察与停止等既有控制也不自动成为 SteerAgent 自主操作。

## 四类能力

| 类型 | 负责的工作 | 主要产物 | 决策与执行边界 |
| --- | --- | --- | --- |
| 材料生成（material） | 将明确目标、规范和依据整理为完整材料，按意见修订、检查缺漏与矛盾 | 文档正文、依据及未决问题 | 生成与发布分别处理；不因生成文档自行扩大任务范围、改变依赖或启动开发 |
| 对话续作（continuation） | 围绕已有问题或执行组织建议、回答辅助及明确用途的后续处理 | 提示词建议、待采用答案或本轮处理结果 | 建议与实际投递分别授权和核验；回答绑定原问题，执行绑定原 Run |
| Roadmap 规划（planning） | 澄清目标与约束，组织任务、依赖、优先级和验收安排，提出增量调整 | 规划提案、任务划分、依赖与待决事项 | 规划确认、正式入图和启动执行分别处理；正式 Task 与 DAG 由原业务所有者维护 |
| 持续维护（maintenance） | 在长期有效的约定范围内，分轮开展文档整理、旧代码清理和重构等改进 | 每轮有限改动、验证结果及交付记录 | 长期目标与单轮执行分开；受范围、预算及交付策略约束，超出范围时交回正式规划 |

### 材料生成

材料生成负责把已确定的工作依据写完整。材料种类可以是 Spec、Plan、验收说明或项目文档，不为每种文件再建立一种 Agent 类型。存在关键歧义时返回问题，不能用未说明的假设替代范围或验收决定。

生成完成只表示取得可审阅产物。保存、提交、发布以及正式采用由对应业务处理。Roadmap 可以委托材料生成形成文档，双方以明确的规划版本衔接，不能在写文档时暗改任务范围或依赖。

当前已有 Roadmap 文档生成，尚无独立的通用材料生成服务。具体材料及发布规则见 [Roadmap 读取与转正](roadmap-promotion.md)。

### 对话续作

对话续作包含三种不同效果：生成建议、辅助形成答案、实际推进原执行。每个操作必须明确自己产生哪一种效果，建议成功不自动取得回答或执行资格。

当前待答提示词建议只提供文本，查看、复制或生成成功都不会解除原问题。采用及执行在建议模块之外，现有契约见[对话建议](main-agent.md)。原问题回答和后续消息继续通过原输入业务处理，资格见[问题、反馈与恢复输入](decisions.md)。

代码合并冲突可以在原任务范围内由原执行处理；需求、验收或材料冲突若涉及范围取舍，应交回材料或规划流程。续作不能通过一条消息改写原 Run 的冻结依据。原执行不可用时保留具体阻断；新任务使用明确的新身份，不能冒充原会话恢复。

### Roadmap 规划

Roadmap 规划负责说明做什么、为什么做、如何拆分以及哪些工作可以衔接。规划应表达成果、范围、依赖、关键约束、通过条件及需要用户判断的事项。

规划提案与正式任务图分别维护。模型提出关系，系统校验引用和依赖，原业务所有者按有效授权确认、发布及入图。规划已生成、已落地与已准许启动分别记录。调整既有工作时保留原执行依据，明确影响范围，不静默替换在途任务的要求。

「Roadmap 规划」使用原生多轮会话讨论目标、调查仓库并修改草稿。SteerLine 负责 Rebase、触发和核验冲突处理，以及按用户审阅结果发布 PR。合入稿交给现有解析、依赖建议及转正流程。[Roadmap 规划 Spec](../../SteerlineFlow/spec/roadmap-planning.spec.md) · [Roadmap 读取与转正](roadmap-promotion.md)

### 持续维护

持续维护采用长期任务与有限执行轮次。长期任务说明目标、范围、必须保持的条件、触发方式、资源预算、交付策略及停止条件；每轮只处理一个可独立验证和审阅的切片。

跨轮保留已核实成果、剩余问题和未结算责任，每轮依据当前项目基线选择工作。长期任务不依赖一个永久运行的模型会话；并行是调度选择，不是每轮必备条件。主线与维护工作存在范围重叠时需协调，维护工作仍遵守正式开发的验证和交付要求。

暂停后续轮次与停止当前执行分别处理。已创建 PR、未知请求及未结算资源不会因暂停或取消消失。涉及行为、公共接口或其他任务范围的调整超出原约定时，交回规划或正式 Task 流程。当前尚无完整持续维护产品能力。

## 解耦与业务权威

| 所有者 | 长期职责 | 与其他部分的交接 |
| --- | --- | --- |
| 用户 | 目标、优先级、关键取舍和授权范围 | 既有有效授权持续适用；超出范围或需要新决定时提出明确事项 |
| SteerLine 业务所有者 | Task、候选、问题、规划、交付及各自的业务资格 | 提供明确来源、材料版本、目标和授权，校验并采用结果 |
| SteerAgent 类型能力 | 本操作的输入输出、固定指令组装和业务产物校验 | 接受明确上下文，返回约定产物，不直接取得其他领域的写入权 |
| SteerLine 宿主适配 | 来源读取、冻结输入、持久请求、配额、观察、取消及恢复 | 经 Runner 公开接口执行，保存原请求及资源结算责任 |
| Runner | 模型、原生 Agent、工作区、会话、Run 内 workflow 和资源管理 | 返回公开执行事实、问题、结果来源及当前允许操作 |

类型能力的纯处理逻辑与外部读取、执行分开。来源解析和 Runner 调用归宿主适配，Task/DAG 等业务变更归原业务所有者。共享分类、配置和活动展示不成为新的业务权威，也不要求所有类型共用一种请求、结果或状态机。

不同能力通过有版本的明确产物交接。例如，规划交给材料生成的是已确定的任务划分；续作遇到范围问题交回规划的是事实与待决事项。后继操作重新核验自身资格，前一项成功不自动授予后一项权限。

## 与 SteerRunner 的协作契约

全部模型执行经过 Runner。SteerLine 负责业务目标、材料和授权，Runner 负责受托执行及 Run 内部流程。SteerAgent 类型属于 SteerLine 产品语义，不要求 Runner 增加四种同名 workflow。

| 业务操作 | 当前使用或后续评估的 Runner 能力 | 契约重点 |
| --- | --- | --- |
| 后续提示词建议 | generate/1 | 一次只读生成；返回文本，采用与执行在外部 |
| 材料生成、Roadmap 解析 | generate/1 | 固定来源与材料、约定输出结构；业务内容由调用方校验 |
| 原问题回答（既有业务控制） | 原 Run 的 reply/answer | 原问题、完整题集、当前版本与回答资格；列为协作通道，不新增 SteerAgent 能力 |
| 解决合并冲突等实际续作 | 原开发 Run 的 message | 原会话与工作区、输入串行、当前消息资格 |
| 多轮规划讨论 | conversation/2 | 本机原生会话和可写 worktree。SteerLine 通过写入租约执行 Git 操作，归还后原会话继续 |
| 持续维护的一轮执行 | 后续优先评估现有开发 workflow | 按该轮范围、验证、审计与交付要求选择，不预设新流程 |

业务类型与 Runner workflow 不一一对应：对话建议使用单次生成，实际续作使用原开发 Run 的消息能力；独立 conversation 也不等同于开发 Run 续作。

能力准入分别核验两件事：所选固定 Runner 构建是否公布所需执行组合、材料及结果契约；当前业务对象和原 Run 是否允许本次操作。公开能力存在不表示原 Run 此刻可输入，原 Run 可输入也不替代调用方业务资格。缺少必要能力时明确不可用，不静默换模型、后端、会话或材料通道。

固定规则及材料沿各用途的正式来源供给，缺失或版本不符时阻断。现有对话建议的完整文本通道有独立边界，不扩展为其他用途的默认方式，见[提示词治理](../prompt-governance.md)。

输出结构校验只证明格式符合要求；来源清单只证明材料版本可供使用，均不证明模型理解正确或逐项读过材料。只读权限也不等于零工具、无隐式上下文或单目录读取隔离。需要更强保证时，由执行层提供可验证的契约，不以提示词承诺代替。

请求保存、未知操作对账、输入串行、取消和停止结算沿用[Worker 生命周期](worker-lifecycle.md)，实际版本、配置和接口要求由 [Runner 接入](../integration/steerrunner.md)维护。产物生成、业务采用或交付、资源结算分别表达；成功生成建议不等于回答，执行结束不等于交付，停止受理不等于资源已停止。

## 当前能力与缺口归属

下表描述当前分类边界，不替代构建能力检查或部署验收。更新实际支持时同步本表，详细证据保留在各领域验收中。

| 项目 | 当前边界与缺口 | 后续所有者 |
| --- | --- | --- |
| 分类与业务归属 | 分类收敛已落地；已有建议、解析和文档活动附加用途说明，沿用原记录和关联请求。冲突处理仍沿原 Run，没有新的统一派发入口。实现与验证见[分类收敛验收](../../SteerlineFlow/testing/acceptance/steer-agent-classification.md) | 各业务所有者与产品查询 |
| 建议模型设置 | 当前只有提示词建议具有专用模型覆盖，准备新请求时冻结；不覆盖原 Run 或 Roadmap 的设置，不按四类建立配置树。保存和生效规则见[执行配置](execution-configuration.md) | 建议宿主与配置管理 |
| 独立材料能力 | 已有 Roadmap 文档生成，通用生成、修订和检查入口尚未形成 | SteerLine 材料业务 |
| 多轮规划接入 | 本机 Codex、受管 worktree、原会话冲突续作和审阅后发布已接入 | SteerLine 规划业务 |
| 规划上下文契约 | 当前 conversation 的材料能力不能直接等同于 generate 的固定仓库、冻结文件及结构化输出；需先明确规划所需保证 | SteerLine 明确需求，再核对或扩展 Runner 契约 |
| 多后端内容生成 | 当前 generate 和 conversation 限本地 Codex；已有 Orca 开发执行能力不代表内容生成支持 Orca 或其他后端 | Runner 执行契约与 SteerLine 接入共同扩展 |
| 更强执行隔离 | 现有只读不提供严格零工具或单目录读取隔离保证 | Runner 及原生执行后端；按实际需求设计 |
| 持续维护 | 长期策略、轮次调度、跨轮记录、预算和主线协调尚未形成；每轮执行优先复用已有能力 | SteerLine 维护业务；发现具体执行缺口后再扩展 Runner |

## 演进与文档维护

分类收敛已固定现有类型、用途及业务归属，并保持原执行行为与领域记录。后续扩展继续按实际职责增加能力，不把当前分类声明当作预先可调用的功能。已有调用不因重新分类取得新权限；未来能力不以空服务、统一动作接口或预置工作流提前实现。

新增操作时说明目标、输入与来源、唯一业务产物、允许效果、授权依据、完成条件及 Runner 依赖。先判断能否复用现有公开契约；确有缺口时明确缺少的材料、执行或结果保证，再开展跨仓变更。分类整理本身不要求新增 Runner 执行协议。

本文维护能力边界；[项目流程](project-workflow.md)维护开发闭环；[对话建议](main-agent.md)、[决策与反馈](decisions.md)、[Roadmap 读取与转正](roadmap-promotion.md)维护具体业务。单次实现通过 Spec/Plan 固定范围，验收记录证明实际结果；本文不积累运行日志、字段清单或实现步骤。
