# 规划界面原型

`index.html` 是可直接用浏览器打开的单文件交互原型，无构建步骤或外部脚本依赖，长页直接滚动。用于讨论页面结构、文案和状态流转；页面内的任务、回执、文档校验结果都是演示数据，按钮不连接 SteerLine 服务或 Codex。

原型用于讨论交互，不代表已经交付的能力。2026-10-23 测试管理页已按用户确认收敛为只读 Git 测试历史；其契约见[测试记录 Spec](../../../../SteerlineFlow/spec/test-records.spec.md)、[Plan](../../../../SteerlineFlow/plans/test-records.plan.md)与[专属验收](../../../../SteerlineFlow/testing/acceptance/git-test-records.md)。其他分页保留早期规划演示，以各自当前 Spec 为准；[归档界面设计](../../../../SteerlineFlow/archive/design/planning-ui.md)仅供历史参考。

## 本轮交互

- 本版入口为“Roadmap 草稿”，只读仓库中已有 Markdown；无规划聊天、草稿新建 / 编辑、手工任务创建和归档功能。原型只用内嵌文件快照，不实际扫描仓库。
- Markdown 是唯一草稿输入，不要求配套 JSON。点击“Runner generate · 解析任务与依赖”，同时传入草稿、已有任务目标 / 相关 Spec 与 DAG，模拟识别候选任务、批内依赖、已有正式任务依赖、重复覆盖与待澄清问题。
- Markdown 编写时没有新正式任务编号，可以使用所属 Roadmap 内部代号 T1 / T2，自行描述任务间及对已有正式任务 #8 等的拟议依赖。Runner 解析保留这些信息，展示原文依据、草稿原有依赖、核对后的依赖和建议变化；缺少代号时建议临时代号，仍需用户确认。
- 确认只固定 Roadmap 内部代号、任务范围与依赖并保存 JSON；不分配新正式编号。JSON 是 SteerLine 输出，不作为用户输入或实时执行状态来源。任务身份由 roadmap_id + ref 定位，不同 Roadmap 都可有 T1。demo-* 仅为页面变化标识。
- 解析失败可显式重新解析；待澄清问题要求外部补充 Markdown。断线保留原解析请求，重连后查询原结果。演示外部更新需点击刷新读取，旧结果保留；来源或已有 DAG 变化后重新解析并确认。
- 确认任务与依赖后进入文档生成，固定解析结果、代码基线和规范。文档阶段单独列出 Runner 能力需求，默认显示待接入；开启“演示：文档生成所需能力已就绪”才能体验生成。扩展 generate 或新增 workflow 尚待设计。
- 文档阶段先调查代码并做跨任务整体设计，再生成逐任务 Spec / Plan 和必要验收安排，复核已确认依赖。文档可受控修改并重新核对；改变任务拆分或依赖须回到解析确认阶段，不静默变更。
- Spec / Plan 使用不依赖正式编号的稳定路径和 Roadmap 内部引用。审阅发布的 JSON / execution-map 同样使用内部身份，原 Markdown 不变。文档合并后进入待入图阶段，此时新正式编号仍未分配。点击“正式入 DAG · 分配编号”才创建 Task、转换批内依赖并保存编号映射。
- 映射表和独立映射 JSON 展示 roadmap_id / ref → 正式编号；已发布文档不回填或重命名。入图采用同一批次事务，编号、Task、依赖、来源映射和回执全部提交或回滚。回执丢失显示待核实，查询原请求恢复原映射，不重新分配。DAG 可返回来源代号，草稿可跳正式任务。自动派发开启时，新入图且满足前置的任务可能启动。
- 一级导航底部“设置 → 执行”独立管理全局默认候选参数，依次选择执行路径、机器、Agent、模型和推理强度，再显式保存。此处不展示任务派发或并行数量，也不选择预先成组的方案。
- 本机 Codex 路径固定为本机与 Codex；Orca 路径先选择本机或远端电脑 A，再按该机器返回的能力选择 Agent、模型和推理强度。可选项来源标为 Orca 返回或本机预检测配置，均为演示能力；切换上级清空受影响的下级选择，未完整选择不能保存或启动。远端机器/演示型号不证明真实接入支持。
- 当前项目自动派发开关放在 DAG 页头。未执行任务可从 DAG “手动启动”首次创建一个候选，预填已保存的全局默认参数，本次调整不改全局默认。
- 自动派发为尚无候选的就绪任务启动一个默认候选，不补位，不使用手动并行数量。关闭不停止运行中的候选。
- 只有“执行与待处理”中已执行且未合并的任务提供“新增并行候选”入口。任务面板仅展示本次新增数量，每个候选分别按路径、机器、Agent、模型和推理强度依次选择；不同候选的未提交选择保持独立。完全相同的参数组合按现有候选约束拒绝。DAG 对已有执行只提供查看执行入口，未执行/已合并任务不展示新增按钮。已有候选保留冻结参数，受阻/已交付任务禁用启动。
- 执行页按任务汇总，候选卡片切换独立输出、问题与回答草稿。输出每 1.5 秒模拟追加，支持跟随、暂停、滚动阅读、新输出提示及断线/重连。
- 实时输出工具栏按原执行路径提供“在 Codex / Orca 中查看对话”。本机 Codex 定位原 thread / 工作区，Orca 路径定位原机器 / terminal；即使 Orca 使用 Codex Agent，也通过 Orca 打开。点击显示绑定当前 Task / 候选 / Execution / Attempt / Turn 的演示目标，不启动真实工具。离线或缺失绑定时禁用，每个候选的定位回执独立保留。
- 候选可以演示本轮完成、中心核实 PR 合并、不可撤销放弃及停止待核实。交付后其他候选保留实际演示状态，后继依赖按交付释放。
- 一级“验收管理”按 Task / 固定 Plan 分组，显示自动 / 人工、前置 / 后置、阻塞性质和精确影响范围，支持通过 / 失败 / 待人工 / 环境与时点 / 正在阻塞筛选、查看 Plan 计划与任务专属结果记录。Plan 未关联时不推断为全部通过。
- 人工登记要求参与人、实际操作说明和证据；失败及后续通过分别保留。自动项缺环境不能改为人工，定向自动检查由演示入口产生结果；通过计数匹配固定 Plan 版本、候选 / turn / 交付构建，旧目标结果只留历史。观察断线时保留原自动操作，重连查询原结果，不另发检查。
- 前置项目验收暂停后续派发，现有执行继续；任务前置验收仅阻塞对应启动。手动 / 自动派发均检查门槛。DAG 仅显示正在生效的阻塞与办理链接；未到时点、非阻塞待验项不进入 DAG 阻塞提示。
- 项目交付检查独立于任务代码合并事实。后置项目交付门槛在检查交付时生效，不回退 TaskDelivery；非阻塞后置项继续待验，草稿归档后仍在验收管理中保留。
- 验收管理提供“验收项 / 调试环境”视图，页头始终可以创建调试环境，任务派发门槛不阻止此独立准备操作。项目设置维护公共调试根目录，默认 `C:\SteerLineDebug\DemoProject`；环境以 `dev-短SHA-YYYYMMDD-HHmmss` 命名，同秒同提交重复创建追加序号，每个环境独立目录、数据库、配置与端口。
- 创建来源是当前项目主分支，或未合并任务的指定候选提交。没有可用提交的候选不能创建。确认时固定完整 SHA、来源、根目录与准备身份；后续推送、合并及配置变化不改写已有环境，目录存在也不直接标为可验。准备失败继续原环境，不重新分配目录或端口。
- 环境就绪后，演示固定 Agent 为待人工项生成逐项指南，绑定固定 Plan、环境 SHA 与当前验收目标。指南包含启动、操作、预期 / 通过条件和证据要求，生成中 / 失败 / 可用分别显示。版本不适用和未到时点的人工项仍列出等待原因，指南生成不代表验收通过。
- 人工结果必须选择可用且版本适用的环境及匹配指南，自动带入环境 ID、目录、完整 SHA、来源、Plan 与指南版本和指南快照。不同环境的未提交人工说明分别保留。未合并候选结果不自动算作合并后的目标通过，要求主分支版本的项不能在候选环境登记；旧主分支环境也不自动包含后来合并的任务。
- 一级“测试管理”按测试集组织，默认展示运行记录，另有只读测试定义页签；支持名称 / ID 搜索、L1–L4 筛选，以及原始结果、复验情况、分支 / SHA、环境和日期筛选。目录不按 Task / Plan 分组。
- 记录由测试脚本产生和登记；人工命令行与 Agent 执行使用同一记录模型，可以没有任务 / 候选绑定。页面没有执行、重跑、结果修改、入口登记或环境创建按钮。
- 每次运行分别保留实际范围、原始结果、代码 SHA、工作区是否有修改、定义、环境、开始 / 结束时间和证据引用；有原候选来源时可跳转。脏工作区的历史通过不冒充固定 SHA 通过。
- “复验通过”依赖脚本显式关联前次失败。失败→再次失败→通过保留完整链；单次部分覆盖显示“部分复验通过”，跨记录 / 跨 SHA 的子集通过不能拼成完整通过；较新的失败优先，定义变化提示另行核对，无关联的后来通过不解除旧失败。筛选隐藏链中记录不改变完整链的判断。
- 汇总展示代码 / 环境 / 日期范围内的执行次数、最近原始结果、最近通过时间和失败待完整复验数；结果 / 复验筛选影响列表命中数，汇总口径明示，不混成当前项目全部通过。
- 分级解释采用当前[测试架构规范](../../../../SteerlineProjectGuideDoc/testing-architecture.md)：L1 包括快速单元和小范围集成；L4 并非全部串行。测试集 ID、命令、摘要与内容均为演示，不映射为真实入口。
- 草稿转正、执行页中的固定 L1、旧 PR 测试门槛和 Bug 自动测试仍是早期演示，本次未重构这些流程；“查看脚本测试记录”只导航，不再从测试管理运行测试。正式产品不因此新增测试通过 / PR / Delivery 门禁。


实时增量文字与工具正文是新增产品方向，当前服务仍只提供近期活动摘要、必要状态与完整最终回复。本原型不证明实时输出接口已实现；断线期间不生成或补画模拟输出。设置、解析 / 转正记录及模拟外部文件变化只在当前页面实例内有效，刷新浏览器恢复演示数据。

JSON、解析结果、文档、入图编号映射与转正快照均为页面内演示数据。解析由确定性示例逻辑模拟 Runner 返回，不证明真实 Markdown 识别或依赖推理能力；编号不调用真实计数器，不写入实际 Spec、execution-map 或数据库。规范读取、仓库调查、正式生成、PR、合并与入图都不调用服务或 Agent。产品要求见本轮 [Spec](../../../../SteerlineFlow/spec/roadmap-promotion.spec.md)、[Plan](../../../../SteerlineFlow/plans/roadmap-promotion.plan.md)与[验收计划](../../../../SteerlineFlow/testing/acceptance/roadmap-promotion.md)，均仅规划、未实施。生成规范以仓库 SpecGuide.md 为基础并标明本版只读流程，页面维护仅更新演示版本。

## 版本蓝图演示

1. 版本蓝图是 AI 维护的文档。打开一级“版本蓝图”，切换示例文档并只读查看目标、能力范围、非目标、完成标准和未决问题。项目界面没有蓝图新建、编辑、保存和确认功能。
2. 页头“项目愿景”展示 `SteerlineFlow/Roadmap/product-vision.md` 的内嵌快照；关闭或按 Esc 返回原蓝图，断线仍可阅读。
3. 当前不做 Roadmap / Task / PR 关联，不显示任务进度。蓝图路径明确标为示例，原型不读取 / 写入真实蓝图文件或调用 AI 维护文档。

## 长期文档演示

1. 打开“长期文档”，分为“SteerLine 流程”和“项目文档”。流程文档的文件名由 SteerLine 约定，工作过程中调用为上下文输入；目前包含 `SteerlineFlow/spec/SpecGuide.md`（Spec / Plan 生成规范）和 `SteerlineFlow/testing.md`（测试规范），分别用于正式生成与测试规划 / 执行。项目文档按项目实际目录结构展示，不固定文档名称或目录；当前架构、并行设计及主题设计仅为示例。目录树从文档相对路径生成，支持展开 / 收起和查看正文；原型使用内嵌示例，不扫描真实仓库。流程规范及部分项目正文来自本地快照，主题设计与覆盖状态为示例。
2. 查看结构约定，分别阅读流程规范的约定路径、必要内容与调用时机，以及项目文档的示例目录树和自由组织方式，并查看接入 / 正式生成前 / 代码合入 / 长期入口变化的触发说明。流程文档的查看与维护入口统一在长期文档页，选择生成规范或测试规范后可查看最新版本并维护演示内容；项目文档只读。设置中不再放置生成规范。
3. 切换正文与待合入预览，分别查看已同步、待更新、更新中、文档 PR 待合入和更新失败。失败 / 待合入保留正文及原覆盖，不伪造已同步。
4. 从执行页核实 #8 的 PR 已合并，架构 / 并行文档随演示代码事件进入维护，再形成文档 PR；Bug 代码合入同样触发相关资料。纯文档转正 PR 不触发架构事实维护。
5. 长期测试入口候选登记后，测试规范保留候选预览并等待合入；本任务代码合入后再整理主分支说明。两份流程规范的维护均在长期文档页进行，保存后显示待合入内容，原正文快照及既有生成输入保留。
6. 任务与依赖确认后，文档生成前按约定读取生成规范与测试规范，本次参考的项目文档快照另行标明并记入输入；文档维护不会生成执行任务。所有 AI / 覆盖 / PR 操作为页面演示，无真实维护和 Git 写入。

## 草稿解析与正式 Spec / Plan 生成演示

1. 初始打开“执行界面改进”，只读查看使用 T1 / T2 内部代号、没有新正式编号的 Markdown。解析前 JSON 和任务列表为空，生成文档入口禁用。
2. 点击解析，查看草稿原有 T1 → 正式 #8、T2 → 本 Roadmap T1 的关系和 Runner 核对结论。确认后查看 JSON，仍仅使用内部代号，formal_mapping 为空。切换“执行控制改进”，另一个 T1 与前一份无冲突，Runner 建议补充正式 #8，须确认后采用。
3. 点击“生成 Spec / Plan”，文档能力默认就绪，可继续演示；取消能力选项可验证缺能力阻断。能力表单独列出固定仓库只读调查、批量整体设计、多文档输出的要求；此开关只控制演示，不调用真实 Runner。
4. 生成前按固定规范调查代码并整体规划；切换任务 / Spec / Plan 查看正文、依据和测试安排。可演示规范读取失败重试、关键需求矛盾、修改生成正文后重新核对，以及采用最新版规范重新生成。
5. 审阅后发布 PR，核实合并后停在待入图，此时映射仍为空。点击“正式入 DAG · 分配编号”，才分配正式编号并转换依赖。可勾选整批提交后的回执中断，观察映射待核实，查询原请求后恢复完整映射；原 Markdown、文档正文和路径不变。
6. 在“演示场景”勾选待澄清依赖或 Runner 失败，下一次解析进入对应状态。解析时到执行页模拟断线，再回草稿页，重连后查询原请求。
7. 模拟外部 Markdown 更新，刷新后旧解析不再适用；重新解析仍保留原文内部代号，不占用正式编号。更改来源不会覆盖既有转正文档快照。
8. 选择“任务调度基础”，T1 / T2 / T3 通过正文明确对应已有正式 #7 / #8 / #9。确认只关联已存在身份，不分配新编号或重复创建任务。

## Runner 文档生成能力需求

| 范围 | 本版定位 |
| --- | --- |
| Markdown 任务与已有 DAG 依赖解析 | 复用现有 generate/1、只读配置、内联材料与结构化结果契约；本原型只模拟 |
| 固定仓库与代码调查 | 需核对 / 补齐指定仓库、分支、完整 commit 下只读调查及实际来源证据 |
| 本批任务整体规划 | 需明确共用修改、职责与交接条件；拆分 / 依赖变化返回用户重新确认 |
| 多文档结果 | 需输出逐任务 Spec / Plan、必要验收材料、路径、正文与调查依据，由 SteerLine 校验发布 |
| 原请求 / 查询 / 停止 / 恢复 | 复用现有调用生命周期；不为转正另造 Agent 运行时 |

2026-10-27 生产已接入 generate/1 的固定仓库扩展，完整结果上限 1 MiB；原型开关仍只控制模拟，不能用演示替代生产验证。

## Bug 管理演示

## 如何迭代

- 小幅视觉和状态调整直接修改 `index.html`，保持无构建步骤，方便审阅 Git diff。
- 新页面或流程应先更新当前 Spec/验收；本原型及[归档界面设计](../../../../SteerlineFlow/archive/design/planning-ui.md)不作为当前产品契约。
- 当需要可复用前端组件、独立设计系统或真实 API 联调时，再把原型升级为有构建配置的 UI 工程；届时仍由 Go 服务提供业务权威接口。
- 正式实现应整合当前 Web 前端与公开 Go API；本原型不证明产品接线、Runner 能力或自动 / 人工验收已经完成。
