# 主 Agent：材料澄清与要求冲突

状态：首批已实现，未部署。范围为手动分析材料不明确和要求冲突；实现及实际核验范围见[验收记录](../../SteerlineFlow/testing/acceptance/main-agent-materials.md)。本稿具体化[项目流程的职责边界](project-workflow.md#4-steerline-与-runner-的职责边界)。

## 1. 首批范围的取舍

首批只帮助用户处理两类问题：**任务要求不够明确、已有要求相互冲突**。这是执行 Agent 无法仅靠工程判断解决、又需要 SteerLine 补充依据的业务缺口。主 Agent 调查已有材料，给出建议、可直接提交的澄清回答或完整材料修订，用户查看后点击处理。

目前没有各类异常的发生频率统计；以下取舍依据现有流程及可补充的业务价值，不把设计预判当成已测频率。上线后可按分析记录核对实际使用，再决定扩展。

| 原清单 | 首批取舍 | 原因与现有处理路径 |
| --- | --- | --- |
| MA-01 原生待答 | 不普遍接入；仅作为下述两类问题的分析入口 | 普通选项、权限或简单问答已有原问题回答，不需要每题调用主 Agent |
| MA-02 材料不足 | 保留其中的“任务要求缺少信息” | 主 Agent 可调查材料、建议答案、准备补充正文；文件未提交、缺路径、待生成等机械问题沿现有维护流程处理 |
| MA-03 要求冲突 | 保留 | 需要解释矛盾、提出取舍并保持材料一致，现有执行链路缺少该协调能力 |
| MA-04 依赖与前置交付缺口 | 暂不独立接入 | 正常依赖等待和基线准入已有规则；跨任务补交付、改 DAG 会显著扩大首批范围 |
| MA-05 材料生成与规划受阻 | 暂缓 | 生成准备、重试、Roadmap 编辑/重新解析已有入口；首批不接多个生成 owner |
| MA-06 环境或配置阻断 | 沿现有入口 | 检测报告、配置校验、登录与重新检测已有处理路径，不增加环境修复 Agent |
| MA-07 执行或审计受阻 | 沿 Runner；材料问题可手动进入首批两类 | 实现、审计、修复、补报和恢复归 Runner，不由主 Agent 再判断或规划内部阶段 |
| MA-08 PR 合并冲突 | 沿现有冲突解决入口 | 机械冲突已有原 Run 续作；需要新产品取舍时可由用户报告为要求冲突，不补自动冲突采集 |
| MA-09 操作未知或身份冲突 | 首批不接入主 Agent | 沿原请求对账与人工诊断；不为恢复问题建设额外分析和重试机制 |

首批同时去掉：后台自动发现/分类、分类开关、全项目文档巡检、事项自动归并、多 session 调度、任务图修改、自动恢复/重试和通用动作编排。取消的是本阶段接线，不删除原有诊断、人工入口或可靠性约束。

## 2. 两类情况的入口与处理

### 2.1 任务要求不够明确

- 典型情况：Spec 未说明空输入行为，执行者提出两个合理选择；Plan 的验证要求缺少必要参数；原任务中某个产品决定没有明确依据。
- 入口：用户在候选详情点击“分析材料问题”，选择“要求不够明确”，可以补一句问题描述。原生 question 若存在则自动带入；没有 question 时以用户报告为起点。首批不从状态或自然语言诊断自动分类。
- 上下文：原 Task/候选及固定 Spec、Plan、直接引用的相关规范/验收/测试安排；原问题完整题集与选项、已有回答及送达事实；相关 verified final；用户补充的信息。首批只提供候选绑定的 Spec/Plan、公共规范和验收引用，不提供自由代码调查；原候选版本与当前材料分别标明。
- 提示词重点：先调查是否已有答案，区分“材料已有、只需解释”“缺少产品决定”“必须修改正式材料”；给出推荐答案、依据与必要的替代选项，不凭常识发明产品要求。
- 结果：已有契约足以支持的澄清，准备完整回答；涉及新增或改变目标、范围、通过条件的决定，准备 Spec/Plan 修订，不能用一次回答暗改契约。需要用户取舍时先列问题，用户补充后再生成可执行方案。

### 2.2 已有要求相互冲突

- 典型情况：Spec 要求保留某种行为，Plan 或验收却要求相反结果；当前任务要求与适用规范不能同时满足；执行者与用户对同一条要求有不一致解释。
- 入口：同一“分析材料问题”入口选择“要求相互冲突”，用户指出相关正文或带入原 question/final；首批不扫描全部材料寻找矛盾。
- 上下文：上一类的基本材料，加冲突双方完整相关正文、来源/版本/定位、适用范围及已有用户决定。首批不自动增加其他任务材料；使用者可在补充信息中提供必要事实，来源不足时继续询问。
- 提示词重点：先证明哪里不能同时满足，排除版本混用和误读；给最小一致修订、理由、替代方案和对本任务验证的影响。没有依据裁定时请用户选择，不自行宣布 Spec、Plan 或某位执行者始终优先。
- 结果：误读可以按已有依据澄清；真实要求变化则准备完整修订。若必须修改其他任务、公共规范、DAG 或补充代码交付，说明影响和后续人工处理建议，首批不提供跨任务执行按钮。

## 3. 最小上下文与保存方式

每次分析固定：项目与仓库、Task/候选/Run 身份、用户报告和情况选择、适用的 question、原材料 commit/path/digest、所用正文和完整性、已知用户决定，以及原输入和停止资格。缺少必要来源时说明缺口，不生成依赖该事实的可点击方案。

后端从原 owner 读取事实并保存分析记录，关联原候选及可选 question。记录只包含本次来源、上下文版本、用户补充、模型结果、具体待发回答/文件产物和动作回执；不建设跨来源的通用事项系统。两类共用同一条“分析 → 补充信息 → 修订建议”的流程。

上下文复用[任务详情](../../internal/product/api/pages.go)、[原材料](../../internal/projectmaintenance/model/material.go)和[公开执行观察](execution-observability.md)，并新增独立的材料分析记录，不借用开发候选状态。用户已提交的答案与送达状态必须保留；未提交草稿仅由用户明确加入本次分析。各来源带版本和观察时间，不把多系统观察当作原子快照。没有原问题时不制造 question，也不承诺可以向原 Run 投递回答。

静态规则与当前选定文档沿固定仓库读取；原候选正文、动态问题、用户决定和状态使用 Runner 已有的正式私有只读文件材料能力并核对 manifest，不内联正文兜底。原候选固定版本和当前版本不混用；需要最新材料时分别提供，不让模型自行将当前工作树当作原任务依据。只提供相关文件，不默认加载全项目；上下文缺失或超过现有通道容量时明确说明。

不读取 Runner 私有数据库、原生日志、登录文件或完整原生工具 transcript。首批不采集新的 PR 冲突事实或环境诊断，也不新增全局图和跨项目上下文服务。

## 4. 提示词提纲与多轮讨论

共同提纲只覆盖以下步骤，两类分别追加第 2 节的分析重点：

1. 明确本次问题，只调查指定任务材料，提出建议和待审产物，不执行正式写入。
2. 阅读原 question/用户报告和固定材料，标明版本、原文依据及缺失信息。
3. 判断是已有依据可澄清、缺少决定，还是实际要求冲突；区分证据与推断。
4. 提供推荐方案、必要的替代方案、用户必须回答的问题及对本任务测试/验收的影响。
5. 已可确定时，输出完整待提交回答或指定文件的新正文/差异；不改契约的解释与正式材料变更分别表达。
6. 输出引用、未决问题、处理前提和处理后的核验方式；超出首批范围时只给后续建议，不自行扩大任务。

首批沿 Runner 本地 Codex 的 generate 仓库/文件通道做一次明确的只读分析。用户补充或修订时，将已保存的相关讨论、原建议和新增事实组成下一次完整输入；不依赖一个长期 session 记忆，不为追问接入新的 conversation 材料协议，也不调度调查子 session。

界面仍按同一条讨论连续展示。已有产物完整就直接使用，不强制再发一轮“整理”；上下文变化时保留旧建议及其来源，再明确生成新版本。主 Agent 的分析任务不建立开发候选，也不进入开发的审计/发布 workflow。

运行短入口为 `internal/prompts/main-agent.md`，完整规则为 `internal/prompts/materials/main-agent.md`，由同包嵌入。项目显式准备 `SteerlineFlow/main-agent-rules.md` 后需自行审阅、提交并合入；已有不同正文不覆盖，缺失或版本不符阻断新分析。业务代码只传冻结事实，正文、接线和验证依[提示词治理](../prompt-governance.md)独立审核。

## 5. 只保留两个处理出口

| 出口 | 用户先看到什么 | 点击后做什么与限制 |
| --- | --- | --- |
| 提交此澄清回答 | 完整原题、实际待发回答及依据 | 复用原回答入口，重核 question/题集、候选与 Runner revision、参与资格和未结算输入；沿现有 2,000 UTF-8 字节限制，不截断；没有可回答的原问题就不显示该按钮 |
| 创建材料修订 PR | 允许修改的本任务 Spec/Plan 的原文、新正文、完整差异、理由和测试影响 | 在独立 worktree 准备并发布本次明确文档修订，保留原提交和 PR 绑定；新增该用途的业务适配，不假设现有 Roadmap 发布入口支持任意材料 |

文档修订只允许本任务绑定的 Spec/Plan；规范、其他任务、环境配置、测试清单和代码均不在该动作范围。需要修改这些材料时给具体建议和原处理入口，不为首批增加任意文件写入或通用命令执行器。若本任务文件尚不存在或原来源不可核实，则先回现有材料准备入口，不自动创建任意路径。

文档 PR 创建、合并、材料重新准备、新候选执行分别表达事实。首批不新增自动合并、不串联“合并后重生成并启动”、不向旧 Run 注入新契约。用户通过现有 PR/维护/候选入口继续；原候选仍按固定契约保留原资格，不自动停止或撤销交付。没有原问题的分析仍可产出可阅读建议或材料修订。

点击绑定用户实际看到的方案；相关材料、原问题或业务资格变化时重核，不静默改参数后执行。先保存意图再调用原 owner，重复点击返回原回执；未知只核实原操作，复用现有可靠性边界，不建设新的恢复框架。

“建议已生成”“回答已投递”“文档 PR 已创建”分别展示，不把这些状态等同于原任务已解阻。分析失败时保留原业务入口及诊断；不递归调用主 Agent 处理主 Agent 自己的异常。

## 6. 设置与界面

首批设置只保留模型和思考强度：固定本地 Codex，通过 Runner 调用，默认 GPT 6.1 Sol / high。真实模型标识和支持强度沿 Runner 本地 Codex 目录核验；缺失则提示不可用，不隐式改投。每次新分析固定配置，设置变更不影响已有请求。保存沿[执行配置](execution-configuration.md)，重启后生效。执行器路径复用第一个已配置的本地 Codex 预设，模型/强度独立选择，访问权限固定只读；未配置本地预设时使用 Runner 的本地默认，不改投远端。模型目录提供可选模型与强度，不等同于执行环境已就绪。

候选详情提供可展开的“分析材料问题”；打开前不读取分析数据。讨论区提供补充信息、重新分析和两个适用的处理按钮。列表只轮询本候选最近 50 条摘要，完整上下文和结果按分析 ID 读取；超出数量显示提示。没有后台自动分析、分类设置或独立主 Agent 工作台，也不扩展[活动中心](async-activities.md)为通用事项中心。原问答、维护、Runner 恢复与冲突解决入口继续直接可用。

## 7. 首批交付与核验

首批完整闭环为：用户从原候选发起两类分析之一 → 带入固定上下文 → 查看建议并补充信息 → 提交原问题回答或创建本任务材料修订 PR。已实现来源绑定/分析记录、本地 Codex 调用适配、共同提示词及两个具体动作适配。SQLite 使用 schema 42，不新增旧 schema 41 的读取或迁移。

至少验证：两类典型问题能从原文形成有依据的建议；已有材料可回答时不凭空补要求；任务外变更只给建议；普通问答/环境/恢复不自动调用主 Agent；原/新版本不混用、缺来源不可执行；无原问题时不出现回答按钮；多题及回答字节限制；PR 仅改绑定 Spec/Plan、完整差异与实际发布一致；方案过期拒绝、重复点击去重及未知沿原号核实；补充信息重新分析保留原决定；重启只补收原结果，原人工入口不受分析失败影响。

未来是否增加自动触发、更多来源、多 session 协作或跨任务动作，应根据实际使用单独确定，不作为本阶段前置。本页说明实现范围，具体通过与未验范围以验收记录为准。
