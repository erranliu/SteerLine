# 第二阶段推进边界

本文件是可修改的阶段草稿，编辑前先读[RoadmapGuide](../RoadmapGuide.md)。它不参与正式任务派发，也不因包含已有编号而自动进入 DAG。

第二阶段交付原生 UI 与受控规划，拟议范围和依赖见[草稿 roadmap](roadmap.md)，只有受控准入并同步到[正式执行清单](../execution-map.md)的 Task 才可执行。每项执行以中心固定的 Spec/Plan 为准，草稿讨论不产生 Ready 资格。

新增产品方向以[草稿roadmap与审核准入](phase2-draft-roadmap-admission.md)为准：审核agent评估Spec及前置成熟度，适合固定才准入；未成熟内容留草稿。下表描述既有 #43–#52 草稿候选的基础交接，不表示已入 DAG。新增审核范围尚未固定为执行任务，相关 Spec 在正式准入前对齐，不从候选图推断已具备审核能力。

## 推进顺序

已有持续 worker 基础；草稿拟优先 #45 → #50，#50 同时等待 #44 原生基座；#43 先做实际规划能力验证，#44 可独立准备。#83 单独提供安装/调试路径共存，[一期活动](../../acceptance/phase1.md)的 24 小时只阻塞阶段签收，不增加 API/UI 研发前置。完整 stable/dev #40/#41 延后，不属于当前二期任务的传递前置。

#46 建立草稿基础，之后 #48 发布与满足权限前置的 #47 会话服务可分别准备；#44/#48 → #49/#52，#44/#47 → #51，最终以真实单安装版能力参加二期验收活动。涉及草稿/审核/准入的新范围仍在实施前重新固定，不把优先级变更当作规格已对齐。

本机候选基线已具备；全面中心搬包仍不是本机 API 的新前置。不同任务可在依赖满足后独立推进，共享 Service/SQLite、UI 导航和真实宿主资源仍串行集成。前置能力尚未交付时不能用样例界面提前宣告完整功能。

## 完整产品路径

目标讨论/草稿roadmap → 固定送审版本 → 独立审核Spec质量与前置成熟度 → 通过且适合固定者经人的授权由SteerLine受控正式准入 → DAG执行与人工方案实验 → 人合并PR → 唯一TaskDelivery与完成归档 → 主agent据真实结果继续草稿。需修改或需等待前置者留在草稿，不成为正式执行任务。

草稿任务可以提前取得唯一 Task ID，正式准入沿用该身份；只有受控纳入 execution-map 并创建对应中心 Task 时才进入 DAG。送审快照、授权、文件/中心部分完成和恢复算法在后续 Spec 固定，当前不把旧预留/Publication 流程宣称为新审核实现。现有固定契约不因草稿变化被改写。

这里的文档审阅、固定内容/提交核验及权限约束不属于被 #36 删除的项目代码验证。它们保留在各自规划领域；正式文档、草稿和已创建任务继续区分，目标分支集成与 Git/中心部分失败按原请求恢复。
