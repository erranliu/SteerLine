# 第二阶段推进边界

本轮草稿按[RoadmapGuide](../RoadmapGuide.md)修订。任务集合见[主草稿](roadmap.md)，开发派发由 roadmap-runner 按用户确认的[execution-map](../execution-map.md)核对状态、依赖及明确前置。本页后续中心DAG、准入和TaskDelivery描述属于产品能力规划，不构成 Codex 开发调度的中心前置。

## 三个独立验收节点

1. **2.1 DAG与执行UI**：从人工提供的稳定契约进入已有DAG，WinUI完成现有控制台日常操作、任务关系、双本机候选、反馈和唯一PR交付。此节点不需要主agent、草稿发布或新的人工事项模型。
2. **2.2 Roadmap草稿、artifact及人工事项**：人在没有主agent时也能维护草稿、阅读关联文档/成果、办理任务交付后的人工验收和启动前必须的操作。流程和原型仍推导。
3. **2.3 主agent接入**：消费前两节点稳定能力，提供真实Codex会话/草稿工具及确定后的独立审核、授权与受控准入。角色仍为主agent和服务调度的固定审核agent，不扩成通用编排。

[验收总入口](../../acceptance/phase2.md)链接三个独立活动。活动不占Task ID，不进入执行DAG；开发依赖实际能力，人工节点签收不默认作为所有后继开工门槛。

## 人工后验收流程边界

规划任务时识别允许后置的人工验收项，链接任务专属acceptance，标参与安排、截止节点和影响范围。交付时保留TaskDelivery及“待人工验收”；人阅读精确产物/构建版本、执行步骤并记录结果/证据，execution-map汇总随实际记录同步。

通过关闭对应待验项，失败记录受影响能力/后续并办理修复；不能撤改已核实的历史交付事实或把失败当待安排。产物实质改变时重新判断相关验收证据适用范围，不自动沿用旧通过。无关后续继续，真正依赖该验收结论的后续明确阻塞。服务/UI如何登记、校验和同步文档待2.2Spec固定，不先造第二业务权威。

## 必要前置操作流程边界

任务规划时写明必须先做什么、具体对象/版本、完成条件、系统可核验的证据或明确允许的人工作证，以及所阻塞任务/动作。操作办理不伪装成工程Task或TaskDelivery，不用等待任务占DAG编号。

用户从真实入口完成操作，再由服务核验事实或校验精确的人工作证；满足后只释放对应条件，并在领取/副作用前再次检查权威资格。过期或目标变化使原证据不可沿用。已知自动失败、缺权限或未知外部执行不能靠通用“已完成”按钮绕过。服务端门槛必须真实成立，不能只靠UI禁用按钮。

现有环境/权限阻断、服务窗口指引与核验动作在2.1复用；自定义前置定义、登记/办理/历史和artifact交互在2.2推导。先验证一个交付后验收、一个开工前操作代表流程，再决定最小模型。责任人/环境/参与窗口待安排时明确记录，不建设任意审批链、提醒器或通用待办平台。
