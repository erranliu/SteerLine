# 第一阶段版本交付调整方案

本文提出第一阶段的产品交付目标与实施顺序，供新增范围任务化。具体执行仍须遵守[目录规则](readme.md)：每个选定的实现切片取得自己的数字 ID、独立 Spec、Plan 和一个实现 PR，并在同一次规划变更中进入主 roadmap 与 execution-map。本文件不代替执行 Spec，也不把建议切片当作已创建的中心任务。

## 交付目标

第一阶段仍由人在 Codex 中维护 roadmap，SteerLine 负责原生任务 DAG、执行、人工决策、真实 PR 合并核验和后继释放。在已有 local Codex 与 Orca 路径、不同任务人工并行的基础上，增加**同一任务的多个候选执行**：每个候选有独立 WorkflowRun、Execution、步骤尝试、工作区、人工问题和 PR；任务最终只记录一个经核验的 TaskDelivery。候选数量不设业务常数上限，实际同时运行受执行目标能力和资源准入约束；初版由人显式启动候选，自动派发继续按已交付策略运行。

第一阶段另交付 stable/dev 两个固定运行入口。stable 固定已验收的二进制、配置和状态，继续处理当前项目；dev 使用独立测试仓库与独立 home 调试。服务、控制台与任务 CLI 在各自入口解析为同一确定二进制；提升 stable 前核验当前状态、执行身份和能力证据。二者不要求同时访问同一项目仓库，不建立第二个任务权威。正式面向新用户的安装、发布后升级策略和跨版本迁移仍属于第三阶段。

**阶段交付判定**：本机与远端各有可复现的原生任务闭环；同任务多候选各自走完受控流程并提不同 PR，人合并其中一个，中心只按该候选的固定证据关闭 Task；重启和响应丢失不造成重复候选/PR，其他候选不越权推进。stable 在 dev 独立构建和测试期间保持固定运行身份；一次受控提升与重启保留当前格式的 Task、Decision、Operation 和交付证据。第一阶段未通过的原生门槛全部如实结算。

## 新增实施切片建议

以下名称说明交付边界，不是未占用的任务 ID。正式选定时将每行落实为独立 Spec/Plan 和 PR。各 Spec 必须明确当前 SQLite 格式如何保留已创建 Task/DAG 与尚未结算的外部身份；格式不受支持时阻止有副作用操作，不靠清空稳定库升级。

| 切片 | 独立交付范围 | 直接前置及验收边界 |
| --- | --- | --- |
| 多候选模型与准入 | 一个 Task 的首个候选完成既有 claim；后续显式启动为独立 WorkflowRun/Execution，固定执行方案、base、worktree/分支、请求身份；旧的一候选流程仍按同一状态机运行 | 复用已交付的不同任务人工并行。并发同任务启动最多一次取得每个请求的固定候选身份；未知启动不盲重派；不提前实现比较/合并候选代码 |
| PR 胜出与落选候选对账 | 每候选唯一 PR 绑定；一个符合全部步骤门槛且真实合并的候选经中心事务成为唯一 TaskDelivery。同步冻结其他候选的新步骤，保留在途/未知资源并逐一对账 | 前置为多候选模型。选定前发现多个已合并候选时交人核实；选定后迟到的第二次合并记录交付冲突，不覆盖获胜证据或伪造回退 |
| 候选观察与真机验收 | 控制台按 Task 展开全部候选，分别展示流程、问题、能力、PR 与占用；在本机和受监管 Orca 的隔离原生项目实测同时运行、断线、答案与单 PR 合并结项 | 前置为胜出仲裁，远端真机范围仍受 `#4/#6` 门槛约束。保留未知候选及远程不可取消的事实，截图不能代替中心回执 |
| 固定版本与双入口 | 不可变的版本化服务二进制、构建身份与摘要；stable/dev 服务窗口、控制台和任务 CLI 各自指向明确的同一版本，拒绝误连另一入口 | 可与多候选开发及 `#3/#4/#6` 剩余验收并行；不再依赖会被安装命令覆盖的单一 bin 文件或手工修改启动器 |
| dev 隔离与 stable 提升 | dev 专用 home、配置、测试仓库、能力证据；stable 停服、当前状态核验、选择新固定版本、重启和失败阻断；保留原状态与外部执行证据 | 前置为固定版本与双入口。用隔离项目验证提升和恢复；旧开发数据库不自动迁移，当前稳定状态需要的格式变化须在相应 Spec 明确验证 |
| 第一阶段集成验收 | 汇总 `#3/#4/#6`、多候选链和双入口的真实证据，完成本机/远端任务到 PR 合并、稳定版运行和 dev 独立调试的闭环 | 所有前置真实交付后验收；仍需人合并 PR，不以 worker_done、旧证据或稳定版运行时长代替交付核验 |

## 优先顺序及第二阶段并行边界

第一阶段现有 `#3/#4/#6` 继续在固定版本和隔离资源上收尾。多候选模型与双入口的开发可各自并行，涉及 Service、Query/Command、SQLite、控制台或同一真实 Orca 宿主的修改/验收串行集成。多候选胜出仲裁在模型之后交付，固定版本提升在双入口之后交付；最终第一阶段集成验收汇合全部范围。

保留已创建的第二阶段 `#14–#24` 身份与现有边。`#25` 交付后，可在符合安全门槛时受控追加前置，不重新占号、删边或改变固定契约；当前尚未实际加边。人工派发保持第一阶段优先；第二阶段的 `#14` 主 agent 能力验证和 `#15` WinUI 基座可以用独立项目/平台资源准备，不能抢占第一阶段真机验收宿主。`#16` 的执行 Query/Command 将消费多候选身份与列表，先核接口，待多候选读/命令契约固定后集成；其后的阶段二任务遵守原有硬依赖。阶段二完整产品交付另须经过第一阶段版本门槛，但当前 DAG 不表示这一新增交付前置，需由人工派发与发布验收执行。

当前已创建任务中“一任务一实现 PR”的固定规格不因本方向自动变为多候选交付；新能力只在明确允许的后续任务契约或受控验收项目启用。新增硬前置可走 `#25` 的受控加边命令；若要求当前 `#14–#24` 本身改变交付范围或采用多候选 PR，仅补边不够，须另行修订任务契约或重规划。
