# 第一阶段版本交付方案

本文描述 #36 后第一阶段的目标安排。#26–#35 中受影响的旧任务已有固定 Spec/Plan 和中心 DAG；其裁减、合并和待处置关系见[精简审查](worker-flow-review.md)，当前实际依赖见[执行图](execution-map.md)。本文不代替执行 Spec，不修改既有 TaskContract。#3/#4 的原中心[交付](../validation/phase1-task-closure-2026-09-28/README.md)和 #6 的[真实 PR Delivery](../validation/spec03-task6-closure-2026-09-28/README.md)已完成；旧五步证据不能直接证明持续会话能力。

有人值守的远程执行 MVP 可按 [Spec 03](../spec/03-remote-execution-and-viewer.md#有人值守-mvp-交付边界) 先行交付；本文描述包含多候选和双入口的后续完整阶段，不能反向阻塞该最小交付。

## 交付目标

第一阶段仍由人在 Codex 中维护 roadmap。#36 交付持续 worker、统一待决策与真实 PR 交付；worker 依据任务 Spec/Plan 实现、提交并创建 PR，中心不安排项目测试、审查或修复步骤。在此基础上保留**同任务多候选**：每个候选有独立 WorkflowRun、稳定 worker 会话、工作区、反馈及 PR；每个候选内部仍围绕同一 worker。初版由人显式新增候选，任务只记录一个真实 TaskDelivery；自动派发策略不因候选数量改变。

第一阶段另交付 stable/dev 两个固定运行入口。stable 固定已验收的二进制、配置和状态，继续处理当前项目；dev 使用独立测试仓库与独立 home 调试。服务、控制台与任务 CLI 在各自入口解析为同一确定二进制；提升 stable 前核验当前状态、执行身份和能力证据。二者不要求同时访问同一项目仓库，不建立第二个任务权威。正式面向新用户的安装、发布后升级策略和跨版本迁移仍属于第三阶段。

**阶段交付判定**：本机与远端各有持续会话和真实合并闭环；多候选各自创建 PR，中心核验用户合并的真实交付并记录其他候选的资源和冲突事实。中心不将落选标记等同于外部 worker 已停止，也不保证阻止它在途的发布动作。stable 在 dev 独立调试期间保持固定身份；提升后按当前格式重接会话和原操作，保留任务及交付事实。

[不同任务人工并行 Spec](../spec/manual-parallel-start.spec.md)的服务按 WorkflowRun 管理 worker、各任务独立受理控制与恢复的能力已交付。本方案只增加**同一任务**内多个候选所需的准入、投影和结果仲裁；不再建设一套项目级并行 worker 管理器。

## 已选定的执行范围

推荐先交付 #36，将原 #26/#27 整合为新的候选功能规格；原 #28 只交付候选观察增量，原 #29 只验多候选新增风险。#30 的固定版本入口可独立准备；#31 的后继规格调整为空闲持续会话可恢复时的受控提升，最终组合验收保留在第一阶段。新的任务编号和完整 Spec/Plan 需要在正式重规划时固定，不能用现有 ID 自动改指合并后的任务。

已有[第一阶段共同约束](../spec/phase1-delivery-constraints.md)中的 schema 5 专项转换不能直接套到 #36 的新格式；候选后继规格必须根据实际发布格式重新确定输入和保留范围。无法识别的状态仍阻止副作用，不清库升级。固定 stable 24 小时真实运行、dev 独立调试和受控提升目标保留；验收分工见精简审查。

## 优先顺序及第二阶段并行边界

#36 优先确定执行语义；#30/#14/#15 可在隔离资源准备。建议取消 #33 的旧步骤规则提取，把 #34 必要的会话上下文/事件路由放入 #36，#35 的全面 SQL 搬包后移。涉及 Service、Query/Command、SQLite、控制台和真实 Orca 宿主的修改与验收仍需串行协调。

旧中心仍有 #33 → #34 → #26 → #27 → #35 和 #35 → #28/#16 等关系，[创建记录](../validation/modular-refactoring-task-creation/README.md)是其真实依据。它们不会因本建议自行消失；取得旧任务处置回执并登记新任务图前，不能按新顺序绕过中心资格。

新多候选功能复用 #36 的 worker、反馈和交付接口；版本维护屏障只管理中心实际拥有的开始/发送等操作。功能接口可以复用现有包内组件，不要求先交付整库搬包，亦不另建第二套候选或会话权威。

本机 API 的目标后继规格从 #36 接入，不把多候选和全面重构作为 UI/规划链前提。第一阶段组合交付仍作为第二阶段最终产品验收的汇合条件。现有 #16 的前置及其 #17 等传递后继需要一起重新规划，不能只改一个表格单元格；已有 TaskContract 和 #32 → #24 的中心事实继续保留到正式处置。

当前已创建任务中“一任务一实现 PR”的固定规格不因本方向自动变为多候选交付；新能力只在明确允许的后续任务契约或受控验收项目启用。若要求 #14–#24 改变交付范围或采用多候选 PR，仅补边不够，须另行规划；本轮不重绑定这些中心任务的 Spec/Plan。
