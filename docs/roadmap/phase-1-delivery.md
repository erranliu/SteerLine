# 第一阶段版本交付

第一阶段以 #36 的持续 worker 流程为基线：中心负责启动、原会话反馈、主阶段和真实 PR 交付；worker 的测试、修复、审查要求来自任务 Spec/Plan。活动任务及前置见[主 roadmap](roadmap.md)和[执行依赖](execution-map.md)。

一期假定roadmap和任务契约由外部规划稳定提供。草稿roadmap、主agent、审核成熟度与正式准入机制留在二期，见[二期目标](phase2-draft-roadmap-admission.md)。本次收缩不改变版本线和 #42已固定组合目标。

## 三条交付线

- **执行基线 #36**：同一 worker 多轮交互、统一待决策、部分提交继续、PR 发现与真实合并、当前格式恢复。必要的会话上下文整理随功能交付。
- **候选TUI与真机增量 #38 → #39**：稳定任务默认启动一个候选，人工选择不同配置逐个新增；开始时参与数已达5个拒绝，偶尔超出可接受，不建严格名额/队列/自动补位。合并前可不可撤销放弃候选，立即退出实验，外部停止事实独立；已知PR合并后禁止放弃。各候选原会话独立，唯一交付由实际合并核验，人比较成果，中心不评分/融合。业务与查询/控制基础已具备，TUI 实现已具备，CC5 按用户授权保留待人工补验，不阻止 #39 开发；#39 承接少量真实混合方案证据。
- **版本 #40/#36 → #41**：固定 stable/dev 入口、独立 home 和受控提升。版本文件可以独立准备；提升核验真实活动轮次、在途消息和空闲会话的可恢复性。

#42 汇合多候选和版本能力，保留 fixed stable 24 小时、至少五个真实任务、dev 并行及一次受控提升的组合目标。单会话基础由 #36 证明，多候选新增竞争由 #39 证明，组合验收只重跑受影响关键链。

## 与第二阶段的关系

本机 API #45 在 #36 后提供执行查询和原会话反馈，不等待多候选或全面 SQL 搬包。规划权限 #43、WinUI 基座 #44 可独立准备。第二阶段最终验收 #53 汇合页面和 #42，不把最终版本验收当作所有 UI 研发的先行条件。

## 状态与交付边界

采用各任务明确的新协议/状态格式；不保留旧步骤流程、schema 5 专项迁移或双摘要回退。当前格式重启、原消息对账和真实 TaskDelivery 仍须通过。stable 源码构建完整性与 worker 项目文件状态分别处理，取消中心项目 dirty 门槛不取消 stable 构建要求。
