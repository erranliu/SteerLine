# 第一阶段版本交付方案

本文描述第一阶段的产品交付目标与实施顺序。新增范围已形成 #26–#32 的独立 Spec/Plan 并已进入中心 DAG，入口见[主 roadmap](roadmap.md)与[执行依赖图](execution-map.md)。两条跨阶段前置也已追加；本文件不代替执行 Spec，各任务仍待实现与验收。

## 交付目标

第一阶段仍由人在 Codex 中维护 roadmap，SteerLine 负责原生任务 DAG、执行、人工决策、真实 PR 合并核验和后继释放。在已有 local Codex 与 Orca 路径、不同任务人工并行的基础上，增加**同一任务的多个候选执行**：每个候选有独立 WorkflowRun、Execution、步骤尝试、工作区、人工问题和 PR；任务最终只记录一个经核验的 TaskDelivery。候选数量不设业务常数上限，实际同时运行受执行目标能力和资源准入约束；初版由人显式启动候选，自动派发继续按已交付策略运行。

第一阶段另交付 stable/dev 两个固定运行入口。stable 固定已验收的二进制、配置和状态，继续处理当前项目；dev 使用独立测试仓库与独立 home 调试。服务、控制台与任务 CLI 在各自入口解析为同一确定二进制；提升 stable 前核验当前状态、执行身份和能力证据。二者不要求同时访问同一项目仓库，不建立第二个任务权威。正式面向新用户的安装、发布后升级策略和跨版本迁移仍属于第三阶段。

**阶段交付判定**：本机与远端各有可复现的原生任务闭环；同任务多候选各自走完受控流程并提不同 PR，人合并其中一个，中心只按该候选的固定证据关闭 Task；重启和响应丢失不造成重复候选/PR，其他候选不越权推进。stable 在 dev 独立构建和测试期间保持固定运行身份；一次受控提升与重启保留当前格式的 Task、Decision、Operation 和交付证据。第一阶段未通过的原生门槛全部如实结算。

## 已选定的执行范围

具体任务范围与独立 Spec/Plan 已移入[主 roadmap](roadmap.md)。多候选由 #26 模型、#27 交付仲裁、#28 TUI 观察、#29 本机/远端真机验收依次交付；#30 固定版本双入口与 #31 隔离/提升独立推进，最终由 #32 汇合。界面与跨主机验收分开，避免远端主机未认证时阻塞 TUI 实现。

执行共同要求见[第一阶段交付共同约束](../spec/phase1-delivery-constraints.md)：既有 Task/DAG 保留，具体格式转换由 #26 明确实现；无法识别的状态阻止副作用，不清库升级。#32 包含固定 stable 构建连续 24 小时真实运行，以及 dev 独立调试和一次受控提升。

## 优先顺序及第二阶段并行边界

第一阶段现有 `#3/#4/#6` 继续在固定版本和隔离资源上收尾。#26 与 #30 可各自并行，涉及 Service、Query/Command、SQLite、控制台或同一真实 Orca 宿主的修改/验收串行集成。#29 等待 #3/#4/#6 真实交付；#32 汇合 #29 和 #31，不把平台替身或长期运行时长当作任务合并证明。

保留已创建的第二阶段 #14–#24 身份与原有边，中心已追加 #26 → #16、#32 → #24。人工派发保持第一阶段优先；#14/#15 可用独立资源准备，不能抢占第一阶段真机宿主。#16 的接口消费和 #24 的验收仍按原冻结契约执行，新增业务范围须另有执行依据。

当前已创建任务中“一任务一实现 PR”的固定规格不因本方向自动变为多候选交付；新能力只在明确允许的后续任务契约或受控验收项目启用。若要求 #14–#24 改变交付范围或采用多候选 PR，仅补边不够，须另行规划；本轮不重绑定这些中心任务的 Spec/Plan。
