# Roadmap 目录说明

本目录维护随项目进度持续更新的后续规划，包括长期计划、下一阶段计划，以及规划所需的长期约束和局部系统约束。

SteerLine 现阶段的产品目标是：以 roadmap 为核心的自动化软件开发系统。规划、规格、执行和交付反馈形成持续推进的过程，本目录先明确这一过程的文档边界。

## 文档组织

- [product-vision.md](product-vision.md) 描述从当前版本出发的后续产品目标和计划。不限定颗粒度，可以是一句话目标，也可以是具体版本交付计划、功能设计或技术选型；可选链接产品设计文档，不要求列执行约束、Spec 链接或排定执行依赖。
- [roadmap.md](roadmap.md) 是近期与后续推进的主入口，承接从产品方向中选出的目标，描述范围、优先顺序与关键前置，链接具体 Spec。
- [execution-map.md](execution-map.md) 直接列出已规划且尚未交付的执行 Spec、各自的开工与交付前置，以及跨 Spec 的接口交接、共享冲突和并行条件。目标刚进入 roadmap、尚未形成 Spec 时，先记录待明确的执行任务与依赖；形成 Spec 后以每份独立 Spec 为条目，不等到开始实现才补关系。
- Roadmap 可以由多个文档组成，主文档负责组织和链接。
- 长期约束、局部系统约束通常放在独立文档中，主文档只链接相关约束，不重复展开。
- 主文档不维护文档形成、提交、PR 创建或合并情况，不设置这些状态列、提交 SHA、合并清单或基线核对记录。规划内容的增删体现项目进展，无需记录维护动作本身。

## 从产品计划到执行

```text
product-vision.md
  → 选出目标并移入 roadmap.md，同时建立 execution-map.md 关系
  → 形成 docs/spec/ 下的 Spec 或 Spec + Plan
  → 按 Spec 实现、验证和交付
  → 根据实际结果收缩剩余规划、调整依赖，再选择后续目标
```

- 产品计划持续以当前版本为起点；不是固定不变的远期宣言，也不积累已经完成的版本历史。
- 选定推进范围时，将其具体内容移入 roadmap，避免两处维护相同交付清单。较大目标只移出选中的部分，产品文档保留剩余范围；后续仍需依赖的总目标可以保留必要概述。
- Roadmap 中的目标使用稳定标识；execution-map 以当前未完成的独立执行 Spec 为条目，并保留其目标标识。一个目标需要多个 PR 交付时，先规划为多个独立任务，每个任务分别对应自己的 Spec 和 PR；保留目标到任务的可追踪映射，不因文件改名重建目标身份。
- 每个选入 roadmap 的执行任务在形成 Spec 之前就取得仓库内唯一的非负整数规划 ID 和任务名称。数字从 0 起递增，仅表示身份，不表示优先级、依赖或实际执行顺序；目标标识可覆盖多个任务，不能代替任务 ID。任务完成后可从主 roadmap 和 execution-map 移除，但 [task-ids/](task-ids/) 中的身份记录保留；弃用的 ID 也不复用。拆成两个交付任务时，新任务分别申请新 ID，不把原 ID 同时赋给两个任务。
- 规划文档引用另一项未完成任务的前置或交接时统一写 `#规划ID`，例如 `#0`；阶段代号、Spec 编号和目标标识只用于定位对应文档或目标，不充当依赖身份。已交付但未分配规划 ID 的基础能力保留 Spec 链接和能力名称。
- 关系表中区分“Spec 已固定的要求”和“规划假设/待确定项”；有 Spec 时链接相关章节，没有 Spec 时直接表达待确定的边界，不维护文档形成状态。
- 关系至少区分硬前置、接口前置和共享修改冲突，并分别说明开工条件、合并/集成条件。未知依赖不代表允许并行；代码文件不重叠也不能证明协议、业务状态或平台资源互不影响。
- 关系表中的并行建议不自动改变既有 Spec 的串行要求。决定调整执行安排时，将职责、接口、前置和验收条件落实到所有受影响 Spec，再按新契约执行。

### 规划任务 ID 的分配

使用 Python 3.10+，从仓库任一 worktree 执行以下命令；新 clone 首次分配前先运行 `init`，将已提交的 `task-ids/*.json` 身份装入共享计数器：

```text
python scripts/roadmap_task_id.py init
python scripts/roadmap_task_id.py reserve "任务名称"
python scripts/roadmap_task_id.py check
```

`reserve` 原子占用下一个数字，并创建 `docs/roadmap/task-ids/<ID>.json`。随后将相同 ID 和名称写入 `roadmap.md`、`execution-map.md`，在提交前运行 `check`。现有任务首次按主 roadmap 的展示顺序分配 0–10；以后只使用脚本产生的新 ID，不补洞、不手工改号。名称是该 ID 的稳定标签；确需更名时应单独审阅其语义并同步修改身份记录、两个规划表和共享计数器，不能把原 ID 改指另一个任务。

仅修正名称而不改变交付身份时运行 `python scripts/roadmap_task_id.py rename <ID> "新名称"`，再同步两份规划表并运行 `check`。改成另一项交付任务则申请新 ID，原号码弃用。

计数器保存在 Git 共享目录的 `refs/steerline/roadmap-task-ids`，各 worktree 共用；脚本用 `git update-ref` 的旧值校验原子更新，竞争者读取新值后重试。即使分配后放弃任务，计数器仍前进，ID 不再发放。`task-ids/` 每 ID 一个文件，保存已分配的最小身份记录，避免不同 worktree 的新增任务修改同一清单文件。此机制保证**同一 Git 仓库的 worktree** 不重复分配；独立 clone 不共享本地 ref，应先同步已合入的身份文件并在同一分配仓库占号。若以后需要多 clone 同时分配，须改用远端原子计数器或统一分配服务，不能假设本地 ref 能跨 clone 仲裁。

规划 ID 与未来原生模型的 `Task.task_id` 分层：前者在规划时分配、对仓库全局唯一；后者按 [原生任务模型 Spec](../spec/task-core.spec.md) 由中心在任务发布时生成，为项目内不透明身份。原生发布可将规划数字作为外部追踪引用绑定到 Task，不能把它当成 `Task.task_id`、Beads ID 或 DAG 边 ID。规划文档不成为运行时任务状态或发布契约的权威。

## 与 Spec 的关系

### 任务、Spec 与 PR 一一对应

- 严格遵循 **1 task → 1 Spec → 1 PR**：每个任务有且只有一份独立的执行 Spec 文件，并通过一个独立 PR 交付。一个 PR 不合并多个任务，一份 Spec 不承载多个任务或多个 PR 的交付范围。
- Spec 必须是独立文件，不能用一份总 Spec 的多个章节、阶段或验收编号代替多个任务各自的 Spec。不得采用把多个任务统一放进一份 task-dag Spec，再由同一份 Plan 分阶段交付的组织方式。
- 每份 Spec 可以有自己的配套 Plan，也可以不单独设置 Plan。配套 Plan 必须是独立文件，只描述该 Spec 对应任务的实施与验证，不汇总多个任务的计划。
- 多份 Spec 可以引用 Spec 体系中的共用文档，例如架构约束、公共接口或协议契约。共用文档只承载共同要求，不代替各任务独立的 Spec；每份任务 Spec 必须明确自己的范围、前置依赖、引用的共同要求及验收条件。
- 需要多个独立交付阶段时，在规划阶段分别建立任务、Spec、可选 Plan 和 PR 边界，不能把多个任务藏在同一文件中。已有的多任务合并规格须在实施前按此规则拆开；这属于规划与文档整理，不代表系统提供执行中任务拆分流程。
- Roadmap 和 execution-map 中每个任务的执行入口必须链接到该任务独立的 Spec 文件及可选 Plan，不能只链接到同一总文件的不同章节。

### 执行依据与引用方向

- Roadmap 不能直接作为执行依据。执行前，必须将相应内容落实为 `docs/spec/` 下的 Spec，或 Spec + Plan。
- 已经形成 Spec 的规划项必须附对应 Spec 链接，必要时附 Plan 链接；链接用于定位执行契约，不维护文档形成过程或合入状态。
- 具体执行 Spec 和 Plan 不得引用或依赖本目录文档，也不能通过其他说明文档间接依赖这里的执行要求。执行所需的约束、范围、依赖和验收条件必须完整落实到 Spec 体系中。
- Roadmap 后续变化不会自动修改执行要求；需要改变执行要求时，同步修订对应 Spec/Plan。执行范围以明确选定的 Spec/Plan 为准。
- 引用方向为本目录指向 Spec/Plan。产品计划、关系表和约束文档都不能成为绕过 Spec 的执行入口；关系摘要与 Spec 不一致时先核对并修订，不凭摘要放宽门槛。

## 随项目进度维护

- 每个 PR 合入时，主文档都必须同步反映合入后的剩余规划。维护动作随对应 PR 完成：删除已完成范围，调整剩余目标、依赖、顺序和相关规格链接。
- 主文档只表达规划本身的变化。纯文档整理或不影响剩余规划的改动，核对规划仍然适用即可，不添加“文档已形成”“某 PR 已合入”或仅表示已核对的记录，也不再发起用于登记这次维护的循环更新。
- 已通过 PR 合入完成的规划内容移出 roadmap；部分完成的只保留剩余范围。
- 已完成内容仍被后续步骤依赖时，仅保留必要的依赖信息，并明确依赖它的后续步骤。依赖结束后删除。
- 产品计划中的具体范围移入主 roadmap 后，不再两处重复维护。形成 Spec 后，roadmap 仍保留未交付目标的摘要、关系和规格链接，不复制执行细节；目标交付后再移除相应规划条目和关系，仍有消费者的仅保留必要交接信息。共同方向与约束在仍有后续适用范围时保留。
- 长期或局部约束在仍约束后续工作期间保留；失效或不再被后续工作依赖时删除。这些文档同样不承担执行历史记录职责。
- Roadmap 只保留未完成规划及后续工作仍需依赖的已完成信息，不设置归档或回退机制。

## 规划调整与任务操作的边界

本目录中的目标细化、顺序调整和已完成条目删除属于规划维护，不代表系统支持修改已经发布的任务依赖或撤销交付。原生任务方向不提供拆分与回退流程；用户可通过 Codex 人工分析并处置，系统不承担任意人工改动后的自动修复。共同边界见 [原生任务共同约束](../spec/native-task-constraints.md)，具体执行以各任务独立 Spec 为准。
