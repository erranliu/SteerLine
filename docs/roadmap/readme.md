# 草稿规划与正式执行文档规则

当前支持范围是本地 Codex 和本机 Orca。本文区分讨论中的草稿、已入中心 DAG 的正式任务、任务固定契约和历史证据；文件位置、已占编号或文档完整都不单独产生执行资格。

## 文档职责

| 文档 | 职责 | 执行含义 |
| --- | --- | --- |
| [product-vision.md](product-vision.md) | 产品方向、目标及阶段交付节点 | 不直接创建或执行任务 |
| [roadmap.md](roadmap.md) | 草稿 roadmap：讨论、拆分、调整范围/依赖/优先级，链接候选 Spec/Plan | 可自由讨论，尚未准入；不作为日常执行清单 |
| [execution-map.md](execution-map.md) | 已入中心 Task DAG 的正式任务映射 | 日常执行入口；成员、状态/版本、固定契约及依赖必须与实际 DAG 同步 |
| docs/spec/ | 候选或已经固定的独立 Spec/Plan 与共同执行约束 | 被 DAG 固定的 commit/摘要才是正式 Task 的执行契约；当前文件不改写旧版本 |
| [task-ids/](task-ids/) | 所有已分配数字身份，包括历史和未准入编号 | 永不复用；占号不等于正式准入 |
| docs/validation/ 与 docs/archive/ | 原始结果、回执、已交付/退役资料 | 证据有原来源和覆盖范围，不作为草稿自动入图许可 |

规划前读[并行开发指南](../architecture/parallel-development.md)，按本轮影响展开模块、契约和测试。草稿记录拟议依赖、共享语义/代码/资源、所有者、可固定/开工/合入条件和最小验证；正式说明消费已经确认的边界。未知接口或关键前置尚未稳定时继续留草稿，不让目录分离掩盖约束冲突。

## 从讨论到正式任务

```text
产品目标 → roadmap.md 草稿讨论/候选 Spec 与 Plan
        → 固定送审内容、依赖和授权，核对内容质量及前置成熟度
        → SteerLine 受控创建 Task，固定契约/依赖并取得原请求回执
        → 核对实际 DAG 后同步 execution-map.md
        → 从正式清单选择任务，核对当前资格，按固定 Spec/Plan 执行
        → 核验真实交付/丢弃/归档，刷新正式映射，结果返回草稿讨论
```

审核准入的二期目标见[说明](phase2-draft-roadmap-admission.md)，新增自动审核尚未实现。当前人工流程也须取得真实中心回执；本次文档规则调整不实现新的服务、审批角色或跨 Git/SQLite 原子事务。Git 内容、中心创建和映射部分完成时沿原任务/原请求对账，不重新占号或重复创建。

### 草稿

- 草稿可以只有目标、临时标签、讨论点、依赖建议或未完成的 Spec/Plan，不要求每次讨论占正式数字。草稿数字只用于已有占号身份；不能手工造一个可能与正式 Task 冲突的编号。
- 现存数字和 Spec/Plan 可以作为候选资料保留，不表示已经准入。当前既有候选需要与二期新方向对齐，进入正式集合前再固定实际版本及范围。
- 草稿可引用正式任务和成果作为已知基础；需要替换已入 DAG 的范围时，写成新的提案并走受控处置，不能在草稿中改写正式 Task。
- 草稿中尚未准入的候选不因写入表格、通过静态检查或建出原型而允许启动 worker。删除草稿不取消已创建任务。

### 正式清单

- execution-map 只接纳真实 DAG 任务。记录原 Task ID/名称、项目及状态/版本、固定契约、原创建/变更回执与同步基线；本轮可写资源排期等说明不能伪造 DAG 边。
- 表格和图只显示剩余未满足前置，已交付基础改为必要能力摘要。完整依赖保留在中心与固定契约；尚未满足、丢弃后仍阻塞或事实未知的前置不能静默移除。
- 每次入图、依赖或状态改变后，以及执行/恢复前都核对实际 DAG。缺少同步证据或不一致时不派发；空表没有可选任务，不回退读取草稿或旧 run 中的待执行列表。
- 文件清空或删行不清库、不取消 worker，也不改变既有 DAG。本次 execution-map 的条目已清空且尚未核对中心，不能声明中心为空或已完成同步。
- 完成/丢弃/归档以中心真实事实为准，历史和资源处置保持可追溯；PR 合并本身不替代唯一 TaskDelivery 核验。正式映射保留实际在 DAG 中的终态记录，中心受控归档后再按其实际成员变化同步。

## 任务身份与 Spec/Plan

准入前，每个正式任务必须有唯一非负整数 ID/名称、独立 Spec 和配套 Plan，严格保持一个任务、一份 Spec/Plan、一个实现 PR。多个任务不能共用一份总执行 Spec/Plan。草稿没有这组材料时可以继续讨论，不能晋升为正式条目。

新数字使用 Python 3.10+ 及仓库共享计数器，首次使用先 init；既有预留保留，不补洞、不重发。编号递增只表示身份，不代表顺序或资格。

```text
python scripts/roadmap_task_id.py init
python scripts/roadmap_task_id.py reserve "任务名称"
python scripts/roadmap_task_id.py check
```

reserve 原子更新 refs/steerline/roadmap-task-ids 并写入 task-ids/<ID>.json；同仓 worktree 共用，不为独立 clone 仲裁。占号后可先保留候选材料；完整 Spec/Plan、固定版本及真实 DAG 回执都取得后才进入 execution-map。临时草稿标签不参与中心数字分配。

名称修正而身份不变时使用 rename，再同步受影响草稿/正式记录和文档头；既有中心 Task 的固定名称/契约不被文件更名自动更新。改成另一交付任务则重新分配数字并受控处理原 Task。未知创建结果按原 ID/请求核实，不另起任务。

check 独立检查两份文档：草稿允许缺少 Spec/Plan，已有数字及链接仍须匹配身份；正式条目必须有完整独立 Spec/Plan。两份文件允许集合、版本链接不同，正式任务也无需在草稿重复列一行。静态检查不验证实时 DAG、Task 资格或准入回执。

## 执行与引用方向

日常执行从 execution-map 选择，随后按中心固定的 Spec/Plan 和资格办理。roadmap.md、产品设计或并行建议都不能覆盖正式契约。规划文件指向候选/正式 Spec；实现 Spec/Plan 应完整承载自己的要求，不把草稿讨论作为隐式执行前置。

草稿调整不改变已有任务依赖或范围。中心已建 Task 只通过支持的受控命令变更；不能用普通反馈、追加边或删文件行改写旧固定契约。需移除旧前置或替换交付范围时重新规划受影响任务并核实中心结果，保留历史、后继阻塞和未知资源。

## 持续维护

草稿随讨论更新，已交付基础用必要能力摘要承接，不强制追读历史 Spec。正式映射随真实 DAG 准入/变更/状态/归档更新，保持同一项目和固定契约身份；不能为了让两张表看起来一致而复制草稿到正式表。

并行开发指南维护长期模块/契约/测试边界，草稿维护拟议任务关系，正式清单反映已核实 DAG。实现 Plan 按[测试指南](../testing.md)列最小测试计划；纯文档与技能入口调整验证链接、草稿/正式静态边界和技能，不运行产品或模型。
