# SteerLine 产品目标与后续计划

## 现阶段目标

把 SteerLine 建设为**以 roadmap 为核心的自动化软件开发系统**：用户表达产品目标，系统协助持续规划、形成可执行规格、安排多个开发任务，并完成实现、验证、审查与交付；实际交付结果再用于更新剩余规划。

从现有任务来源、本机 Codex 与 Orca 执行能力出发，逐步把单个任务的自动执行扩展为项目目标的持续推进。用户应能看清下一步为何被选择、哪些目标可以同时推进、哪里需要决策，以及交付后还剩什么。

下列是后续产品设想，颗粒度可以继续细化。选定具体范围时移入主 roadmap，建立执行关系并转成 Spec；这里不重复维护已经进入主 roadmap 的控制台、中心状态机、远程接入和原生任务 DAG 交付清单。

任务与依赖将由 SteerLine 自主管理，逐步解除 Beads 必需依赖；具体推进见 [主 roadmap](roadmap.md)，各任务独立 Spec/Plan 的入口见 [规格索引](../spec/README.md)，共同要求见 [原生任务共同约束](../spec/native-task-constraints.md)。发布后的执行图固定依赖与交付契约，系统不提供拆分、回退或动态依赖修改流程。拆分和回退由用户通过 Codex 分析并人工处置，系统不承担自动修复；故障恢复与原契约下的执行重试继续保留。

## 1. 从产品目标生成可管理的规划

支持从一句目标、用户需求、产品设计或版本计划出发，整理出可讨论的目标范围和交付顺序。规划过程能够提出缺失信息，表达取舍，并保留用户对范围和优先级的决定。

希望提供的功能：

- 识别产品计划中可推进的目标，提出草稿目标的细化建议并整理重复需求；不自动拆分已发布任务。
- 将选定范围移入 roadmap，建立稳定目标标识、关系和相关约束；保留尚未选中的后续方向。
- 在界面中浏览产品方向、当前 roadmap、目标之间的关系及选定目标的详细设计。
- 允许按项目选择人工确认点与自动推进范围，使探索性规划和明确交付计划都能使用同一系统。

## 2. 自动形成与维护执行规格

使目标到 Spec 的转换成为产品能力：系统结合现有代码、项目规则和其他目标的接口，生成范围明确、可以验证的 Spec/Plan，并辅助发现遗漏和冲突。

希望提供的功能：

- 提取跨目标的关键链路、业务不变量、共享接口和数据影响，避免每次从头读取全部文档。
- 检查规格是否足以执行，包括验收、兼容、恢复以及前置条件；不明确时请求决策。
- 目标变化时分析受影响的草稿 Spec 和待发布范围；涉及已发布任务时向用户说明差异，不自动修改其契约、依赖或交付事实。
- 从产品目标追踪到对应规格、开发任务和交付证据，查看偏差产生的位置。

## 3. 稳定地并行推进多个 Spec

系统能够识别可独立开发的范围、基于固定接口提前开发的范围，以及必须串行修改的公共部分，合理利用多个执行器。

希望提供的功能：

- 生成可解释的并行安排，展示前置、共享修改范围、接口交接和集成顺序。
- 为不同开发任务配置独立 worktree 和执行上下文，按可用资源安排 local Codex 或 Orca。
- 接口变化、主线变化或执行失败后，报告已知的契约差异和执行阻塞；在固定契约下处理验证与重试，需要拆分、回退或修改依赖时交用户人工处置。
- 处理并行成果的集成验证、冲突和修复，使单项通过的实现也能形成一致的项目交付。

多 Spec 并行首先解决不同目标协作；同一目标由多个 agent 提供候选实现、比较和整合，是可以另行选择的扩展能力。

## 4. 形成持续交付与规划反馈闭环

在用户确定的范围内，系统持续完成开发、验证、审查、修复和交付，并依据真实结果维护后续目标。

希望提供的功能：

- 汇总实际执行的检查、审查意见、修复结果和交付证据，准确区分代码已写、检查通过和交付完成。
- 按项目约定处理 PR、集成与合并门槛；合并失败或验证不足时给出可处理的问题。
- 交付后删除 roadmap 中完成的范围，保留仍被后续目标依赖的交接信息，调整下一步安排。
- 用简洁的用户输出说明已实现能力、剩余范围和需要人工决定的事项；详细过程按需展开。

## 5. 扩展协作与使用场景

- **同任务多 agent**：独立候选实现、比较评估、选用与结果整合。
- **共享服务**：在持续运行的中心服务中管理多个项目、成员权限、执行资源和 Orca 连接。
- **移动端**：随时查看项目推进、阅读结果、处理人工问题和提交受控操作。
- **跨项目复用**：复用项目步骤、验证方式和规划模板，减少接入新仓库时的重复配置。

## 可进一步细化的技术方向

产品计划可以包含技术选型；这里记录值得推进的方向，具体选择随目标移入 roadmap 后在 Spec 中确定。

- 以仓库内 Markdown 文档和 Git 差异承载可阅读、可审查的产品规划；为自动处理提供稳定目标标识和明确文档结构。
- 规划文档表达目标与关系，执行进度和命令结果通过服务状态查询；规划界面不要求把运行记录写回主 roadmap。
- 复用共同执行适配器和中心状态机承载并行规划结果；调度器、执行器和 UI 使用可核验的结构化接口。
- 使用索引或结构化读模型加速关系检索、影响分析与可视化，便于用户修改文档后重新核对规划。
- 在原生任务只读导出之后，另行选择交互式 Web 关系视图；可评估 React Flow 配合 Dagre/ELK.js，保持中心查询权威，不把布局或拖动位置当作执行依赖修改。
