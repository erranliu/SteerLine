# SteerLine 产品愿景

## 产品定义

SteerLine 是一款带有研究性质的开发工具，长期远景是通往**工程 AGI**：让 AI 最终能够自主开发复杂软件项目，包括普通人需要长期借助 AI 协助才能完成的项目。下面四个交付节点是通往这一目标的阶段；第四版仍只实现有限自主推进。

当前产品方向以 roadmap 为中心：把选定的目标转为有依赖的任务，连接本机 Codex 或 Orca worker，围绕原会话传递用户反馈并记录真实 PR 交付。worker 负责实现、提交和创建 PR，测试、修复、审查要求由任务 Spec/Plan 约定。人决定产品取舍、处理待决策事项并合并 PR；SteerLine 核验实际合并后才认定交付完成。草稿任务可以提前取得唯一 Task ID，正式准入沿用该身份；在产品中受控纳入正式任务时创建对应中心 Task 并进入 DAG，规格和依赖随之固定。草稿编号本身不入图或启动执行。PR 合并前可受控丢弃正式任务，后续规划不能暗中改写已创建的任务。持续会话与简化主流程由 #36 交付，产品方向不代表已实现。

具体底层能力与实施顺序见[草稿 roadmap](drafts/roadmap.md)。本文件定义产品交付节点；普通开发由当前聊天直接实现；明确要求 roadmap 调度时，由 roadmap-runner 使用[正式执行清单](execution-map.md)管理已确认的任务与依赖，流程见[RoadmapGuide](RoadmapGuide.md)。

## 交付节点

### 1. Codex 规划，SteerLine 执行

人在 Codex 中规划和维护 roadmap；项目 skill 将选定范围连同任务 ID 整理为 Spec/Plan 与任务 DAG，提交给 SteerLine 校验并创建入图。SteerLine 负责启动与观察 worker、统一待决策和反馈、真实 PR 合并核验及后继释放。本阶段认为输入roadmap及任务契约已稳定。同一项目已支持不同任务人工并行；同任务分叉用于人工对比不同执行方案，默认一个候选、人工逐个新增，开始时参与数已达5个即拒绝，接受竞态偶尔超出，不建设严格名额或调度器。每个候选独立冻结配置、会话、工作区和PR；合并前可放弃退出实验，资源停止另按事实记录，PR合并后不支持放弃。人选择合并结果，中心核验唯一交付，不做自动评分或成果融合。交付结果由人带回 Codex 继续规划；此版不提供 SteerLine 内的 roadmap 规划或 Roadmap UI。

第一阶段目标范围包含本地 Codex、本机 Orca 与远端路径交付。远端历史契约与结果见[远端 Spec](../spec/orca-remote-l3.spec.md)及[专属验收](../acceptance/orca-remote-l3.md)；当前单终端的本机有限样本与远端升级后已准备环境的有限样本通过及首次信任限制见[最新验收](../acceptance/orca-terminal-remote-retest-2026-10-10.md)，目标范围不代表已验收支持。

此版采用一个本机安装版本持续工作，源码调试以独立 exe/home 和测试 clone 共存。服务、控制台及任务命令明确显示并使用各自实际路径和构建来源；日常 build 不覆盖安装版。完整 stable/dev 双 channel、不可变版本库及受控提升延后，维护仍采用人工停止、安装和启动，不承诺跨构建接管活动任务或旧开发格式兼容。剩余任务与推进顺序见[草稿 roadmap](drafts/roadmap.md)，最小隔离由 #83 的独立 Spec 承接，组合验收见[一期活动](../acceptance/phase1.md)，不另维护平行交付清单。

#84 已交付后端无关的 worker 步骤状态：implement 执行与报告分开，publish 单轮，结果由程序核验后推进；后续发布格式错误只追加一次 publish.report。采用简单代码定义和短提示词，复用原会话/adapter，不增加通用编排框架。#83 隔离能力已合入，仍须固定包含后续调整的新一期安装构建；组合、24小时和同构建恢复签收待执行，旧持续 worker 或单次闭环证据不代替该签收。

**交付判定：**有依赖的原生任务完成双本机后端执行、人工决策和 PR 合并核验；同任务多候选独立，中心只记录一个真实交付，其他候选保留资源事实。固定安装版通过源码调试共存、24 小时持续运行及同构建当前格式重启验收。短时 E2E 为定向回归入口，不替代安装入口或长期运行证明。

### 2. 人与主 agent 受控推进 roadmap

第二阶段分三个独立验收节点：

| 节点 | 可用成果 |
| --- | --- |
| 2.1 DAG与执行UI | 人工提供稳定任务契约，原生UI替代现有控制台的日常执行操作，任务关系/候选/反馈/PR与阻塞准确 |
| 2.2 Roadmap草稿、artifact与人工事项 | 没有主agent也可人工维护草稿、阅读关联成果，办理交付后人工验收及开工前必要操作 |
| 2.3 主agent接入 | 消费已交付能力，提供真实规划会话、受控工具及确定后的独立审核/授权准入 |

节点验收见[三节点导航](../acceptance/phase2.md)。2.2/2.3流程和原型仍迭代；近期只固定已合入 #83 的基线及 #84/#45/#44 确定会使用的能力，#49/#50等待2.1最小原型。人工后验收结果、TaskDelivery与启动资格分别表达；允许后置者不阻塞无关任务，必要前置不能靠UI勾选绕过。下述主agent完整闭环是2.3及二期最终目标，不作为2.1前置。

Roadmap规划进入SteerLine，采用[草稿规划与审核准入](drafts/phase2-draft-roadmap-admission.md)。主agent相对自由地维护草稿roadmap与Spec/Plan；独立审核agent检查内容质量和前置是否稳定到适合固定。合格且可固定的任务经人的授权，由SteerLine受控纳入正式roadmap；需修改或需等待前置的任务留在草稿，相关条件变化后再审。产品中的正式roadmap与实际中心 DAG 同步，加入、丢弃及完成归档均走SteerLine流程；这是产品目标，仓库当前的 Codex 开发清单采用 RoadmapGuide 的直接执行流程。主agent仅支持Codex；审核是服务调度的固定角色，不开放主agent调用子agent或通用多agent编排。这不改变任务worker的本机Codex/Orca后端。Roadmap UI 稳定查看和管理目标、Spec/Plan、任务 DAG、运行、决策、PR 与交付证据，保留版本和关联。输入交互以 Codex App 为参照；已发送输入的编辑并重跑，只有在会话历史和文件状态的实际行为均与 Codex App 一致且可实现时才提供，否则第二阶段不提供该入口。主 agent 提建议、生成草稿并解释影响；没有人的确认，不自行推进新的规划或创建任务。

**交付判定：**人能在UI完成目标讨论、草稿、固定版本审核与成熟度判断、受控正式准入、DAG执行及人工合并PR的闭环；未成熟任务保持草稿，交付事实返回规划，正式加入/移出和关联artifact可追溯。机制在二期分步交付，不进入一期前置。

第二阶段的方案与 UI 设计集中在[第二阶段规划目录](../product-design/README.md)。

### 3. 正式可发布产品

第二版能力达到正式发布标准：可重复安装和接入项目，明确平台与后端支持范围，提供用户文档、故障诊断及可复现的端到端和恢复验收。重启和外部动作结果不确定时，任务、规划、决策与交付证据保持一致，不重复派发或错误结项。正式发布后的升级策略在该阶段确定；若频繁更新长期运行安装版已需要保留空闲会话、待合并 PR 或未发送反馈，可提前重新规划延后的完整版本管理。上线前不建设旧版本数据迁移。roadmap 仍由人受控推进。

**交付判定：**新用户可按文档完成完整闭环；当前版本的服务重启可保留任务、待处理事项和交付证据。

### 4. 主 agent 有限自主推进 roadmap

人预先设定目标、授权范围和资源边界后，主 agent 可在范围内选择下一步、维护规划、创建任务并监督执行。它先处理有充分依据且已获授权的 worker 问题；遇到产品取舍、权限、证据不足或越界情况，就暂停受影响的推进，向人说明原因并等待决策。人可随时暂停或接手；PR 仍由人合并。自主动作及答案都保留依据、版本和回执。

**交付判定：**主 agent 能独立推进授权范围内的任务，在需要人决策时准确停下并恢复；重启后不重复操作，未授权范围不推进。

## 后续结构整理

持续 worker 与候选基础已具备，任务、执行、控制台解耦及目录整理已选入[草稿 roadmap](drafts/roadmap.md)，具体职责、独立交付与并行条件在正式规格中维护。结构整理不成为当前 API、界面或产品交付的全面前置；未明确的未来范围不提前建立空领域或执行任务。
