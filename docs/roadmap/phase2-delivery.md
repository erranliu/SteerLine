# 第二阶段推进边界

第二阶段交付原生 UI 与受控规划，任务范围见[主 roadmap](roadmap.md)，依赖见[执行图](execution-map.md)。每项执行仍以自己的 Spec/Plan 为准，新图登记前不从文档推断 Ready。

新增产品方向以[草稿roadmap与审核准入](phase2-draft-roadmap-admission.md)为准：审核agent评估Spec及前置成熟度，适合固定才准入；未成熟内容留草稿。下表描述现有 #43–#53基础交接，新增审核范围尚未固定为执行任务，相关Spec在实施前对齐，不从旧图推断已具备审核能力。

## 业务划分

| 范围 | 归属 | 接口边界 |
| --- | --- | --- |
| 持续 worker、统一待决策和真实 PR 交付 | #36 | #45/#50 消费，不新增任务执行状态机 |
| 规划 agent 权限/工具与受控会话 | #43/#47 | 可共用底层会话能力，规划写入 guard 与任务 worker 权限分别管理 |

## 推进顺序

近期优先 #36 → #45 → #50，#50 同时等待 #44 原生基座；#43 先做实际规划能力验证，#44 可独立准备。#83 单独提供安装/调试路径共存，#42 的 24 小时只阻塞最终验收，不增加 API/UI 研发前置。完整 stable/dev #40/#41 延后，不属于 #53 传递前置。

#46 建立草稿基础，之后 #48 发布与满足权限前置的 #47 会话服务可分别准备；#44/#48 → #49/#52，#44/#47 → #51，最终与单安装版 #42 汇入 #53。涉及草稿/审核/准入的新范围仍在实施前重新固定，不把优先级变更当作规格已对齐。

本机候选基线已具备；全面中心搬包仍不是本机 API 的新前置。不同任务可在依赖满足后独立推进，共享 Service/SQLite、UI 导航和真实宿主资源仍串行集成。前置能力尚未交付时不能用样例界面提前宣告完整功能。

## 完整产品路径

目标讨论/草稿roadmap → 固定送审版本 → 独立审核Spec质量与前置成熟度 → 通过且适合固定者经人的授权由SteerLine受控正式准入 → DAG执行与人工方案实验 → 人合并PR → 唯一TaskDelivery与完成归档 → 主agent据真实结果继续草稿。需修改或需等待前置者留在草稿，不成为正式执行任务。

送审身份、任务数字和文档发布的具体固定策略在后续对应Spec中确定；当前不把旧预留/Publication流程宣称为新审核实现。现有已固定任务契约不因草稿变化被改写。

这里的文档审阅、固定内容/提交核验及权限约束不属于被 #36 删除的项目代码验证。它们保留在各自规划领域；正式文档、草稿和已创建任务继续区分，目标分支集成与 Git/中心部分失败按原请求恢复。
