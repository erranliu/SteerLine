# RoadmapGuide：规划 Roadmap 的指南

每次设计或修改 roadmap，先读本指南，再读下列必需文档，随后按本轮涉及的功能展开契约、源码与测试。本文是持续维护的规划入口，介绍基本用法和准入规则，不维护具体草稿清单或任务状态。

## 仓库文档与外部任务工具

本指南从项目规划者的角度描述流程。**任务 DAG 是外部运行的任务工具 SteerLine 的功能**：由 SteerLine 保存实际 Task、依赖、状态、固定契约、准入回执及执行资格。文中的“中心 DAG”“真实 DAG”均指该外部工具维护的任务图，不是仓库里的 Markdown 表格或本地编号脚本。

| 位置 / 工具 | 所有权与作用 |
| --- | --- |
| 仓库 drafts/、Spec/Plan、task-ids/ | 规划材料与草稿任务身份；可以编辑、占号和静态检查，不操作外部 DAG |
| 仓库 execution-map.md | 仓库内执行及验收汇总的真相源，记录正式任务和待验文档链接；实际执行状态依据外部工具回执/查询同步，不是工具数据库 |
| 外部 SteerLine | 通过其支持的接口办理正式任务创建、DAG 依赖、状态与交付；实际任务事实和资格的权威 |
| 本地规划/检查脚本 | 分配唯一 ID、验证文件身份和导航；不连接 SteerLine、不创建 Task 或 DAG 边 |

正式准入需要通过外部 SteerLine 的接口登记任务，并依据真实回执和查询结果同步 execution-map。它们属于同一逻辑准入流程，但不是一个跨文件和工具的原子事务。编辑或提交文件不会自动调用 SteerLine；增加、删除文件行或通过静态检查，都不能代替工具侧操作和结果核实。

## 目录与基本用法

| 位置 | 用途 |
| --- | --- |
| drafts/ | 可扩展的 roadmap 草稿目录，按主题、阶段或方案命名；讨论目标、拆分、候选文档、依赖与优先级 |
| execution-map.md | 外部 SteerLine 已创建并纳入任务 DAG 的正式任务映射，日常执行索引；以工具回执/查询同步 |
| task-ids/ | 所有已分配数字身份，包括历史和未准入编号；占号不等于准入，号码永不复用 |
| docs/spec/ | 候选或已经固定的独立 Spec/Plan 与执行约束；正式 Task 使用中心固定的 commit/摘要 |
| docs/acceptance/ | 所有自动/人工验收行为、流程及已验/待验明细，包含最小结果摘要、最近基线和原始临时证据定位 |
| docs/archive/ | 有独有追溯价值的历史资料；旧证据通过固定 Git 快照取证，不作为草稿自动入图许可 |

草稿全部放在 drafts/ 下一层目录，可同时维护很多份。本指南只说明目录和规则，不索引其中任何具体草稿，也不要求存在某个固定草稿文件名。规划时根据人的本轮目标明确选定草稿，不把目录枚举当成待执行队列。

草稿可以只有目标、讨论点或未完成 Spec/Plan。已经识别出的草稿任务可以提前分配全局唯一 Task ID，便于引用、依赖讨论和编写文档，无须等待进入 execution-map。尚未形成任务的纯目标讨论可用临时议题标签；标签不与 Task ID 等价。编号后的任务沿用同一身份进入正式准入，不重新编号；未取得准入/DAG 回执前不产生执行资格。草稿可读正式任务与成果，但不能改写已有固定契约；删除或修改草稿不会取消 worker。

任务加入 execution-map 和外部 DAG 后可以继续留在草稿中，便于讨论整体目标；不要求准入时删行，也不严格维护草稿内实时状态。真正执行完成并核对正式结果后，从相应草稿移除已完成任务条目，保留必要能力摘要和编号历史。草稿中的旧状态不用于派发、判断完成或判断验收通过。

## 任务准入与验收分类

验收规划从草稿阶段开始。识别出候选任务时，在草稿中链接 docs/acceptance/ 的专属验收文档，说明自动与人工方式、最小通过条件、预期环境、准备条件与人工参与安排；不等正式准入才补建。任务与验收文档是一对一或一对多关系：一份任务验收文档只归属一个任务，范围较大时可拆成多份，不以一份文件覆盖多个任务。纯目标讨论尚未拆出任务时可先记录验收方向；尚未确定的步骤、命令、环境或窗口明确写待定，随范围成熟细化，不虚构已验结果。

草稿也可以列出独立的阶段签收、体验确认或跨模块验收活动并链接 acceptance，使用活动/验收项身份与执行任务区分。规划提示词鼓励主动识别这些活动、安排参与窗口及可后置范围；这是一项规划建议，不强制为每轮规划生成独立活动、增加 Task 或串成固定执行路径。确有关键验收前置时明确记录实际阻塞范围。

人工操作/判断/持续组织为主的验收活动不能进入执行 DAG，应直接形成 acceptance 文档；验收项用场景 ID，不新建伪任务。自动验收可以作为独立 Task，也可作为实现 Task 的一部分：明确可自动完成的步骤、通过条件、环境和交付结果，按对应 Spec/Plan 验证，不要求另建重复验收框架。

任务主体能自动交付而附带少量人工验收时，尽量集中后置。规划时标明人工项、责任人/窗口或待安排、截止阶段、阻塞范围和文档链接；非人工必需验证通过且后续不依赖该人工结果时，保留“待人工验收”并继续合入/无关后续执行，不填“全部已验”。真实失败、未实现功能、权限/环境前置缺失、未知外部动作或明确先验条件不能通过后置标记绕过。

不设置任意人工比例阈值；按主要交付是否能独立自动完成、是否需持续人工参与及人工结果对核心语义的影响判断。已入图的固定任务若不再适合此分类，须受控处置，不因文档删行修改外部 DAG。

Spec 定义验收要求，Plan 写实施和测试安排，所有具体自动/人工行为、状态及结果明细归 acceptance 并相互链接。验收文档记录已验/待验及真实失败；execution-map 同步执行状态、验收汇总和未验文档，是仓库执行与验收视图的真相源。出现汇总/明细不一致时按实际证据核对修正，不用草稿旧状态或旧汇总覆盖失败。实际 DAG/资格仍由外部 SteerLine 办理和核实。

## Plan 对自动验收的覆盖

Spec 定义成果、边界及通过条件，任务专属 acceptance 文档维护具体自动/人工行为与实时结果，Plan 将自动验收落实为执行安排。Plan 不能只链接验收文档或只列本次文档静态检查；其“测试计划”须覆盖本任务范围内全部自动验收项，可按明确的 ID 范围合并场景，但每项都能定位执行方式、环境、命令、时点、通过条件与证据登记位置。必要回归测试另标，不把所有测试都算作产品验收。

缺脚本、驱动、原生构建或环境能力时，在实施步骤中规划最小补齐工作，或明确已有前置任务与交接。草稿可标待定；准入前固定验证方式、命令参数及能力补齐安排。允许本任务实施过程中新增场景，但实际执行验收前须完成实现/登记和环境准备，不把规划中的入口说成已存在、以零匹配/skip/编译或文档检查冒充通过。

Plan 包含执行自动验收、向专属 acceptance 登记实际构建/结果/证据、同步 execution-map 汇总的交付步骤。验收结果不回写为 Plan 的实时状态表；已交付结果保持原基线，延后任务不因补写测试计划被启用。人工项另写参与人/窗口、截止阶段及实际阻塞范围，少量允许后置的项不串成默认等待步骤，关键先验门槛和真实失败仍阻塞。

建议测试计划表使用：验收项 ID/专属链接、级别/组/场景、环境/命令、执行时点、通过条件、证据及结果登记位置。独立自动验收 Task 同样适用；不扩大为默认 Full、全部 live 或跨任务共用验收文档。

## 任务身份与入图是两个时点

| 阶段 | Task ID | 外部 SteerLine 的 Task / DAG |
| --- | --- | --- |
| 目标讨论，尚未识别任务 | 可先无编号，用议题标签讨论 | 不创建 |
| 已编号草稿任务 | 用共享计数器分配唯一 ID，记录身份；Spec/Plan 可继续完善 | 不因编号或草稿保存而创建，依赖仍为拟议关系 |
| 纳入 execution-map 的正式准入 | 沿用原草稿 ID；未编号者须在固定准入内容前先分配 | 通过外部 SteerLine 接口创建 Task 并入 DAG，再以工具结果同步正式文件；两边核对后才认定准入 |

Task ID 只有一套，草稿、正式执行和后续历史使用同一对外身份；不另造“正式任务号”。删除或放弃草稿保留编号记录，号码不复用。任务创建和入图实际发生在外部 SteerLine，execution-map 记录核实后的对应结果；部分完成时按原 ID/请求核实，不把文件写入当作工具成功或提前宣告可执行。

## 规划步骤

```text
先读 RoadmapGuide 与必需文档
  → 明确本轮目标，选择或新建 drafts/ 内的草稿
  → 按功能所有者、契约、共享冲突和独立验证拆分候选成果，可提前分配草稿 Task ID
  → 在草稿阶段分类自动/人工验收并链接 acceptance，鼓励补充独立活动及可后置的人工项
  → 固定可送审内容、依赖及人的授权，核对质量与前置成熟度
  → 形成完整独立 Spec/Plan，以原 Task ID 调用外部 SteerLine 支持的准入接口创建 Task/DAG
  → 根据工具回执/查询同步 execution-map，核对两边准入结果一致
  → 从正式文件选任务，核对外部 SteerLine 的当前资格，按其固定契约执行
  → 更新 acceptance 明细及正式执行/验收汇总，链接所有未验事项
  → 真正执行完成后再移除相应草稿条目，后置人工项仍在 acceptance 和正式待验索引保留
```

每项候选写清：产品成果与主要模块、消费/修改的契约和受影响消费者、共同语义/代码/资源、修改所有者、可固定/开工/合入条件、最小通过条件。对实际有交接或共享影响的任务说明关系，不构造无意义的全排列矩阵。关键接口或前置尚未稳定时留草稿；没有独立成果和通过条件时不为增加并行数量强拆任务。

人工和自动验收策略在批量排期前记录：批次通用审阅/授权统一说明，额外人工需求逐任务标出；提前准备人、环境和窗口，纯人工阶段签收不作为自主执行队列中的等待任务。

### 规划提示词（建议）

> 先读 RoadmapGuide 与必需文档，明确本轮 drafts/ 草稿。拆分候选任务时同步规划最小必要验收，区分自动和人工行为，并在草稿链接 docs/acceptance/ 的任务专属文档；一个任务可有多份文档，一份文档只归属一个任务，未定步骤、环境和参与窗口写待定。请主动考虑是否需要独立的阶段签收、体验确认或跨模块验收活动，有需要时记录范围、通过条件、参与窗口及实际阻塞范围并链接其独立文档。独立活动不强制串成执行路径；人工为主的活动不占执行任务号、不入 DAG，少量人工尽量后置。没有实际需要时不为凑清单新增活动或扩大验证。草稿不维护实时执行/验收状态，正式准入及实际安排后按 execution-map 和 acceptance 核对事实。

正式准入前，每个任务必须有唯一非负整数 ID/名称、独立 Spec 和 Plan，保持一个任务、一份 Spec/Plan、一个实现 PR。ID 可在草稿阶段先取得，文档未完整时继续完善；准入沿用已有 ID。数字表示身份，不代表顺序或就绪，任务身份分配与冻结执行契约分别处理。

当前二期自动审核/同步尚未交付，不能以目标文档声明已经实现。按当前支持的受控创建流程核对真实回执；未来审核协议在正式 Spec 中固定，不从草稿文字直接生成执行许可。Git 文件、中心创建和映射不存在跨系统原子事务，部分完成按原 ID/请求核实，不重新占号或重复创建。

## 正式执行与同步

execution-map 的正式任务表只接纳真实 DAG 任务，记录原 Task ID/名称、项目、状态/版本、固定契约、依赖及回执，增加验收汇总和待验文档链接。人工阶段活动、已完成/归档任务的未验事项放独立待验索引，不混入活动成员表。表格和图可只显示剩余未满足前置，完整原依赖保留在中心和固定契约；尚未满足、丢弃后仍阻塞或事实未知的前置不能静默移除。

每次准入/变更后及执行/恢复前核对实际 DAG，保存同步来源、时间和版本。缺少证据、不一致或正式表为空时不派发，也不从 drafts/、占号文件或旧 run 的待执行列表回填。文件清空不清库、不停止 worker，不证明实际中心为空。

完成、丢弃和归档依中心真实事实更新，PR 合并本身不代替唯一 TaskDelivery，更不意味着所有验收通过。正式映射保留实际仍在 DAG 中的终态记录，中心归档后同步成员；待人工补验链接继续保留到真正验收完成。共同接线或原生资源排期说明不伪造 DAG 边。

日常执行从 execution-map 选任务，随后核对中心资格和固定契约；本指南、草稿及产品设计都不能覆盖已冻结要求。任务范围或旧依赖需要替换时先重新规划并受控处置，保留历史、后继阻塞和未知资源。Spec/Plan 应完整承载自己的要求，不将草稿讨论作为隐式执行前置。

## 编号与静态检查

数字由仓库共享计数器原子分配，首次使用先 init，既有编号不补洞或重发。同仓 worktree 共用 refs/steerline/roadmap-task-ids，独立 clone 不共享仲裁；未知创建结果仍沿原 ID/请求核对。

```text
python scripts/roadmap_task_id.py init
python scripts/roadmap_task_id.py reserve "任务名称"
python scripts/roadmap_task_id.py check
python scripts/check_doc_links.py
git diff --check
```

reserve 只分配草稿也可使用的 Task ID，写入 task-ids/<ID>.json，不访问外部 SteerLine 或创建 Task/DAG。正式准入以该 ID、完整文档和受控请求通过 SteerLine 接口入图，再核对并同步 execution-map；两边结果确认后才进入可执行集合。名称修正但身份不变时使用 rename 并同步受影响记录和文档头；当前文件更名不自动改变工具内的固定名称/契约，另一项交付任务应使用新数字。

check 分别检查 drafts/ 内全部 Markdown 草稿与正式表，不要求相同集合或文档版本。不同草稿可讨论同一预留身份的备选方案；同一文件的数字条目不重复，已有数字/链接仍须匹配身份。草稿允许缺少 Spec/Plan，正式条目必须完整且独立。工具只检查静态身份与导航，不证明 live DAG 同步、准入或 Task 资格。

## 持续维护

草稿随讨论独立更新，无需加入本指南索引或严格实时同步；已准入任务执行完成后才移除。正式清单维护当前执行和验收汇总，acceptance 维护所有自动/人工行为与已验/待验明细。指南随规则、必须资料和工具入口改变而更新，不积累本轮日志；实际模块/契约/测试归属变化同步并行开发指南。

实现 Plan 按项目规则写最小必要测试计划，包含级别、组/场景、环境、命令、时点、通过条件及 acceptance 记录定位。纯文档、导航和规划入口修改只做必要的静态/工具检查，不启动产品或模型验收。acceptance 只提交计划/明细与最小结果摘要，原始运行产物留在临时目录；历史路径、commit、摘要和回执通过固定 Git 快照追溯。
