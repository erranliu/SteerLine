# 并行开发指南

本文用于判断哪些成果能独立实现、验证和交付，以及共享修改如何集成。当前源码 owner 唯一维护在[代码架构](current-code-architecture.md#模块与资源归属)，业务权威见[架构总览](../architecture.md)；旧任务交接和独立性探针见[历史入口](../../SteerlineFlow/archive/design/architecture-web-history.md)。

## 并行开发的判断

每项任务应有独立成果、主要所有者、输入/输出契约和通过条件。目录、worktree 或编译目标不同，只说明部分隔离；还须核对业务语义、共享格式、事务、组装、测试和外部资源。

| 安排 | 成立条件 | 集成方式 |
| --- | --- | --- |
| 直接并行 | 消费稳定契约，内部变化、验收及可写资源互不依赖 | 分别交付，核验实际共享接线 |
| 先固定契约 | 多方共同依赖新增字段、接口、权限或来源语义 | 明确生产者、消费者、身份、失败行为和验证后再拆实现 |
| 分开实现，有序集成 | 成果可独立验证，但共用构造、注册、schema 或客户端接线 | 指定共享段唯一修改所有者及合入顺序，后合入者验证组合 |
| 等前置交付 | 前置会改变后继核心模型、权限、范围或通过条件 | 设置真实硬前置，不用猜测接口固定后继范围 |

分别记录能否固定契约、能否开工和能否合入。接口签名或夹具提前完成不等于前置成果已交付；研发可并行也不自动授予产品任务开工资格。共享 SQLite 或 actor 不要求所有研发串行，文件重叠也不自动构成业务硬前置。

## 冲突识别与处置

| 共享面 | 典型影响 | 处理 |
| --- | --- | --- |
| 业务语义 | 阶段、候选参与、反馈、恢复或交付判定同时变化 | 由语义所有者统一规则和反例；未稳定时保留同一成果或等待前置 |
| 公共契约 | DTO、错误、游标、端口、codec、权限及配置字段 | 列出全部生产者、消费者和失败行为，指定共同修改所有者 |
| 持久化与事务 | schema、CAS、唯一约束、同快照及提交边界 | 统一格式与合入顺序，保留原子交付；按项目规则拒绝旧开发格式 |
| 组装与界面 | 构造、注册、dispatcher、连接及共享组件 | 一项任务拥有共享段，其他任务消费固定边界，后合入者验证组合 |
| 测试与夹具 | 公共 helper、driver、断言及测试登记 | 由测试 owner 核对受影响场景，不削弱断言换取并行通过 |
| 外部资源 | 仓库 common-dir、home、端口、终端、账号设置及发布目标 | 建独立现场或串行排期；不同 worktree 不解除共享仓库锁与外部资源冲突 |

同一源码 checkout 的 Web 依赖、构建输出和程序生成仍有共享可写路径，构建按[路径清单](../../SteerlineFlow/paths.md)串行；生成后的独立包再核对 home、仓库、端口和发布目标。远端权限、恢复和停止能力单独取证，不能从本机通过推定。

## 交接契约

已有设计、源码接口、活跃 Spec 与测试可作为当前依据。缺少独立契约文档时，在任务 Spec 中说明以下内容并链接源码，避免为每项任务新建通用框架或空包：

- 谁生产、消费及修改，谁持有业务状态和资源。
- 输入/输出、原请求、实例与版本怎样绑定，哪些能力尚不可用。
- 查询、明确失败、未知结果及授权如何处理，哪些动作不可重放。
- 哪些事实必须同事务提交，哪些外部动作在事务外执行。
- 契约、持久格式、组装和测试的完整影响面及集成顺序。

形成可复用的领域文档后由对应 owner 维护正文，任务引用它。模型执行、工作区、会话及原生资源归独立 Runner，SteerLine 任务消费公开契约；跨仓修改须明确双方交付与验证，不能分别复制执行规则。

## 规划与集成

1. 按成果和当前 owner 划分范围，核对现有源码、契约及验证缺口。
2. 对确有交接或共享影响的任务，区分硬前置、接口依赖、合入顺序与资源排期。
3. 指定共享修改所有者及最小组合验证；没有独立通过条件的半成品保留在同一成果中。
4. 在 Spec/Plan 写清独立验收、共享段、测试入口和人工参与；人工项标明窗口、截止阶段及实际阻塞范围，避免阻塞无关任务。
5. 仅用户明确要求 roadmap 调度时，按[RoadmapGuide](../../SteerlineFlow/Roadmap/RoadmapGuide.md)确认正式范围、依赖和固定材料后执行。普通开发直接在当前聊天推进。

可用以下简表记录本轮关系，不要求全任务建立两两矩阵：

| 成果与 owner | 契约及消费者 | 共享段与所有者 | 开工及集成条件 | 验证与资源 |
| --- | --- | --- | --- | --- |
| 独立可交付成果 | 稳定输入或待固定边界 | 语义、代码、格式和接线 | 硬前置、合入顺序、未稳定点 | 最小测试、人工窗口与隔离现场 |

例如，新增后端字段及页面展示应先固定来源、失败语义和 DTO；后端与 UI 可各自实现，共享接线指定所有者。两个原生后端的局部调整可并行，但共享 codec、权限或身份格式变化须先协调。UI 夹具只证明展示，不能证明真实执行链已接通。

## 测试与独立性证据

按[测试指南](../../SteerlineFlow/testing.md)选择验证：局部规则使用受影响 owner 用例；公共契约、端口或组装变更覆盖真实消费者和[依赖守卫](../../internal/testkit/boundary)；跨进程、身份、事务或资源窗口需要相应集成场景。真实模型、远端与 controlled 的结论分别判断，构建通过不等于独立交付。

无专门契约测试时先复用现有入口，确有缺口再补最小场景，并在 Plan 记录环境、命令、时点、通过条件和证据。历史探针只证明原版本受测边界；新的组合须有自己的证据，不继承整模块“已独立”的结论。

## 持续维护

本文只维护判断方法和共享冲突，不复制模块地图、维护任务实时状态或积累交接日志。职责归代码架构，领域规则归产品设计，任务范围与验收归 Spec/Plan。涉及 roadmap 时按其专属规则维护规划；本页不创建任务、中心依赖或新的执行资格。

纯指南与导航调整做文档静态检查，实际实现再按影响验证。长期反复出现共享冲突时，先复核成果划分与契约归属，再决定是否需要调整结构。
