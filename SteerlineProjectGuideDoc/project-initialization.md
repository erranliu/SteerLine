# 项目初始化指南

本指南用于把一个真实 Git 项目准备为 SteerLine 可管理的项目，覆盖流程文档、任务测试材料、环境检测接口、自检、Git 采用和首次接入。新项目与已有项目均从实际仓库调查开始，沿用已有有效材料。

当前由项目维护者或其明确授权的开发 Agent 准备仓库，再通过现有应用配置接入。完整的自动调查、生成修复和纳管仍是拟议功能。本文采用任务测试入口 version 1、项目共用环境 manifest 6 和结果信封 version 3。开始前核实拟使用的 SteerLine 与独立 Runner 构建支持这些接口。

通用职责遵循[受管理项目规范](project-standards.md)，测试分层遵循[测试架构规范](testing-architecture.md)，环境接口遵循[环境适配指导](environment-adaptation.md)。本指南串联准备步骤；接口字段和执行行为由各自契约维护。

## 1. 确认输入并调查仓库

先确认仓库在 SteerLine 服务机器上的实际位置、Git remote、目标分支、PR 发布目标和所需执行方案。目标未知时保留待确认项，不默认使用 origin/main，不根据目录名推测远端仓库或环境。

在选定仓库中完成以下调查，保存本次准备所依据的完整 commit：

- 读取现有 `AGENTS.md`、README 和项目约束，确认 Git 顶层、common-dir、分支、remote、工作区修改以及正在进行的合并或变基。保留已有修改，不用 reset/clean 制造空白现场。
- 调查实际源码、架构、依赖/构建声明、启动方式、测试入口和 CI，记录可直接复用的文件、命令及尚无实现的能力。空白仓库先按项目正常开发流程形成初始提交，不能伪造架构或测试事实。
- 确认目标是本机还是指定远端环境，列出工具、权限、凭证所在位置及外部副作用。认证由执行配置和目标机器维护，不写入 Git 文档或示例。
- 核对已有 SteerLine 登记和状态归属；同一 Git common-dir 的 linked worktree 不作为多个独立项目重复登记。旧版状态或任务系统冲突单独处理，初始化不删除、迁移或接管它们。

本次准备范围可以只包含仓库文档、测试接线或环境检测脚本。依赖安装、远端写入、实际模型/PR 验证和正式派发须有相应授权；不要把运行这些操作作为查看仓库结构的副作用。

## 2. 建立项目材料导航

`SteerlineProjectGuideDoc/` 由 SteerLine 规范提供方维护，项目采用可追溯的规范版本；项目自身约定写入 `SteerlineFlow/` 或已声明的现有文件。更新规范时核对相对链接，不复制平台内部提示词、私有源码链接或与项目无关的 SteerLine 实现细节来填充材料。

| 材料 | 初始化时应完成的内容 |
| --- | --- |
| 根 README、AGENTS | 项目用途、代码/文档入口、修改边界、实际检查和协作约束；能定位固定规范与项目流程入口 |
| 现有架构、并行开发与长期设计文档 | 模块及职责、主要调用/数据路径、共享接口、独立交付边界和已知缺口；优先链接原正文 |
| `SteerlineFlow/paths.md` | Git 材料、测试报告、临时工作区及运行状态的实际路径和所有权，区分仓库与仓库外产物 |
| Spec/Plan、验收目录入口 | 如何编写、固定引用及记录自动/人工验收；具体任务形成后再创建对应文档 |
| 测试指南、可读列表、机器清单 | 采用第三节的实际路径，说明分级、命令、前置条件、证据和未实现项 |
| 环境要求和检测入口 | 按第四节维护项目共用接口，并为实际运行机和链路分别核实资格 |

需要 roadmap 时再维护项目自己的 `RoadmapGuide.md` 和正式 `execution-map.md`，并与确认的任务 DAG 同步；普通初始化不强制规划任务。没有实际需求时不创建示范 Spec、Plan、任务编号、测试安排或成功验收记录。Git 不保存空目录，用有实际用途的 README 记录目录职责及现状。

项目需要使用 Roadmap 草稿转正时，可在 Git 采用前运行 `steerline project prepare-roadmap -repository <项目绝对根目录>` 准备平台静态规则及缺失的 `SpecGuide.md`，或附加 `-check` 只读检查。已有自定义指南保留，准备出的文件需进入目标分支。适用范围及页面入口见 [Roadmap 静态材料](../docs/product-design/roadmap-promotion.md)。

`.steerline/project.json` 和完整的添加项目结构核验器仍是拟议方案，不是当前测试入口或应用配置。不要为完成本文把拟议清单当作现有 CLI 已支持的登记格式。

## 3. 准备项目测试材料

### 每项目一份测试入口

在仓库固定位置创建 `SteerlineFlow/environment-project.json`，同项目任务共用。它定位任务测试规范和唯一正式测试清单；尽管文件名含 environment，它不保存运行环境、执行方案、凭证或 ready 状态，也不承担所有环境的总入口职责。

采用默认测试布局时，完整内容为：

```json
{
  "version": 1,
  "requirements": ["SteerlineFlow/testing.md"],
  "testing_catalogue": "SteerlineFlow/testing/test-list.json"
}
```

已有项目可以原位采用自己的测试规范和清单，例如把 `requirements` 指向 `quality/testing-policy.md`，把 `testing_catalogue` 指向 `quality/cases.json`。先确保实际文件存在，再修改声明，避免维护同内容的第二份规范或清单。

- `version` 固定为 1；`requirements` 必须为数组，可以为空，但不能省略或为 null；`testing_catalogue` 必须定位一个正式清单。
- 所有路径使用仓库相对路径和 `/`，精确匹配大小写；使用普通 Git 文件，不用绝对路径、穿越、通配符、符号链接或目录代替正文。requirements 中的路径不重复。
- 这里只声明项目测试公共材料。环境要求、检测入口和平台环境适配指导另有来源。
- JSON 使用 UTF-8，不加入未支持字段或重复键。入口及全部引用必须存在于 SteerLine 采用的同一目标提交中；仅放在本地工作区或未合入的准备 PR 中仍不可用。

### 测试指南与唯一机器清单

测试指南按[测试架构规范](testing-architecture.md)说明 L1–L4、实际选择方法、前置条件、通过标准、报告与清理位置。L1 是固定最小检查，L2 是固定核心冒烟；L3 满足资源隔离和无顺序依赖，L4 保存边界、串行或可复用集合。具体命令由项目实际入口决定，不要求使用 SteerLine 自身的 Go 工具。

正式清单顶层为 `tests` 数组。下例只演示字段：仅当项目确有对应 npm 脚本和完整断言时才采用这些条目，否则填写本项目已实现的入口。

```json
{
  "tests": [
    {
      "id": "quality.minimum",
      "name": "固定最小检查",
      "level": "L1",
      "environment": "local",
      "command": "npm run test:l1",
      "check": "全部登记用例执行，断言通过，无意外跳过，保留本次原始报告"
    },
    {
      "id": "core.smoke",
      "name": "核心流程冒烟",
      "level": "L2",
      "environment": "local",
      "command": "npm run test:l2",
      "check": "完整核心流程及必要清理通过，报告包含实际源码版本与执行范围"
    }
  ]
}
```

每项必须有唯一稳定 `id`、非空 `name`、`level`、`environment`、`command`、`check`，可选 `note`。level 只接受 L1–L4；`environment` 是测试执行环境说明，不是平台环境已就绪的证明。可读列表、机器清单和真实执行器的 ID、级别、环境与入口保持一致。无测试时可以声明 `{"tests":[]}` 并写明缺口；这不表示 L1/L2 已具备或已通过，不能靠空清单完成任务验收。

### 固定协议、进度写入与任务 Plan

测试安排生成从固定提交读取 `SteerlineFlow/testing/runtime-progress.md`，按所用 SteerLine 版本的正式原文采用。真实测试入口可复用正式进度写入器 `tools/testing/RuntimeProgress.ps1`。项目路径存在且内容在 CRLF/LF 归一化后同源时，候选实施和代码审计步骤引用该路径；缺失或不同源时，平台向相应步骤提供正式写入器源码及接线要求。具体接线见[运行时测试进度](../docs/integration/runtime-progress.md)。

把进度接到项目真实测试入口：开始/重跑标记未完成，只有选择完整、实际断言和必要清理全部通过才标记完成。失败、前置缺失、零匹配、跳过或不完整结果不能由模型手填为通过。原始报告保存源码版本、实际选择、结果、日志与清理事实；布尔进度不代替报告。

实际任务的 Plan 使用规范化 `.plan.md` 路径，说明对应 Spec、必跑测试及必要影响项，引用清单中的实际 ID；尚缺测试能力时把建设与验证安排写进 Plan。Spec/Plan 分工遵循[编写规范](spec-plan-guidelines.md)。

在“项目维护”显式点击“准备材料与测试安排”，后台为该次固定范围核验材料并按需生成；查询、轮询和任务启动不隐式登记生成。明确失败后由用户重试，未知结果只核对原请求。每次生成读取同一固定提交中的 Plan、测试入口、公共规范、完整清单和固定测试协议，只选择该清单中的 ID。校验成功的安排保存在项目库，并在创建候选时随该候选冻结。初始化应提交真实测试入口和程序，安排由系统生成和保存；主工作区同步且全部未完成任务材料与安排有效后，项目才允许新建候选。详见[项目维护](../docs/product-design/project-maintenance.md)。

## 4. 适配各目标的环境检测

项目为所有运行机和执行链路维护同一套材料。先确认拟用执行方案的 adapter 和目标，以及项目实际依赖的工具、SDK、权限和服务。资格仍按项目、运行机和链路分别核实，系统派生的环境键用于绑定检测活动及结果。

```text
SteerlineFlow/
├── environment.md
└── scripts/
    └── verify-environment.ps1     # 或 verify-environment.sh，按实际解释器选择
```

`environment.md` 写项目实际要求、就绪判据、失败诊断、权限及自有清理约定。脚本可用独立的最小调用确认项目工具或服务可用，所有目标采用相同标准。项目测试和发布各沿自己的流程验证，解释器启动、Codex/Orca 执行链路及 Runner 结算由平台负责。

在文档中维护唯一的 `steerline-environment` JSON 代码块。下例采用 PowerShell 入口。使用 shell 时将 `script` 改为 `SteerlineFlow/scripts/verify-environment.sh`，`interpreter` 改为 `bash`。

```steerline-environment
{
  "version": 6,
  "script": "SteerlineFlow/scripts/verify-environment.ps1",
  "interpreter": "powershell.exe",
  "dependencies": [],
  "requirements": {}
}
```

在 `dependencies` 中声明检测实际使用、会影响结论的辅助程序及工具、权限和服务要求配置。使用唯一的仓库相对路径，机器段和入口自动纳入依据；requirements 声明非秘密的有效要求，脚本以此作为要求权威，说明正文不参与摘要。测试入口、清单、测试程序与报告归任务测试，业务文档、Spec/Plan 和 Roadmap 归各自流程。完整格式与约束见[环境适配指导](environment-adaptation.md)。

检测入口一次完成要求读取、检查、诊断、自有收尾和结果写入，保持以下接口边界：

- 从固定源提交的工作区根调用；当前参数为 `powershell.exe -NoProfile -NonInteractive -File <script>` 或 `bash <script>`，不传 Phase 或自由上下文参数。
- 从 Runner 提供的 `STEERLINE_RESULT_FILE` 读取预置信封，保留版本、项目/环境/活动、来源、输入摘要及 call_context 等原字段，原子写回同一文件，填写 completed、ready、人可读 message 和可选 details。result 3 的具体信封由平台提供，不在项目创建第二份输入或凭证文件。
- 工具缺失、服务不可达、标准未定或自有收尾未完成时报告 not_ready，说明原因及下一步。正常完成负向检测也应正常退出；异常退出保留尽可能完整的诊断。
- 平台依据原执行的可信终态、停止和最终结果封存消费结论。脚本退出 0、生成完成或静态格式正确都不单独授予 ready；项目不代替 Runner 宣称其资源已结算。

脚本必须在目标尚未 ready 时可启动。不要要求先获得本环境资格、领取业务 Task 或完成一次测试安排生成，才允许检测。

## 5. 在准备侧完成自检与修复

先检查文件与接口，再按已授权范围做隔离运行验证。自检由项目维护者或授权工具执行，SteerLine 日常检测不负责调查仓库、生成修复入口或审核业务标准。

| 检查 | 通过条件或应保留的结果 |
| --- | --- |
| 测试入口与引用 | JSON 字段、路径和唯一清单有效；实际任务的 Plan、规范、清单和固定协议在同一提交可读，项目采用的写入器与正式版本同源 |
| 测试定义与接线 | ID/级别/命令和执行器一致；已运行的最小检查有报告，失败/零匹配不会写完成；缺少能力单列 |
| 环境格式与来源 | 共用文档、入口、解释器和显式依赖符合 manifest 6，预置的目标身份原样写回，无秘密输出 |
| 环境负向行为 | 项目受控缺依赖或不满足要求时能给出正确 not_ready、原因和自有清理结果，不以制造“通过”修补负例 |
| 环境正向行为 | 在确有条件且获授权的目标执行成功，结果和停止/封存证据可追溯；目标不可达或权限缺失则保留未验证 |
| 导航与 Git | 必需链接有效，所有准备材料都是精确普通 blob，提交范围清楚，无运行状态或临时认证混入 Git |

直接脚本自测可以使用明确标为测试用途的预置信封和隔离结果文件，核对脚本行为；它不能伪造生产活动或当前环境资格。完整平台链路验证使用独立 home、仓库、端口及自有资源，通过所用版本的正式调用入口核实原执行停止和结果封存，不能在真实安装状态上试写数据库、回执或 ready。

只运行与本次变更相称的检查。代码/检测入口修改按项目规范运行 L1/L2 及受影响项；纯文档准备检查链接、清单和实际命令来源即可，不能把未运行的模型/远端/PR 链路登记为通过。自检后保存修改清单、实测命令、版本、结果、原始证据位置和未验证项；修复后补测保留原失败。

## 6. 审阅并发布到目标分支

整体审阅要求、实现与证据：测试入口应指向本项目实际清单；环境文档与脚本配套；准备结果不包含假任务、假成功、数据库、认证或 Runner 私有状态。按项目正常 Git/PR 流程采用本次文件，遵守已有提交和发布授权。

SteerLine 使用配置 remote/目标分支的已发布提交。记录该分支实际完整 commit，并逐项核实初始化材料已进入该版本；本地 HEAD 领先、未提交文件、准备分支或尚未合入 PR 都不能代替它。只新增空目录不会成为 Git 文件。新提交若变更测试定义或环境依赖，应按各自来源规则重新验证。

准备报告至少列出仓库身份、remote/分支、采用 commit、材料路径、实际验证与未验证项，以及待审阅/合入事项。可以报告“材料准备完成”，不能据此报告“已纳管”或“环境 ready”。

## 7. 接入后分别核实三种状态

由维护者在目标应用 home 的 `etc/*.json` 配置项目，核对服务机器上的仓库路径、remote、目标分支和 PR provider，再核对同一 home 的 `execution.json`。按[应用配置与启动说明](../web/README.md#构建与启动)正常停启宿主以装载配置。应用负责解析项目身份和仓库外状态。完整的添加项目和核验流程仍属[产品方案](../docs/product-design/project-onboarding.md)。

先保持手动、暂停派发，逐项核实：

1. **材料已采用、项目在线。** 服务实际读取的是预期目标提交，项目可正常查询；缺配置或版本不兼容时先解决接入问题。
2. **任务测试可生成。** 有真实任务时，核对其 Spec、Plan、验收引用和依赖，在“项目维护”查看对应 Plan 的实际生成状态及结果。无真实任务时保留待核实状态。
3. **对应环境可执行。** 在“项目运行环境”选择实际运行环境和执行方案，发起检测并核对最终结果、原执行结算及当前有效性。启用环境准入要求时，新任务必须使用匹配目标且仍有效的 ready 结果。

材料存在、生成成功、项目在线和环境 ready 是不同事实。安排生成只选择测试，环境检测不自动派发业务任务；恢复派发由用户在前置满足后明确决定。此指南本身不执行登记、检测、PR 合并或派发。

## 常见阻断的处理

| 现象 | 先检查与处理 |
| --- | --- |
| 所有 Plan 都报缺少 `environment-project.json` | 先核对目标分支的固定入口及其引用；补齐、审阅、合入后刷新项目基线，再重试，不逐任务复制入口 |
| 本地文件存在，仍报 pinned path missing | 核对应用采用的 remote/分支/完整 commit、精确大小写和普通 blob；不要只检查当前工作区 |
| 固定测试协议不同源 | 采用所用 SteerLine 版本正式交付的完整协议，核对换行归一化后的正文 |
| 运行时测试进度未更新 | 核对真实测试入口是否使用正式写入器和注入的进度文件，以及实际测试是否完整通过 |
| 测试安排生成成功，任务仍不能开始 | 检查正式任务契约、依赖、执行方案、对应环境 Current 及明确诊断；生成成功不授予环境资格 |
| 检测入口返回 not_ready | 根据项目给出的原因处理缺失条件；这是可用的负向结果，不因初始化目标而改写为 ready |
| 环境结果无法读取、原执行未结算或身份不符 | 通过原操作查看诊断、停止或对账，保留未知事实；不重发未知请求、改信封或直接写库放行 |

初始化完成后，项目继续维护测试入口/清单、环境要求/检测入口及相关导航。requirements 是有效要求权威，依赖只列实际运行要求配置与辅助程序，不应绑定仅提供少量版本字段的整份业务依赖文件。公共测试材料变化影响测试安排；声明的环境依据变化会使对应资格失效，按正式入口重新检测。机器、凭证或服务动态变化无法单靠 Git 文件发现，知悉变化时主动标记失效或重新检测。
