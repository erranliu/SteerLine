# 测试架构规范

适用范围：SteerLine 所开发项目及 SteerLine 自身。本文定义通用测试架构；各项目在自己的测试指南中落实命令、环境、内容清单和差异。规则适用于不同语言、技术栈和测试框架，不要求采用某个测试执行器或固定目录结构。

## 设计原则

以最小必要范围验证本次变更，优先把规则和反例放到快速、易定位的单元或集成测试。只有跨组件、进程或系统的实际行为需要共同验证时，才增加完整流程测试。按受影响范围选择级别和场景，不默认每次运行全量；确需全量时优先使用已有并行入口。

测试要能说明验证对象、触发条件、主要断言、执行入口和通过条件。编译、启动成功、零匹配、意外跳过、超时或缺少必需证据均不能代替场景通过。

## L1–L4 定义

| 级别 | 定义 | 设计要求 |
| --- | --- | --- |
| L1 | 快速的集成测试或单元测试 | 验证规则、组件和小范围接口集成，提供快速反馈。优先使用隔离且可重复的夹具；局部边界断言仍可属于 L1。 |
| L2 | 代表最小核心流程的 Smoke test（冒烟测试） | 用固定、精简的核心闭环判断产品基本流程是否可用。各项目明确流程起点、终点、必要组件及真实/受控环境；受控部分通过不能冒充真实链路通过。 |
| L3 | 可并行的多种不同流程测试 | 覆盖 L2 之外有独立价值的不同流程；场景资源隔离、无执行顺序依赖，设计应尽量互相正交。 |
| L4 | 无法并行或边界情况的测试 | 覆盖确有独占资源或顺序约束的流程，以及需要系统级验证的边界、异常组合。逐项说明串行原因或边界条件；可并行的系统边界场景也属于 L4。 |

级别按验证目的、范围和并行约束划分，不单按耗时、是否使用真实服务/模型或测试名称划分。局部边界条件优先由 L1 验证，确需完整系统现场时才进入 L4。L4 不意味着其中所有测试都必须串行。

Full 是项目定义的全量执行范围，不是第五个级别，也不等于 L4。项目须说明 Full 实际包含哪些集合、是否包含真实外部副作用；不以 Full 通过代替未执行的级别或场景。

## L3 的正交设计与并行约束

每个 L3 场景要说明相对 L2 和其他 L3 新增的流程、触发条件、主要断言和风险，使失败尽量能定位到一个明确职责。

- 允许复用准备、登录、基础数据、交付及清理步骤。共享流程骨架不等于重复测试。
- 仅更换名字、参数或数据而重复同一流程和断言时，优先合并或参数化。不同后端或平台只有存在独有行为、契约或风险时才增加独立场景，不默认展开笛卡尔积。
- 场景不得消费其他场景的执行产物或依赖运行顺序。每项拥有独立可写数据、目录、数据库、端口、账号/命名空间或远端资源，以及明确的清理所有权；只读构建产物可以复用。
- 并行能力与调度策略分开说明。资源隔离成立后，可按机器预算限制并发数；暂时顺序调度须如实记录，不能据此声称已经验证并行运行。确实不能解除共享可变资源或顺序依赖的流程归 L4。
- 不为凑场景数量扩展 L3。先检查现有场景是否能表达独有流程；系统边界和异常组合按 L4 维护。

例如，任务管理产品的核心领取交付链可作为 L2；依赖汇聚后释放任务、不同项目独立处理、任务定义导入导出可作为不同 L3 流程；冲突版本、损坏输入、独占资源争用可由 L1 或必要的 L4 覆盖。该示例只说明划分方法，不要求项目照搬场景或数量。

## L2、L3、L4 内容清单

各项目必须分别维护 L2、L3、L4 的明确内容列表，并从本项目测试指南可直接找到。没有场景的级别也写明“未登记”、执行器是否支持及已知缺口，不用空级别暗示相关风险已经覆盖。

每项至少记录以下内容；可按级别分表，在公共段落统一说明共享的环境或入口，不要求为重复信息增加表格列。

| 字段 | 内容 |
| --- | --- |
| 稳定 ID 与级别 | 用于选择、Plan 引用和结果关联；验证目的不变时保持 ID 稳定。 |
| 测试内容 | 触发条件、完整流程范围、主要断言及通过条件。 |
| 所有者与独有覆盖 | 负责模块或系统；L3 说明相对其他场景的覆盖差异。 |
| 环境与入口 | 真实/受控依赖、必要前置、可执行命令及代码/执行器映射。 |
| 执行约束 | 资源隔离、并发限制；L4 说明边界条件或具体串行/独占原因。 |
| 证据约定 | 结果及日志登记位置、清理要求；具体运行结果另行维护。 |

若执行器通过 manifest/catalog 选择场景，该登记为机器执行来源；可读清单解释各 ID 的语义。只有可读文档的项目也必须逐项映射到实际命令和测试，不能长期保留无法执行的“已覆盖”条目。

新增、删除、改级、改环境或改变主要断言时，同一变更同步实现、执行登记、可读清单及相关选择/证据校验。执行器不支持某级别时，先落实能力或明确待实施，不登记为可运行。退役 ID 不静默映射到不同验证目的。

清单表示“测试什么”，运行记录表示“某版本实际测得什么”。项目在独立验收记录中保存源码版本、实际选择、环境、结果、日志位置和清理事实。固定清单或一次通过不等于已经证明运行稳定；失败与补测分别保留，子集通过不表述为全级别通过。

## 跨模块与跨项目测试归属

规则与故障矩阵由实现该能力的 owner 维护。依赖项目已经拥有的执行、协议、恢复或重试专项，不在调用方重复建设；核对测试的触发条件、断言和实际覆盖后，等价重复项可以直接删除，独有要求先落实到正确 owner。

调用方仍须验证自己的请求保存、参数传递、授权、结果消费、业务事务及后续行为。相同故障名称不代表相同职责：依赖正确去重，不能证明调用方没有错误地创建新请求；依赖提供停止证明，不能证明调用方正确核对并使用该证明。

保留必要的跨系统 L2 冒烟，证明真实接线及调用方业务闭环。夹具只表达公开边界上的输入与输出，避免在调用方重建依赖内部状态机。删除重复专项时，同步清理专属入口和无消费者的夹具，保留共享工具与独有断言。

## 环境、执行与验收安排

流程测试使用隔离现场，明确资源所有权、期限及清理方式；真实外部动作的配置、权限和副作用由项目单独说明。缺少必需环境或能力时明确失败/阻断或标为待实施，不切换模拟后宣称真实场景通过。失败保留诊断，补测按独立记录处理。

实现 Plan 的测试计划按验收项映射级别、组/场景 ID、环境、命令、执行时点、通过条件及证据登记位置。范围采用最小必要集合，可由同一场景覆盖多个验收项；未选择相关级别时简述原因，不默认所有任务都运行 L2/L3/L4 或 Full。

需要新增驱动、夹具或环境能力时，把能力补齐纳入实施步骤或明确前置，并在验收前落实可用入口。人工验收单列参与窗口和阻塞范围；允许后置的人工项不成为无关工作的等待步骤。Plan 描述安排，实时结果在项目验收记录维护。
