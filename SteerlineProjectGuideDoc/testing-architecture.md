# 测试架构规范

适用范围：SteerLine 所开发的具体项目及 SteerLine 自身。本文定义统一的测试分层与文档结构，由 SteerLine 维护，具体项目不可修改；项目通过自己的测试文档落实测试内容、命令和环境，不限定语言、技术栈或测试框架。

## L1–L4 定义

| 级别 | 定义 | 执行与组织要求 |
| --- | --- | --- |
| L1 | 用于代码检查的最小单元测试或集成测试集 | 每次修改代码后、提交 PR 前必须运行。建议整体在 1 分钟内完成，最好只维护一个固定测试集。 |
| L2 | 验证产品核心流程可用的 SmokeTest（冒烟测试） | 每次修改代码后、提交 PR 前必须运行。建议整体在 5 分钟内完成，最好只维护一个固定测试集。 |
| L3 | 符合并行要求的多个功能测试 | 按变更影响选择运行，可随开发持续扩展；每项覆盖有独立价值的功能流程。 |
| L4 | 多种可复用测试的集合 | 管理临界情况测试、无法并行的功能测试，以及单元测试和集成测试集等；按验证需求选择运行。 |

L1、L2 保持精简、稳定，分别提供统一执行入口；一个测试集可以包含多个用例和必要步骤。耗时是整体运行时间的设计建议，不能通过跳过必要断言达标。L4 中的测试可复用于 L1–L3，清单应明确引用关系和执行范围，避免重复维护。

分级不单按耗时、测试名称或是否使用真实服务判断。局部规则与反例优先用单元或集成测试验证；只有跨组件或系统行为需要共同验证时，才增加完整流程测试。L4 不要求全部串行。

Full 是项目定义的全量执行范围，不是第五个级别，也不等于 L4；项目须明确其包含的测试集、环境与外部副作用。

## L3 并行要求

- 各测试无执行顺序依赖，不消费其他测试的执行产物。
- 可写数据、目录、数据库、端口、账号或远端资源相互隔离，清理所有权明确；可复用只读构建产物和公共准备逻辑。
- 各项说明相对 L2 和其他 L3 的独有流程、触发条件与主要断言；仅参数或数据不同的重复用例优先合并或参数化。
- 并行能力与调度策略分开记录，可按资源预算限制并发；尚未验证并行运行时如实说明。无法解除共享可变资源或顺序约束的功能测试归 L4。

## 三级测试文档

| 层级 | 文档 | 职责 |
| --- | --- | --- |
| 第一层：统一规范 | `SteerlineProjectGuideDoc/testing-architecture.md` | SteerLine 维护的测试结构定义，具体项目不可修改。 |
| 第二层：项目指南 | `SteerlineFlow/testing.md` | 按本文规则生成的项目自定义测试说明，是项目日常使用入口；说明 L1–L4 的运行方式、环境、选择规则及已知缺口，并链接各级测试列表文档和结构化清单。 |
| 第三层：测试列表 | `SteerlineFlow/testing/` 下的多个测试列表文档及 `SteerlineFlow/testing/test-list.json` | 可读文档维护各级测试的说明列表；JSON 维护结构化测试列表，供系统读取。两者的 ID、级别、入口和验证内容保持一致。 |

`SteerlineFlow/testing.md` 根据项目实际测试内容生成并持续维护，必须遵循本文约定；具体命令、环境和清单在项目文档中定义。各级均须有明确列表，无测试时写明“未登记”及已知缺口，不以空列表表示已覆盖。

每个测试集或功能测试至少记录：

- 稳定 ID、名称、级别与验证内容，包括触发条件、主要断言和通过条件。
- 环境、前置条件、可执行命令及对应实现。
- 执行约束与复用关系；L3 说明独有覆盖和资源隔离，L4 按需说明临界条件或串行原因。
- 结果、日志与清理证据的登记位置；公共信息可统一说明。

新增、删除、改级或改变环境、入口、主要断言时，同步更新测试实现、执行登记、可读列表、JSON 和项目指南中的相关说明。执行器另有登记文件时，须与上述清单一致；未实现的能力标为待实施，不登记为可运行。稳定 ID 不静默改用于其他验证目的。

## 执行与结果

代码修改后、提交 PR 前运行 L1、L2，并按变更影响补充所需 L3、L4；不默认运行 Full。实现 Plan 的测试计划应映射验收项、测试 ID、环境、命令、执行时点及通过条件，缺少必要测试能力时纳入实施步骤。

测试使用隔离现场，明确资源所有权、清理方式和真实外部副作用。环境或能力缺失时明确阻断或待实施，不能切换模拟后宣称真实场景通过。编译、启动成功、零匹配、意外跳过、超时或缺少必需证据均不能代替测试通过。

清单说明“测试什么”，独立运行记录保存源码版本、实际选择、环境、结果、日志和清理事实。失败与补测分别保留，子集通过不能表述为整个级别通过。

跨模块或跨项目的规则与故障测试由实现该能力的 owner 维护；调用方验证自己的参数传递、授权、结果消费和业务闭环，保留必要的跨系统冒烟，避免重复建设依赖内部测试。
