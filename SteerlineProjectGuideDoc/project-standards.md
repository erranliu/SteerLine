# SteerLine 受管理项目规范

适用范围：由 SteerLine 管理开发流程的项目，包括 SteerLine 自身。本文规定项目应具备的流程文档结构、内容职责与维护边界；源代码、构建配置及测试程序的目录由各项目按技术栈安排。

本文规定项目采用的结构。项目是否符合规范，应同时核对实际目录、文档引用与工具读取路径，不能仅以规范文档已经存在作为依据。

## 目录结构

项目根目录下采用以下结构，目录名称及大小写保持一致：

```text
<项目根目录>/
├── SteerlineProjectGuideDoc/       # SteerLine 提供的固定规范
└── SteerlineFlow/                  # 本项目的 SteerLine 流程文档
    ├── spec/                      # Spec 文档
    ├── plans/                     # 实现 Plan 文档
    ├── archive/                   # 过期、退役或被替代的流程文档
    ├── Roadmap/                   # roadmap 规划与维护文档
    │   ├── execution-map.md        # 正式 roadmap，与任务 DAG 一致
    │   └── RoadmapGuide.md         # 本项目定制的 roadmap 维护规则
    ├── testing.md                 # 本项目测试总入口
    └── testing/
        ├── test-list.json         # 机器可读测试清单
        ├── <测试列表文档>          # 各测试项的可读说明
        └── <历史测试报告>          # 历次执行的结果与证据定位
```

尖括号表示内容类别，不是固定文件名；测试列表文档和报告的具体文件名、分层方式由项目在 `testing.md` 中说明。`Roadmap/` 可按项目需要维护草稿及辅助材料，但须与正式执行规划明确区分。

## 固定规范与项目定制的边界

`SteerlineProjectGuideDoc/` 由 SteerLine 提供并统一维护，对受管理项目是不可自行改动的固定文档目录。项目不得在其中改写通用规则、加入项目特例或保存运行结果。规范新增、修订和版本更新由 SteerLine 规范来源统一提供；SteerLine 自身维护这套规范属于规范提供方的工作。

项目特有的流程、命令、环境、测试安排和 roadmap 维护规则放在 `SteerlineFlow/`。项目文档引用固定规范并补充本项目的落实方式，避免复制一份通用规则后独立修改。采用的规范来源与版本应可追溯。

`SteerlineFlow/` 是项目流程文档的统一位置，不要求将产品设计、源码架构、用户手册等其他文档全部放入其中。项目自己的 `AGENTS.md` 或文档导航应能定位固定规范及本项目流程入口。

## Spec、Plan 与归档

| 位置 | 内容职责 | 维护要求 |
| --- | --- | --- |
| `SteerlineFlow/spec/` | 描述成果、范围、约束和通过条件的 Spec | 需求与边界可独立理解，关联对应 Plan；遵循 [Spec 与 Plan 编写规范](spec-plan-guidelines.md)。 |
| `SteerlineFlow/plans/` | 对应 Spec 的实现步骤与验证安排 | 链接所依据的 Spec，说明实施与测试计划；实时测试结果另存报告。 |
| `SteerlineFlow/archive/` | 已过期、退役或被替代且仍有追溯价值的流程文档 | 保留原任务、替代文档或历史版本的定位；归档材料不作为当前执行依据。 |

Spec 与 Plan 应有稳定、可关联的名称或标识。移动或归档时同步相关导航与引用，避免当前 roadmap 指向失效路径。文档是否过期按其内容是否仍有效判断，不因任务完成就自动将仍被引用的有效规范归档。

## Roadmap 与任务 DAG

`SteerlineFlow/Roadmap/execution-map.md` 是正式 roadmap 文档，描述确认纳入执行的任务及其依赖，并可由 SteerLine 按任务 DAG 执行。草稿、备选方案或历史规划不能代替它成为执行入口。

正式 roadmap 应满足以下要求：

- 任务身份明确，能定位对应的 Spec、Plan 和必要的执行前置。
- 任务集合与依赖关系和 SteerLine 中对应的任务 DAG 一致；依赖能够解析，不存在循环依赖或含义不明的前置。
- 任务状态及交付、验证结果的记录与实际执行事实一致；规划变更和执行结果须同步到对应的文档与 DAG，不能长期维护互相矛盾的两套记录。
- 开始或恢复执行前核对一致性；发现任务、依赖或状态冲突时先核实修正，不根据草稿或过期材料推断执行范围。

`SteerlineFlow/Roadmap/RoadmapGuide.md` 是项目定制的 roadmap 维护规则，说明本项目的规划入口、必读材料、任务拆分、确认与纳入执行方式、DAG 同步、状态维护和归档约定。通用规则仍引用固定规范，具体任务及实时状态归 `execution-map.md`，不在指南中重复维护。

具体的任务字段、DAG 接入及执行接口遵循 SteerLine 对应功能的契约；本规范不新增导入格式，也不将 Markdown 文件的存在等同于已经成功接入或获准执行。

## 测试入口、清单与历史报告

`SteerlineFlow/testing.md` 是本项目测试总入口，落实 [测试架构规范](testing-architecture.md)，说明测试分级、选择方式、环境与准备条件、执行命令、通过条件，以及清单和历史报告的位置。入口应能直接找到 L2、L3、L4 内容列表及已知缺口；级别尚无场景时明确说明现状。

`SteerlineFlow/testing/` 维护以下三类内容：

| 内容 | 职责 | 维护要求 |
| --- | --- | --- |
| `test-list.json` | 供 SteerLine 读取的机器可读测试清单 | 每项可定位实际执行入口和检查要求，格式遵循 SteerLine 测试清单契约。 |
| 测试列表文档 | 解释测试内容、范围、主要断言、环境和执行约束 | 与机器清单使用相同的稳定测试 ID；清楚说明分级、独有覆盖及未实现项。 |
| 历史测试报告 | 保存某次、某版本的实际测试结果与证据定位 | 记录源码版本、实际选择、环境、结果和证据位置；保留失败及后续补测的关联，不用新结果覆盖历史事实。 |

清单回答“测试什么”，报告回答“某个版本实际测得什么”。新增、删除或调整测试时，同步实现、机器清单、可读列表和相关引用；不能将登记在清单、编译成功或未执行的场景写成测试通过。

历史测试报告保存在 `testing/` 下，由项目约定组织方式。体积较大的原始日志和运行产物可另存受管产物目录或外部存储，报告保留证据定位与必要摘要，不要求将所有原始产物提交到 Git。报告本身不是过期规划文档，不因一次新测试就移入 `archive/`。

## 项目落实与维护

项目应维护清晰的入口和相对链接，使正式 roadmap、任务 Spec/Plan、测试入口、清单及报告能够相互定位。固定规范中已有的通用要求直接引用，项目实际采用的命令、路径和差异写入项目流程文档。

既有项目按明确的迁移安排对齐本结构；迁移时同时处理文档链接、工具读取路径和相关配置。尚未迁移的现状须如实记录，不能仅新增本规范就宣称目录结构或执行能力已经符合。
