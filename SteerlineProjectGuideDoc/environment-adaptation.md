# 项目环境接口适配指导

本文说明 manifest 4 / result 3 的项目环境接口；契约以[环境 Spec](../SteerlineFlow/spec/project-environment-workflow.spec.md)为准，实施与实测范围见[验收记录](../SteerlineFlow/testing/acceptance/project-environment-workflow.md)。使用前核实实际部署的 SteerLine/Runner 支持该接口，不将源码或单一目标验收外推到其他安装/执行链。自动项目初始化适配功能未实现；当前仓库准备与自检步骤见[项目初始化指南](project-initialization.md)，日常环境检测不负责生成或复核项目材料。

## 两级职责

SteerLine 提供调用/结果规范及本通用指导，负责目标定位、调用、执行生命周期和最终结果消费。项目自行解释实际情况，形成并维护要求与检测入口，从检测到诊断和自有收尾完成闭环，给出 ready/not_ready、失败原因及可选明细。

```text
通用指导 + 实际项目 + 明确目标
            ↓ 项目开发流程／未来初始化适配，自检后交付
项目要求说明 + 检测入口 + 显式资格依赖声明
            ↓ 项目审阅并正常 Git 采用
SteerLine 调用入口 → 项目完成检测闭环 → 最终结果及原因/明细
            ↓ 原执行停止、结果封存、关联及当前依据有效
SteerLine 展示并据最终 ready 控制对应环境准入
```

指导和平台提示词由平台交付，不复制、生成或提交到受管理项目，不要求与当前 SteerLine 程序逐字同源。项目实现接口契约即可，平台提示词措辞升级不要求项目同步文件；真正不兼容的接口变化按明确版本处理，不引入多版本兼容框架。

## 根据实际项目形成配套接口

由项目维护者或项目授权的生成工具调查真实源码、构建/依赖声明、运行方式、权限及已有测试。工具、版本和业务标准都应有项目实际依据；不确定的要求留作项目待确认事项，不猜测或填造通过。SteerLine 日常不参与调查、生成或验证这些过程。

要求和检测逻辑整体维护、审阅和采用。复用项目正式程序；项目自行决定检查集合、执行顺序、内部重试、是否跑 L2、是否验证 TTY、是否需要 PR，以及何时可报告 ready。没有 L2 或不需要 PR 本身不违反平台接口。工具尚未准备、服务不可达、标准未知或自有清理未完成，由项目检测得出 not_ready 并说明原因；不让平台从检查明细重新计算结论。

沿用每环境 environment.md 和 verify-environment.ps1 或 verify-environment.sh，不加另一份 input/context、检查清单或框架。文档是项目要求说明的权威入口，脚本实现该要求，调用机器段只定位本环境入口/解释器和显式 dependencies。字段/版本/安全约束以 Spec §3 为准，本文不复制第二套 schema。

环境接口不依赖 environment-project.json 或固定测试清单存在；该文件仍可用于原任务测试功能。项目检测自行使用某政策、清单或程序时，将影响就绪判定的文件在 dependencies 中声明，包括间接辅助文件。平台只校验/哈希这些文件，不扫描业务依赖或解释检查规则；漏声明导致错误复用由项目负责。

## 项目自行完成检测闭环

入口应在目标未 ready 时也能启动，不能先领取 Task、要求通过自己的检测、提交平台协议或完成一轮生成后才能检测。解释器/通道无法启动属于调用能力问题，平台如实报告；入口可运行时，缺工具等项目问题应尽量形成可读负结果，不只抛一个无说明退出码。

调用工作目录固定为原提交的工作区根，命令是 `powershell.exe -NoProfile -NonInteractive -File <script>` 或 `bash <script>`，按参数数组执行，不传 Phase。入口从 `STEERLINE_RESULT_FILE` 读取预置身份及固定 call_context，完成后原子更新同一文件。稳定调用字段只有项目身份、环境键、adapter 及 target.kind/environment，全部计入摘要，不由平台判断项目使用了哪些字段；不传模型、发布目标或自由参数。

脚本退出0表示正常返回，业务未就绪也应写完负报告；非零退出可保留负报告。平台要求 Runner 公布 status=completed 及 verified 原生成功终态，才判断调用正常结束，不从日志复核脚本退出码；无可信终态不准入。

一次调用内部由项目处理要求读取、检测、内部重试/诊断、自有资源清理和最终结果原子写入。平台不拆分 tty/prepare/publish，也不因业务失败自动三轮重跑或修脚本。受理未知、超时和取消由平台对账/停止原 Run，项目不自行重发平台请求或删除 Runner 持有资源。

项目保留调用方预置的项目、环境、活动、来源、call_context 及输入摘要，只填写最终结论和说明；缺必要检查、未完成或结论不确定时不得报告 ready。项目自有副作用/资源尚未知或未收尾时应报告 not_ready。Runner 的进程停止及结果封存由平台/Runner 核实，项目不得以自己的 message 宣称已完成平台结算。

最终 ready 只代表该项目自定标准已满足。平台不复核项目检查是否真实充分，不二次执行、不抓取 PR/报告证据后重判；格式、身份和生命周期校验仍保留。

平台重启对账只读取原调用事实并结算原执行，不重新调用项目入口；取消后的原执行由原 Runner 构建恢复收尾，跨构建未知明确阻断。项目无需复制平台恢复协议或参与 stop 编排。

## 丰富结果与失败原因

结果必须包含最终 ready/not_ready 及人可读说明。未就绪至少说明哪里失败或尚未验证、已知原因和可采取的下一步；原因未知应如实说明，不用空说明、单一布尔值或凭据正文代替诊断。

可选 details 可以携带项目自己的检查明细、错误摘要、日志或报告定位等结构数据；完整日志也可留在原运行产物中。平台有界读取、保存和安全展示，不规定业务明细 schema、不解析“全部 checks 通过”或“PR 已创建”以覆盖 ready，不自动访问证据链接进行复核。敏感信息由项目输出前去除。

结果 completed 表示报告已写完，不等于 ready。ready=true 但原执行异常退出、仍运行或结果未封存时，平台不放行；最终负结果与调用失败/未完成/结算未知分别展示。消息和明细的丰富程度不改变平台信任项目结论的责任边界。

## 结果适用范围与日常更新

项目应完整声明会影响就绪结论的文件。平台把本环境文档、入口、全部显式依赖、上述全部固定稳定调用字段及接口语义版本固定为 inputs_digest；每次活动/Run/request 身份、调用序号、源提交、当前引用 revision、时间戳、临时结果路径及摘要自身不计入该摘要，只作原信封绑定。结果原样回传该摘要及原提交，不能在执行后另选依据或改成当前提交。

平台原观察 owner 确认要求、检测程序或声明等依据变化后，按原 Current revision 持久撤销资格；后续回退原字节也不恢复，须新检测。纯读取故障只暂阻断，不误作变更撤销；只读查询不写撤销。未观察到的中间提交不声称已检测。共享文件只影响明确声明它的环境。无关源码提交且全部声明依据不变时，可以沿用原提交的结果，历史来源不改写。模型、生成记录和平台提示词措辞不单独使资格失效。

动态机器状态、凭据或服务变化无法仅靠 Git 文件发现。项目或用户知晓变化时，应使用既有标记失效/重新检测操作；平台不承诺持续监控，也不新增 TTL/自动扫描。新检测切换当前引用后，旧成功不兜底；迟到成功不能撤销人工失效或覆盖新的引用。

## 未来初始化的自检边界

未来初始化适配应一次形成配套材料，并在生成侧自行检验、修复接口格式/目标/声明完整性、启动行为、正负结果、失败原因和自有收尾。交付草稿、自检结果及未验证项，整体审阅后正常 Git 采用；不先提交输入、协议副本或中间文件，不将生成过程接到 SteerLine 日常检测链。

自检可以使用项目自己的受控正负输入，不要求目标先 ready；实际未准备环境得到正确 not_ready 也可验证负向行为，不能为自检成功伪造环境就绪。目标不可达或权限不足时保留未验证范围，不将静态格式通过等同真实检测通过。自检通过也不能直接授予生产 ready，正式检测仍绑定自己的活动和来源。

本轮不实现初始化 API、自动调查/生成修复、自动提交或纳管。当前由项目正常开发流程完成维护；打开项目、普通添加项目、查看结果都不能触发生成或执行。平台完整材料交付通道不足时由平台解决，不退回要求项目同步提示词。
