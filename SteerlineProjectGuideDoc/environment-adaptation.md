# 项目环境接口适配指导

状态：本轮实现已声明项目的环境材料生成、更新及验收消费；整个项目的首次初始化适配仍是未来功能。实际模型接线须核验完整指导/协议可读、采用版本、实际正文与字节数，并完成独立审核。

## 两级机制

第一级是 SteerLine 提供的通用指导和生成、执行、报告协议，说明怎样调查项目、形成接口和交换结果，不预设项目语言、工具版本、服务或目录。

第二级是根据真实项目形成的环境要求文档和脚本。未来初始化适配读取指导、固定源码和明确目标，一次生成配套草稿；整体审阅并经一次正常 Git 固定后，SteerLine 自动读取接口、经目标 Agent 调用并核验结果。项目材料归项目维护，不把通用指导抄成另一份项目生成指南。

```text
通用指导/协议 + 实际项目 + 目标事实
                ↓ 首次适配，一次生成
项目入口 + 各选中环境的 environment.md / 验收脚本 + gaps
                ↓ 整体审阅，一次 Git 固定
目标机器准备 → SteerLine 调用验收 → 核实后授予对应资格
```

不先要求项目手写或提交 input、context、检查清单再生成脚本。指导用于形成/更新项目接口，日常验收读取正式环境文档、脚本和执行/报告协议，不重复加载调查指导。已有正式材料直接复用；新目标只补该目标材料。

## 根据实际项目形成配套草稿

1. 固定真实仓库来源，读取已有规则、构建/依赖声明、测试及发布程序；每项工具、版本、服务、权限和非秘密引用要求都能追溯到实际文件或用户明确决定，不按项目名称、CI 示例或生成宿主推测。
2. 复用项目正式测试入口、原始报告和 PR 工具。识别公共政策与目标适用条件，在同一个环境文档中说明要求、检查 ID、期望及检测方式；不同平台/链路不凑另一环境的检查。正式 L2 仍取唯一清单的全部 L2。
3. 根据调查结果一起生成要求文档和薄调用脚本，列出实际运行依赖。缺版本、凭据引用、正式 L2 或发布规则时列 gaps，不发明通过标准、安装工具或另造测试平台。缺口不因生成成功而消失。
4. 没有本环境文档时，以完整指导/协议和固定项目快照调查实际程序，不能只交入口和清单；使用已有整树快照或核验足够的显式文件集，遵守原权限/限额，不执行项目程序探测。已有有效文档且引用足够时，按有限引用更新；这是同一生成操作的两种读法，不增加文件、配置或用户步骤。
5. 旧脚本/依赖删除、改名或机器段错误时，保存原可读正文、源码摘要和失效路径，转入同一固定源码调查提出修复草稿，不先要求旧接口通过。危险旧路径不解引用，原标准不自动降级；本次实际必读的完整协议/指导、核验源码和项目政策/正式测试定义缺失仍阻断，未知事实如实写入文档缺口。验收继续要求全部正式运行依赖齐备。

## 最小材料与唯一权威

| 材料 | 职责 |
| --- | --- |
| `SteerlineFlow/environment-project.json` | 仅定位公共政策/事实材料和项目唯一正式测试清单；环境验收、测试安排、任务材料/记录共用该来源，不定义环境检查集合 |
| `SteerlineFlow/environments/<完整 environment_key>/environment.md` | 本环境唯一验收要求契约：正文解释要求/检查 ID，唯一 manifest 索引 required_checks、阻断 gaps、脚本/解释器、验证分支和 dependencies |
| 同目录 `verify-environment.ps1` 或 `verify-environment.sh` | 薄调用项目原正式程序并按协议写报告；实现文档标准，不维护另一套可放宽的要求 |

具体字段以采用版本的协议为准，本文不复制 schema。公共文档可以明确引用，环境文档确定哪些要求适用，发生冲突须报告缺口；不在项目入口、独立 input 或脚本中再维护一份必需检查表。机器段只索引正文同一组 ID，不重复一份条件描述。

未确定的标准、引用、平台或运行文件等阻断事实写在该 manifest 的 gaps；非空可审阅导出并经 Git 保存，但不能开始验收。生成结果顶层 gaps 只投影文档，同项同序，不维护另一套缺口。SteerLine 单独读取正式文档即可显示/阻断，新 home、没有生成记录或人工维护的材料也相同；解决后经 Git 更新，空 gaps 仍须完整验收。已明确标准而目标机器工具尚未准备属于现场 checks 的 failed/incomplete，允许检测，不误当无法开始验收的标准缺口。

完整目标键和少量公开事实由 SteerLine 在原活动/请求中冻结，不要求提交 environment-context.json，也不复制 execution、模型或秘密到项目。生成参考只留在原活动来源记录中，不增加项目参考清单。实际运行依赖仅由 manifest.dependencies 补充；纯参考不自动使环境资格失效。

首次缺失的项目入口、必要公共说明、协议副本与各选中环境的文档/脚本一起交付，已有文件复用；不能先提交一批输入再输出另一批产物。项目自身缺测试/依赖等真实问题可以阻断正式采用和验收，但不通过占位脚本或虚构标准凑齐配套材料。

## 自动调用与更新

SteerLine 从同一正式提交读取环境文档，先按 gaps 判断材料是否可验收，再严格核对入口/脚本/运行依赖，冻结 required_checks 并追加 terminal.tty；材料完整后才通过 Runner 启动目标 Agent。支持的脚本类型由调用协议限定，工具/版本由项目声明且在目标进程检测，不以 Runner 链路能力或生成宿主安装代替，也不查询原生成状态补验收资格。

接口配套支持最小 TTY 检测、prepare、publish 和协议规定的失败记录：prepare 逐项保留通过/失败/未验证事实，满足前置后运行完整 L2；publish 仅在 prepare 完整通过后执行唯一验证 PR 发布并报告自有清理。结果关联、原子写入、未知只对账、停止和封存遵循执行/报告协议，不在本指导重写。外部审核/合并及原始项目报告的独立 L4 核验归对应外部所有者。

草稿不直接运行或授予 ready。更新要求时同时展示文档与脚本差异，经项目审阅并一次 Git 固定后供验收使用；执行中的脚本不得改要求、删减 L2、手填成功、启动嵌套 Agent 或删除 Runner 持有资源。实际验收前须按正常 Git 流程核实项目验证分支已存在且包含采用源码，不把它提前变成生成前置。

## 交付与未来能力边界

交付草稿包、gaps、实际来源及采用版本，不把应用、提交、推送或发布视为生成的默认副作用；每项操作按实际授权完成。整体采用可以一次 Git 固定，项目正常评审/发布方式不被强制改为自动提交或合并。

本轮不提供整个项目的初始化适配，产品不能据此自动纳管任意仓库。未来初始化需先核验现有只读文件能力能共同提供完整指导/协议和项目快照，不能假定未公布的 Runner 临时文件/跨来源接口；能力不足时列明待实现项，不内联固定规则或要求项目预提交输入。当前可由用户或授权 Agent 按指导一次准备配套草稿；已有项目入口与完整协议后，原生成操作可调查新环境或修复旧环境，已有有效材料按引用更新。安装版能力以实际部署版本为准。打开项目、只读核验和普通添加项目不能隐式启动适配。

静态/文档检查只证明材料结构。正式验收另在隔离现场核验全部 checks、完整 L2、原 PR 身份、自有清理、Run 停止和封存；保留失败与补测，不跨环境、项目或轮次拼接通过事实。
