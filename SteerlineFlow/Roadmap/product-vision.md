# SteerLine 产品愿景

## 产品定义

SteerLine 是一款带有研究性质的开发工具，长期远景是通往**工程 AGI**：让 AI 最终能够自主开发复杂软件项目，包括普通人需要长期借助 AI 协助才能完成的项目。下面四个交付节点是通往这一目标的阶段；第四版仍只实现有限自主推进。

当前产品方向以 roadmap 为中心，将选定目标转为有依赖的任务，并核验实际 PR 交付。SteerLine 为任务登记候选、关联 Runner 的 Run，并沿原会话转交用户反馈。执行 Agent 按 Spec/Plan 实现、测试、修复并提交代码，SteerRunner 按所选流程组织执行和发布。人决定产品取舍、处理待决策事项并授权合并，SteerLine 核验实际合并后记录交付。正式入图时创建 Task 并固定其规格和依赖。PR 合并前可受控丢弃正式任务，后续规划不能暗中改写已创建的任务。

具体底层能力与实施顺序见[草稿 roadmap](drafts/roadmap.md)。本文件定义产品交付节点；普通开发由当前聊天直接实现；明确要求 roadmap 调度时，由 roadmap-runner 使用[正式执行清单](execution-map.md)管理已确认的任务与依赖，流程见[RoadmapGuide](RoadmapGuide.md)。

## 交付节点

### 1. 早期阶段：Codex 规划，SteerLine 执行

早期流程由人在 Codex 中规划和维护 roadmap，项目 skill 整理 Spec/Plan 与任务 DAG，再提交给 SteerLine 校验并入图。SteerLine 当时直接管理执行启动与观察，统一处理待决策事项、反馈、实际合并核验和后继释放。持续会话与简化主流程由 #36 交付。早期阶段尚无 Roadmap UI，交付结果由人带回 Codex 继续规划。

该阶段已支持同项目内不同任务人工并行，以及同任务多候选对比。默认一个候选，可人工逐个新增，启动检查时参与数达到五个即拒绝新增，允许并发检查偶尔超出。各候选独立固定执行配置，拥有各自的会话、工作区和 PR。合并前可退出候选参与，资源停止另行记录，合并后不支持放弃。人选择合并结果，SteerLine 核验唯一交付。该阶段未安排自动评分或成果融合。

第一阶段目标范围包含本地 Codex、本机 Orca 与远端路径交付。远端历史契约与结果见[远端 Spec](../spec/orca-remote-l3.spec.md)及[专属验收](../testing/acceptance/orca-remote-l3.md)；迁出前单终端的有限样本与首次信任限制见[历史验收](../testing/acceptance/orca-terminal-remote-retest-2026-10-10.md)；后续本机 Orca 配置、真实目录和受控验证见[执行配置验收](../testing/acceptance/web-execution-config.md)，不以目录或夹具通过推定真实业务链通过。

此版采用一个本机安装版本持续工作，源码调试以独立 exe/home 和测试 clone 共存。服务、控制台及任务命令明确显示并使用各自实际路径和构建来源；日常 build 不覆盖安装版。完整 stable/dev 双 channel、不可变版本库及受控提升延后，维护仍采用人工停止、安装和启动，不承诺跨构建接管活动任务或旧开发格式兼容。剩余任务与推进顺序见[草稿 roadmap](drafts/roadmap.md)，最小隔离由 #83 的独立 Spec 承接，组合验收见[一期活动](../testing/acceptance/phase1.md)，不另维护平行交付清单。

#84 已交付后端无关的 worker 步骤状态：implement 执行与报告分开，publish 单轮，结果由程序核验后推进；后续发布格式错误只追加一次 publish.report。采用简单代码定义和短提示词，复用原会话/adapter，不增加通用编排框架。#83 隔离能力已合入，仍须固定包含后续调整的新一期安装构建；组合、24小时和同构建恢复签收待执行，旧持续 worker 或单次闭环证据不代替该签收。

**交付判定：**有依赖的原生任务完成双本机后端执行、人工决策和 PR 合并核验；同任务多候选独立，中心只记录一个真实交付，其他候选保留资源事实。固定安装版通过源码调试共存、24 小时持续运行及同构建当前格式重启验收。短时 E2E 为定向回归入口，不替代安装入口或长期运行证明。

### 2. 客户端与业务服务分离，Roadmap 受控转正

当前交互入口为 Web。Go 服务管理任务、候选、身份、资格、原命令和交付事实。Web SPA、项目切换和统一启动/多项目宿主已完成约定自动验收，桌面体验尚待人工确认。旧任务 #91 提供的 HTTP 客户端基线仍由 Web 使用，其 TUI 客户端已按[退役任务](../spec/tui-retirement.spec.md)删除。交付和待验明细见[Spec 索引](../spec/README.md)、[执行清单](execution-map.md)及各专属验收。

**当前 Web 能力。** Web 支持查询、任务操作、反馈、final、恢复和原生会话查看。Roadmap 页面可读取外部维护的草稿，解析任务与依赖，供用户确认后生成并审阅 Spec、Plan 和验收文档，再按授权发布并将任务正式入图。正式任务编号在入图事务中分配。流程与边界见[Roadmap 读取、解析与入图](../../docs/product-design/roadmap-promotion.md)。

规划讨论主要在外部聊天中进行，草稿由用户在仓库中维护。按需 SSE、完整项目添加与纳管、受控规划 Agent 仍按各自 Spec/roadmap 推进。早期 Web 构想见[设计归档](../archive/design/planning-ui.md)和[原型说明](../archive/design/prototypes/planning-ui/README.md)。

### 3. 正式可发布产品

第二版能力达到正式发布标准：可重复安装和接入项目，明确平台与后端支持范围，提供用户文档、故障诊断及可复现的端到端和恢复验收。重启和外部动作结果不确定时，任务、规划、决策与交付证据保持一致，不重复派发或错误结项。正式发布后的升级策略在该阶段确定；若频繁更新长期运行安装版已需要保留空闲会话、待合并 PR 或未发送反馈，可提前重新规划延后的完整版本管理。上线前不建设旧版本数据迁移。roadmap 仍由人受控推进。

**交付判定：**新用户可按文档完成完整闭环；当前版本的服务重启可保留任务、待处理事项和交付证据。

### 4. 主 agent 有限自主推进 roadmap

人预先设定目标、授权范围和资源边界后，主 agent 可在范围内选择下一步、维护规划、创建任务并监督执行。它先处理有充分依据且已获授权的执行 Agent 问题；遇到产品取舍、权限、证据不足或越界情况，就暂停受影响的推进，向人说明原因并等待决策。人可随时暂停或接手；PR 仍由人合并。自主动作及答案都保留依据、版本和回执。

**交付判定：**主 agent 能独立推进授权范围内的任务，在需要人决策时准确停下并恢复；重启后不重复操作，未授权范围不推进。
