## 产品需求

### 规划分页与多轮改稿

- 在项目内增加「Roadmap 规划」分页，列出尚未交接的规划任务。可以同时推进多项规划。每项任务有独立的可写 worktree 和持续的原生会话，同一任务一次执行一轮。
- 创建时固定 `SteerlineFlow/Roadmap/drafts/` 下的一个 Markdown 路径。同一项目的同一路径同时只允许一个活动规划任务。一份草稿可以包含多个候选开发任务，候选用草稿内代号标识。
- 用户可以描述目标、回答问题、确认取舍、要求按前文修改。SteerAgent 能读取仓库、调用工具、直接编辑草稿，也能修改仓库里的相关文件。每轮结束后展示回复、最新草稿预览和工作区累计改动。
- 提供可复制的稳定链接，以项目和规划任务 ID 定位。草稿还未生成时，链接打开任务并显示当前状态。有新版本时，同一个链接打开最新已保存的草稿。某轮失败或中断时，仍可查看上一份已核验的预览，并看到本轮状态。

### 单任务 Rebase、全部 Rebase 与冲突处理

- 每项规划任务提供「Rebase」，将其工作区的改动同步到最新目标分支。页面提供「全部 Rebase」，对本项目符合条件的规划任务使用同一次获取的目标分支版本，各自执行并显示结果。正在执行或有未结算操作的任务显示跳过原因。一个任务遇到冲突，其他任务照常继续。
- Rebase 遇到冲突时，SteerLine 显示冲突文件和「让 SteerAgent 解决冲突」按钮。点击后，SteerLine 向原生会话发送一条固定短指令。SteerAgent 在原 worktree 解决冲突并继续 Rebase。SteerLine 核验结果，成功后更新草稿预览和累计 diff，仍有冲突时保留现场并显示剩余文件。
- Rebase 和冲突处理完成后，用户按新的 diff 审阅再发布。已经创建 PR 的任务仍使用原 PR，确认后由 SteerLine 更新。

### 审阅、发布与交接

1. 用户打开提交审阅页时，看到从任务当前基线到工作区的累计文件清单和差异，包含新建、修改和删除。草稿默认选中。其他改动由用户看完 diff 后逐文件勾选，可和草稿一起进入同一个 PR。
2. 用户点击「确认并创建 PR」，SteerLine 提交所选文件、推送发布分支并创建 PR。确认绑定当时看到的草稿、选中文件及其内容。内容发生变化时，重新展示差异并确认。未选改动保留在规划工作区，继续可供讨论。
3. 待合并的任务留在「Roadmap 规划」。需要修订时，在同一任务里继续对话，重新审阅后由 SteerLine 更新原 PR。用户按仓库流程合并，SteerLine 显示 PR 链接及核验状态。
4. SteerLine 确认原 PR 已合并且合入稿可被下一页读取后，任务退出「Roadmap 规划」，原稳定链接跳到「Roadmap 草稿」的对应来源。若 PR 已合并而草稿读取端尚未同步，任务显示「已合并，待同步」。用户随后按现有流程发起解析、审阅依赖、生成文档并正式入图。[现有草稿转正流程](../../../docs/product-design/roadmap-promotion.md)

## 关键技术方案

### Runner 的可写原生会话与 worktree 写入协调前置

- SteerLine 接入前，Runner 须提供从指定 Git commit 创建并绑定受管可写 worktree 的原生多轮会话能力。当前 `conversation/1` 提供本机只读会话。新能力应复用现有会话、逐轮消息、历史、停止与恢复机制，并公开能力、输入 schema、worktree 身份和当前操作资格。首版以本机 Codex 为验收目标。[Runner 接入边界](../../../docs/integration/steerrunner.md)
- 一项规划任务对应一个 Run、一个原生会话和一个 worktree。每轮通过原 Run 发送显式消息，沿用原生会话上下文。SteerLine 持久保存对话、用户确认的决定和各轮请求身份，用于页面展示、审阅和恢复。多个任务按现有执行额度并行。
- Runner 提供空闲期间的 worktree 写入协调。原轮及输入操作已结算后，SteerLine 可排他取得写入资格。持有期间 Runner 拒绝开启 Agent 轮次和授予其他写入，SteerLine 结束本地操作并交还资格后，原 Run、会话和 worktree 可继续使用。重启或结果未知时沿原请求对账写入资格，避免双写。
- SteerLine 维护固定短指令和完整规则。实施前验证固定材料的供给与会话输入契约，固定材料缺失时给出诊断。[提示词治理](../../../docs/prompt-governance.md)

### Rebase 执行与核验

- SteerLine 获取并固定本次目标 commit，取得空闲会话的 worktree 写入资格后执行 Rebase。同一任务的 Rebase、Agent 轮次和发布共用互斥。Rebase 前将草稿及其他本地改动保存为可恢复的本地检查点，确保已提交、暂存、未暂存和未跟踪的候选改动都能参与同步或在失败后恢复。
- Rebase 停在冲突时，SteerLine 核验当前 Rebase 属于原任务分支，记录目标 commit 和冲突文件，再交还 worktree 写入资格。用户点击按钮后，由 SteerLine 向原会话发起冲突处理轮次。Runner 保留原 worktree 绑定，包括 Rebase 期间的临时 detached HEAD。
- SteerAgent 按固定短提示词解决文件冲突并执行 `git rebase --continue`。需要用户取舍时保留现场并说明。轮次结算后，SteerLine 通过 Git 状态核验 Rebase 是否完成、是否还有未合并条目、任务分支是否基于目标 commit，再更新规划基线和 diff。旧发布确认随基线变更失效，发布仍由用户重新确认触发。

### 版本预览和独立发布

- 规划记录保存固定草稿路径、最近可展示的草稿版本和内容摘要。在当前写入已结算的情况下，从工作区读取草稿和文件差异。差异取当前规划基线与工作区文件内容，覆盖已提交、暂存、未暂存及拟发布的未跟踪文件。页面展示的文件版本就是用户可授权发布的版本。
- SteerLine 保存确认的基线、草稿摘要、文件选择及对应内容摘要，在独立发布工作区从干净基线构建提交。创建或更新 PR 前校验提交的完整差异与用户确认一致。即使 Agent 在工作区已有本地提交，发布内容仍以确认的文件集合为准。目标分支同路径发生变化而影响发布结果时，处理冲突后重新审阅。
- 原生会话负责规划和本地改稿，发布请求与凭据由 SteerLine 持有。首版需在选定执行环境验证工作区读写与 PR 发布权限如何分开，以及执行主机原生 Git 凭据的可达范围。复用现有 Roadmap 发布的 provider 访问、原请求对账和合并核验方式。[Roadmap 发布实现](../../../internal/app/roadmap_publication.go)
- 以原 PR 的目标、已确认 head、实际合并事实和目标分支中合入的草稿内容核验交付。现有草稿来源从项目工作树读取，交接需显式处理同步差距，并以项目和路径生成的来源 ID 建立跳转。刷新页面或服务重启后，仍可恢复原任务、待核实 PR 和跳转关系。[草稿读取实现](../../../internal/app/roadmaps.go)

## 验收方向

| 场景 | 最小通过条件 | 方式 |
| --- | --- | --- |
| 多轮继续规划 | 两轮沿用同一 Run、原生会话和 worktree。第二轮能理解用户对前文的指代，读取仓库并在第一轮的文件上继续修改。稳定链接展示更新后的 Markdown。 | 固定 Runner 的本机真实执行与浏览器验证 |
| 并行与恢复 | 两个任务并行修改各自草稿。同一任务的活动轮次与 Rebase 互斥。重启或响应丢失后沿原请求对账，后续消息继续使用原会话，同一消息和同一发布请求各执行一次。 | 受控自动验收 |
| 单任务与全部 Rebase | 单任务操作只更新选中工作区。批量操作使用同一目标 commit，各任务单独报告成功、冲突或跳过。一个任务冲突时，另一个可完成同步。草稿和未提交改动仍可恢复。 | 隔离 Git 仓库与浏览器验证 |
| 一键解决冲突 | 构造真实 Rebase 冲突，点击后固定短指令进入原生会话，Agent 在原 worktree 继续。Git 核验完成后更新基线、预览与 diff，用户可按新差异确认发布。未解决时保留现场和剩余冲突。 | 固定 Runner 的本机真实执行与受控失败验证 |
| 选择文件并创建 PR | 工作区同时包含草稿和多个额外改动，默认只选中草稿。用户选中一项额外改动，真实 PR 的差异只有这两项。审阅后变化的内容须重新确认。 | 受控反例、隔离仓库与真实 PR 验证 |
| 合并后交接 | 待合并及合并结果未知时任务留在本页。合并后尚未同步时可继续打开草稿。下一页读到合入稿后，任务退出本页，原链接打开可解析的对应来源。 | 浏览器与真实 PR 合并验证 |
| 页面操作 | 用户能切换并行任务、继续对话、复制链接、查看预览和逐文件核验差异。 | 人工体验验收，参与窗口待定 |

- 草稿入口建议先支持新建；从「Roadmap 草稿」选择既有文件回来继续规划，待确认是否同时交付。
