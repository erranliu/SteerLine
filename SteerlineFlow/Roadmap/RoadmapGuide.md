# RoadmapGuide：规划 Roadmap 的指南

本指南约束明确选择 roadmap/roadmap-runner 的规划与调度。普通开发需求默认由当前聊天直接实现，不要求占号、纳入 execution-map 或创建执行聊天/worktree，见[项目规则](../../AGENTS.md)。

每次设计或修改 roadmap，先读本指南，再读下列必需文档，随后按本轮涉及的功能展开契约、源码与测试。本文是持续维护的规划入口，介绍规划与 Codex 开发执行流程，不维护具体草稿清单或任务状态。

## 开发流程与产品运行

开发期间由 roadmap-runner 直接使用 Codex 聊天和 worktree 执行任务，承担规划范围内的依赖检查、调度、独立复审、合并与结果同步。用户确认的 execution-map 是本流程的任务与依赖权威；外部 SteerLine 中心准入、创建回执和 Task/DAG 版本不作为开发前置。

| 位置 / 工具 | 所有权与作用 |
| --- | --- |
| drafts/、Spec/Plan、task-ids/ | 候选范围、独立需求与计划、永久任务身份；草稿和占号不产生执行授权 |
| execution-map.md | 用户确认的任务范围、依赖、执行状态、PR 和待验链接 |
| SteerlineFlow/testing/acceptance/ | 自动/人工验收计划、实际结果和证据定位 |
| Codex 仓库外 run 状态 | 聊天/worktree 身份、固定文档版本、候选 SHA、审核和外部动作记录，用于恢复与防重复 |
| Git / PR 平台 | 文档与代码的实际版本、head/base、真实合并事实 |

SteerLine 产品管理其用户任务时，仍通过支持的接口创建中心 Task/DAG、固定 TaskContract 并核验唯一 TaskDelivery，详见[数据模型](../../docs/product-design/data-model.md)。开发文件与 run 状态不写入该业务权威；具体产品测试需要的配置、权限和服务能力按任务 Spec/Plan 准备。

## 目录与基本用法

| 位置 | 用途 |
| --- | --- |
| drafts/ | 可扩展的 roadmap 草稿目录，按主题、阶段或方案命名；讨论目标、拆分、候选文档、依赖与优先级 |
| execution-map.md | 用户已确认的正式执行规划，按状态和依赖判断是否可启动，日常派发只选用户已确认的任务 |
| task-ids/ | 所有已分配数字身份，包括历史和草稿编号；占号不等于执行授权，号码永不复用 |
| SteerlineFlow/spec/、SteerlineFlow/plans/ | 分别保存候选或已经固定的独立 Spec、实现 Plan；共同执行约束在 spec/，启动时固定实际 Git commit 和文档路径 |
| SteerlineFlow/testing/acceptance/ | 当前自动/人工验收计划与未闭合项；archive/分层保存历史结果及旧方案，保留最小摘要和原始临时证据定位 |
| SteerlineFlow/archive/ | 有独有追溯价值的历史资料；旧证据通过固定 Git 快照取证，不作为草稿自动执行许可 |

草稿全部放在 drafts/ 下一层目录，可同时维护很多份。本指南只说明目录和规则，不索引其中任何具体草稿，也不要求存在某个固定草稿文件名。规划时根据人的本轮目标明确选定草稿，不把目录枚举当成待执行队列。

草稿可以只有目标、讨论点或未完成 Spec/Plan。已经识别出的草稿任务可以提前分配全局唯一 Task ID，便于引用、依赖讨论和编写文档，无须等待进入 execution-map。尚未形成任务的纯目标讨论可用临时议题标签；标签不与 Task ID 等价。编号后的任务沿用同一身份纳入执行，不重新编号；用户确认纳入 execution-map 后，按当前状态和前置判断是否可执行。草稿可读正式任务与成果，但不能改写执行者使用的固定 Spec/Plan；删除或修改草稿不会取消 worker。

任务经用户确认加入 execution-map 后可以继续留在草稿中，便于讨论整体目标；不要求纳入时删行，也不严格维护草稿内实时状态。真实 PR 合并、必要验证与验收同步完成后，从相应草稿移除已完成任务条目，保留必要能力摘要和编号历史。草稿中的旧状态不用于派发、判断完成或判断验收通过。

## 纳入执行与验收分类

验收规划从草稿阶段开始。识别出候选任务时，在草稿中链接 SteerlineFlow/testing/acceptance/ 的专属验收文档，说明自动与人工方式、最小通过条件、预期环境、准备条件与人工参与安排；不等纳入执行才补建。任务与验收文档是一对一或一对多关系：一份任务验收文档只归属一个任务，范围较大时可拆成多份，不以一份文件覆盖多个任务。纯目标讨论尚未拆出任务时可先记录验收方向；尚未确定的步骤、命令、环境或窗口明确写待定，随范围成熟细化，不虚构已验结果。

草稿也可以列出独立的阶段签收、体验确认或跨模块验收活动并链接 acceptance，使用活动/验收项身份与执行任务区分。规划提示词鼓励主动识别这些活动、安排参与窗口及可后置范围；这是一项规划建议，不强制为每轮规划生成独立活动、增加 Task 或串成固定执行路径。确有关键验收前置时明确记录实际阻塞范围。

人工操作/判断/持续组织为主的验收活动不能进入执行 DAG，应直接形成 acceptance 文档；验收项用场景 ID，不新建伪任务。自动验收可以作为独立 Task，也可作为实现 Task 的一部分：明确可自动完成的步骤、通过条件、环境和交付结果，按对应 Spec/Plan 验证，不要求另建重复验收框架。

任务主体能自动交付而附带少量人工验收时，尽量集中后置。规划时标明人工项、责任人/窗口或待安排、截止阶段、阻塞范围和文档链接；非人工必需验证通过且后续不依赖该人工结果时，保留“待人工验收”并继续合入/无关后续执行，不填“全部已验”。真实失败、未实现功能、权限/环境前置缺失、未知外部动作或明确先验条件不能通过后置标记绕过。

不设置任意人工比例阈值；按主要交付是否能独立自动完成、是否需持续人工参与及人工结果对核心语义的影响判断。已启动任务若需要调整分类或范围，先核对原执行和固定要求，取得范围变更授权后安排，不能仅删行取消 worker。

Spec 定义验收要求，Plan 写实施和测试安排，所有具体自动/人工行为、状态及结果明细归 acceptance 并相互链接。验收文档记录已验/待验及真实失败；execution-map 同步执行状态、验收汇总和未验文档，是仓库执行与验收视图的真相源。出现汇总/明细不一致时按实际证据核对修正，不用草稿旧状态或旧汇总覆盖失败。启动资格由当前任务状态、依赖交付和明确前置决定。

## Plan 对自动验收的覆盖

Spec 定义成果、边界及通过条件，任务专属 acceptance 文档维护具体自动/人工行为与实时结果，Plan 将自动验收落实为执行安排。Plan 不能只链接验收文档或只列本次文档静态检查；其“测试计划”须覆盖本任务范围内全部自动验收项，可按明确的 ID 范围合并场景，但每项都能定位执行方式、环境、命令、时点、通过条件与证据登记位置。必要回归测试另标，不把所有测试都算作产品验收。

缺脚本、驱动、原生构建或环境能力时，在实施步骤中规划最小补齐工作，或明确已有前置任务与交接。草稿可标待定；纳入执行前明确验证方式、命令参数及能力补齐安排。允许本任务实施过程中新增场景，但实际执行验收前须完成实现/登记和环境准备，不把规划中的入口说成已存在、以零匹配/skip/编译或文档检查冒充通过。

Plan 包含执行自动验收、向专属 acceptance 登记实际构建/结果/证据、同步 execution-map 汇总的交付步骤。验收结果不回写为 Plan 的实时状态表；已交付结果保持原基线，延后任务不因补写测试计划被启用。人工项另写参与人/窗口、截止阶段及实际阻塞范围，少量允许后置的项不串成默认等待步骤，关键先验门槛和真实失败仍阻塞。

建议测试计划表使用：验收项 ID/专属链接、级别/组/场景、环境/命令、执行时点、通过条件、证据及结果登记位置。独立自动验收 Task 同样适用；不扩大为默认 Full、全部 live 或跨任务共用验收文档。

## 任务身份与执行授权

| 阶段 | Task ID | 执行含义 |
| --- | --- | --- |
| 目标讨论 | 可先无编号 | 不派发 |
| 已编号草稿 | 共享计数器分配唯一 ID | 可完善 Spec/Plan，不因编号自动派发 |
| 用户确认纳入执行 | 沿用原 ID | 写入 execution-map；前置满足者待执行，其余等待明确依赖 |
| 启动执行 | 同一 ID、一个实现 PR | 固定 Spec/Plan commit/路径，记录聊天/worktree 与执行起点 |

Task ID 永不复用；取消或放弃候选保留身份记录。用户确认纳入规划确定任务范围；实际启动、发送提示、提 PR、复审修复、评论、合并与定期续跑的授权按本聊天用户指令及明确调用的技能核对。仅编辑文件或讨论技能不启动任务。

## 规划步骤

```text
先读 RoadmapGuide 与必需文档，选择 drafts/ 草稿
  → 拆分独立任务、分配 ID，准备 Spec/Plan 和专属验收文档
  → 用户确认范围与依赖，纳入 execution-map
  → runner 检查状态、前置和授权，固定文档版本，创建 Codex 聊天/worktree
  → 实现、自查提 PR、独立复审修复、必要验证、核验真实合并
  → 同步 acceptance 与 execution-map，移除已完成草稿条目，按依赖继续
```

规划成熟度与前置交付分别判断：后继规格已稳定时可以提前纳入执行，前置尚未交付则标记等待；编号、接口草案或原型完成不能代替真实前置交付。

每项候选写清：产品成果与主要模块、消费/修改的契约和受影响消费者、共同语义/代码/资源、修改所有者、可固定/开工/合入条件、最小通过条件。对实际有交接或共享影响的任务说明关系，不构造无意义的全排列矩阵。关键接口或前置尚未稳定时留草稿；没有独立成果和通过条件时不为增加并行数量强拆任务。

人工和自动验收策略在批量排期前记录：批次通用审阅/授权统一说明，额外人工需求逐任务标出；提前准备人、环境和窗口，纯人工阶段签收不作为自主执行队列中的等待任务。

### 规划提示词（建议）

> 先读 RoadmapGuide 与必需文档，明确本轮 drafts/ 草稿。拆分候选任务时同步规划最小必要验收，区分自动和人工行为，并在草稿链接 SteerlineFlow/testing/acceptance/ 的任务专属文档；一个任务可有多份文档，一份文档只归属一个任务，未定步骤、环境和参与窗口写待定。请主动考虑是否需要独立的阶段签收、体验确认或跨模块验收活动，有需要时记录范围、通过条件、参与窗口及实际阻塞范围并链接其独立文档。独立活动不强制串成执行路径；人工为主的活动不占执行任务号、不入 DAG，少量人工尽量后置。没有实际需要时不为凑清单新增活动或扩大验证。草稿不维护实时执行/验收状态，纳入执行及实际安排后按 execution-map 和 acceptance 核对事实。

纳入执行前，每个任务应有唯一 ID/名称、完整独立 Spec/Plan 与专属验收安排，保持一个任务、一份 Spec/Plan、一个实现 PR。启动时使用已提交且执行工作区可读取的确定文档版本，将 commit/路径记录在仓库外 run 状态；代码执行起点另核对最新默认主干。规格变更需协调原执行者和重新核验受影响成果，不静默切换执行依据。

## 正式执行与同步

execution-map的“待人工验收”索引只列实现任务已结束，或所需任务已完整纳入执行规划而仍待人工验收的具体事项。完整排入不等于可立即验收，需在安排栏标明待哪些交付/准备条件及人工窗口。开发范围未完整排入的未来节点只在草稿/acceptance规划，不进入该索引；某任务自身已完整排入的人工项可单列，不代表整阶段已排入。自动补验单独链接，不混为人工待验；真实自动失败或关键前置未满足仍按实际阻塞处理。

execution-map只收录用户确认的任务，记录完整依赖和必要的共享合入顺序。任务状态使用待执行、等待前置、执行中、待复审/合并、实现完成、阻塞或取消，并链接实际 PR/结果；验收状态单独汇总，不能把实现完成写成全部验收通过。

每次启动/恢复核对当前清单、run 状态、原聊天/worktree、实际 PR 和验收证据。前置实现完成、必要验证通过且成果已进入最新默认主干后，才能启动后继；明确先验的人工门槛也须完成。少量允许后置的人工项保留待验，继续无关后续任务。

清单为空、缺固定 Spec/Plan、前置未知或记录矛盾时不派发，也不从草稿、验收导航或旧 run 回填。已有动作先对账；清单删行不自动停止 worker，未知外部结果沿原请求核实。

经实现、自查、独立复审修复、必要自动验证和真实 PR 合并核验，再同步 acceptance 与 execution-map 后，记为本开发流程的实现完成。PR 合并本身不代表验收全部通过；run 中已合并记录也不能替代清单及验收同步。已完成任务可移出当前任务表，保留 PR/交付摘要和所有待验链接。

## 编号与静态检查

数字由仓库共享计数器原子分配，首次使用先 init，既有编号不补洞或重发。同仓 worktree 共用 refs/steerline/roadmap-task-ids，独立 clone 不共享仲裁；未知创建结果仍沿原 ID/请求核对。

```text
python scripts/roadmap_task_id.py init
python scripts/roadmap_task_id.py reserve "任务名称"
python scripts/roadmap_task_id.py check
python scripts/check_doc_links.py
git diff --check
```

reserve 只分配唯一身份并写入 task-ids/<ID>.json。用户确认纳入执行后沿用 ID；名称修正用 rename 并同步文档。编号脚本不创建 Codex 聊天或外部 Task。

check 分别检查草稿与正式表的身份和导航；草稿允许缺 Spec/Plan，正式条目须完整独立。静态检查不证明实际实现、依赖交付或产品验收通过。

## 持续维护

execution-map保持当前任务表、推进顺序、待验索引和交付摘要；通用规则归本指南，维护结果归 acceptance，设计理由归草稿。启动文档版本、原会话和审核动作的详细恢复证据放仓库外 run 状态。

草稿无需实时同步；执行完成后移除已完成条目。任务依赖、范围和顺序变化先核对用户授权，已经在途的执行保持原身份对账。实际模块/契约/测试归属变化同步并行开发指南。

实现 Plan 按项目规则写最小必要测试计划，包含级别、组/场景、环境、命令、时点、通过条件及 acceptance 记录定位。纯文档、导航和规划入口修改只做必要的静态/工具检查，不启动产品或模型验收。acceptance 只提交计划/明细与最小结果摘要，原始运行产物留在临时目录；历史路径、commit、摘要和回执通过固定 Git 快照追溯。
