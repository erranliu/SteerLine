# Spec：worker 停服恢复与手动继续

当前恢复行为由[最终回复与原会话恢复精简](../archive/spec/completed/product-simplification-04-conversation-recovery.spec.md)收窄：只恢复原 session，取消 new_session 与无原会话的人工新建路径。本文其他原请求/身份/停止边界保留。

目标：`WORKER-SERVICE-RECOVERY`。状态：实现候选；本机 local Codex 闭环与 Orca fake 定向验证已通过，Orca 新 agent 的安全重建仍缺真机能力证据。配套 [Plan](../plans/worker-service-recovery.plan.md)及[验证记录](../testing/acceptance/worker-service-recovery.md)。日期：2026-09-30。实现基线：`origin/main` 的 `472d61e`（含 #144、#148、#149）；不创建或绑定生产 Task。

## 1. 目标与替代范围

SteerLine 服务重开后核对已有 worker 的真实状态，恢复观察和结果对账；新的执行输入由用户手动触发。本地 Codex 不再要求服务关闭后保持运行，也不要求 worker 脱离 Windows Job Object。服务停止后 worker 继续运行或已经终止，都必须得到准确处理。

本任务覆盖 local Codex app-server 与 Orca 两条 worker 路径。Orca native 和已有 supervised 适配共同遵守恢复规则；本任务不据此解除 supervised 的既有能力限制。平台协议层提供执行事实，worker 层解释事实，workerflow 与 Service 决定业务状态和人工继续权限；不把停服恢复业务加入 `codexapp` 传输客户端或 Orca CLI 通用封装。

本 Spec 实现交付后，在下列边界优先于既有规定：

| 既有规定 | 本次替代 |
| --- | --- |
| [本地 app-server Spec](local-codex-app-server.spec.md) §2、§5、验收 A/B | 移除活动 turn 与请求必须跨停服存活的要求；原 worker 存活时仍精确重接，终止时等待人工继续 |
| [worker-flow Spec](../archive/spec/completed/worker-flow.spec.md) §4、§5、§8 | 普通反馈继续原会话；本次新增的显式停服恢复可建立新 worker 运行记录，原生会话能核实则复用，失效时只能由用户明确选择新会话 |
| [Orca native Spec](../archive/spec/retired/worker-flow-orca-native.spec.md) 的恢复及会话替换边界 | 保留原 terminal/Dispatch 的重接和退出后结果结算；确认旧 worker 终止后允许经过本 Spec 人工授权的恢复，不能把新 terminal/incarnation 冒充原会话 |
| [架构规划约束](../Roadmap/architecture-constraints.md)中的单会话描述 | 同一任务保留一条权威活动 WorkflowRun/Execution；显式恢复可顺序建立新 worker 代次，任何时刻不能产生两个未排除活动可能性的 worker |

复用 Task 领取、固定任务契约、五个业务主阶段、统一 Decision/Command/Operation、会话记录及真实 PR 合并交付。停服不释放领取，不重建工作区，不 reset 已有代码或提交，不因进程退出认定任务完成。不实现 SCM、专用 broker、宿主权限修改、跨后端切换或旧格式迁移。

## 2. 产品行为

“重开后不自动继续”指服务不会因为重启而发送新的 prompt、答案、原生 reply/send、turn 或 Dispatch，也不会补建执行资源以恢复工作。适用于重启前已保存但未送达的用户输入及未完成的首次启动；不能由自动派发模式、启动恢复或定时轮询绕过。

允许自动完成的工作是核实身份、补读输出、接回观察、确认原操作回执和已完成结果、查询关联 PR，并按现有交付事务结算已核实的合并。必要的短命历史读取辅助进程只用于读取持久化证据，不恢复执行或发送轮次。已经存活并运行的 worker 可能在服务离线期间继续工作；接回观察不会暂停它，也不等于服务发起了一次“继续”。界面如实显示“原 worker 仍在运行”，不得显示为已暂停。

这个人工门槛属于重启前的受影响 Execution，不改变其他任务的既有派发资格。原任务仍保持领取和实际资源占用；同一任务不能通过再次领取绕过恢复。Task 已关闭/丢弃、PR 已真实合并时，终态规则优先。

| 恢复时核实的事实 | 上层处理及允许操作 |
| --- | --- |
| 原 worker 存活，原轮次仍运行 | 接回原身份观察，不发送新的执行输入；持续接收结果 |
| 原 worker 存活，原问题仍有效 | 展示原问题；用户重开后的明确提交可回复原请求；旧的未送达答案仅作为保留输入 |
| 原轮次已有可信完成结果，worker 可存活或退出 | 对账并结算该结果；需要后续工作时等待用户反馈，不重复执行原轮次 |
| 原 worker 已确认终止，原轮次无成功完成证据 | 进入统一待决策，原因是“执行已中断”；保留现场，提供满足条件的手动继续方式 |
| 进程/terminal 身份、活动状态或外部操作结果无法核实 | 进入统一待决策，显示“状态未核实”及原因；可继续只读对账，不允许启动替代 worker |

“中断”“未核实”和继续方式是 Execution/Decision 的事实与操作可用性，不新增第六个 WorkflowRun 主阶段。进程消失只证明该进程已退出，不能补造原生 `turn/completed`、`worker_done` 或成功结果。若旧 worker 产生的子进程仍可能修改工作区，必须先排除并发执行风险，才能允许新 worker 写入。

## 3. 停服与启动恢复

正常停服先停止接受新的执行输入，保存已知身份、未完成操作和需要手动继续的事实，再通过 worker 适配层完成有界退出处理。local Codex 采用服务管理的子进程：能安全中断原轮次时先请求中断并保存可取得的事件，然后关闭拥有的进程及子进程。只操作身份已核实且由本次执行拥有的资源；确认退出后才记录退出事实。停服超时或强制退出时保留未知状态，不能因服务已停止而声称 worker 已结束。

Orca 正常停服结束本地观察，继续沿用其平台资源生命周期；不新增不受支持的远端取消，也不关闭用户接管的 terminal。恢复必须兼容 agent/terminal/宿主在停服期间结束的情况。

启动时，在任何恢复发送或决策投递之前，为既有未结算 Execution 建立人工继续门槛，并进行一轮有界核验。即使上次来不及保存停服标记，也必须根据前一服务实例留下的未结算记录建立门槛。单个目标不可达不阻塞其他目标的核验及服务就绪。

定时恢复与启动恢复采用相同规则。门槛持久化，重复重启不能清除它；进程仍活着、原结果已完成等新证据只更新真实状态。用户在本次恢复状态下提交的新命令才授权后续执行；服务再次退出且该命令尚未执行时，下次重开仍需用户确认。

## 4. 手动继续与身份

用户通过现有统一待决策入口继续，保留自由文字、选项加备注与完整历史输入。查询结果同时给出继续是否可用、原因及将使用原会话还是新会话。终止后的继续有以下条件：

1. 原 worker 与其可能继续写入的活动已确认结束；原轮次结果和发送/发布操作已经对账到足以安全继续的状态。只知道连接断开、terminal 不在列表或请求超时不满足条件。
2. 核实原 Task、WorkflowRun、Execution、冻结配置、worktree 与分支；保留当前 HEAD、未提交文件和已有 PR。恢复输入要求先检查当前成果再继续未完成工作，不能直接重放旧工具调用。
3. 原生会话可恢复时使用其精确身份；local Codex 在新 app-server 中核验原 thread 与工作区后开启新 turn。原生会话不可恢复时，仅展示明确的“新会话继续”动作，说明上下文来自持久化历史及当前文件；用户选择后才可建立新会话。若平台不能安全创建/绑定该资源，继续保持不可执行并说明原因。

重用存活 worker 时保留原运行身份。需要重建 worker 进程或 agent 时，在同一 Execution 下创建新的 worker Attempt，旧 Attempt 结束并保留进程、会话、轮次、操作和事件记录。新 Attempt 保存自己的进程/terminal/incarnation、代次和会话绑定；同一原生 thread 可跨 Attempt 复用。当前 Attempt 指针由 Service 原子推进，旧不可变 binding 不被覆盖。正常完成一轮后向仍存活的原 worker 反馈，不因换 turn 而创建 Attempt。

人工继续命令绑定 Task/Execution、来源 Attempt、恢复版本、目标继续方式和完整输入。相同命令重交只返回已有事实；连续点击、过期界面、另一服务实例的输入不得创建多个 worker。创建/恢复操作先保存意图，新身份落盘后才能发送新轮次。创建响应丢失沿原意图核实唯一资源；不能用第二次点击无条件补建。

恢复过程中再次停服：若新 worker 已实际启动，重开后核验并接回观察；若尚未开始执行，只保存准备结果并等待新的人工授权。原命令结果未知时仍沿原操作对账，人工点击不代表可以忽略重复执行风险。旧代次的迟到事件可补充旧操作结果，但不能推进当前 Attempt、投递给新会话或重开终态任务。

## 5. 问答与未确认操作

业务 Decision、用户答案和原生请求的有效性分别记录。待答进程退出后，原 JSON-RPC request/call ID 不再是可投递目标；保留旧问题、答案、已知投递证据和失效原因。不能把旧答案标记为已被原请求接受，也不能自动改投新 turn。

原请求仍有效时，用户重开后的明确提交可授权原请求回复。旧答案已保存但没有发送意图时，界面可供确认后提交；通过关联旧答案的恢复 Decision/新 Command 记录本次授权，不覆盖旧答案或绕过同一 Decision 的 first-wins 规则。旧回复已尝试且结果不明时，先核对原工具结果或 Orca 消息回执。无法确认的副作用保持未知，不能再次发送。已确认接受的答案不会要求用户重复回答。

原请求已失效且满足继续条件时，创建恢复 Decision，关联并保留旧 Decision。显示准备带入新轮次的问题、答案和用户补充，用户明确确认后作为新的恢复输入发送；旧请求的结果记录不被改写。原轮次成功完成、Task 终态或较新轮次已启动，都会使过期恢复命令失效。

## 6. 两条 worker 路径与模块边界

| 层 | 本次职责 |
| --- | --- |
| `codexapp`、Orca 通用调用封装 | 保持原生 RPC/CLI、DTO 和传输错误语义；不读取业务恢复状态、不决定人工继续 |
| `codexworker`、`orcaworker` 及其 worker 适配接线 | 核实 liveness、身份、原生轮次/Dispatch 结果、待答请求、可恢复会话和子进程/平台资源；产生平台事实并执行已授权动作 |
| `workerflow` | 以平台事实及已持久化的人工授权判断观察、结算、待决策及继续资格；不调用平台或写数据库 |
| Service、Command/Query、持久化和 UI | 按固定执行上下文路由，单写提交门槛、Decision、Attempt、Operation 和当前指针；展示并受理手动继续 |

local Codex worker 启动不再调用必须保证 Job 外生命周期的启动入口，能力预检改为本机进程可启动、可识别、协议/历史可用。Windows 允许 worker 在 Job 内；保留真实 PID、创建时间、可执行文件身份及受控清理。确实要求独立服务生命周期的 `startDetachedProcess` 及其脱离核验不作放宽，不把该错误整体吞掉。新语义还须适用于已有 Linux 本地实现。

Orca 使用原 runtime/worktree/terminal/incarnation/Run/Task/Dispatch 与消息回执核验。沿用 `f9de3f6` 的终端对账和 `6f78a15` 中退出后结果 relay/settlement 修复；已有可信 `worker_done` 不因 terminal 退出而丢失。恢复扫描禁止通过 `prepare*`、`startNativeOrcaTurn`、Dispatch/reply/send 或结果补报发起尚未执行的动作；必要的外部写操作须等待手动继续授权，已存在的回执仍可读取并结算。不得借改 worker 恢复重新耦合平台传输与 worker-flow。

## 7. 持久格式与不确定性

SQLite 仍是唯一业务权威。人工继续门槛及其版本属于 Execution 的执行控制事实；原因、输入及确认属于既有 Decision/Command；外部调用进度属于 Operation；运行身份属于 Attempt 及不可变执行 binding。只扩展必要字段，查询投影不能形成第二套可写状态。

如新字段或多 Attempt 绑定改变格式，统一提升受影响的持久版本，在有副作用之前拒绝不支持的旧状态并保留现场，不做迁移、双写或旧版回退。存活/终止两种恢复属于新格式内的正式行为，不是旧版本兼容。

不能把“手动继续”作为清除未知 Operation 的通用授权。PR 创建/推送、平台发送和 worker 启动等已尝试动作先核实；无可靠证据时保留不可继续的理由。PR/DAG 终态和资源清理沿用已有身份与事务规则。
