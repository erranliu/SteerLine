# 重构与维护并发与运行环境选择 Spec

2026-11-12 · 已实现。真实并发已观察，真实交付整链未通过。[Plan](../plans/refactoring-maintenance-concurrency.plan.md) · [专属验收](../testing/acceptance/refactoring-maintenance-concurrency.md)

## 1. 成果与范围

用户从项目「重构与维护」选择已就绪的运行环境并提交维护行动。行动由项目服务后台推进，用户可以继续创建、查看和操作其他行动。每个项目默认有 3 个维护行动推进名额，超过名额的行动进入队列。排队时间计入总历时，从时间预算中扣除的只有实际推进区间。

本期替代[最小闭环 Spec](refactoring-maintenance.spec.md)中的单项目在途唯一、单当前卡片和执行配置优先选择规则。每条行动沿用[SteerAgent 交付和独立 PR 合入评审](refactoring-agent-delivery.spec.md)的首轮固定只读目录、结构化人工答复、Runner Final 核验和独立合入评审。首版可选组合沿用已验证的本机 Codex。其他运行环境在具备并验证完整维护组合后接入。首版名额使用固定默认值，不增设并发设置入口。

## 2. 环境选择与新建侧栏

1. 页面标题区始终提供「新建维护行动」。桌面从右侧打开表单，窄屏使用全屏表单。打开时焦点进入表单，键盘可完成选择、预览和提交。关闭后焦点回到触发按钮。成功提交后进入新行动详情。关闭未提交的表单可在本次页面访问中重新打开草稿，切换项目或服务实例时清空草稿。
2. 表单先选「运行环境」。按运行机分组，环境项显示执行链路、Agent 以及必要的区分信息。身份使用项目运行环境的原键。可选项须同时满足当前项目环境资格已就绪及维护组合支持条件。一个环境由多个方案共享时只列一次。随后展示该环境下可用于维护的执行方案及其名称、模型。单一方案直接带入，多方案时仅预选该环境下可用的项目默认方案，否则要求明确选择。初次打开时仅在项目默认方案符合条件时预选它及所属环境。其余情况环境留空。换环境时清除旧方案和资格错误，按新环境重新选择。
3. 区分「查询中」「查询失败」「没有可用环境」「已就绪但当前维护组合不支持」。无可选项时展示具体原因并链接「运行环境」，能确定方案时定位到该方案。项目基线单独展示分支、完整提交的可查看值和就绪状态。基线阻断链接「项目维护」。资格失效、观察未知、离线以及开发者关闭环境门禁均不授予新建资格。普通刷新保留用户选择和最近成功观察。查询失败或离线时把旧结果标为「上次已知，当前待核实」，禁用提交。所选环境或方案变为不可用时保留原值与原因。方案内容、环境资格版本或基线在表单打开后变化时，展示更新后的事实，由用户确认后再提交。
4. 保留单选维护方向、完整方向提示词预览、补充要求、三种策略与预算输入。默认「谨慎决策」和 1 轮，至少填写一项有效预算。确认区显示选定环境、方案、目标分支和起始提交。容量已满时说明提交后排队，「开始维护」仍可用。
5. 提交使用现有命令信封。服务重新核实用户所见的环境键、当前资格版本、所选方案版本、方向版本、远端 HEAD 和项目基线，以及原有 Runner、模型、材料、预算和发布准入。拒绝时保留草稿、刷新相关资格，并在表单内显示原因。原命令、行动 ID、初始排队状态和冻结事实原子落盘后返回回执。同 ID 同正文得到原行动，异正文冲突。结果未知沿原请求核对，允许关闭侧栏并查看其他行动。回到同一项目和实例重开原草稿时仍显示待核实，阻止重复提交。回执在原侧栏仍打开时收起侧栏并进入新详情。用户已关闭侧栏或切换行动时，刷新原项目的列表并在操作反馈提供「查看行动」，由用户决定是否跳转。迟到回执只结清原提交的草稿。

环境及方案关系沿[运行环境设计](runtime-environment-ui.spec.md)与现有资格来源。浏览器消费后端结构化事实，不自行计算环境键、根据诊断文本猜资格或选择替代方案。

## 3. 后台推进与预算

| 场景 | 产品规则 |
| --- | --- |
| 名额与排队 | 3 个名额按项目独立计算。受理只入队，调度按本次入队时间和稳定身份为可推进的行动原子分配空位。持有名额的行动可以跨多轮推进；轮次结束本身不释放名额。重新入队的答复、停止后收尾和冲突续作排在已经入队的行动之后。核实后无可继续动作的行动释放名额，单条观察异常只占本行动名额。 |
| 首次派发资格 | 接受时冻结远端 HEAD、环境身份、方案、派生配置、材料、方向、策略和预算。行动排队期间，当前环境引用的显式失效、重新检测或资格依据变化可以阻断首次派发。在将首个 Runner 请求持久化为可发送时复核当前资格，和当前引用的失效/重新检测按同一项目事务定序。已保存的待发准备记录及等待共享容量期间的预检均未取得派发授权。 |
| 排队期间的变化 | 远端目标分支正常前进且当前资格覆盖原冻结提交的环境依据时，仍从原提交开始。冻结方案被移除或有效配置改变、环境已失效或新依据与冻结提交不相容时，行动进入「已阻断」，释放名额并显示原因和环境入口。恢复环境后由用户新建行动。暂时无法核实时，保留原队列顺序并按原选择有界复查，其他可推进的行动可以先行。复查期间不占名额、不计时间预算。复查耗尽仍未知时以「资格无法核实」结束排队并显示「已阻断」。 |
| 已取得首次派发授权 | 首个可发送意图合法落盘后，后续环境失效影响尚未获得该授权的行动。该行动沿原冻结授权推进，包括答复、收尾与冲突续作，仍须满足各操作原有的 Runner、工作区和发布准入。实际执行条件不满足时记录具体阻断。观察、停止与资源结算始终绑定原身份。 |
| 行动隔离 | 同项目可在同一环境并行。每条行动有独立关联、预算、轮次、问题、Runner 请求、worktree、分支和报告。有有效改动时各自交付一个 PR。行动内同一时间最多有一个未结算的 Runner 操作。可写后继只接管原行动最近持有者的 worktree。重叠范围通过既有主线变化与冲突审计处理。 |
| 共享容量 | 只读决策继续通过现有应用 home 级共享生成队列，其他派发受实际 Runner 准入约束。已取得项目名额的行动等待共享或 Runner 容量时仍占项目名额，显示具体等待原因。停掉尚未发送的操作时同时撤销其共享队列登记。已发送或结果未知的操作在原资源核实结算后才释放相应占位。 |
| 时间预算 | 受理入队时预算用时为零。开始实际准备、执行、验证或审计时开始累计，进入已核实的项目/共享/Runner 容量等待或待答复时暂停，恢复实际推进时从累计值继续。只根据本地调度事实或原 Runner 的结构化等待事实暂停。提交未知或观察失败沿用最后已知的计时状态。记录区间边界以便对账，同一时间段最多累计一次。立即停止自撤销后继意图时暂停，离线按原生命周期边界截断。预算耗尽只禁止开启新轮次，收尾仍记录实际消耗。 |
| 总历时 | 从首次受理算到最近一次终态，推进中算到当前观察时刻，包含排队、待答复及离线。重新入队或开启冲突续作时，先前结束与本次续作之间的间隔只计入总历时。列表和详情同时使用服务的预算用时与总历时口径。 |
| 等待、停止和收尾 | 待答复的名额在原操作结算后释放。答复绑定原问题和版本，保存后重新排队。已经执行过的排队行动可「结束并交付」，仅调整该行动的后续工作，保留本次排队顺序。首次尚未派发的行动只提供「立即停止」。停止撤销当前行动的待发操作，保留已有成果。已发送、结果未知或未完成封存/原资源结算的操作继续占名额，直到原操作结算。 |
| 重启和关闭 | 关闭页面、切换项目或刷新不会停止后台行动。服务关闭或重启逐条沿原生命周期撤销未投递意图、核对已投递请求和完成停止结算。只排队且从未提交的行动按已停止处理。未知请求不重发，原成果仅经明确的「结束并交付」继续。 |

「项目名额」「有待处理记录」「原 Runner 尚未结算」分别按各自事实判断。已交付行动请求冲突续作时核验原开放 PR，排队后派发前再核实 PR 和原写者资格。原 PR 在等待期间关闭或合并时结束续作，保留原交付、报告及诊断并释放名额。符合条件时沿该行动最新工作区更新同一 PR 及报告。命令、观察、停止和恢复遵循 [Runner 调用生命周期](../../docs/product-design/runner-lifecycle.md)，变动集中在多行动的调度与容量结算。

## 4. 行动列表、详情与活动中心

| 位置 | 交互 |
| --- | --- |
| 标题与计数 | 展示「重构与维护」、新建按钮和「推进名额 X / 3」。列表分「进行中」「待答复」「历史」三组。进行中覆盖排队、准备、执行、收尾、停止待结算及结果待核实。待答复独立展示。已停止、已交付和已阻断进入历史。计数来自服务。 |
| 列表 | 每行显示方向、运行环境、阶段、轮次、最近进展及时间。相同方向由时间与行动短 ID 区分。进行中和待答复完整列出。待答复按问题出现时间排列。进行中先展示已获名额的行动，按最近进展倒序排列，再展示未获名额的行动，按本次入队顺序排列。历史按最近结束时间倒序分页，同时间以行动 ID 稳定排序。轮询和翻页按行动 ID 合并，同一行动只出现一次。完成或续作后行动换组，所选详情和已展开的历史范围保持。空状态引导新建，加载或查询失败明确标出。 |
| 详情 | 桌面列表与详情并排，窄屏点列表进入详情，提供「返回行动列表」并恢复原列表位置。`action=<id>` 是当前选择的来源，支持浏览器前进、后退和直接打开历史深链。不合法、已不存在或不属于本项目时保留明确提示及返回入口。桌面首次进入且 URL 没有行动 ID 时，优先选第一条待答复、再取第一条进行中、再取最近历史。轮询、视口切换和返回列表不触发重新默认选择。只轮询列表和选中的详情。 |
| 内容与操作 | 详情头部展示阶段、环境和方案快照、起始分支及提交、轮次、预算消耗和当前工作。按后端允许动作显示「结束并交付」「立即停止」「答复并继续」「处理冲突并重新评审」和「重新评审」。轮次和原 Runner 反馈可展开，交付区展示原 PR、独立合入评审和历史版本。排队或停止待结算显示具体原因。未知费用仍标待采集或未核实。 |
| 操作隔离 | 停止、交付、答复与续作绑定行动 ID、原版本及适用的原问题 ID。按钮等待、错误和答复草稿按项目/实例及行动或原问题隔离。刷新若发现问题已更换，旧答复不能提交到新题。切换行动时新详情独立加载，迟到数据和回执只更新原行动。列表、详情和资格查询独立报错，失败或离线时标记上次已知事实。列表或资格查询失败时，仍可使用已核实的在线详情控制原行动。详情当前待核实时禁用该行动的控制。 |
| 活动中心 | 沿现有维护来源每条行动展示一条活动，标题显示维护方向及环境，状态与页面同源。点活动进入对应行动详情。每条辅助 Run 留在对应维护行动的轮次记录中。页面轮询、刷新、深链和返回均为只读。 |

## 5. 通过条件

| ID | 可核验结果 |
| --- | --- |
| RMC-A01 | 环境按运行机和原键展示，覆盖默认方案、多方案、无可用环境、门禁关闭和查询失败。陈旧表单保留草稿并要求确认。首个派发意图保存前后分别发生失效时，验证零派发和冻结授权两条路径。 |
| RMC-A02 | 同项目提交四条可用行动时前三条可重叠推进、第四条排队。结算释放后按序派发，同环境可并行，第二项目名额独立。可控时钟验证占位等待、排队、停止待结算和总历时，重复或迟到观察不改变已核实的累计结果。 |
| RMC-A03 | 等待人工、停止、拒绝、未知提交和观察超时各有独立效果。对账、恢复、排空和迟到回执绑定原行动，其他行动可推进且无重复发送。冲突续作排队期间原 PR 关闭或合并时零派发。 |
| RMC-A04 | 宽窄屏的侧栏、列表、详情、前进后退和活动深链均可操作。跨页换组、查询失败、轮询、切换项目、离线和晚到回执保持正确的选择、草稿、焦点和操作资格。浏览和刷新零执行命令。 |
| RMC-A05 | 固定 Runner、本机 Codex 和独立远端测试分支上，同项目、同环境至少两条实际 Run 的执行区间重叠，均产生各自已核验的 worktree、分支、PR、合入评审与费用归属。交付后冲突续作更新原 PR，在同一行动登记对应新 head/base 的第二份评审，PR 正文保持原样，所有测试资源结算。 |

完整通过以[专属验收](../testing/acceptance/refactoring-maintenance-concurrency.md)的自动结果为准。人工走查单独记录。
