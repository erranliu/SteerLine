# Spec / Plan 生成规范

本规范用于 SteerLine 产品的 Roadmap 草稿转正流程。规划工作台的对话只维护 Roadmap 草稿及其任务约束；正式 Spec / Plan 由固定转正流程生成、审阅和发布。它不替代仓库开发中的 AGENTS.md 或用户直接授权的普通开发流程。

## 先固定输入，再设计

- 读取本规范全文，并记录实际读取的路径与版本。文件缺失或读取失败时停止生成。
- 固定 Roadmap Markdown / JSON、待转正任务、任务编号、代码基线及规范版本。变化后的输入通过明确的重新生成操作采用，不悄悄替换已有结果。
- 先列出任务目标、行为边界、约束、待澄清问题和验收要求。有关键矛盾或未决范围时先补充草稿，不用推测填成正式契约。

## 警惕过度设计

- 默认选择满足当前确认需求的简洁设计，不为假设中的未来需求增加框架、扩展层或配置组合。
- 不为凑并行数量拆分任务；每个任务应有独立成果、清晰职责和最小通过条件。
- 未发布项目默认不为旧数据、配置或协议新增兼容、迁移、双写或回退路径，除非任务明确要求。

## 先查现有代码，再做整合与整体规划

- 新功能设计前阅读相关现有代码、调用入口、状态模型、契约、测试及其实际消费者；记录查看的位置和结论。
- 优先复用或调整现有实现。说明保留、整合、替换及删除的部分，避免在旁边新增一套重复能力。
- 多个相关任务先形成整体整合安排，再生成各任务 Spec / Plan。明确共用语义、修改所有者、依赖及真实交接条件，避免多个任务分别重建相同模块。

## 执行链路与桥接必须显式且必要

- 不隐式增加第二套执行链路、独立状态来源或不同的业务准入规则。
- 确实需要多路径时，明确各路径的职责、选择条件、统一的业务事实与维护代价；不能用实现方便代替必要性。
- 不引入没有必要的桥接、适配、转发、包装或重复状态。确需新增时写清现有入口为何无法承担、最小职责以及消费者。
- 不以临时演示数据或 Agent 自述宣称真实接口、运行能力、权限、测试或交付事实已经存在。

## Spec 和 Plan 分工

- Spec 明确目标、当前行为与预期行为、范围、非目标、契约、状态与交付要求，以及验收项和通过条件。
- Plan 明确代码整合步骤、涉及位置、依赖与前置、必要能力补齐、测试和交付安排。不得另立与 Spec 矛盾的第二套行为。
- 自动与人工验收分别安排；人工项标明参与窗口及真实阻塞范围。验收要求和实时结果分开，结果不回写为 Plan 的状态表。
- Plan 必须包含最小必要的测试计划：验收项 ID / 专属文档、长期测试级别与组 / 场景、环境、命令、执行时点、通过条件及证据登记位置。
- 自动验收全部映射到可执行安排；缺驱动、入口或环境能力时规划最小补齐步骤或明确前置。不默认扩大到 Full、全部 live 或无关回归。
- 新增或扩展长期 L1–L4 流程时明确稳定入口与登记安排；临时开发测试不替代长期测试证据。

## 审阅与发布

- 审阅时展示现有代码调查、复用 / 整合方式、执行链路变化、桥接必要性、跨任务安排及测试验收覆盖。
- 生成正文可在转正流程内受控修改；修改后重新核对规范、依赖及 Spec / Plan 一致性，取消此前确认。
- 审阅确认后，正式文档随 Roadmap / JSON / execution-map 文档 PR 发布。核实合入主分支后，才以固定文档版本创建正式 DAG。
- 规范可以维护并随 Git 版本管理。已生成操作保留所用内容快照；更新规范不自动覆盖正在审阅或已发布的文档。
