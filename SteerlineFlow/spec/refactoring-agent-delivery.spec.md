# 重构与维护的 SteerAgent 决策与 PR 合入评审

## 1. 目标和边界

同一维护行动记录保存冻结的方向、策略、工作区身份、各轮执行与人工答复、PR 和评审版本。SteerLine 推进状态、核验平台事实及预算；SteerAgent 负责决策和评审；Runner 负责受管工作区中的代码执行与发布。人决定是否合入。

- 首轮决策在启动提交的固定只读目录执行。后续决策只读取行动上下文。SteerLine 在请求正文中发送适用的决策指令。部署后可添加自定义维护方向。SteerAgent 生成的执行指令写明改动、保留的行为和验证。
- 可写执行复用公开 `execute/1`，直接交付原执行指令、固定回执格式和本次结构化事实。后继沿原受管 worktree，引用最新持有者。消费已停止 Run 的已验证成功 Final，核对原请求、Run、会话、轮次及行动和操作 ID，再严格解析最终 JSON。无效回执保留反馈，发布结果未知时禁止重发。已知原 PR 的冲突续作可以先对账原 PR 上的新提交。维护不要求 `result_file` 或 Runner 新能力。
- 预算耗尽后收尾，证据支持时也可提前收尾。需要人决定时保存结构化问题、已知事实、选项和推荐，暂停计时。有效答复恢复原阶段，过期、重复和迟到操作按[Runner 调用生命周期](../../docs/product-design/runner-lifecycle.md)沿原请求结算。

## 2. 阶段推进

| 阶段 | 结果与去向 |
| --- | --- |
| 首轮与选题 | execute 派发当前切片；ask 等待人工；finish 收尾；blocked 保存原因 |
| 实施、修复与本轮审计 | Runner 执行执行指令并返回 Final；SteerAgent 按本轮目标和反馈决定接受、修复或补证。接受须有与回执一致的干净工作区提交；预算允许时继续选题 |
| 收尾 | SteerLine 按状态派发固定的发布或冲突续作执行指令。有已接受成果时，核验平台 PR 身份、原受管分支及完整 head/base。没有已接受成果时直接保存结论 |
| PR 合入评审 | 根据固定 PR 差异、可取得的检查、冻结维护方向和用户要求给出合入建议。评审正文保存在行动记录 |
| 续作 | 人工请求解决冲突才重新执行代码。平台确认原 PR 的 head 已更新后才能结算续作；结果未核实可重查原 PR。待审 PR 的 head/base 或检查状态变化时保留旧评审并重新取证。可在冲突续作结算后显式重新评审 |

## 3. PR 合入评审

SteerLine 只读查询 PR，按核验的目标分支提交与 head 从绑定远端获取 Git 对象，以合并基点计算 PR 差异，忽略本地 Git 替换对象。执行 worktree 不参与取证。对 GitHub，检查汇总只采用匹配 head 的平台结果。无法取得差异时记录证据不足；检查未知时评审须说明局限。评审使用正式文件材料，既不附仓库快照，也不授予目录访问。完成时重查版本和检查状态，丢弃基于过期证据的在途评审；历史结果保留原证据。空闲时检查已交付的待审 PR，证据变化后在原行动只读重评。评审仅在 SteerLine 展示，无 PR 正文同步或合入操作。

评审给出建议合入、修改后再审或证据不足，说明收益、风险、检查及缺口，区分本次新增的结构债与已有问题，引用涉及的文件或边界并说明维护成本。无 PR 时仅保存维护结论。

## 4. 固定指令

[决策指令](../../internal/prompts/maintenance-decision.md)由共用规则和当前阶段的判断标准组成，选题时附适用策略。行动上下文和固定版本 PR 差异通过文件材料提供。
