# 重构与维护的 SteerAgent 决策与交付 Spec

整体方案已确认。实施和验证记录见 [Plan](../plans/refactoring-agent-delivery.plan.md) · [测试选择](../plans/refactoring-agent-delivery.tests.json) · [专属验收](../testing/acceptance/refactoring-agent-delivery.md)

本期在[重构与维护最小闭环](refactoring-maintenance.spec.md)上调整提示词、人工决策和交付流程。历史验收继续对应原版本。本期成果为在同一个维护行动中完成首轮只读调查、多轮证据驱动的决策、结构化人工答复，以及先核验 PR、再生成报告、再原样同步的交付。沿用现有单方向、执行配置、预算、停止、提前交付和冲突续作入口。

## 1. 阶段、权限与材料

| 阶段 | SteerAgent 输入与输出 | SteerLine 与 Runner 接线 |
| --- | --- | --- |
| 首轮调查 | 第一份一级正文、完整二级方向、选中的策略正文、用户补充要求和启动事实。只读访问固定在启动提交的工作目录，输出首条三级指令、人工问题、收尾建议或阻断 | SteerLine 固定完整启动 SHA 和首轮只读目录来源。目录内容在调用期间须对应固定提交。首条三级指令发出前，人工答复可恢复此阶段。若调查充分且无待处理成果，可直接生成无改动报告 |
| 后续决策与收尾 | 第二份一级正文、同一二级方向和策略正文、行动上下文。按当前阶段输出审计判断、后继三级指令、人工问题、收尾建议或阻断 | 首条三级指令发出后，审计、人工答复恢复、后续选题、收尾和冲突续作均使用上下文调用，省略仓库和工作目录访问授权 |
| 报告生成 | 第三份一级正文、同一二级方向和行动上下文，含所选策略名称及实际决策记录。输出报告正文和有 PR 时的同步指令，或指出缺失证据 | 以核验后的 PR 及完整 head/base 为依据。无可交付改动时，以已确认的结论为依据。报告阶段省略仓库和工作目录访问授权 |

启动时冻结三份一级正文、所选二级方向完整原文及选中的唯一一段策略正文。既有内置方向与安装级自定义方向继续作为二级方向，沿用现有策略选项及默认值。

### 行动上下文边界

原请求、封存结果、问题及答复保存在同一行动记录及其从属操作中。SteerLine 从原记录构造本次调用所需的有界上下文，通过正式文件材料传递。固定输入包括行动事实、预算快照、适用的版本事实和相关人工决定。后续决策携带当前操作的指令与关键反馈、未解决问题、相关的已接受成果摘要。报告携带与最终版本相符的关键差异、验证证据和覆盖全行动的轮次摘要。摘要保留原轮次或操作身份，以便回查。后继调用可使用新的只读会话。

沿用现有材料和结果文件限额。控制重复历史和大块差异的传递，优先保留当前决策所必需的证据。发现关键证据缺失或超限时，指出具体缺口，由 SteerAgent 请求有针对性的补证。相同缺口未取得新证据时停止重复补证，保存诊断。原始记录继续可查。

每次可写执行的业务提示词仅为 SteerAgent 生成的三级指令。固定短接线仅说明文件读取和结果回传协议。执行身份、提交、PR、报告原文等通过相应事实或数据字段交付。Runner 在原受管分支及 worktree 执行，后继引用最新已结算的持有者。SteerLine 负责新轮次准入；证据支持时可以提前收尾，预算耗尽后继续处理已有成果和交付。等待人工暂停行动计时，后续必要处理、报告和同步计入行动实际消耗。

维护可写请求启用 Runner 的必需结果文件初始化。Runner 在原准备期限内核验本轮文件和种子摘要后才派发。若初始化失败，SteerLine 在行动操作中保留原诊断，停止原 Run 并等待封存。确认未派发且已结算的发布可通过原行动继续收尾。

### 单一行动与阶段转换

维护行动是唯一业务记录，沿用现有 worker 的串行推进。SteerLine 根据阶段和已保存事实确定执行用途。SteerAgent 输出决定及三级指令，阶段转换、预算准入和原请求对账由后端负责。下表中的决策用途可共用现有阶段及操作记录，PR 已核验、报告已生成、同步待核实等页面状态从同一行动的事实投影。

| 当前用途 | 合法输出或事件 | 后继 |
| --- | --- | --- |
| 首轮调查 | `execute`、`finish`、`ask`、`blocked` | `execute` 经预算准入后发出首条实施指令；`finish` 有充分结论且确认没有可写执行或成果时直接进入无改动报告 |
| 后续选题 | `execute`、`finish`、`ask`、`blocked` | `execute` 经预算准入后开启一轮；`finish` 转收尾 |
| 成果审计 | `accept`、`execute`、`ask`、`blocked` | `accept` 由 SteerLine 按预算和收尾意图选择后续选题或收尾；`execute` 仅补证、修复或撤销当前成果，完成后回到审计 |
| 收尾与冲突续作 | `execute`、`ask`、`blocked` | `execute` 处理已有成果，发布或更新原 PR，或返回可核验的无改动结论；封存后进入核验。显式结束或预算耗尽时仍需核实可能已发出的原请求 |
| 核验与报告 | 核验成功或待核实；报告返回 `report` 或 `needs_evidence` | 核验成功才调用报告。无 PR 时保存报告即交付，有 PR 时保存正文和同步指令后进入同步；缺证进入报告补证 |
| 报告补证 | `execute`、`ask`、`blocked` | `execute` 仅取得指定版本所缺的证据。证据封存后回到核验与报告，不进入新轮次或发布 |
| 正文同步 | 原 PR 正文匹配、明确失败、结果未知或版本变化 | 正文与版本均匹配时交付；其余按 §4 恢复，保留原 PR 和报告 |
| 版本变化后的成果审计 | `accept`、`execute`、`finish`、`ask`、`blocked` | 复用成果审计调用。`accept` 表示证据覆盖新版本，转入报告；`execute` 仅补证或重验，随后复核；`finish` 表示需要处理原 PR 成果，须说明依据，再进入原 PR 收尾 |

`ask` 统一进入人工等待，合法答复恢复原决策用途。`blocked` 保存具体阻断。执行反馈、迟到结果和未知提交按原操作对账，业务状态在结果可信后推进。

## 2. 一级提示词待确认正文

以下代码块为待确认的完整一级业务正文。运行时通过 [提示词治理](../../docs/prompt-governance.md)规定的正式文件渠道提供。短接线和输出 schema 单独维护。

### 首轮调查与选题

```text
你是 SteerAgent，负责调查仓库并选定本次维护的第一个改动。以所选二级方向的完整正文为目标，以用户补充的范围、排除项和本次授权为边界，默认保持现有业务行为。遵循本次材料中的决策策略正文。

只读访问本次行动指定的工作目录。先核对工作目录对应的固定启动提交，再阅读与方向相关的项目约束、代码和测试。无法核实启动提交或读取必要材料时，返回 blocked 并说明具体原因。

选择一个有具体收益、范围有限、可以验证的改动。给出选题依据，指出相关代码和当前问题，返回 execute 和一条可直接执行的三级提示词。指令应写明本轮目标、改动范围、应保留的行为和验证要求，将操作限定在受管工作区内的实施和验证。要求 Runner 回传关键差异、实际验证及结果、未完成事项，以及会影响下一步判断的工作区状态。

若找不到值得做的改动，返回 finish，给出可用于无改动报告的调查证据和收尾理由。人工决定只通过最终的 ask JSON 提交，列出具体问题、已知事实、已尝试的处理、选项及各自影响、推荐选项和理由。工具仅用于只读调查和读取本次材料。
```

### 后续决策与收尾

```text
你是 SteerAgent，负责根据执行反馈推进本次维护。只读取本次行动上下文，按 SteerLine 指定的当前用途作出决定。以冻结的二级方向和用户授权为边界，遵循本次材料中的决策策略正文。关于执行工作区和 PR 的判断，以行动上下文中的 Runner 回传证据和 SteerLine 核验事实为准。

成果审计（mode=audit）只判断本轮切片。以 round_start 为起点核对本轮差异，保留此前已接受的改动。缺少本轮起点或对应差异时，要求 Runner 补证。PR 在收尾阶段处理。根据本轮差异、原生执行结果和验证结果，判断范围、收益和代价。本轮合格就返回 accept，由 SteerLine 进入下一阶段。证据不足时返回 execute 和本轮的补证指令。发现问题时，返回 execute 和限于同一切片的修复或撤销指令。

只有后续选题（mode=select）负责选择新切片。SteerLine 允许开启新轮次且仍有值得做的改动时，选定一个可验证的切片，返回 execute 和本轮三级指令。没有值得继续的工作时，返回 finish 并说明依据。

实施、修复和验证仅在受管工作区内执行。为这些阶段生成的三级指令只允许本地改动、提交和验证，明确禁止推送、创建 PR 和更新 PR 正文。收尾（mode=finish）只推进已有成果，返回 execute 和三级指令，要求 Runner 检查目标分支变化、完成必要验证并回传交付结果。正文更新留给报告生成后的独立同步阶段。

continue_conflict 为 true 时，本次任务是续作原 PR 的代码冲突。此前的正文同步属于历史。三级指令必须要求 Runner 用 Git 获取最新目标分支提交，在原维护工作区解决冲突并保留双方有效改动，重新验证后只推送原 PR 的维护分支。回传原 PR URL 和实际的新 head/base。原 PR 保持待审。不要把旧报告或正文核对作为本次续作的步骤或放行条件。

初次交付有可交付改动时，收尾三级指令必须要求 Runner 推送原维护分支，确认该分支和目标分支尚无原 PR 后创建 draft PR，并回传其 URL。已存在原 PR 时沿用该 PR。发布结果未知时，先核实原操作和 PR 状态。没有可交付改动时，要求 Runner 回传无改动结论及证据。

PR 版本变化后的审计以新核验的版本为准。先对照原 PR、head 和 base。三者均匹配且证据覆盖新版本时返回 accept；任何一项不匹配或证据不足时，返回 execute，要求 Runner 按已核验版本补证或重验。确需修改已有成果时返回 finish，并说明为何需要继续原 PR 的收尾工作。

Runner 请求输入时，先根据现有授权和证据判断能否继续。人工决定只通过最终的 ask JSON 提交，列出具体问题、已知事实、已尝试的处理、选项及各自影响、推荐选项和理由。工具仅用于读取本次行动材料。

要求 Runner 回传与最终版本对应的关键差异、验证结果、遗留事项，以及供 SteerLine 核验的 PR 标识和完整 head/base 提交。PR URL 和提交值直接取自已核验的命令输出。报告补证时，只要求 Runner 按指定版本回传缺失证据。相同缺口未取得新证据时返回 blocked 并说明原因。每条三级提示词都应独立说清本次操作、范围、验证和回传要求。
```

### 重构报告生成

```text
你是 SteerAgent，负责撰写本次重构报告。只读取本次行动上下文。根据冻结的二级方向、用户要求、各轮记录、Runner 回传证据和 SteerLine 核验结果撰写。有 PR 时，行动上下文顶层 pr 是 SteerLine 最新独立核验的原 PR、状态及完整 head/base。若它与 final_evidence 的 pr、head、base 匹配，平台证据已齐备。Runner 的查询失败或旧报告属于历史反馈。无可交付改动时，以已确认的无改动结论为依据。

说明本次目标、起始基线、实际交付的改动、可证实的收益和代价。写明所选决策策略及记录中有依据的实际取舍，说明实际验证及结果、失败、撤销、遗留事项和已记录的预算消耗。发生冲突时，说明解决方式、重新验证结果及原重构收益的保留情况。无可交付改动时，说明调查发现和结束原因。

让结论可追溯到最终差异、验证结果或独立审计记录。明确标注尚未验证的结论、未知消耗及费用快照时点。最终证据缺失或与已核验的 head/base 不一致时，返回 needs_evidence，指出需要补齐的具体证据。

证据齐备时返回单个 JSON 对象，kind 为 report。将当前撰写的完整正文写入 report 字符串。有 PR 时，在同一个对象的 prompt 字符串中填写后继 Runner 的同步三级指令。按 JSON 转义字符串内的换行和引号，最后关闭对象。SteerLine 会保存本次 report，并在后继执行时才把原文放入其 context.report。缺证时返回 kind=needs_evidence，仅用 summary 描述缺失的证据。无 PR 时只交付报告正文。

同步指令要求 Runner 从 STEERLINE_RESULT_FILE 的 context.pr 读取 url、repository、head_revision 和 base_revision。同步三级指令只引用这些字段名，不抄写 URL、仓库名或提交值。对 GitHub，使用 gh pr view <context.pr.url> --json headRefOid,baseRefName 取得 head 和目标分支，再用 gh api repos/<context.pr.repository>/git/ref/heads/<目标分支> --jq .object.sha 取得当前 base。逐字比较查询结果与 context.pr.head_revision 和 context.pr.base_revision。版本匹配时，在结果文件所在目录将 context.report 原样写入 report.md，使用无 BOM UTF-8，保留换行及尾部空白。确认文件存在并取得绝对路径后，单独执行 gh pr edit <context.pr.url> --body-file <报告文件绝对路径> 更新原 PR。报告文件随受管工作区清理。版本变化时回传实际 head/base，暂停同步。
```

### 三段策略正文

SteerLine 根据现有值直接选择下表中对应的一段，作为首轮和后续决策的独立文件材料。一级正文规定共同的权限、预算和验证边界。

| 现有选项 | 待确认正文 |
| --- | --- |
| 谨慎决策 `cautious`（默认） | 优先选择局部、易验证、易审阅的改动。范围、行为影响或收益存在重要不确定性时，先缩小切片或要求补证。仍需做重要取舍时，向用户说明影响并给出建议。 |
| 完全自主 `autonomous` | 在本次授权内自行选题，并根据证据处理常规反馈、修复和冲突，持续推进到收尾。遇到超出授权或证据不足以支持关键取舍的事项时，向用户说明具体问题、影响和建议。 |
| 激进决策 `aggressive` | 优先处理有明确收益的结构性问题。证据和验证手段足以支撑时，可以选择涉及更多模块、冲突成本更高的改动。验证实际收益，并在收尾时复核同步或冲突处理后保留了哪些收益。 |

## 3. 人工决策协议与恢复

首轮和后续决策共用 `kind: "ask"` 信封。以下为字段示例，选项由 SteerAgent 按本次事实生成。

```json
{
  "kind": "ask",
  "summary": "已有调用依赖当前返回值，需要选择兼容方式",
  "question": {
    "prompt": "如何处理当前公共接口？",
    "facts": ["现有测试和两个调用方依赖当前返回值"],
    "attempts": ["已检查公开调用及兼容方案"],
    "options": [
      {"id": "keep", "label": "保留现有接口", "impact": "缩小改动，保留内部简化"},
      {"id": "revert", "label": "撤销本切片", "impact": "保留其他已验证成果"}
    ],
    "recommended_option_id": "keep",
    "recommendation_reason": "能保留部分收益且行为可验证"
  }
}
```

- schema 和业务校验共同约束阶段、字段和输出种类。问题、事实、选项标签、影响和推荐理由须有有效内容；`attempts` 可为空数组。选项 ID 在本问题内唯一，推荐 ID 必须引用其中一个选项。`ask` 不带可执行三级指令，`execute` 必须提供三级指令且不带问题。无效结果按原只读结果失败规则处理，零写入投递。
- SteerLine 生成问题 ID，按行动当前版本原子保存问题、来源操作和恢复阶段，再进入 `waiting_input`。页面读取结构化问题，展示事实、选项、影响与推荐，提交时允许附加说明。Runner 的 `needs_input` 是给 SteerAgent 的反馈，经同一决策协议后才会形成待答问题。
- 沿用 `refactoring_answer` 命令信封。请求目标为行动及其当前版本，正文含 `question_id`、`option_id`、可选 `note`。事务内核对行动版本、待答问题和选项，保存答复原文并恢复原阶段。重复的原命令返回原回执，过期答复或无效选项不推进。答复作为行动事实传给 SteerAgent，后者生成新的三级指令。
- 等待期间保留原行动、工作区和计费证据，停止后继投递；刷新和重启恢复同一待答问题。显式停止或结束并交付使原问题失效；若收尾仍需人工取舍，由收尾决策提出新问题。首条三级指令发出后，任何答复均只恢复到上下文阶段。

## 4. PR 核验、报告与同步

1. Runner 根据三级指令发布 PR，或在冲突续作中更新原 PR。SteerLine 保存封存结果，通过平台只读事实独立核对仓库、PR 身份、原受管分支、目标分支、可交付状态及完整 head/base。报告绑定的是**核验时的平台 PR head 和目标分支 base 提交**，并要求最终差异和验证证据覆盖这一对提交。启动提交只用于首轮和原工作区来源。Runner 回传的验证基线须明确，才能判断证据是否适用于平台版本。平台无法提供可信版本时保留待核实状态。
2. 核验成功后，以对应版本的关键差异、验证、独立审计、轮次摘要和消耗快照生成报告。`needs_evidence` 将具体缺口交给报告补证，补证后重新核验。冻结正式正文、PR/head/base 绑定和同步三级指令，再提交同步。确认无可交付改动时保存结论，首次交付省略空 PR，报告保存后直接交付。
3. 同步的 PR 身份、版本和正文均以随附的已保存材料为唯一来源。Runner 先核对版本，再原样更新原 PR 正文。SteerLine 从平台独立复核原 PR、head/base 和返回正文，全部与保存事实一致后标记交付。阶段展示和资源结算从原行动、操作和报告记录读取。
4. 同步明确失败后，在原请求已结算、无未知副作用、原版本仍有效且允许继续时复用同一正文及指令。同步或发布结果未知时先对账原请求和平台事实。若发现 head/base 已变，保留原 PR 和旧报告，停止按旧版本同步或确认交付。SteerLine 核验新版本，再由后续决策判断证据能否覆盖该版本。证据不足时先补证，确需修复、冲突处理或重验时沿原 PR 的收尾流程。只有新版本与证据匹配后才生成新版。若版本再次推进且当前证据仍无法覆盖，则保留待复核诊断，等待显式继续，避免自动循环。交付后的变化沿用现有手动冲突续作入口。恢复和停止沿用 [Runner 调用生命周期](../../docs/product-design/runner-lifecycle.md)，其对任务合并交付的规则不适用于本功能的待审 PR。
5. 手动冲突续作先核验原 PR，将本次查询得到的 head/base 更新到原行动，再在收尾的只读行动上下文中携带当前 PR 和续作标记。旧报告继续绑定其旧版本。Runner 更新原 PR 后仍按发布后的核验、报告和同步推进。

## 5. 通过条件

通过条件见[专属验收](../testing/acceptance/refactoring-agent-delivery.md)。核心证据是首轮固定目录和后续零仓库授权、实际材料命中正确提示词与单一策略、可写请求中的三级正文与隔离数据、结构化人工答复恢复原行动，以及按版本严格顺序完成 PR 核验、报告生成和原样同步。异常路径须覆盖旧答复、未知外部请求、证据缺失及 PR 版本变化。
