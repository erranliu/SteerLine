## 2. 范围与职责

覆盖 Runner 公开支持的本机 Codex、本机 Orca、远端 Orca 开发执行。能力不足的组合明确不可用，不能退回免门禁。项目负责文档/脚本/测试/发布标准，用户准备实际执行账号可见的工具、变量、依赖、许可和凭据引用；SteerLine 维护准备关联、编排原活动及派发资格；Runner 继续负责原执行、工作区、请求、停止和文件回传。

复用现有环境生成、development/2、prepare/publish、progress/result 和具体生命周期入口。生成材料、准备验收、创建任务和必要查询/停止均不以业务环境 ready 为前置。旧 Runner 专用 Check 已按[退役规格](legacy-environment-check-retirement.spec.md)删除，不再构成诊断或准入前置。

不增加全局环境注册表、profile.environment_id、配置 generation、人工清单确认命令、自动环境修复、主机发现或通用工作流/证明框架。不改变 Runner 接口或任务的原恢复授权。

## 3. 环境键与依据

### 3.1 从现有配置派生

执行配置继续使用现有 profile.execution，不增加可编辑的环境对象或修改其文件格式。由一个纯函数生成规范化执行上下文，再计算环境键：

- 包含完整 adapter、target 和 settings；保留权限、认证引用、可执行入口、参数和 transport 等所有字段。
- 仅去除公开结构化模型字段：Codex 的 `settings.model` / `settings.reasoning_effort`，Orca 的 `settings.agent_launch.model` / `settings.agent_launch.reasoning_effort`。不解析命令行参数猜模型，不忽略其他或未知字段。
- 使用现有规范 JSON 与摘要函数，缺字段/无效 JSON 或不支持的 adapter 返回错误，不能以空键表示放行。

本机 Codex 与本机 Orca 是两个不同环境，不能共用准备资格。

同一上下文、不同 profile 名称/模型/effort 得到相同键；不同 adapter、目标、Agent 入口或权限上下文分别准备。执行方案 ID/名称仅用于选择、展示和保留本次来源；同一机器的不同执行上下文不推断为可互换的环境。展示名称由现有目标和关联方案给出，不增加名称持久化或别名配置。

同一 home 中各项目可得到相同环境键，但资格始终按“项目原身份 × 环境键”独立保存。当前列表只从已加载的开发方案派生并按键去重，生成专用方案不计入环境计数。配置保存/待重启及生效沿原机制；配置内容与运行时冻结值不一致时继续按原配置守卫拒绝新操作。

### 3.2 完整执行事实与准备依据分开

每次活动/候选的原 execution、workflow、profile digest、Run 输入和请求字节仍完整冻结，模型字段不得从这些执行事实删除。

准备依据沿既有 `Prepared.Inputs` 的有限文件、L2定义、公开PR/验证base和仓库目标构造，仅将其中的 execution 投影替换为上面的规范上下文。该投影只供准备适用性比较，在同一纯模型入口定义；新活动准备、当前查询、候选固定提交和存储复核共用，不允许各层另写摘要规则。

验收来源提交仍保存。普通源码提交在有限依据未变时不机械失效；脚本、执行规则、声明依赖、完整L2或公开PR设置/目标变化则拒绝旧证明。更换模型不等于环境永久支持该模型，实际 profile/workflow 仍须通过 Runner 原能力校验。

外部机器重建、账号凭据变化或远端名字改指机器无法从公开 execution 自动识别。用户在受影响项目的对应环境明确标记失效并重新验收；首版不增加跨项目批量失效、全局版本或自动故障分类。普通任务失败保留原诊断，不自动推断该环境已损坏。

## 4. 最小当前记录与唯一状态来源

增加一张项目 × 环境当前引用表，唯一键为 project_identity/environment_key，内容仅为 revision、当前 activity_id（可空）、显式失效标记/原因及更新时间。引用的活动必须属于同项目、kind=adaptation 且 execution 派生键一致；错配视为不可信，拒绝资格。

原 `project_environments` 继续保存完整活动、轮次、报告、状态和材料，不增加第二份 ready、六阶段流程、通过摘要或最后通过指针。历史通过时间和报告按原活动查询。当前资格只检查明确引用，不按历史顺序回退到某条旧成功记录；当前引用缺失即未准备，GET 不补记录或写业务。

开始准备在同一个项目 SQLite 事务中创建原活动/原请求并 CAS 更新当前引用，清除该引用的失效标记；事务提交后才允许发送已持久的原 Runner 请求。旧活动未结算时不得新建替代活动。开始即切断旧通过资格，失败回滚不能留下仅活动或仅引用的半状态。原命令重放返回原回执和关联，不重新选择当前活动。

观察和完成只按原活动 revision 更新原活动；当前引用不跟随每次进度增长，也不复制结果。显式失效命令通过原 journal 和当前引用 CAS 保存失效标记/回执；不会停止原 Run。失效后迟到的 ready 结果留在原活动，不能清除失效标记；其他旧活动的完成也不能改变当前引用。再准备须原活动已结算，由新明确操作选择新活动。

最终资格的唯一判定为：当前引用存在且未显式失效，原活动 `Status()==ready` 且原收尾已核实，准备依据与当前项目及所选候选固定依据相同。任何读取失败、错配、依据缺失或未核实均为 not_ready，不能改写原报告或最近一次通过事实。

页面可以展示下面六种说明，均为读取上述事实后的投影，不持久化另一套阶段：

| 展示 | 来源 | 新派发 |
| --- | --- | --- |
| 未准备 | 无当前引用/活动且准备材料尚未完整 | 否 |
| 待用户准备/验收 | 无当前活动，材料可用；展示清单和开始入口 | 否 |
| 验收中 | 当前活动未结算，包括排队、执行和停止待核实 | 否 |
| 已就绪 | 当前资格判定全部通过 | 是，仍须其他派发前置通过 |
| 阻断 | 缺材料/能力、明确失败/取消/耗尽，或操作未核实；保留具体原因 | 否 |
| 已失效 | 显式失效或原通过依据已不适用 | 否 |

显示优先级固定为：显式失效优先；原操作仍未结算则显示验收中及待核实原因；无当前活动时按材料完整与否显示待用户准备/未准备，并列缺失项；有已结算活动且失败/取消则显示阻断。只有原活动通过后才比较依据：无法读取显示阻断、摘要变化显示已失效、全部相同显示已就绪。准备中材料变化不掩盖原停止义务。展示不参与业务判断，页面始终返回结构化 ready/not_ready 和原原因代码。

## 5. 准备流程

1. 项目中选择现有开发方案对应的环境，显示当前准备情况和影响到的方案；服务在线不能使其自动就绪。
2. 沿已有生成/更新入口预览、导出准备文档和验收脚本及缺口，经正常Git审阅提交。缺文件或规则不同源明确报告准备不足，不在业务代码内联补材料，生成成功不授予资格。
3. 页面读取固定文档，说明实际账号的工具入口、变量、依赖/服务和许可要求；用户在外部完成准备。阅读或勾选清单不新增持久状态，也不增加“已准备”人工批准入口。
4. 用户点击既有“开始验收/重新准备”提交明确授权，页面说明真实L2/验证PR和模型/外部副作用；无需再增加前置确认命令。冻结本次原profile/完整execution/材料/期限，通过原Runner路径执行固定prepare/publish，不在SteerLine代跑shell。
5. 原执行停止后取得唯一result最终快照。同轮checks（含TTY）、完整L2、同一真实验证PR的检查/审核/合并和清理、原Run收尾均通过后，原活动才能ready；进度、Agent final、PR ready、completed或基础check不能替代。
6. 失败显示具体未通过/未验证项和下一步；继续原首次加最多两次有界重验，不修环境、不跨轮拼通过项，未知先查原请求。预算用尽后由用户处理环境并显式重新准备，旧记录保留。

本机 Orca 与远端 Orca 的执行、ready 判定及外部取证使用同一流程；外部取证统一经绑定目标的 Orca 公开 repo/terminal 创建、读取和关闭，不因本机直接读取文件。差异仅为明确 target/目标选择器。本机 Codex 独立验收，外部取证可直接读取该原 Run 的工作区，不能把 Codex 的资格借给 Orca。

材料内容和Agent责任继续受[原环境适配规范](project-environment-adaptation.spec.md)约束。本机扩展不削弱报告、TTY、真实PR及收尾标准，也不增加另一种验收工作流。

## 6. 查询、依据刷新与派发事务

查询使用原项目维护已固定的提交和不可变Git文件/现有读取缓存；不在页面轮询重新fetch、调用模型或远端命令，不把“查询失败”写成新的环境事实。沿原项目基线刷新取得新观察；准备和新候选开始时核实当前配置及材料，候选固定提交的有限准备依据须与当前观察和原通过依据相同。原维护观察已有的提交锁后复核保留，不新增环境配置epoch或后台同步器。

所有手动启动、自动派发、默认方案、新增及重试为新候选的入口共用相同规则。本机不得空键放行。原Start在重放处理、选定profile之后，必须先完成准备资格预检，再进入可能触发材料生成的PrepareExecution/PrepareTestPlan；明确未准备时这些准备回调和该Start产生的新Runner提交/生成/控制调用均为零。原实例的必要只读校验和独立材料活动的原授权保持。预检和最终复核使用同一资格函数，不能各立一套准入。

自动派发在生成新Start请求号前，按当前默认方案先做廉价只读资格检查，未准备是正常blocker，不按每次tick生成持久失败命令或新Runner请求；最终仍以候选事务复核为准，不新增等待队列或第二份可派发状态。

候选预留在原请求重放之后、领取Task/分配候选编号/写submit之前，在同一项目SQLite事务中读取当前引用和其原活动，复核引用revision/activity、环境键、未失效、原活动ready/收尾和准备依据。事务外只传当前配置/候选材料固定观察及预期引用；SQLite中不得执行Git、网络或Runner。拒绝或CAS冲突时整项回滚，零Task领取、候选、编号及新submit；候选只保存最小环境键/引用revision/活动ID/依据摘要用于原准入审计。

显式失效、开始准备和候选预留按同一项目事务串行决定：先失效/开始则后预留拒绝；先合法预留则候选保留原授权，后失效只阻止后继新候选。原请求重放返回原事实，不因当前资格变化改写或重复提交原候选。

准备与同目标业务的冲突继续用现有home目标准入临界区和各项目持久未结算活动检查；将公开adapter/target键扩展至本机，不使用权限/模型不同就忽略同目标占用的准备键。Git/Runner调用在临界区外；临界区只做原占用/配置复核和落库，保持既有目标准入→材料保留锁→SQLite的顺序。原目标任一任务/准备未知或未结算都不得新开始准备；本次不强停旧任务，也不承诺跨home/物理别名发现。

旧候选查询、停止、人工回答/恢复和交付继续遵守冻结授权及Runner原资格。创建Task和查看DAG不要求环境ready。环境阻断不改写用户dispatch_mode/paused，不自动切换方案，不自动submit/reply/resume。

## 7. 页面、接口与职责落点

沿现有项目环境Query/命令/journal扩展当前引用、分组列表、开始/停止/失效；清单和六阶段由后端统一投影。开始及显式失效保持原项目目标和外层版本语义，在各自payload中增加必填的 `expected_current_revision`（引用缺失为0）；开始的环境键从所选profile派生，失效payload显式携环境键和原因。停止仍以原活动ID/revision为目标；不得把当前引用revision塞进活动revision或用0改变外层命令通用版本规则。保留原请求查询/对账，不提供直接写ready入口。

项目顶部区分“服务在线”和“环境已准备0/2”，按现有开发方案派生的不同环境键计数。环境详情按材料→用户准备→验收→结果组织，保留原活动/轮次/checks/L2/PR/进度/停止证据。相同环境的多个模型方案合并显示，变更目标或权限后显示新的未准备环境，旧历史仍可查。

任务选择profile后显示对应环境资格；未准备禁用新开始并提供准备入口。派发栏同时展示用户模式/暂停意图与默认环境blocker；其他已通过环境须由用户显式选择。查询/停止保持可用，沿现有项目/实例缓存隔离、可见页轮询和定向刷新，GET零业务写入。

纯模型负责上下文/依据和资格规则；环境service负责原活动及当前引用选择；app负责配置/材料观察和目标占用；SQLite负责原事务复核；taskrunner不解释环境活动生命周期；Web只展示结构化投影。复用原typed端口及具体事务方法，不新增通用事务、证明验证器或配置注册服务。

## 8. 生命周期与交付

沿[Worker生命周期](../../docs/product-design/worker-lifecycle.md)W01–W03准备/资格、W08–W16原请求/未知、W17交付和W18收尾及原E/V规则。新引用不持有执行资源；启动census、pending stops、兼容接管、关闭/离线核验/reset继续枚举原活动，不能仅枚举当前引用而漏掉旧未结算活动。无需为每次结果回写另一份准备状态或引入新Runner节点。

配置格式保持原样；因新增引用表/活动字段需要的SQLite格式按项目规则升版，旧准备结果不自动回填为ready，不新增迁移/双写/回退。实现和验收使用独立新现场，不部署、归档或清空现有安装任务，除非另有明确用户授权。
