# Spec：Git 管理任务测试安排

日期：2026-11-09。用户已授权按本文及 [Plan](../plans/git-test-arrangements.plan.md)实施并提 PR；当前实现和验证事实归[专属验收](../testing/acceptance/git-test-arrangements.md)。普通开发，不启动 roadmap 调度或安装维护。

## 1. 目标与范围

恢复 Plan 同目录、同名 `.tests.json` 作为任务测试选择的唯一运行权威。测试选择在编写材料时由模型理解 Plan、项目测试要求和正式清单后产生，随材料一起审阅、提交和发布；执行阶段读取 Git 中的正式安排，校验并冻结，不再调用模型补测试安排。

正常路径为：roadmap 草稿讨论 → 确认范围与依赖 → 同批生成 Spec、Plan、测试 JSON 和专属验收材料 → 审阅及同一文档 PR 发布 → 核实合并并入图 → 从确定提交读取安排并创建候选。

草稿阶段允许材料不完整；正式文档发布和任务入图要求材料完整。用户在产品外编写任务材料时采用相同文件约定，不强制经过 roadmap。

本任务同时移除任务测试安排专用的生成请求、批次、profile 配置、生成状态和重试/取消操作。保留 roadmap 等其他功能的生成能力、项目 Git 检查与同步、候选独立冻结、真实测试进度、报告和唯一交付机制。

## 3. 文件与内容契约

### 3.1 唯一文件与唯一职责

`SteerlineFlow/plans/<name>.plan.md` 对应 `SteerlineFlow/plans/<name>.tests.json`，嵌套目录同样适用。路径由 Plan 路径确定，不增加任务创建参数、可配置路径或 Markdown 中的另一份结构化选择。

JSON 继续使用原格式：

```json
{"tests":["l1.minimum","smoke.delivery","go.http"]}
```

`tests` 是有序且唯一的测试 ID 数组。拒绝未知字段、重复键、重复/未知 ID、错误类型、非普通文件、越界路径、无效 UTF-8 和超限文件。复用现有 JSON、路径和大小约束。文件只保存选择，不复制测试定义、模型、生成状态、执行结果或时间戳。

项目公共要求和唯一正式测试清单仍由 `SteerlineFlow/environment-project.json` 定位；不改为另一份硬编码清单。JSON 中的 ID 必须在采用提交的清单中存在，完整定义含 `note` 从该清单展开。

允许 `{"tests":[]}`，但 Plan 必须明确说明无需自动测试及原因；材料审阅核对其合理性。空安排显示“未安排自动测试”，不显示测试全部通过。不得以空数组代替缺失文件。

### 3.2 材料分工与语义责任

- Spec 定义成果、边界、验收项和通过条件。
- Plan 定义实施步骤、验收项到测试 ID 的映射、选择原因、执行时点和特殊准备，链接同名 JSON 与正式清单。已有定义的通用命令、环境、断言不重复抄写；定向诊断或本任务额外操作仍写清执行方式。
- 测试 JSON 是完整测试选择的唯一来源，包含项目必跑项及本任务必要测试；运行时不额外插入、删减或重新影响分析。
- 正式清单维护稳定 ID 及完整可执行定义；专属 acceptance 沿当前规则维护具体安排、结果和证据，不作为测试选择来源。

模型在材料生成时做语义选择，作者及文档审阅负责核对 Plan、验收项、项目必跑要求与 JSON 是否一致。程序检查文件和引用，不宣称仅凭 JSON 就证明了语义覆盖，也不新建一次模型复审或用脚本解析 Plan 自然语言来替代规划。

新增测试用例仍可在本任务实施时补齐，由已有登记入口承接，不因新增用例而要求新增 ID 或拆出前置任务。确无可用正式入口时，生成阶段沿原 `questions` 机制报告实际缺口，先调整测试组织或交付安排，再发布材料；不预登记尚未实现的入口为可运行，也不新增一套“待实现测试”状态或解析规则。

## 4. Roadmap 同批生成、审阅与发布

1. 沿现有固定代码提交、项目测试入口、完整公共要求、正式清单和确认规划生成材料；不另发一次测试安排 generate 请求。
2. 每个新任务的生成结果只增加一个必需的有序测试 ID 数组。平台复用原 JSON 编码器生成 `{"tests":[...]}`，路径由 Plan 推导；模型不重复输出路径或嵌套 JSON 字符串。已有正式任务仍只作为引用，不为其重写安排。
3. 生成结果采用前核对文件集完整性、精确路径、编码/大小及 ID 引用；测试选择按固定生成提交的清单校验。关键缺口返回问题，不采用部分文档。
4. 测试文件进入原审阅 diff 和文档确认摘要。任何文件编辑均撤销原确认，沿原流程重审；Plan 编辑时核对测试选择，选择仍适用可保留原 JSON 字节，不强制重新调用模型。
5. Spec、Plan、测试 JSON 与既有验收材料在同一发布分支、同一文档 PR 中提交。diff、确认摘要、发布和合并核验复用原文件集组装函数，使用唯一、确定的 JSON 编码方式，不另外维护一份可独立编辑的 JSON 正文。生成采用时按生成提交校验；合入采用时从实际合并提交读取清单、校验 ID 并展开定义，不混用两个提交。若所选定义相对生成基线有变化，在原审阅/差异机制中明确提示实际变化；语义是否仍适用由正常文档审阅负责，不增加定义版本锁、模型复审或新的采用状态。
6. 测试文件缺失、正文不符或 ID 无效时，发布/入图明确失败；不创建部分 Task/DAG，不补发测试生成，不静默删去选择。发布未知、停止、重启和入图重放继续沿原请求核实。

JSON 路径可由 Plan 推导，不增加 TaskContract 的测试引用参数。文档来源、确认、PR 和正式编号的现有归属保持。

## 5. 运行时读取、冻结与变化

### 5.1 新候选

从本次已核实 base 的同一提交读取任务材料、同名测试 JSON、项目入口、公共要求、正式清单及固定测试协议/writer。不得混用主工作区未提交文件、另一个提交或项目库旧生成结果。

候选预留前完成有界静态读取和校验。复用原候选契约与测试 Snapshot 中的采用提交、Plan 路径、项目入口、有序完整定义和定义摘要，移除 `GenerationID`、生成输入及生成成功证明。JSON 路径从 Plan 推导，原文件由采用提交定位；不另建 Git 来源对象或为可推导事实增设字段。数据库只保留原材料观察缓存和候选不可变快照，观察缓存由 Git 读取覆盖，不提供独立编辑、采用或批准入口。

读取缺失、Git/网络失败、格式错误、所选 ID 删除或必要能力缺失时明确诊断和阻断，不生成文件、不猜路径、不用空数组或旧结果兜底。只读查询读取已保存投影，不触发 Git 写入或模型；项目检查/更新后可由现有后台维护路径完成有限的材料读取，启动路径再次核对版本与预留资格，无独立“准备测试安排”操作。

材料资格只表示 Git 材料与安排有效，不缓存执行配置/Runner 能力结论；当前所选方案的文件通道、进度和工作流能力仍在候选预留前由原输入校验核实。

沿用现有项目统一就绪范围：公共基线和所有 open/in_progress 任务的材料有效才允许新候选。此次只替换其中的安排依据，不改为单任务准入；closed/discarded 排除、预留事务重核及已预留请求优先重放保持。

### 5.2 版本规则

| 变化 | 行为 |
| --- | --- |
| 只推进代码提交，关联材料与所选定义相同 | 读取并采用新 base；不调用模型，不因提交号变化把原候选标成材料过期 |
| Plan 修改测试要求 | 作者在同一材料变更中核对并按需修改 JSON，正常审阅；运行时不替作者重选 |
| Plan 仅修改实施说明，测试选择仍适用 | 可保持 JSON；保留文档版本差异，沿原材料新鲜度规则展示，无生成操作 |
| 清单只变更未选条目 | 新快照记录实际采用来源；不改变已有选择，也不单因整份清单 blob 改变而将候选标成材料过期 |
| 选择、顺序或任一所选完整定义变化 | 新候选读取新定义并冻结；原候选显示相关材料变化，原快照不改写 |
| 所选 ID 删除、文件损坏或读取未知 | 新候选阻断并显示原因；旧快照和原资源义务保留，不自动修复或重试模型 |
| 补写验收结果、日期或证据 | 不改变测试选择，不触发安排生成；其他关联文档的新鲜度仍沿当前契约判断 |

完整清单通过候选原采用提交和项目入口追溯，无须另存一套来源摘要。原材料摘要计算中移除整份清单正文摘要，改用原有有序所选定义摘要；不新增清单差异服务或第二个新鲜度状态。公共要求和协议变化仍按原固定材料规则重新校验，但不引出生成任务。ID 不得静默改用于其他验证目的。

原候选始终使用自己的快照。过期不自动停止、重启或撤销反馈/发布，原请求重放不升级材料；旧候选 PR 的交付资格、唯一交付、后继释放和全部停止义务继续按[生命周期](../../docs/product-design/worker-lifecycle.md)核实，不加“最新 JSON 的测试必须通过”门槛。

## 6. 删除专用流程与保留能力

删除任务测试安排专用的后台生成 worker/请求、批次/关联、生成 profile 设置、生成记录读写端口与无消费者表、重试/取消 API/CLI、Web 操作、活动中心投影、生成 schema/短提示及对应死代码。保留真正被其他功能使用的通用 generate、Runner、队列、原请求与停止能力；不按名称批量删除共享代码。

维护及任务页面展示采用提交、JSON 路径、测试列表和具体错误。取消“生成中/等待模型/重试生成”等安排状态，以及手动“准备全部安排”。仍保留仓库检查/同步、必要的静态读取状态和原候选测试进度。外部编辑通过正常 Git/PR 采用，不恢复 `tests apply`、文件监听自动写回或第二套人工批准。

未发布项目直接调整内部格式，不新增旧生成结果到 JSON 的导出、旧库迁移、双读、双写或回退。真实旧构建活动资源必须先按其原正式维护流程核实与结算，不能通过删表/删记录消除原停止义务；本任务不授权操作安装环境，也不建设跨构建接管。

## 7. 范围外与约束

- 不改变 L1–L4、真实通过条件、进度 writer 或 Runner 原生工作流，不新增 Runner 协议或修改 Runner 源码。
- 不把项目统一就绪改成单任务门槛，不重设计 acceptance 引用和通用材料新鲜度。
- 不给现有所有 Spec/Plan 批量补 JSON，不根据旧生成数据库回填；实际需要执行的旧材料通过正常文档变更补齐。
- 不新增自动测试选择算法、结构化 Plan 小块、测试编辑器或产品内安排批准流程。
- 提示词、接线及对应测试/CI 的实施变更按[提示词治理](../../docs/prompt-governance.md)提交实际正文差异、前后 UTF-8 字节数、原因、验证及独立审核，不能以更新黄金样本替代审核。

## 8. 验收要求

全部状态及证据登记于[专属验收](../testing/acceptance/git-test-arrangements.md)，本表仅定义通过条件。

| ID | 方法 | 最小通过条件 |
| --- | --- | --- |
| GAT-A01 | 自动 | 同名路径和原 JSON 契约可复用；完整非空/合理空安排可采用，缺失、重复、未知 ID、非法路径/文件及跨提交来源均拒绝，零模型调用 |
| GAT-A02 | 自动 | roadmap 一次生成返回测试 ID 数组，平台产出精确测试文件；原 diff/确认/发布/合并/入图完整覆盖，编辑撤销确认，生成与合入各用自己的提交校验、所选定义变化明确可见，缺文件/错正文/无效引用零部分入图；原请求重放不重发 |
| GAT-A03 | 自动 | 新候选冻结同提交完整定义与来源；提交推进及无关清单变化不导致错误过期，相关选择/定义变化可见，原候选/重放/重启均保留原快照 |
| GAT-A04 | 自动 | 材料就绪与 SQLite 预留不依赖生成记录；原项目统一门槛、兄弟任务错误阻断、事务回滚和已有预留重放保持；静态读取错误不借旧 ready 放行 |
| GAT-A05 | 自动 | 专用生成配置、批次、API/CLI/UI/活动入口及死端口清除；检查/同步/查询/启动不产生安排模型调用；roadmap/其他生成与停止能力继续正常 |
| GAT-A06 | 自动 | 按 Git 所选定义构造原安排与进度字段；受控公开进度的初始化、通过、重跑清零和异常保留正确，原请求/候选隔离保持，旧候选 PR 交付和资源结算不依赖最新安排。验证范围是调用方冻结与消费，不宣称真实模型执行或重验未改动的 Runner/writer |
| GAT-A07 | 自动及独立审核 | 当前指南、提示词、模板、执行登记和测试一致；真实本机 roadmap 材料生成取得合法 JSON 并完成原发布/入图链；固定正文差异、字节数、失败与清理可复核，独立审核闭合 |

错误诊断及显示由现有 owner/Web 自动测试覆盖；材料 diff、Git 来源和没有补安排操作的界面行为由现有自动浏览器场景验证。本任务不新增人工签收活动。
