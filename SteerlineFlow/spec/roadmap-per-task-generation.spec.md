# Roadmap 按任务并行生成 Spec

2026-11-10 用户确认：任务规划确认后，每个新任务使用一个独立 session 生成自己的 Spec、Plan 和验收材料，多任务并行；不再要求一个 session 输出整批文档。本文按普通开发规划，不分配 Task ID、不修改 execution-map。实施安排见 [Plan](../plans/roadmap-per-task-generation.plan.md)，验证安排和实际结果见[专属验收](../testing/acceptance/roadmap-per-task-generation.md)。

## 目标与当前问题

当前 `internal/roadmap/documents.go` 从已审阅解析派生一个文档记录，提交一次 Runner generate/1；`model.DocumentSchema` 要求该 Run 返回所有新任务的正文。整体设计、修改所有权和新增测试 ID 提供关系也在这次长输出中确定。一项输出失败使整批无法采用。

现场请求 `f0e92e786936445a9803a20b8e9cdcbd` 的 Runner Run `936fee4067edcb45770f6f868966808a` 要求六组，Codex 原生终稿只返回 demo-tools，且 JSON 后有非法尾部。原生与 Runner 终稿摘要相同，问题不是 Runner 丢失五组。本设计减少单次生成职责；非法或不完整的单项输出仍须明确失败，不清洗正文冒充成功。

Rebase 后的产品已将确认与生成合并为“确认任务依赖并生成 Spec / Plan”一次操作。本设计沿用该交互，在确认前展示完整规划；确认是该命令内独立持久化的里程碑，不增加第二个确认按钮。

## 范围与非目标

范围覆盖确认前的完整任务规划、确认快照、同一文档记录内的按任务生成执行、共享额度、逐项观察/停止/重生成、审阅聚合，以及 API、活动中心和 Web 展示。

复用当前 Runner generate/1、固定仓库与 file 材料、原请求绑定、内容队列、文档编辑/发布和批次入图。每项使用独立 Runner Run，从而获得独立原生 session；不在一个 session 中调用多个子 Agent 替代此要求。无需 Runner 新协议或原生 `outputSchema` 接线改动。

不执行业务任务，不要求业务前置先交付才生成后继文档，不增加自动模型切换、自动失败重跑或模型汇总 session。不扩建通用 DAG 调度器，不兼容旧整批生成记录、数据库形态或原协议。

## 确认前的完整规划

解析继续依据原始草稿、已有正式任务/依赖、来源映射和固定解析规则，补充读取项目声明的固定测试清单以核对测试 ID。确认前补齐任务间已知的共用安排、修改所有权、交接条件和新增测试提供关系；不把解析扩展为全仓代码调查或完整实现设计。每个文档 session 仍调查自己任务相关的固定代码，发现规划冲突时返回问题。

确认页面必须可查看以下内容，且纳入同一确认摘要：

| 层级 | 必需信息 |
| --- | --- |
| 整批 | 原始来源/摘要、已有正式图/映射、解析规则与测试清单来源、必要的共用安排、未决问题。共用安排使用一段可审阅的 `coordination` 正文，无共享影响时明确说明。 |
| 每项 | 稳定内部代号、标题、目标、范围、约束、验收要求、逐字原文依据、已有正式任务关联、原始/拟议依赖及变更理由。 |
| 协作 | 有共享影响时，在现有 scope/constraints 及整批 coordination 中写清修改所有权、提供/消费的能力和交接条件。不再新增同义的 ownership/handoff/interface 结构或要求无关任务填空表。 |
| 测试提供 | 每项 `provides_tests` 的有序唯一 ID 数组；无新增填空数组。新增 ID 的提供者唯一，不能覆盖固定清单已有 ID。消费者只能引用严格本地前置（含传递前置）提供的新增 ID。 |

确认前核验必需字段、已有任务绑定、依赖、提供者唯一性、已登记测试 ID 冲突和未决问题。单项代码调查引用仍在文档生成时由模型提供 source/path/reason，平台核验摘要，不在解析阶段复制一套引用核验流程。规范和代码通过固定仓库读取，动态材料走 file 渠道，不在 schema 或提示词中内联原文。提供关系是未来实施契约，不是已登记的测试定义或测试结果。

确认不能临时补一次未展示的模型规划。确认摘要覆盖完整 Analysis、coordination、provides_tests 及规划所用测试材料；沿现有规则重核原文/正式图，并检查上述规划材料未变。代码生成基线仍在创建文档记录时一次固定，所有任务共享；不因无关代码提交变化要求用户重新解析。若生成基线的清单与确认的测试提供契约冲突，则明确要求重新规划。失败项重生成和恢复只读原固定上下文，不采用当前源码或其它任务的迟到结果。

## 批次、单任务及输入契约

一个用户生成操作仍只创建一个 `purpose=documents` 文档记录，parent_id 指向已确认解析；“批次”是该记录的业务含义，不新增记录类型。已有正式任务只作引用，不创建文档生成项。固定上下文和最终审阅/发布事实只保存在该文档记录。

文档记录内新增有序 `generations` 执行数组。每项仅保存 generation_id、local_key、不可变创建时间 CreatedAt、原 Runner 请求、提交/结果/停止事实及原执行身份，复用现有单 Run 绑定和生命周期；不复制完整 Roadmap Record 的规划、发布或入图字段。首轮和重生成项按持久化顺序追加，同一 local_key 的最后一项就是当前执行，不再保存当前轮次指针、计数器或选择表。原始结果不可改，最终 `Documents` 仍是原审阅/编辑入口。

所有单项 Run 使用同一固定代码、规范、执行方案和完整确认规划。原文、完整规划沿用 `roadmap-inputs/source.md`、`roadmap-inputs/confirmed-planning.json` 两份 file 材料；短指令只增加目标 local_key 这一业务事实，文件路径沿平台生成的单任务 schema 固定，不再增加 target 文件渠道。首轮完整执行数组在一次文档记录保存中持久化后才可派发，任务划分由平台确定。

单任务结果包含来源/确认/代码绑定、调查引用、问题，以及本任务一组 Spec、Plan、tests、provides_tests 和专属验收正文。单任务 schema 只描述本项；不要求模型返回批次任务数量，也不把其余任务正文作为本次输出字段。

- 无问题时，结果必须且只能属于目标 local_key 和稳定语义路径。Spec/Plan/验收均完整；tests 按项目政策选择，provides_tests 必须等于确认契约。
- 有关键问题或发现需改范围、依赖、协作契约时，返回问题和空文档，阻断该批采用；须修订草稿并重新解析确认，不允许失败项重生成暗改规划。
- 每项结果沿现有 1 MiB 上限和 UTF-8/严格 JSON 校验；非法尾部、缺正文、错误身份/路径/摘要、manifest 不符均失败。既有发布业务总量限制仍须单独校验，不通过截断正文满足限制。
- 只有原 Run completed、原生 final 经核实、资源 stopped、文件/仓库来源核验及单项业务校验通过，才成为可采用结果。

## 并发与生命周期

沿用应用 home 级 `ContentQueue` 和 `max_generate_concurrency`，默认五个名额；与其它内容生成用途共享，不为本批另建额度。每个单项 generation_id 占一个名额，文档记录不额外占位。沿现有观察循环逐项提交，Runner 接受后异步执行即可并行，不另建提交线程池、批次调度器或事件总线，也不串行等待模型生成结束才提交下一项。

队列登记和重启重建都使用该执行自己的 CreatedAt，不能使用外层文档记录的创建时间。首轮可同刻创建，沿队列既有 generation_id 顺序打破并列；失败项重生成在追加时取得新时间，不越过已经排队的其它执行，恢复时保持原值。

六任务且额度五、没有其它占用时，首批五个独立 session 应能同时在途，第六个等待。并发依据文档生成额度，业务依赖图不决定生成顺序。一个子项失败不停止其它已授权项或阻塞无关排队项；结果失败但资源未结算时仍占额度。

以下细化遵循 [Worker 生命周期](../../docs/product-design/worker-lifecycle.md) 的原请求、未知零重放、同构建恢复和停止边界，不新设原生重试策略：

| 情况 | 行为 |
| --- | --- |
| 重复生成命令/丢回执 | 原请求返回同一文档记录、同一执行数组；已保存但未发送与发送未知分开核实。不能重复创建六个 Run。 |
| 单项未知 | 只查询该项原请求/Run；不能按“失败项重生成”创建替代 session。 |
| 同构建重启 | 枚举已保存执行数组，恢复原结果与停止义务；按原授权处理可证明未发送的项，只使用已保存原请求。不得新建替代执行或重发已发送请求。 |
| 停止批次 | 先持久化禁止后续派发，再取消未提交项，对已发送或未知项保存各自原停止义务；迟到受理仍停止。已成功正文保留，停止批次不能发布。 |
| 单项失败 | 保留原诊断及执行身份，允许其它项继续；整批不能进入可发布审阅。 |
| 失败项重生成 | 用户点击某个已失败且原资源结算任务的重生成按钮，追加该任务一项新执行/新 Run；保留历史及成功项，原确认快照不变。 |

批次停止不可撤销；需要继续时重新发起整批生成。失败项重生成只适用于未停止、未发布文档记录中的明确失败项，不适用于未决语义问题、运行中、提交未知、未结算或已成功项。一次命令只重生成一个 local_key，不增加多选/批量重试机制。重复请求必须幂等，同一任务不能同时有两个当前有效执行。

重生成还须复用原生成入口的同来源资格检查：其它未结算解析/文档记录或在途发布阻止追加；此检查排除当前文档记录，不因本记录其它任务仍在生成而阻止合格失败项重生成。只有同来源最新文档记录可以追加执行，存在更新文档批次时，历史批次拒绝重生成；最新关系从既有创建时间/记录 ID 顺序推导，不新增 latest 指针。新建批次与重生成共用现有生成锁，和首次发布意图的资格检查/保存沿既有写入入口串行重核，防止并发命令各自通过后同时启动冲突操作；不持锁等待模型或远端发布结束。旧请求对账和停止责任始终保留。

## 汇总、审阅与交付

汇总由 SteerLine 完成，不调用额外模型。按确认任务的稳定顺序，读取每个 local_key 的最后一项执行，检查集合恰好覆盖所有新任务、无额外项、固定快照一致、路径唯一、tests 合法、provides_tests 与确认一致。进度、各项状态和是否可审阅从执行事实推导，不重复持久化完成数、百分比或另一套批次执行状态机。更新仍经文档记录原 revision/CAS，旧观察不能覆盖新执行。

部分成功可以只读预览，不能发布、入图或作为整批成功。所有项通过且无待处理问题后，一次性采用到原 Documents，复用既有 DocumentsVerified、编辑、review_digest、发布预览、单个文档 PR 和原子入图。进入审阅后 Documents 是可编辑正文权威，后续执行观察不能重新聚合覆盖人工编辑。编辑取消旧审阅摘要；改变任务/依赖/协作契约仍须重新规划。发布和入图未知按原号核实，不为每个生成项各建 PR 或正式任务。

页面继续使用现有确认并生成按钮。生成时显示整批进度和逐项排队/运行/核实中/收尾/成功/失败/取消状态、具体问题及失败项重生成入口。每项复制其自身 Run/Attempt/session 信息；批次只复制批次/确认记录身份，不把某个子 Run 冒充整批 Run。活动中心保留一条用户操作的聚合活动，关联逐项详情；历史重生成轮次可追溯，轮询/GET 不创建 session。

## 验收要求

| ID | 自动通过条件 |
| --- | --- |
| RPG-A01 | 确认前可查看完整任务、必要协作及提供关系；缺材料、冲突和未决问题阻断；不引入确认前全仓调查或无关代码变化门禁。 |
| RPG-A02 | 六任务受控夹具生成六个不同 Run/session，每 Run 仅生成其目标一组；已有正式任务不生成；两份 file 材料一致、目标事实明确，严格核验原始结果。 |
| RPG-A03 | 额度五时五项可同时在途，第六项排队，释放后派发；共享额度、收尾占位正确。重生成使用新创建时间，不能越过已等待项，重开后次序不变。 |
| RPG-A04 | 重复命令、提交未知、保存失败、重启与迟到回执不重复 Run/session；批次停止覆盖全部子项和迟到受理，资源未停不释放额度。 |
| RPG-A05 | 一项失败时保留其余五项；显式重生成仅新增所选失败任务的 Run，旧结果不能覆盖新轮次；未知/未结算/停止/成功项拒绝。同来源有更新文档批次或其它活动/发布时拒绝历史重生成，竞争命令不能绕过资格。 |
| RPG-A06 | 单项 questions、非法尾部、缺正文、身份/版本/manifest/测试契约错误均不能采用；缺项不发布，完整汇总可沿原单 PR/批次事务发布入图。 |
| RPG-A07 | 页面及活动展示真实批次/逐项状态与身份，重生成/停止目标准确，重复点击及历史/跨项目快照不误操作；宽窄屏可用。 |
| RPG-A08 | 两任务隔离真实 Runner/Codex 夹具完成两个并行独立 session，各生成一组完整文档，原生身份、输入、结果和停止证据齐全；六任务规模、失败项重生成及发布入图由受控链覆盖。 |

RPG-M01 为自动验证后的人工体验走查，核对确认信息、进度、失败项操作和审阅体验；参与人/窗口待安排，允许后置，不替代自动失败或真实 session 证据。现按用户授权实施，实际自动结果与未验边界见专属验收。
