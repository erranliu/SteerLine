## 范围与权威

模板只管理 SteerLine 自身增加的固定文字。Runner 发布正文、用户步骤覆盖及原回答继续使用原来源和选择语义；Plan、测试清单、schema、正式 writer 源码及原报告仍归原所有者。动态参数仅提供原事实，不承担追加固定规则的职责。

不新增 Runner 协议、数据库字段、旧版兼容、热更新、提示词服务、运行时编辑界面、自动摘要/截断或字节/token 上限。现有输入限额、来源校验和生命周期不变。

## 行为契约

### PG-A01：文件是固定文字的唯一来源

在 `internal/prompts/` 按现有用途保存 Markdown，编译嵌入程序。覆盖测试安排生成、测试执行/只读、writer 两种使用说明、环境生成/准备/发布、Roadmap 解析/文档生成。迁移后删除原固定常量及旧文件副本。

文件与用途直接由 Go 中少量显式函数绑定；不另建 `catalog.json`、参数元数据表、模板版本表、动态注册或片段引用图。确有两处完全相同且必须同步的固定说明时，可共用一个私有片段，调用关系写在代码里，不为此实现 include 系统。

模板解析、必需参数错误在提交外部请求前失败，不回退到内联正文或另一模板版本。程序只使用当前构建嵌入的文件，不读取应用 home、项目目录或网络上的替换模板。

### PG-A02：集中组装，不集中业务决策

`internal/prompts` 提供按用途的小函数，共用私有渲染辅助函数。参数沿用现有事实投影和必要的 Go 参数结构；不额外为每个字段维护一份 schema/注册表，也不引入通用 `extraInstructions` 或对外开放任意模板入口。

原 owner 继续决定测试安排、材料资格、失败投影及步骤选择；prompts 只做文字渲染和原正文组合，不查询 Git/数据库、调用 Runner 或管理执行状态。叶模型不反向依赖 prompts/app；无需为格式化建立第二套业务模型。writer 源码复用正式资产入口，不在模板中复制源码。

固定标签、阅读要求和行为约束来自模板；提交、路径、ID、前轮原因等来自原事实。动态值只作为数据参与一次渲染，不再解释其中的模板语法。保持必要原因、数组顺序和用户原文；仅固定模板明确采用 UTF-8/LF，不对外部正文和材料统一 trim 或改换行。事实参数不得由业务代码硬编码成新行为规则，但不以关键词过滤实际用户内容或诊断事实。

### PG-A03：一次组合与原有阶段语义

普通任务仍由 runnerclient 按公开 contract 选择原 Runner/用户正文：实施和审计附执行上下文，发布和报告附只读约束。环境 prepare/publish 仍按现有契约覆盖指定步骤，不改成追加 Runner 默认正文。组装器从原始正文生成最终结果，业务适配点只将结果放入原协议字段，不在前后拼接固定规则。

用单一调用路径与实际请求断言避免重复追加，不新增组件 ID、来源凭证类型、运行时文本识别或跨请求去重状态。相同输入重复调用纯函数应得到相同结果；不得根据正文相似度删除用户输入。

有同源 helper 才引用实际固定工作区文件，否则完整内联正式 writer；发布/报告不得获得测试 writer 或测试进度写入权限。必要材料继续走现有 inline、固定仓库快照及真实文件通道，不改成模型无法访问的调用方本机路径。

### PG-A04：有限结构检查与消费者验证

复用源码边界设施，检查两个可机械判定的结构约束：固定模板只能由 prompts 嵌入；实际指令字段和 workflow 覆盖只在明确的现有消费者中写入。扫描产品源文件，包含新增文件和非当前 build tag 文件；新增写入点须显式接入并补实际请求测试，不能靠注释豁免。

对已登记适配点的直接内联正文、渲染后直接拼接/替换补简单语法反例。不承诺静态识别所有辅助函数、动态数据和任意事实字符串的含义，不实施全程序数据流追踪或维护事实生产者白名单。间接夹带规则由相关代码审查和实际请求差异发现，守卫通过不构成语义安全证明。

在现有消费者测试中捕获 submit 前实际请求，核对最终正文、原内容完整性、阶段和重复次数。覆盖生产入口，而非只测试独立 Markdown。

### PG-A05：用少量快照暴露增长和改写

给每个实际用途及有意义分支维护无秘密的合成输入和完整调用方正文期望值，覆盖 writer 两分支、Runner/用户正文、环境前轮事实及 Roadmap 规范引用。沿用 owner 测试中的大材料，避免多处保存同一套业务夹具。

模板、组装代码或快照变化时，PR 给出同一输入的实际正文差异和 UTF-8 字节数前后值；简单测试输出或测试辅助函数即可，不要求运行两个 Git 提交的程序或持久化分项计量体系。必要大材料单独说明，不把字段搬家当减量，不把调用方正文统计说成全部模型输入。

新增、增长、缩短和等长改写都须说明业务依据；增长还须说明是否替代已有规则及为何需要保留。检查不自动接受/刷新快照；显式更新期望值只表示记录变化，仍须审核。保留关键业务断言，不能只靠“快照一致”证明正确性。

### PG-A06：复用仓库审核与原生保护

在项目规则中明确：固定指令只能改模板，提示词变更必须展示正文差异、原因和验证。审核范围包括模板/组装包、实际接线、被发送的固定资产、相关测试和检查配置；普通业务 PR 含上述变化也适用。新写入点由 PG-A04 检查发现，不把一切无法排除的源码变动都升级成提示词专属审批。

本地门禁使用现有 Go 测试和 L1 入口，不新增 `cmd/prompt-check`、跨版本比较器、审批状态机或独立 CI 执行服务。首次交付本机制时，维护者审核完整新增模板和组装差异，不能自行信任首份快照。

远端硬性阻止未经审核合并时，复用托管平台原生必需状态与审批/代码所有者规则，保护模板、组装、接线和 CI 配置；平台不支持按路径审核时可采用仓库统一独立审批，不自建审批服务。必需检查绑定最新 PR head，更新后撤销过期批准，合并前按平台支持核验目标基线；普通角色不得直接推送或绕过。修改快照或 CI 本身不能免除独立审核。

实施时已只读核实 GitHub 仓库原有 Actions 工作流为 0、main 未保护，并提供复用 L1 的原生 job；审核资格及远端接入效果仍待核实。不能以自建可信 runner、离线执行隔离或新安全平台作为本功能前置。原生功能不满足必要保护时记录限制，不暗加替代系统。本轮不配置远端；仓库内检测与真实保护生效分别验收，保护未生效就不能宣称已阻止未经审核合并。管理员主动关闭规则不在保证范围。

### PG-A07：沿用已有冻结机制

新请求准备与预留时，用迁移后的同一渲染函数继续完成原测试安排/正文绑定校验，保留来源、writer 模式、CAS 和原幂等冲突检查。不得因为迁出模板就删除原约束，也不从自然语言反推测试安排。

已持久化候选的读取、更新、观察与恢复沿用原请求及不可变比较；不因新模板重新渲染、改写或产生新请求。不同 Runner 构建准入、原号重放及未知投递继续沿[worker 生命周期](../../docs/product-design/worker-lifecycle.md)，本次不扩大或重写这些规则。

不新增冻结正文解析、历史模板查找、模板 pin、快照绑定字段或专属恢复流程。若实施中发现某个真实恢复调用点依赖当前模板，先用用例证明，再修订最小范围；不能把尚不存在的问题当成本次存储重构依据。

### PG-A08：交付判定

仓库实现以 PG-A01–A07 的测试、实际正文差异及正常独立代码审查验收，不增加可信 CI 编排模拟器或对抗整套托管平台的测试工具。测试与审核配置在同一 PR 变更时，也必须展示并审核其影响。

真实原生保护作为 PG-E01 单独验证：缺状态/缺审批被拒绝，追加提交后旧批准失效，合法最新提交可合并。使用专属测试仓库或分支，权限和操作范围执行前固定。未启用或未验证仅能交付本地检测能力，不能把真实保护算作已完成；也不因此阻塞与托管设置无关的仓库代码实现。

实现与最小验证见 [Plan](../plans/prompt-governance.plan.md)，实现、回归与必需外部项分别按[专属验收](../testing/acceptance/prompt-governance.md)的实际状态判断，不以仓库内通过代替远端生效。
