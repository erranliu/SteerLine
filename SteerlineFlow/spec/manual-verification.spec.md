# 人工核验 Spec

本文记录首版设计。后续待办关闭及合入后核验行为见[长期产品设计](../../docs/product-design/manual-verification.md)。实现与联验状态见[专属验收](../testing/acceptance/manual-verification.md)。[实施 Plan](../plans/manual-verification.plan.md)

## 目标与范围

用户在项目级「人工核验」页面处理开发候选的待核验 PR。Plan 可声明人工核验项和项目自己的启动命令。Runner 完成原发布前步骤后直接创建草稿 PR。核验人从页面启动该 PR 的具体提交，逐项保存结论。人工核验通过后，负责人在 PR 平台标记 Ready 并决定合并。SteerLine 按现有真实合并核验记录交付、释放 DAG 后继。 [可靠性交付](../../docs/architecture/reliable-delivery-chain.md#当前业务交付链路)

首版在 SteerLine 本机启动程序，支持已能证明草稿创建及 PR Head 查询能力的发布组合，首个联验目标为 GitHub。已有 PR 合并流程继续由平台和负责人执行。核验失败可从页面进入原候选详情，由用户经现有反馈入口提交复现信息。[Runner 调用生命周期](../../docs/product-design/runner-lifecycle.md)

## 1. Plan 伴随文件

`<name>.plan.md` 的人工核验文件为同目录下的 `<name>.manual-checks.json`。Plan 引用核验 ID 并写明需要人工判断的原因，JSON 是可执行启动配置和核验步骤的唯一来源。支持人工编写和随 Plan 自动生成。自动生成返回可选结构化对象，由 SteerLine 校验并编码，同批交付给文档评审。删除核验需求时同批移除伴随文件。

```json
{
  "version": 1,
  "launch": {
    "program": "node",
    "args": ["scripts/start-preview.mjs", "--port", "${PORT}"],
    "cwd": "web",
    "url": "http://127.0.0.1:${PORT}"
  },
  "checks": [
    {
      "id": "M01",
      "title": "切换项目后显示对应任务",
      "steps": ["打开任务执行页", "从项目 A 切换到项目 B"],
      "expected": "列表显示项目 B 的任务，项目 A 的任务不再出现。"
    }
  ]
}
```

### 字段与校验

整个文件为无 BOM 的 UTF-8 JSON，最大 64 KiB。顶层为单一对象。各层拒绝未知键、重复键、`null`、错误类型和尾随内容。字段长度按解码后的 UTF-8 字节计。字符串禁止 NUL，命令、路径和 URL 另禁止控制字符。标题、步骤、预期结果必须包含非空白内容。

| 路径 | 要求 |
| --- | --- |
| `version` | 必填，JSON 整数 `1`。 |
| `launch` | 必填对象，一份文件定义一个启动入口，供全部核验项共用。 |
| `launch.program` | 必填，1–256 字节。系统可执行文件名匹配 `^[A-Za-z0-9_][A-Za-z0-9_.+-]*$`。仓库内可执行文件使用 `./` 加相对于 `cwd` 的规范路径，采用与 `cwd` 相同的路径分量规则。系统程序从宿主配置的可信绝对 PATH 目录解析，排除当前目录和核验 worktree。脚本可用 `pwsh`、`bash`、`node` 等解释器作为 `program`，通过参数指定脚本。 |
| `launch.args` | 必填数组，0–64 个字符串，每个最多 2,048 字节，允许空参数。按原顺序传给程序。仅在此字段和 `url` 中展开 `${PORT}`，其他 `${…}` 形式或不完整占位符报错。 |
| `launch.cwd` | 可选，默认 `.`，最多 512 字节。除根目录 `.` 外，须为以 `/` 分隔的规范仓库相对目录，无空段、`.`、`..`、反斜杠、冒号或占位符。实际目录及仓库内可执行文件均须在受管 worktree 内，解析时拒绝经过符号链接、junction 或其他重解析点，并按运行机文件系统规则拒绝非法路径。 |
| `launch.url` | 可选，最多 1,024 字节。仅允许 `http://127.0.0.1:${PORT}`，可带路径及查询，禁止凭据和片段。URL 中 `${PORT}` 只出现一次，且 `args` 至少一处使用同一占位符。无 URL 时仍可在参数中使用 `${PORT}`。 |
| `checks` | 必填数组，1–32 项，显示顺序沿用文件顺序。 |
| `checks[].id` | 必填，匹配 `^[A-Z][A-Z0-9_-]{0,31}$`，同文件唯一，作为人工记录的稳定引用。 |
| `checks[].title` | 必填字符串，最多 120 字节。 |
| `checks[].steps` | 必填有序数组，1–20 个字符串，每项最多 1,024 字节。 |
| `checks[].expected` | 必填字符串，最多 2,048 字节，描述核验人可观察的通过条件。 |

生成或写入 Plan 时校验结构。候选准备时，以 Plan 的固定提交读取同名普通 Git 文件，冻结文件路径、提交、原始字节 SHA-256 及解析后的配置。确定文件不存在表示无需人工核验。文件不可读、形状非法或 Git 对象异常时给出定位诊断，阻断新候选准备。运行环境缺依赖、命令启动失败及人工结论未完成均发生在此之外，草稿发布无需等待。候选实现提交即使改了同名文件，核验页面仍使用原冻结配置。更改核验要求需更新 Plan 依据并创建新候选。[固定材料与候选准备](../../docs/product-design/runner-lifecycle.md#项目材料与辅助执行)

## 2. 草稿 PR 的发布与观察

1. 有核验项时，SteerLine 在候选受理前验证所选 Runner 工作流和发布组合支持草稿创建、稳定 PR 身份、草稿状态及 Head 查询。把创建草稿的意图随原发布输入持久化。缺能力的组合报告明确原因，无人工核验要求的候选沿原路径发布。
2. Runner 在现有发布阶段按冻结目标提交、推送、创建草稿 PR。首个成功发布以候选的原 PR 身份、目标仓库、base、head 仓库及分支、完整 Head SHA 和平台显式 `draft=true` 为证。PR 创建未知时查询原发布意图，沿既有 W16 对账。已绑定到同一候选的普通 PR、草稿状态缺失或身份冲突进入发布诊断，保留原绑定和可核实事实，避免重复创建 PR。负责人后续在平台合法切换 Ready 时，继续观察同一个 PR。
3. SteerLine 在首次核实草稿后创建候选 PR 核验记录。既有 PR 观察更新当前 Head 与终态，短暂查询失败保留最后确认的 Head 并显示观察状态。同一任务的并行候选各自独立。修复更新原 PR 后，新 Head 的核验项全部待核验，旧 Head 的结果留在历史。PR 关闭、合并或候选终止参与后归档，保留真实结论和本机资源的收尾入口。PR 若在核验完成前被平台合并，历史显示实际未完成项，交付仍沿现有合并事实结算。

## 3. 页面、worktree 和进程

### 页面与命令边界

项目侧栏在「测试管理」旁提供「人工核验」。默认待办按候选 PR 展示任务、PR 链接、当前 Head、通过数及最近启动状态。全部通过的当前提交显示「可打开 PR」，已关闭和旧 Head 在详情历史中查询。详情展示冻结命令与 `cwd`、核验步骤、实际 worktree、启动参数、进程状态、有界日志、可访问 URL 及逐项结论。页面读取只展示保存的事实。启动、停止和保存结论使用项目范围的显式命令，携带请求 ID、目标记录版本及所见完整 Head。服务端核对项目和实例，按原请求回执去重。

### 创建并启动

1. 核验人查看命令及 PR Head 后点击「创建 worktree 并启动」。服务端按候选冻结的 provider 重新查询 PR，确认仍开放、身份匹配且 Head 等于请求所见值。Head 变化则返回新值，由用户对新版本发起启动。请求体只选核验记录和 Head，命令从冻结配置取得。
2. 保存启动意图，再从已绑定仓库按受支持的 PR Head ref 拉取，或从已核实属于该 PR 的远端 Head 分支拉取到私有 ref。核对拉取对象是目标完整提交，采用 `git worktree add --detach` 在本机受管目录创建核验 worktree，检查实际 HEAD、仓库身份及路径。创建期间分支前移且无法从该次拉取证明原提交时，报 Head 变化并保留诊断。开发候选 worktree 仍由 Runner 管理。
3. 在进程启动前校验实际 `cwd`、解析程序并展示实际参数。`${PORT}` 由宿主分配一次本机回环端口，同一值用于参数和 URL。SteerLine 串行分配自身端口并跟踪占用。端口交给子进程时若遭占用，记启动失败，由用户重试。程序按可执行文件及参数数组直启，无隐式 shell、变量扩展或命令拼接。命令可显式调用解释器运行项目脚本，脚本从核验 worktree 读取。仅显式启动操作运行 PR 代码，以本机用户权限执行。worktree 提供 Git 隔离，进程可能访问该用户可访问的资源。子进程使用精简系统环境、可信 PATH、独立临时目录，不继承服务的 PR token 或 Runner 认证环境。项目启动入口负责隔离其数据库及外部资源，使用前台进程和所分配的端口。
4. 每个项目、候选 PR 与 Head 最多一个在途或运行实例。重复点击回到原实例。启动失败、已结束或已停止且资源已结算后可显式再启动，使用新尝试 ID。URL 存在时，最多等待 120 秒，观察本次前台进程存活及回环 HTTP 返回 2xx 或 3xx，探测不跟随跳转。探测成功仅表示预览可访问。无 URL 时展示实际进程状态和退出码，允许正常退出的 CLI 核验。失败保留有界 stdout、stderr、退出码和诊断。

### 停止与清理

服务端记录原启动身份、进程树、端口及目录。用户可以停止原实例，或者在确认进程树停止后显式移除自己的核验 worktree。关闭浏览器只结束观察。宿主正常退出时结算本机核验进程。异常退出后先按原启动意图核实受管目录和进程身份。身份未知时显示需处理，停止、删除和重复启动等动作须等原资源核实。清理使用 Git 的非强制 worktree 移除，遇本地变更保留目录并显示原因。日志和核验历史独立于 worktree 保存。

## 4. 核验结果

每项初始待核验，核验人可在同一 Head 下逐项保存 `passed` 或 `failed`。结果追加记录，当前状态采用该项最新结论。记录包含项目、任务、候选、PR 身份、完整 Head、核验项 ID、冻结文件摘要、启动尝试 ID、服务端操作者和 UTC 时间、结论、备注及可选证据链接。失败必填复现或实际表现。备注最多 4,096 字节，证据最多 8 条绝对 HTTP(S) URL，每条最多 2,048 字节，禁止 URL 凭据，服务端仅保存链接。

允许引用一次已启动且未发生启动失败的尝试，进程随后正常退出或被停止仍可提交。提交时核对尝试与原记录、Head 和冻结配置绑定，确认 worktree 的实际 HEAD 和受跟踪文件与该提交一致。服务端刷新 PR Head，并在事务内重核记录版本和尝试关联。PR 查询失败、PR 已终态、版本冲突或 Head 已变化时，保留输入供用户查看并拒绝本次提交。若远端提交发生在本次查询之后，下一次观察切换当前 Head，已写入的结论仍只属于原 SHA。已提交的旧 Head 结论可在历史中查阅。启动成功、自动测试通过和 PR 合并均不生成 `passed`。

## 5. 通过条件

| ID | 可观察结果 |
| --- | --- |
| MV1 | 同批生成的核验 JSON 通过确定性校验，候选冻结原文件来源，省略文件仍可走原发布流程。 |
| MV2 | 有核验项的候选在零人工输入、零核验进程时发布真实草稿 PR，查询后出现一条候选 PR 待办，发布未知沿原意图对账。 |
| MV3 | 页面从实际 PR 提交创建独立 worktree，执行冻结命令并展示正确 URL 或进程输出。重复启动、失败重试、停止及清理均定位原资源。 |
| MV4 | 逐项结论可追溯到 PR、提交和启动尝试。推送新 Head 后旧结论不计入当前进度，过期提交被拒绝，兄弟候选结果独立。 |
| MV5 | 人工通过后可打开原 PR，用户在平台决定 Ready 和合并。直接合并仍记录真实交付，未核验项保留在历史。 |
