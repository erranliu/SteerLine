## 1. 问题与目标

当前环境资格已按项目 × 环境键隔离，并合并仅模型、思考强度不同的方案。但页面先展示项目级准备材料及“生成配置”，再展示运行机和环境；材料生成请求只选生成方案，没有独立指定待准备环境，生成与验收历史也混在项目级列表中。用户难以判断自己正在准备哪台机器、哪条链路，以及模型选择会影响什么。

本次统一为：**先确定项目 × 运行机 × 执行链路，再围绕该对象生成材料、完成准备、运行验收和查看结果。模型方案属于生成或验收操作的参数，不作为环境准备列表的条目。**

2026-11-01 补充：**被管理项目负责提出环境要求和声明材料来源；SteerLine 只拥有生成、执行及报告协议。** 当前实现以内部完整规则要求项目复制同源正文，并硬编码项目辅助脚本和测试文件路径，混合了两种所有权。本稿撤销这些项目内容约束，保留已实现的准备单元、目标绑定及页面组织；不把长规则换个文件后继续由 SteerLine 决定项目要求。

本次收简为：首次适配一次生成项目入口、环境要求文档和配套脚本，整体审阅后一次 Git 固定；每个环境以 environment.md 为唯一验收要求及检查声明来源。取消独立 input、待提交 context 和生成参考清单，不再先提交输入后生成产物。环境与任务仍共用唯一正式测试来源，运行依赖复用 manifest，原始报告解析归测试场景。本轮实现已声明项目的接口消费、环境生成/更新和验收；整个项目的首次初始化适配另行实现。

用户应能直接回答：当前准备对象是什么、要求是什么、下一步做什么、通过后覆盖哪些执行方案、失败发生在哪里。

## 2. 操作对象与边界

| 概念 | 含义 | 在流程中的位置 |
| --- | --- | --- |
| 项目 | 当前业务仓库、正式 L2、发布目标及要求 | 项目导航已确定，不在操作中重复选项目 |
| 运行机 | 当前 execution.target 表达的本机或明确远端目标 | 环境列表的第一层分组 |
| 执行链路 | adapter、Agent 入口、权限及其他非模型执行上下文 | 运行机下的环境准备条目 |
| 执行方案 | 已保存的完整 execution/workflow，含模型和思考强度 | 在生成、验收操作中选择；业务任务仍按原流程选择 |
| 环境准备单元 | 项目身份 × 原 environment_key | 关联目标材料、当前资格、验收活动及生成历史 |

“链路”不是仅按名称归类。相同运行机上的 Codex 直连、Orca → Codex、Orca → Pi、Orca → DSH 分别准备；同名链路的入口或权限不同，也仍是不同准备单元。页面应展示可读名称和共用方案，必要时用原环境键短值辅助区分，完整键由后端提供和校验。

继续由现有规范函数对完整 adapter/target/settings 计算环境键，仅排除已约定的结构化模型和思考强度字段。不得由前端按机器名、模型或链路标题重新分组资格。模型名称、profile ID/名称变化不单独产生新环境；其他设置变化是否产生新环境完全遵循原键规则。

运行机分组来自已加载 target，不新增主机注册、自动发现、环境别名或全局 ready。本机表示当前宿主本机，不承诺自动识别机器重建或跨 home 物理身份。项目之间分别验收；生成专用方案不形成开发环境条目。

当前安装配置可用于说明列表结果：

| 项目 | 运行机 | 链路 | 共用执行方案 |
| --- | --- | --- | --- |
| SteerlineTest | 本机 | Codex 直连 | Luna medium、high、xhigh |
| SteerlineTest | 台式机64g | Orca → Codex | Luna high、xhigh |
| SteerlineTest | 本机 | Orca → Pi | DeepSeek Flash high |

这是七个方案对应四个准备单元的示例，不把具体机器、Agent、模型或数量硬编码为产品规则，也不表示这些环境已经通过。

### 2.1 要求与协议的所有权

| 归属 | 内容及约束 |
| --- | --- |
| 被管理项目 | 平台、工具与版本、依赖、服务、权限和非秘密凭据引用、必须检查的环境项、准备方法、正式 L2 定义与入口、PR 验收标准及所需文件。由项目在 Git 中维护，正文不与 SteerLine 内置资产比对；生成 Agent 不得自行发明要求 |
| SteerLine | 目标与来源绑定、有限文件选择、生成输出 schema、环境 manifest、prepare/publish 阶段、进度及报告 schema、原 PR 身份、停止与封存、资格和活动事务。固定指令只说明如何遵循项目要求及交换结果 |
| 初始化适配 Agent（未来能力） | 按通用指导调查实际项目，形成项目要求、接口声明和脚本草稿及 gaps；经审阅与正常 Git 流程固定为项目材料，不把模型推测或生成完成当作通过 |
| 日常材料生成 Agent | 按已采用的项目要求及目标事实生成/更新环境说明、脚本和 gaps，薄调用原入口，不自行改变已批准的标准或补装工具 |

完整正式 L2、真实验证 PR、实际 TTY 及原 Run 停止/报告封存继续作为 SteerLine 环境准入协议的统一门槛。项目定义 L2 的内容、工具、版本、业务环境检查和 PR 规则；声明不能为空，不能通过项目说明取消这些协议门槛。分支规则核实、审核及合并仍由外部所有者负责，不加入生产 ready 的 Agent 步骤。

SteerLine 限定当前支持的脚本类型、解释器入口及调用参数；Runner 能力目录只核验实际公布的执行链路、workflow 和结果通道，不假定存在解释器能力目录，也不新增该契约。目标机器是否具备解释器、工具及所需版本，由项目脚本现场检测，不能以生成宿主的安装代替。最低工具版本由项目要求声明，不规定所有项目都依赖 Windows PowerShell 5.1、Python 或某个安装路径。项目声明超出现有脚本调用协议时明确阻断，本轮不扩展脚本类型。`File.Replace` 参数、数组写法等语言实现经验属于项目脚本或项目自选参考，不进入通用行为规则。

### 2.2 指导 → 项目接口的二级机制

第一级由 SteerLine 在 [SteerlineProjectGuideDoc/environment-adaptation.md](../../SteerlineProjectGuideDoc/environment-adaptation.md) 维护通用适配指导，并提供生成、执行与报告协议。指导说明如何调查真实项目、识别缺口、形成项目要求及接口；项目工具、版本和业务检查不是该固定指导的默认要求。

第二级是据此形成的项目自有要求和具体脚本。未来“项目初始化适配”以完整指导/协议、固定项目源码及明确目标为输入，一次输出项目入口、所选环境的 environment.md 与配套脚本及 gaps，整体审阅后一次 Git 固定；已有正式项目入口直接复用。SteerLine 随后读取这些文件并调用验收。要求和必需检查在同一份环境文档中，不再生成另一份标准 input 或项目通用指南。

指导在形成/适配项目接口时读取；日常脚本生成按已采用的项目要求及生成协议执行，验收按项目正式接口及执行/报告协议执行，不强制每次附带完整调查指导，也不把它或纯生成参考计入 ready 依据。

本轮交付指导设计稿及消费边界，不实现初始化适配 API、项目自动调查、落盘/提交或纳管功能。现阶段可由用户或授权 Agent 一次准备配套草稿；未来初始化适配提供同样的整体生成，不要求先有项目入口、环境文档/脚本、input/context 提交或 ready。日常更新优先遵循正式 environment.md；确需变更标准时在同一草稿包中显示要求与脚本的配套差异，经 Git 采用后生效，运行验收不能自行改标准。

未来接线须冻结指导版本、项目来源、目标事实和输出，缺指导或事实不全则阻断或保留 gaps，不把固定指导内联成业务代码规则。生成、应用、Git 发布、环境验收与资格判定各保留原授权和事实边界；本指导不触发当前只读项目结构核验或普通“添加项目”自动执行。相关产品设计见[添加项目](../../docs/product-design/project-management.md)及其[准备方案](../../docs/product-design/project-onboarding-prompt.md)，未来能力另行补实施与真实验证，不继承本轮验收。

## 3. 页面结构

沿用项目“运行环境”入口及现有路由。页面先选择环境，选中后展示该环境的工作区；没有选中环境时不显示可提交的材料生成或验收表单。

```text
SteerlineTest / 运行环境       服务在线 · 环境已就绪 1/4

运行机及链路                        当前准备对象
本机                                SteerlineTest / 本机 / Codex 直连
  Codex 直连        已就绪           状态、原因、下一步
  Orca → Pi         未准备           共用方案：Luna medium / high / xhigh
  Orca → DSH        验收阻断
台式机64g                           准备要求与材料
  Orca → Codex      待准备与验收       [阅读要求] [生成或更新材料]

                                    在本机实际执行账号下完成准备
                                    按要求准备工具、依赖、变量及权限

                                    环境验收
                                    [开始验收 / 重新验收]

                                    当前结果与本环境历史
                                    检查 / L2 / PR发布 / 收尾
```

宽屏可使用列表与详情两栏；窄屏按环境选择区、当前对象、详情的顺序排列。层级与操作归属必须一致，不要求保留两栏几何布局。原始技术信息折叠，主要界面不展示完整 settings、认证值或大量执行 ID。

列表每项显示链路名称、环境阶段和简短原因；模型不占独立行。顶部环境数量按准备单元去重，区分服务在线与环境就绪。没有开发方案时显示配置入口；查询未成功不能以空列表或 `0/0` 冒充没有环境。

详情标题始终显示“项目 / 运行机 / 链路”，同一标题下组织以下内容：

| 区域 | 首屏信息与操作 |
| --- | --- |
| 当前状态 | 原六阶段、当前原因、下一步、通过后共用的方案范围 |
| 准备要求与材料 | 选中环境的准备文档、脚本入口、来源提交、材料缺项；生成或更新入口 |
| 用户准备 | 在该运行机实际执行账号下准备的具体要求与责任 |
| 环境验收 | 开始或重新验收入口，运行中显示进度与停止原活动入口 |
| 结果与历史 | 当前验收结果，本环境材料生成及验收记录；历史通过与当前资格明确区分 |

这些区域是阅读和操作顺序，不新增持久化的“已阅读、已安装、已确认准备”状态，也不要求用户逐步打勾解锁。材料完整且原前置满足时可直接开始验收，无须先运行生成。

## 4. 端到端流程

### 4.0 项目要求和接口从何而来

用户只需经历“选项目/环境 → 首次适配一次生成配套材料 → 整体审阅并一次 Git 固定 → 在目标机器准备 → 调用验收”。已有正式材料直接进入准备和验收；标准变化再配套更新。未来初始化适配根据指导调查实际项目并生成完整草稿包，当前可按指导人工或经授权 Agent 准备；生成不等于已准备或 ready。只为已选目标生成，新目标补自己的文档/脚本，不要求先建声明文件或先提交一次目标上下文。预览区分项目事实缺口和目标工具不满足。

### 4.1 选择环境

用户进入当前项目的运行环境页，先在运行机下选择链路。直接从任务阻断入口进入时，沿已选 profile 定位对应环境，并带入验收方案；普通进入可选中该项目默认执行方案对应的环境，没有有效默认定位时让用户明确选择，不因排序变化自动改投。

切换环境只改变观察和操作草稿，不发送 Runner 请求、不标记失效、不改变默认执行方案。生成或验收表单提交前必须再次显示完整目标及本次模型方案。切换后不得将旧表单的目标键、revision、生成结果或回执套到新环境。

### 4.2 针对所选环境生成材料

用户点击“生成或更新准备材料”，在当前环境详情中展开操作区，明确分列：

- **材料适用环境**：当前项目 / 运行机 / 链路，只读，含权限或入口的必要区分说明。
- **生成所用方案**：从当前支持 generate 的已保存方案中选择，显示生成执行位置、Agent、模型和思考强度。

生成执行位置与材料目标可以不同。例如，本机 Codex 为“台式机64g / Orca → Codex”生成材料。选择生成方案不得改变材料目标，目标环境未就绪也不阻止生成。首版沿现有仅本机 Codex 的只读生成能力，不因目标是 Orca 就扩展远端生成或借验收权限生成。

只有一个可用生成方案时直接展示并使用；多个时优先使用有效的原生成选择，其次使用支持生成的全局默认方案，否则要求明确选择。普通进入时不把任务带入的远端开发方案当生成方案。界面统一使用“生成所用方案”，移除含义不清的“生成配置”。

生成冻结选中环境完整键、允许公开的少量目标事实、固定项目提交、发布目标及实际读取的项目文件；已有 environment.md 为正式标准。完整 execution 只在后端计算键并冻结，不导出 settings 原文。生成 execution 仅负责生成，不代表待准备环境；切换模型不能改变材料目标。

目标事实来自已加载配置，只含项目/键、adapter/target、Agent、明确入口/平台、结构化权限及公开发布目标；未知信息列 gaps，不按机器名或生成宿主猜测，不透传参数、环境变量值、transport 或认证正文。它们作为原调用信封中的定位事实冻结，由同包短指令参数引用，不生成项目 context 文件。完整历史报告保留在原活动供回看，不再作为生成必读长正文；验收后继轮初始文件中的完整 previous 沿原规则保留，不删改历史或跨环境拼接。

首次适配读取完整通用指导、采用版本的生成/执行协议和真实项目快照，调查后一次形成配套草稿；待生成项目入口、环境文档和脚本不存在不构成前置失败。指导和完整协议仍经实际可读的固定文件提供，不能以 inline 规则或预先往项目提交文件绕过渠道缺失。未来初始化接线前核验现有只读文件能力能共同提供指导和项目快照；不假定 Runner 有尚未公布的跨来源/临时文件接口，能力不足须列为未来功能缺口，不能退回要求用户先提交输入。

已有项目的材料生成只有两种读取方式，由原生成入口处理，不新增用户步骤、状态机或配置：没有本环境文档时，读取完整适配指导/协议和固定项目快照调查，直接形成首份文档/脚本；已有有效文档且其引用足以更新时，优先按显式引用读取有限文件。首份环境材料不只读取入口和测试清单，否则无法调查实际程序。调查使用 Runner 已公布的固定整树快照或经核验足够的显式文件集，受原安全/容量边界约束，不猜命令、不执行项目程序调查环境。

旧文档机器段错误、脚本缺失或旧运行依赖已删除/改名时，保留原可读正文、源提交/摘要及失效路径诊断，转入同一固定源码的适配调查提出修复草稿；不要求用户先把旧接口修好才能生成。旧引用仅作为待修事实，非法/跨环境路径不解引用，不能自动降低原要求。完整指导/协议、已核验源码及本次实际必读的项目政策/正式测试定义属于生成依据，缺失或无法安全读取时仍在新请求前阻断，不能以旧引用失效为由补造标准；可核实的事实不足时写入下述阻断缺口。生成能完成不等于验收材料已完整，验收始终严格要求全部正式运行依赖存在。

两种读取方式都冻结原请求的目标、来源和实际可读文件集合；所需调查渠道/完整指导不可用时显示执行能力缺口，不假定新 Runner 接口，不回退为 input/context 预提交。没有独立生成参考列表或“输入先通过”步骤，查询只预览不写仓库。项目事实缺口、旧接口失效与目标机器工具不满足分别说明；更新阶段不靠扫描或猜测拼正式运行依赖。

日常生成只输出该环境的 environment.md、配套脚本及从文档投影的 gaps；未来首次适配额外一并形成缺失项目入口/必要公共说明，不拆成中间产物。输出校验目标、manifest、路径/解释器、检查 ID、依赖及字节边界，错误保留原输出与诊断。未解决的标准/引用缺口写入同一环境文档机器段的 gaps，顶层 gaps 仅供界面展示并须与文档逐项相等，不维护另一套缺口事实；非空可审阅导出和 Git 保存，但正式验收不能启动。标准与脚本变更一起显示 diff，不自动应用、提交或运行。

页面明确显示“生成完成，尚未提交到项目”。此提示说明产品没有自动写入；后续只能依据正式提交内的实际材料读取结果说明可用于验收，不能长期断言用户尚未自行提交。源代码提交变化后，生成结果仍属于原来源，不能在刷新时假装已应用。已有材料适用时直接读取，不强制重生成。

生成失败或取消保留原活动和原因；重试沿原明确授权和请求规则。生成成功、查看、下载均不授予资格，也不自动切断原 ready；正式提交后，只有该环境的有限准备依据实际变化才按原规则失效。

### 4.3 用户完成实际准备

用户阅读选中环境的要求，在对应运行机、实际执行账号及执行进程可见的上下文中准备工具、依赖、服务、环境变量、许可与权限。准备文档可引用项目公共要求，但必须清楚说明本环境适用项和具体工具入口，不能让用户从其他链路文档中自行推断。

SteerLine 展示要求和缺口，不新增安装器、远端修复、自动改 PATH、凭据复制或人工批准 ready 的入口。材料完整只表示可以按既有规则申请验收，不证明机器已满足要求。

### 4.4 在所选环境验收

点击“开始验收”或“重新验收”，在当前环境内展开操作区：

1. 显示固定的项目、运行机、链路、材料来源及本次影响范围。
2. 选择“验收所用方案”，只列该环境键下的开发方案；展示模型与思考强度。单方案直接展示，多方案优先使用任务带入的有效方案，其次该环境内的默认方案，否则要求明确选择。
3. 保留原每轮总超时及原三轮预算说明，说明将调用模型、运行检查和完整 L2、执行 commit/push 及创建真实验证 PR。
4. 已就绪环境重新验收时，在提交按钮旁说明开始后立即撤下旧资格；不新增单独的前置批准命令。
5. 用户明确提交后才开始原活动。原活动未结算、配置待生效或原目标占用等情况按原守卫阻断并显示具体原因。

开始后定位当前活动，展示第几轮/共三轮、进度、截止时间及停止原活动。未知回执只对账原请求；双击或刷新不得另建活动。切换观察其他环境不停止原执行。

验收在选定环境的实际链路执行；通过要求仍为同轮 checks（含实际 TTY）、完整 L2、同一原 PR 发布身份、脚本自有资源清理、原 Run 停止及 result 封存全部核实。Agent 不承担外部分支规则核实、审核或合并；相关真实 L4 仍独立取证。不得跨轮、跨链路或跨项目拼接通过项。

通过后仅本项目该准备单元就绪，共用方案仍须满足 Runner 原能力及任务其他前置。失败展示具体不通过/未验证项与下一步，沿原预算及未知处理规则，不自动安装修复、不改验收标准、不回退历史资格。

## 5. 材料按环境归属

材料只保留项目级定位入口和每个环境的一份要求文档、一个脚本。固定生成/执行协议是产品提供的契约副本，不能承载项目工具政策。

```text
SteerlineFlow/
  environment-project.json            # 公共材料引用及唯一正式测试清单
  environment-generation.md           # 生成协议
  environment-execution.md            # 执行/报告协议
  environments/
    <完整 environment_key>/
      environment.md                  # 唯一环境要求、检查声明及 manifest
      verify-environment.ps1          # 或 verify-environment.sh
```

不维护 environment-input.json 或必须提交的 environment-context.json。公开目标事实在 SteerLine 原活动中冻结；首次适配连同所需协议副本、项目入口和环境文档/脚本一次形成草稿包，整体经正常 Git 流程固定。已有正式入口/协议直接复用，不制造“先提交规则/输入才能生成”的中间轮次。

### 5.1 项目入口与唯一要求来源

项目入口 `SteerlineFlow/environment-project.json` 使用 version=1，字段只有 version、requirements、testing_catalogue：

```json
{
  "version": 1,
  "requirements": ["docs/project-policy.md"],
  "testing_catalogue": "quality/catalogue.json"
}
```

requirements 是项目公共政策/事实文档的显式唯一数组，可为空；入口只定位来源，不定义各环境检查集合，也不放生成参考或运行依赖清单。路径为项目自选示例，不是内置模板。初始化可引用已有正式清单，不要求先生成一份空清单；项目实际没有正式 L2 时报告真实缺口，不能凭草稿编造测试或视为可验收。

testing_catalogue 是整个项目唯一正式清单路径，沿现有格式解析。测试安排生成/固定校验、任务材料/准入、测试记录/页面与环境流程均共用该入口及同受测提交；环境取全部 L2，至少一项，不按链路/模型裁剪。不保留旧路径回读、另一份正式清单或等价对账机制，不扩大为通用测试配置平台。

每个环境的 environment.md 是本环境唯一验收要求契约：正文逐项说明平台、工具/版本、服务/权限、非秘密引用、准备方式和每个业务检查 ID 对应的期望与检测入口；唯一机器段索引同一组 ID，脚本只实现这些要求。公共文档可明确引用，公共入口和脚本不能另列一套标准；引用存在冲突则报告缺口，不由模型自行选宽松项。不同环境拥有各自适用集合，不要求为别的平台填通过占位项。

机器段采用本轮实现的 manifest version=3，在原 version/environment_key/script/interpreter/validation_base/dependencies 上增加 required_checks 和 gaps；检查及阻断缺口都由同一文档声明：

```json
{
  "version": 3,
  "environment_key": "<完整 environment_key>",
  "script": "SteerlineFlow/environments/<完整 environment_key>/verify-environment.ps1",
  "interpreter": "powershell.exe",
  "validation_base": "<项目预先维护的验证分支>",
  "required_checks": ["tool.runtime", "service.database"],
  "gaps": [],
  "dependencies": ["quality/verify.ps1", "quality/report_writer.py"]
}
```

该示例为字段示意，键/分支占位符须由实际值替换。required_checks 是业务检查 ID 的唯一声明，可显式为空；terminal.tty 由协议追加，不接受项目重复定义。SteerLine 从同一固定文档冻结检查集合，精确核验报告：漏项、重复、未知、失败或 incomplete 都不能 ready。正文解释该组 ID 的实际要求，机器段不再复制一份条件描述。

gaps 是必须显式提供的唯一、非空白说明字符串数组，可为空，不含秘密；记录尚未确定的项目标准、工具/凭据引用、平台、测试/发布规则或拟用运行文件缺失等阻断事实。gaps 非空、缺字段或格式错误时，仅凭该固定项目文档即可在新验收请求及 Runner 提交前阻断，并显示原原因；无生成记录、新 home 或人工维护的同一材料得到相同结论，不查询原生成活动来补资格状态。缺口解决后随文档/配套实现审阅并 Git 更新；清空 gaps 不是通过证明，仍须完整验收。已有明确标准但目标机器尚未安装工具/配置凭据属于现场 checks 的 failed/incomplete，不写成生成阻断缺口来禁止检测。

dependencies 是验收运行所需文件的唯一补充清单，包含所引用的环境要求依据和正式辅助入口；生成可调查项目源码并将真实运行文件列入草稿，正式采用前供项目审阅。纯生成调查文件只记在原活动来源中，不形成项目配置或自动加入 ready 依据；正式文件已声明但缺失/越界时必须阻断验收。

两个机器格式均拒绝缺字段/null、未知/重复 JSON 键、重复项和非法 ID。路径复用仓库根相对 regular Git blob 规则，拒绝绝对路径、反斜杠、空段、路径穿越、目录/glob、symlink/LFS 和其他环境专属目录；禁止自身/脚本互相依赖或把生成指导、生成协议及目标事实列作运行依赖。保留现有 1 MiB 材料、原 Runner 快照及 64 KiB 报告限额，不新增任意路径长度/项数限制，不递归推断运行依赖。script 精确绑定本键目录内的 ps1/powershell.exe 或 sh/bash；最低版本由项目声明，实际可用性由目标现场检测。

### 5.2 来源、更新及资格依据

源提交由原 repository 入口冻结；少量公开目标事实在原生成活动/请求中保存，不能要求用户先把它们提交到项目，不能写回生成模型的 execution 或用最新事实重构原请求。facts 预览不依赖项目输出存在；配置变化在下一新请求生效，未知回执仍只对账原请求。完整生成文件来源保留原路径/提交/摘要，验收轮次的完整 previous 继续走原结果初始文件。

生成包经一次审阅和 Git 固定后，SteerLine 从同一正式提交读取入口、环境文档、脚本和运行依赖。生成期不要求验证分支事先包含尚未生成的文件；实际开始验收前，项目按原正常 Git 流程核实 validation_base 已存在且包含采用的源码，不将该远端发布条件混成多轮生成前置。manifest3 与报告 version2、Runner 快照版本分别处理，不迁移或兼容 manifest2。

准备依据为本环境文档/脚本、执行/报告协议、实际引用的公共政策及 dependencies 原字节、全部 L2 定义、规范项目入口和原发布/仓库/执行上下文。项目入口集合排序，不计其排版；正文、required_checks 和 gaps 在同一文档摘要内，无另一个 input 投影或生成状态资格。纯调查来源、通用指导、生成协议、模型、活动历史、目标事实的生成投影和其他环境材料不进入依据；真实 execution 仍按原键/规范上下文计入。修改 B 不撤销 A，改共享实际依据使受影响资格失效，仅改生成参考或指导不失效。所有读取和候选事务共用此判定；正式文档改为有阻断缺口时旧资格也不能继续放行。

运行依赖的固定读取/摘要与 Agent 阅读引用分别承担职责：所有声明依赖仍逐项核验并进入原资格依据，完整固定 Git 工作区供脚本按 manifest 调用；不把每个运行辅助文件再次列为 Agent 的阅读引用。原阅读引用保留执行协议、项目入口、正式清单和公共政策，Spec/Plan 仍定位环境文档/脚本。不靠扩大 Runner 文字预算、缩减依赖/检查或新建中间材料来容纳重复路径。

更新标准时要求和脚本作为同一草稿包审阅；只有正式采用后的依据变化才撤销旧资格，生成/导出不撤销或授予 ready。运行中的固定脚本不得修改标准；外部 L4 的 steerline-pr-acceptance 段继续从所选环境文档读取真实项目规则，不猜测零检查/审批。

### 5.3 外部验收证据的边界

SteerLine 产品只消费本规范报告协议及 Runner/PR 身份事实，不解析所有项目的 Python、PowerShell 或其他原始测试报告。L4 的原始 L2 独立核验由测试场景拥有：每个测试项目使用其正式工具和原始报告格式对应的明确校验器，位置随测试项目夹具一起维护，核验固定源码及实际工作区原始证据。现有两类报告解析代码只能作为对应测试项目的专属取证，不可放入生产材料解析 owner，也不可仅改工具路径后宣称支持任意报告格式。

本轮在原 testenv/driver 内按场景显式组织这两类既有校验器和自定义目录夹具，不新增产品侧报告格式注册表、动态校验器协议或项目必须提供的“通过证明”入口。不得执行模型新生成的自证脚本来替代独立核验；若新测试项目使用另一格式，须为该场景明确安排并验证独立校验器。A18 的真实结论仅覆盖实际测试项目及其格式，不扩大到任意项目。

### 5.4 协议维护与版本

固定生成、执行和报告协议由 [internal/prompts](../../internal/prompts/)及同包组装函数维护，按[提示词维护规则](../../docs/prompt-governance.md)仅核验协议副本同源；项目要求正文不由该包维护。新请求从固定仓库读取完整协议及项目材料，缺失阻断，generate.materials 不内联补正文。实施时删除当前长规则中的项目版本/工具政策和项目脚本实现细节，不挪到另一个强制内置文件；同步短指令接线、输出约束、正式资产和验证，给出实际正文差异、UTF-8 字节数前后值、完整必读协议总量与去向、业务原因及独立审核。原 10055 字节版本的批准不覆盖新正文；黄金样本更新不代替批准。

未发布开发版本不提供旧全局材料、旧生成活动或旧格式的读取兼容、迁移、双写或回退；实现如需持久格式变更按项目规则换代。不得自动更新、清空或部署安装环境。

## 6. 请求、查询与历史的最小调整

继续复用原项目环境 Query/Command、活动记录和 journal，不新增环境管理服务或 Runner 专用环境协议。

| 边界 | 本次要求 |
| --- | --- |
| GET /environment/options | 每环境返回对应材料路径、材料状态、阶段和可读展示信息；生成方案独立返回模型/思考强度等公开字段，不透传完整 execution；列表不携带所有环境文档和完整前轮报告 |
| GET /environment/materials?environment_key=… | 只读取得选中环境正式材料、来源、缺项及公开目标事实预览；校验完整键，不接受任意文件路径；无材料仍可定位首次适配，不返回必须提交的期望 context 文件 |
| environment_generate | 显式区分必填的 target_environment_key 与 generator_profile_id；核对目标归属，冻结少量公开目标事实与完整生成 execution，无项目 context 文件前置 |
| environment_start | 显式携带选中 environment_key，保留 profile_id、round_timeout_seconds、expected_current_revision；后端派生 profile 环境键并与选中键相等后才按原流程创建活动 |
| 生成活动 | 保存项目、目标键、目标事实来源/摘要、生成方案及完整生成 execution、源提交、输出和原请求；不能从生成 execution 推导材料目标 |
| 验收活动 | 沿原 execution 推导并核验环境键，冻结所选环境材料及原来源，不增加第二份 ready |
| GET /environment?environment_key=… | 按项目与完整环境键筛选后取最近 20 条摘要；不是先取项目 20 条再由前端筛选。省略筛选时返回原项目最近 20 条；原按活动 ID 详情查询保持 |
| 停止与失效 | 停止仍针对原活动 ID/revision；失效仍针对所选环境及当前引用 revision，不使用活动 revision 替代 |

生成请求目标键不能仅由前端展示保证，验收 profile 也不能允许跨环境提交。无效目标、方案错配或缺少必要固定材料时，在产生本次新 Runner 请求前拒绝，不调用模型、领取 Task 或创建替代验收。旧命令格式不提供兼容别名。

生成与验收使用各自严格 payload，不再将生成借为带 profile_id 的通用 Start；生成不接收验收轮次超时或当前资格 revision。外层仍使用原项目命令目标/version 语义。已有请求号必须先按原完整信封查询回执及冻结活动，再核对新请求的当前配置/材料；目标已移除或材料已变化不能阻断原请求对账，也不能重组冻结输入。原环境目标、来源和请求字节在 SQLite 更新中保持不可变约束。

新增只读路由与查询参数贯通原应用端口、应用 HTTP、客户端、Web 代理及共享路径 allowlist；不靠前端自行拼接绕过校验。读操作只使用项目原提交观察和活动事实，不 fetch、不启动 Agent/Runner、不写库；筛选不改变全量活动枚举与原停止义务。

材料查询要求目标属于当前已加载开发环境；历史筛选只校验完整键格式与原项目范围，不要求该键仍在当前配置中。原活动 ID 查询继续核对项目归属，不能因配置移除而拒绝合法旧历史，也不能越项目读取。

历史默认只显示选中环境，生成项标题为“材料生成 · 生成所用方案”，验收项为“环境验收 · 验收所用方案”；详情保留来源及完整技术证据。旧通过报告不冒充当前资格。

页面另保留“项目全部活动”次要入口，覆盖已从当前配置移除或环境键已变化的活动。配置变化导致旧环境不在列表时，旧未结算活动仍可观察并按原授权停止；不得只按当前环境列表枚举停止、重启或 reset 义务。

## 7. 状态、导航与恢复

沿用未准备、待准备与验收、验收中、已就绪、验收阻断、已失效六阶段及原后端投影优先级，不增加安装完成或材料生成成功即通过的状态。生成自身状态在材料操作及历史中展示，不覆盖环境验收状态；生成中仍可查看原通过报告。

页面应区分：项目材料待适配、目标事实缺口、用户实际工具不满足、执行能力不支持、结果/资源待核实、查询失败。只展示原结构化事实和诊断，不从模型回复或诊断散文推导新资格。

任务准备链接沿所选方案定位项目/环境，并保留返回原任务及原方案的参数；不把生成所用方案写回任务选择，不自动改变全局默认。链接目标已删除或不再匹配时明确提示重新选择，不静默跳到另一环境。

同项目、同实例查询失败时，缓存只标为上次已知状态并显示观察时间；环境新操作按各自原守卫禁用，独立活动详情及停止不被无关 options 失败封死。切换 home、项目、实例或目标环境时隔离查询、操作草稿、结果及 pending 状态；旧环境迟到结果只更新原活动。

生命周期继续遵循 [Worker 生命周期](../../docs/product-design/worker-lifecycle.md) W01–W03、W08–W18 及原 E/V 规则。本次只补目标材料绑定及页面组织，不增加新轮次、自动修复、未知输入重发、跨环境故障推断或资源所有者。原生成配额、单环境当前引用、同目标占用、停止封存、失效与候选预留的事务顺序保持。

## 9. 本轮交付范围

本轮按用户授权实施环境准备解耦，交付项目入口/manifest3 消费、按实际来源生成/修复及验收、共享测试来源、界面与对应协议/测试；工程和真实验收结果按[专属验收](../testing/acceptance/project-environment-workflow.md)分别登记。最终实际正文与接线须独立审核，不能用设计稿或黄金样本更新替代批准。整个项目初始化适配功能仍未实现，不新增初始化按钮、API 或自动纳管流程。测试项目专属 refs/PR/精确合并仅用于已授权隔离验收，不作用于业务主分支，不部署或自动合并功能 PR。
