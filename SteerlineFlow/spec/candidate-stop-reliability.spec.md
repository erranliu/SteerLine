# Spec：候选停止参与的可靠受理与核实

2026-10-25，用户要求完整方案。状态：2026-10-25 自审收敛后已按用户授权实现，自动验证见专属验收，人工体验后置。配套 [Plan](../plans/candidate-stop-reliability.plan.md) 与 [专属验收](../testing/acceptance/candidate-stop-reliability.md)。普通开发规划，不创建 roadmap 任务，不部署或修改安装现场。

## 问题与目标

调查基线为 `9607fb0099dfc00d9f3de35429d4c43fcdc80407`。Task 18 的候选 C3 `6022d7445336420b93fcf253bf9743fd`，原停止请求 `e414cda1e2dc4f9996c2e06139cf2f5f` 于北京时间 2026-10-25 06:47:58 提交，06:49:22 明确拒绝，代码为 `stale_version`，候选仍参与。正式查询接口能够返回原拒绝回执。本次不能把界面持续待核实的直接原因判定为已复现；已确认代码存在过宽版本门禁、共享调度阻塞及浏览器核实无独立期限的风险。

目标是让停止不受无关投影变化影响，外部观察阻塞时仍能及时处理；明确结果可靠到达界面，真实未知则有原因、时间和继续核实入口。不能靠超时伪造失败或成功来结束等待。

本方案替代 [原停止 Spec](candidate-stop.spec.md) 和 [Web 实施 Plan](../plans/web-candidate-stop.plan.md) 中停止要求候选/派发版本完全相等及相应确认禁用条件；其他参与资格、原请求、最后一个保护和停止资源边界继续适用。实际实施后再更新长期产品文档，不提前改写历史验收。

## 1. 停止只核对与参与资格有关的事实

停止永久退出这个固定候选的业务参与。候选 ID、项目和 Task 归属不可变，退出后没有重新参与入口，因此不新增 participation revision、版本历史表或停止状态机。

| 输入或事实 | 停止时的规则 |
| --- | --- |
| 项目/仓库、服务实例、Task ID、候选 ID | 精确匹配；实例更换不得把未知请求转投新实例 |
| request ID、操作者、完整正文 | 固定并持久化；同 ID 内容变化拒绝 |
| `expected_version` / `expected_run_revision` | 保留为用户确认时的观察版本，必须合法、非零且不大于当前版本；当前版本增长不拒绝停止 |
| `expected_control_revision` | 保留为原请求审计内容；停止不要求等于当前派发版本，切换 auto/manual 或暂停不使停止失效 |
| 当前参与状态 | 必须仍为 active 且没有 Task 终态停止义务；已结束返回明确 `candidate_ended` |
| 同任务参与数量 | 写事务重新统计；停止后至少保留一个参与候选，否则 `last_candidate` |
| Runner 状态、连接、PR、测试、材料、Task 状态/版本 | 不作为人工停止的准入条件，不为停止查询外部系统 |

上述放宽只适用于 `stop_candidate`。回答、恢复、派发配置、新建候选及交付继续使用自己的严格版本规则。数据库内部仍以事务读取的当前 revision 做 CAS 并递增，避免覆盖同时提交的真实变化；不拿用户旧观察版本充当数据库写版本。

确认框固定候选身份、编号、项目、任务和实例。后台 revision/派发版本更新不自动关闭或禁用确认；参与资格变化、实例变化、仅剩一个、离线或服务停止接收命令时，展示具体原因。确认后原信封不可改写。

## 2. 复用原请求与退出事实恢复

保留现有 control inbox、commands、withdrawal 和 transport record。withdrawal 在候选写事务内保存 request ID、原观察版本、操作者和首次时间，本身就是原退出已提交的证明。原 Control.Handle 先重放 Command 结果，外层结果丢失时按相同 withdrawal 恢复成功；不增加第二个原子命令 API、不重建事务框架。

原回执读取补齐对原 Command 和 withdrawal 的核对，外层 receipt 文件缺失时仍可得到已提交结果；读取不执行退出，不按别的请求或 Task 终态推测成功。同 ID 改正文拒绝；同请求已提交时，后来过期/重启仍返回原结果。外层回执存在但身份/摘要不匹配时拒绝，不绕过冲突。

事务回滚不留退出事实；业务提交后 HTTP/外层结果丢失不重做退出。未取得持久证明则保持未知，查询端不写 `not_submitted` 或其他推测性终态。停止 POST 开始后自动核实只读原请求。

## 3. 停止及时处理，保留一个串行业务执行者

现有 actor 同步执行候选观察、测试生成观察、派发和 PR 检查，control 的 500ms tick 不能抢占正在执行的长调用。仅调整 select 顺序不能解决问题。

本次在原 actor/scheduler 中加入停止通知和让路机制：

- 原停止请求持久化后，发布可合并的唤醒通知。通知取消当前普通 tick 的子 context，使其结束等待；不取消项目/应用生命周期 context，不结束 Runner 服务或原生 worker。
- 停止通知只促使读取 inbox。请求身份、TTL 和业务资格仍由原处理入口核验，不能通过通知参数直接退出候选。
- 普通 tick 的取消必须传播至 Runner CLI 等所有在途调用及候选循环；取消后停止遍历下一候选。CLI 的 Start/Wait/管道排空有界，不能遗留持有候选门闩的后台 goroutine。当前调用先退出并释放原锁，再由同一 actor 处理停止。
- tick 主动让路只产生调度结果，不成为服务失败；同时发生的实际存储或协议错误继续保留。发布快照使用仍有效的生命周期 context。
- 已保存并可能发送的 submit/reply/resume/stop/collect 保留原请求及 unknown 事实；不能因打断 CLI 等待把它们还原 pending 或自动重发。已派发输入可以晚到，停止后的结果仅按原门禁保存事实。
- actor 每次开始新的外部工作前先处理待停止请求，停止优先于普通控制；长批次在每个外部步骤之间检查通知和 context。其他控制错误不能阻断后面的停止，失败按请求分别记录。
- control 处理仍串行，先处理停止，再处理普通控制；逐请求保存失败并继续，不因单项错误跳过其他停止。重复通知不执行重复退出；原 500ms inbox 检查继续存在，重启在首轮外部工作前检查原 inbox。

补齐所有会占住 actor 的外部操作的可取消等待，不仅修 `Service.Reconcile`。不为本功能另起并发写 actor、直接 HTTP 写候选旁路或跨线程修改 actor.State。

正常存储、单个或少量停止的受控夹具中，外部 Runner/provider 永不响应时，从 inbox 持久化至停止终态回执应不超过 5 秒。该上限用于自动验收；数据库/文件系统不可用、进程退出和大量排队不得承诺 5 秒成功，而应在请求预算内返回可识别的错误/未知。

## 4. 有效期、处理超时与查询超时分别表达

| 情况 | 权威结果及后续 |
| --- | --- |
| 受理前超过原 2 分钟有效期 | 由服务持久化 `rejected / expired`；浏览器自己的时钟不能代判 |
| 明确业务拒绝 | `rejected`，显示 `last_candidate`、`candidate_ended`、`stale_instance`、`invalid_request` 等具体原因，结束待核实 |
| 已提交退出，响应或投影丢失 | 按原 Command/withdrawal 恢复 `applied`，不重做退出 |
| 单次处理预算内未取得可证明结果 | 保留原请求，返回/显示 `outcome_unknown` 及已知阶段，不伪造终态 |
| 单次 GET 超时、断网、5xx | 本地“本次核实超时/失败”；不改变最后一条权威回执，不创建替代请求 |
| 查询 404、身份不符或记录损坏 | 显示具体问题；停止请求不因 404 自动重新 POST。无法证明原结果时继续保持未知 |

预算采用固定默认值，首期不新增用户配置：停止 HTTP POST 整次 10 秒；原请求 GET 整次 5 秒；服务端停止本地处理每次 5 秒。预算包括应用内等待、锁和重连，不仅 fetch 或最后一次 CLI 调用。嵌套调用只能消费剩余预算。

停止发布和原请求读取复用已冻结的运行时身份，不等待候选观察、生成观察或 Runner 健康检查。处理请求不得持有全项目 registry 锁执行外部工作；同 request ID 的仲裁等待必须可取消，复用同一 registry 的请求门闩，不用超时后遗留的 goroutine 包装不可取消锁。

业务原子事务若在取消边界已经提交，以持久结果为准；不能将 context 取消无条件翻译为 rejected。确实未知可以长期未知，但不能长期展示“正在停止”的忙碌状态而不说明原因。

## 5. 核实互不阻塞，明确失败释放界面

复用 `Api`、journal 和 `useOriginalRequests`；核实调度只有一个 owner，自动和手动查询共用同一请求的 single flight。

- 当前项目最多同时核实 3 条请求，各请求独立超时、完成和安排下次查询；一条失败或挂起不阻塞其他请求和后续刷新。
- `navigator.locks` 的排队也纳入预算，并传入可取消 signal；不能先无限等待锁再开始计时。其他标签页持锁时显示等待/超时，不能绕过锁发送副作用。
- 首次立即查询；未终结请求采用 2、5、10、30 秒间隔，30 秒封顶。手动“重新核实”可立即排队，终态停止轮询。离线暂停，恢复在线后核实；切项目/实例和卸载取消旧查询与计时器，晚到结果只更新原身份的 journal。
- 超过 30 秒尚无结果，显示“结果尚未确认”、已等待时长、最后核实时间、具体错误与复制原 request ID；取消忙碌动画。退避是只读查询，不是重新执行停止。
- `applied` 和 `rejected` 不可被晚到 submitted/超时错误降级。每条请求错误独立保存，不用全局最后一条错误覆盖其他请求。
- `rejected` 到达后同时清除 journal 的未决判定和 Runs 组件的 pending 引用；保留错误说明，解除该请求对按钮的占用。重新发起必须是用户根据当前资格再次确认的新操作。
- `applied` 到达后结束“停止结果待核实”。若候选快照仍 active，另显示“停止已生效，列表刷新中”，只重取快照，禁止在旧画面继续回答/恢复；快照刷新失败展示单独原因，不能重发停止。
- 快照已 abandoned 而原回执尚未到达，展示已观察的退出事实，但不能冒认本次请求成功。选择切换仍要求原请求 applied 加权威快照；用户期间切换则不抢回选择。

本次共享核实调度的有界并发/超时适用于原请求查询；其他写动作的自动补交规则不随之放宽。停止 POST 一旦开始，自动核实只读原请求，不自动提交新 ID，也不通过修改原版本来重发。

## 6. 交付边界与验收

继续遵循 [worker 生命周期](../../docs/product-design/worker-lifecycle.md)：W12 输入门禁、W17 唯一交付、W18 停止/资源事实分离，E04/E05 的未知和故障处理，V03/V06–V08 的原请求、换代与持久窗口。此次差异只改变调用方停止准入、调度等待和原请求呈现；没有 Runner 原生停止/恢复授权变化。

停止后不新发业务输入，不关闭原终端、PR、分支或工作区。与交付竞争时只有一个事务获胜；与最后两个候选并发停止时只能成功一个。原候选/Run/input/PR 绑定及请求摘要检查保持。

验收 CSR-A01–A08、CSR-M01 见专属文档，覆盖版本增长、调度卡住、原子性/重启、过期/未知、前端挂起/锁、多标签和状态收敛。实施必须运行固定 L1/L2、定向故障回归和现有隔离恢复场景；浏览器故障注入复用现有 Web 测试接线；现有安装候选只作为诊断来源，不作可写测试夹具。不新增旧库/旧协议读取、迁移、双写或回退。

## 2026-10-25 自审决定

删除新增原子回执事务接口、GET 推断/保存 not_submitted、任意 16 条批次门槛和独立验收框架。现有 withdrawal 已是持久操作证据，重复建模会形成双路径；查询写入推断终态会扩大竞争面。复用现有恢复用例及 fixture，长期功能验证选择现有 recovery 场景，新增的必要故障用例归所属模块。核实调度在现有 hook 中收敛，不建立持久轮询状态机。
