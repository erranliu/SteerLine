日期：2026-10-26。状态：用户已于本轮授权实施。已接入读取、Runner 解析、确认、发布/入图及 Web；2026-10-27 已接入 Runner 固定仓库 generate/1，完整业务路径和真实本机 Codex 生成均已验证；正式浏览器整链与真实 GitHub 文档 PR 合并/入图/清理已通过；人工体验、Gitea 外部写入和安装部署未验。普通开发文档，不分配本仓开发任务号、不修改 execution-map。配套 [Plan](../plans/roadmap-promotion.plan.md)、[专属验收计划](../testing/acceptance/roadmap-promotion.md)、[交互原型](../../docs/product-design/prototypes/planning-ui/index.html)。

## 1. 成果与范围

已纳管项目可以读取外部维护的 Roadmap Markdown，经现有 Runner generate 解析任务、核对批内与已有正式 DAG 的依赖；用户确认后，调查代码并生成正式 Spec / Plan，审阅发布文档，核实合并后在正式入 DAG 时分配任务编号并保存来源映射。

主线：

> 读取 Markdown → generate 解析任务与依赖 → 确认内部代号、范围和依赖 → 调查代码与生成 Spec / Plan → 审阅并发布文档 → 核实合并 → 正式入 DAG、分配编号及转换依赖。

本版只读草稿，不提供草稿创建、正文编辑、规划聊天、手工创建草稿任务、归档、跨草稿组合转正或正式任务范围/依赖编辑。一次处理一份 Roadmap 中全部尚未入图的新任务；对已有正式任务只作关联或提出问题，不重建或改写。纯目标讨论和人工验收活动不自动变成执行任务。

本版不建设 Agent 运行时、不直接调用 Codex、不让内容生成 Run 创建 Task / Candidate、不增加统一测试通过门禁。生成后的执行继续采用当前[项目材料维护](../../docs/product-design/project-maintenance.md)与候选级冻结规则。

SpecGuide 已同步本次身份规则：生成前固定 Roadmap 内部身份，正式编号只在入图时分配，不能要求提前占号。本轮不修改本仓开发 roadmap 的编号规则。

## 3. 身份与材料权威

| 对象 | 含义 |
| --- | --- |
| Roadmap 身份 | SteerLine 为当前项目/仓库中的来源文档保存稳定 roadmap_id；首版按规范化仓库相对路径关联。移动或改名不自动猜测原身份 |
| Roadmap 内部代号 | 如 T1、T2，身份为 roadmap_id + local_key。不同 Roadmap 都可使用 T1；不是正式 Task ID，不占用编号 |
| 解析快照 | 原 Markdown、来源路径/内容摘要、已有 Task / DAG / 相关材料、模型配置、指令/Schema 版本及原 Runner 请求 |
| 已确认规划 | 内部任务、范围、来源依据、依赖及用户确认的确定版本；与之后的生成/发布操作关联 |
| 正式材料 | 稳定路径上的 Spec / Plan 及必要验收材料，经文档 PR 发布到项目目标主分支 |
| 正式 Task / DAG | 只由既有 Task 权威创建；新正式编号在入图事务中分配，依赖解析为正式 Task ID |
| 入图映射 | 项目/仓库、roadmap_id、local_key→正式 Task ID，以及原入图请求/回执；持久唯一且可重复查询 |

原 Markdown 是需求输入；解析与文档生成 JSON 是 SteerLine 校验后保存的结构化结果，不要求作者预先提供，也不让用户编辑 JSON。JSON 不保存另一套实时执行状态。

确认、文档生成和文档合并前后，新任务均只持有内部代号。已有关联的正式任务可展示其原编号，这不等于为新任务提前分配编号。不得借用本仓开发流程的 task-ids 或 Git ref 计数器为产品任务占号。

## 4. 读取 Markdown 与解析

### 4.1 来源

从已纳管项目主工作区的 SteerlineFlow/Roadmap/drafts/ 读取 Markdown，列表按相对目录展示。仅读取受限的普通 UTF-8 文件，不跟随重定向到仓库外；复用现有普通文件、编码和大小检查，超限/不可读必须列出文件和原因，不静默截断。

允许读取尚未提交的草稿。记录实际读取的字节及内容摘要、主工作区 HEAD 和来源状态，不将未提交内容冒充远端 commit 中的文件。生成时的代码基线另按项目目标远端主分支固定，不能用草稿所在 HEAD 代替。

刷新只重新读取，不触发模型、编号分配、发布或 Task 创建。原快照仍可查看；新内容需显式重新解析和确认。首版无移动/重命名映射维护入口，身份不明时提示外部处理。

### 4.2 草稿已有信息与 Runner 输入

作者可以自行拆分任务、使用任意清晰且文档内唯一的代号，并分析依赖。例如：

    T1 候选控制：依赖已有正式任务 #8
    T2 状态同步：依赖本 Roadmap T1

Markdown 不要求固定标题层级或固定模板。解析应保留作者已有代号和拟议关系；未写代号时，可提出文档内唯一的临时代号供确认。标题、普通数字或“阶段 1”不能推定为正式任务编号。

每次显式解析调用现有 Runner generate/1，一次提供原 Markdown、当前已有正式任务目标/状态与依赖图、判断关系所需的 Spec/相关正文、生成指令与输出 Schema。材料的路径、版本和完整性可追溯；不足以判断依赖时返回问题，不能仅凭名称补成确定事实。

结果至少包括：

- 内部代号及其来源：作者原代号或生成建议。
- 名称、目标、范围、主要约束、通过条件/待补信息。
- 原文依据，可定位段落/摘录；建议内容不能标为原文。
- 草稿原有批内/正式依赖、Runner 核对后拟议依赖、建议变化与理由。
- 已有任务的重复/重叠/疑似已覆盖范围、建议关联及待澄清事项。

Runner 可以保留或建议调整关系；只有用户确认后的关系才能用于生成和入图，不改写原 Markdown。

### 4.3 SteerLine 校验与确认

校验 Schema、代号唯一性、引用存在、内部/正式身份类型、方向和依赖环，结合已有正式图验证；模型自述不能替代这些检查。不存在的正式引用、跨 Roadmap 的未入图引用、关键范围矛盾、内部代号缺失或含糊不清均阻止确认。

重叠不是直接删除或合并任务的许可。明确对应已有任务时，保留关联并不重建；可能重复而无法判断时，要求外部补充草稿。已有任务不因“再次确认”被改范围、改依赖或重新编号。

界面展示原文、原有依赖、拟议依赖、变化理由、已有 DAG 快照及问题。确认固定整个本次规划的摘要；此时只保存内部身份 JSON，零新 Task / Candidate / 正式编号。

重新读取/解析不能用名称相似自动复用或重绑定正式任务。原代号改变或无代号草稿内容变化导致身份不明时，返回待澄清；不得重复创建已入图任务。

## 5. 固定输入与变化处理

生成前固定：已确认规划、原 Markdown、目标仓库/主分支、实际取得的完整代码提交、[生成规范](SpecGuide.md)、[测试规范](../testing.md)及本次参考的项目文档。记录实际读取版本与摘要。

来源或规范之后变化不替换原生成输入。发布前采用新来源需重新解析/确认；只更新规范可显式重生成，保留历史并撤销旧审阅确认。代码或 DAG 的相关变化在生成/发布/入图前核对：仅新增无关任务可重新做确定性检查；影响范围、前置身份/目标/契约或环判断时，回到解析确认。候选运行状态变化不能误判为依赖结构变化。

已发 PR 后按原发布请求核对；不以重新生成绕过在途或未知发布。已入图任务来源映射永不转给另一任务；后续新材料遵循当前项目维护规则，不冻结所有候选到本次转正版本。

## 6. 正式文档生成与 Runner 前置

用户确认后才可生成。读取必需规范，实际调查固定仓库中的代码、契约、消费者与测试，对本批任务整体规划，再输出逐任务完整 Spec / Plan 及必要验收材料。明确复用/替换、共享修改所有者、交接条件和测试实施安排；不为假设的未来增加兼容、双写或第二套执行链路。

Spec 定义行为与验收要求，Plan 定义实现、环境、命令、通过条件与证据登记。少量非阻塞人工项可以后置；不会凭生成文档宣称测试已通过。后续系统测试安排仍走已有项目维护生成机制。

文档使用稳定且唯一的语义路径，如 SteerlineFlow/spec/execution-control/candidate-control.spec.md；Plan 和验收材料同样不依赖正式编号。正文可以引用所属 Roadmap 的 T1 和已有正式 #8。入图后不因分配编号重命名、回填或再开一轮文档 PR。

用户可在生成流程内修改正文，修改后撤销旧确认并重核 Spec / Plan 一致性。涉及任务拆分或依赖变化时返回结构化问题，要求重新解析确认，不靠正文编辑暗改 DAG。

| 固定仓库只读调查 | 明确仓库身份和完整提交，读取相关源码/契约/测试；返回实际文件/版本与调查依据 | 缺能力显示待接入；只给提示词一个路径不能冒充实际仓库调查 |

## 7. 审阅、发布与合并核实

展示 Spec / Plan 正文与差异、调查依据、路径、确认的任务/依赖、JSON 及 execution-map 变化，以及目标仓库/分支。路径冲突、越界、覆盖无关文件、缺规范/调查/完整文档或关键问题未解决时不能发布。

发布操作在界面说明其实际权限范围：创建文档 PR、按明确授权合并并核实；仅创建 PR 的操作不能隐含合并授权。正式实现可提供“确认发布并合并文档”统一动作，但须明示两种外部效果，并遵守 provider 的保护规则，不 force merge。

SteerLine 负责确定的文档落盘、隔离文档分支、Git/provider 发布和合并事实核对。现有内容 generate 为只读，不承接写 Git、发 PR 或合并；不得伪装成开发 Candidate。新增所需窄 Git/provider 适配与恢复记录，不另造完整发布平台。

文档 PR 仅包含本次生成文档、SteerLine 输出的内部身份 JSON 与执行清单；不改原 Markdown。JSON/清单在入图前使用 roadmap_id/local_key，正式运行状态仍属 Task 权威。

提交外部动作前保存原意图、固定文件/提交/目标、请求与回执。未知创建/推送/合并只查原分支/原 PR；不换号盲重发。只有实时核实目标仓库、base/head、真实合并和所需正文已进入目标主分支后，进入“文档已合并，待入图”。

## 8. 入 DAG 时分配正式编号

“正式入 DAG”是文档合并后的显式动作。重新核对原入图请求、已确认规划、实际合并文档、目标/权限、已有映射与当前图；缺正式材料、未知合并、无效依赖或相关变化未确认时零入图。

本版沿用已有 Task 批次事务：本次全部尚未入图的新任务作为一个批次，分配编号、Task/Contract、内部依赖→正式依赖、来源映射、事件及原请求回执一并提交。整批全部提交或全部回滚；不新增逐行写入的第二套准入逻辑。既有已入图来源不在本批重复创建。

新编号由 Task 权威在同一事务内，按当前仓库身份的已使用编号及持久分配位置确定唯一非负整数；包含已终止/取消历史，不回收、不补洞。并发请求串行/CAS/唯一约束必须真实生效，不能先在 UI、生成 JSON、模型或发布工作区里占号。

业务唯一键至少约束项目/仓库身份 + roadmap_id + local_key。重放先查原请求/结果；同号换正文冲突；另一请求试图重建已存在来源时返回已有映射或明确冲突，不分配第二个任务。事务失败不暴露可使用的正式映射。

示例：

| 入图前 | 入图后 |
| --- | --- |
| Roadmap A / T1，依赖正式 #8 | #101，依赖 #8 |
| Roadmap A / T2，依赖本 Roadmap T1 | #102，依赖 #101 |
| Roadmap B / T1 | 独立身份，不能借用 A / T1 的编号 |

回执丢失/重启不意味着部分 Task 创建。沿原请求查批次实际提交事实；全部提交时返回原映射，不重新分配。页面按已核实回执展示映射，原型的中断演示应表达“结果待核实”，不能当成生产逐行提交语义。

入图完成展示双向来源：Roadmap/内部代号→正式 Task；Task→来源 Roadmap/内部代号/固定发布版本。正式状态读取 Task，不回填原 Markdown 或已发布文档。创建 Task 不绕过派发资格；项目已开启自动派发时，正常调度可能启动新就绪任务，确认入图前应明示。

## 9. 状态、恢复与隔离

查询、列表和刷新均只读。解析/生成各自保存原请求与固定输入；业务状态可分为待读取/解析中/待澄清/待确认/已确认、生成中/待审阅、发布中/待合并核实、待入图/入图结果待核实/已入图，不用一个“完成”混同生成成功、Git 合并和 Task 创建。

执行异常、显式停止、迟到接受和服务换代沿[Worker 生命周期](../../docs/product-design/worker-lifecycle.md)、[Runner 接入](../../docs/integration/steerrunner.md)及现有生成生命周期。本功能只增加自己的内容请求和发布/入图业务事实，不复制 Runner 的原生执行状态机。未绑定/迟到生成同样保留停止义务，加入 home 共享服务结算。

明确失败后可显式重试；未知结果只对账原号。浏览器关闭或服务重启不自动另开模型请求、不重授用户输入、不自动扩大发布/合并授权。项目/home/实例/仓库切换及迟到响应不得串用解析、生成、PR、编号或映射。
