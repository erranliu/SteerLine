# Spec：执行方案与项目运行环境界面梳理

2026-10-31。状态：2026-10-31 经用户要求审计并收窄后实施。[Plan](../plans/runtime-environment-ui.plan.md) · [专属验收计划](../testing/acceptance/runtime-environment-ui.md)。普通开发，不分配任务编号、不进入 roadmap。

## 1. 问题、目标与现行规则

调查基线：`cb0c888e7ed6ccea3f9d5c9e2e6427cc3884d0a6`。执行方案配置已有运行机、链路、Agent 和模型编辑；项目环境已有按环境键去重的资格、活动和派发门禁，但界面还存在以下问题：

- 设置入口混用“环境检查、环境适配、项目环境准备”；远端环境标题只显示目标名称，多个不同执行上下文可能同名。
- 环境卡片与页面下方的验收、失效对象选择分离；从任务阻断跳转后还要重新寻找环境和选择方案。
- 配置保存、配置加载、能力目录、环境资格和派发模式分散展示；查询失败后缓存的环境计数仍可能看起来有效。
- 材料生成、环境状态、原始执行文件和历史报告处于同一阅读层级，难以先找到原因和下一步。

成果是让用户能回答：配置了什么、当前项目哪个环境可用、为什么不能启动、下一步做什么。验收资格和活动生命周期不重建。

本规格细化并替代[项目环境准备规格](project-environment-readiness.spec.md)第 7 节涉及的页面组织、入口文案和跳转要求；其环境键、当前引用、资格规则、准入事务和状态优先级保持。[正常发布能力规格](environment-publication-scope.spec.md)继续定义 ready：同轮 checks（含 TTY）、完整 L2、原 PR 发布身份、脚本自有资源清理和原 Run 停止结算均核实。外部检查、审核、合并和测试资源清理属于独立 L4 证据，不增加生产审核阶段。旧 Runner Check 继续按[退役规格](legacy-environment-check-retirement.spec.md)保持删除。

## 2. 页面职责与导航

| 页面或位置 | 职责与固定表达 | 不承担的职责 |
| --- | --- | --- |
| 全局“执行方案配置” `/settings/execution-configs` | 配置运行机、执行链路、Agent、模型及思考强度；按运行机分组已保存方案；显示保存和加载事实、能力目录查询状态 | 不显示全局“环境已就绪”，不在此授予项目资格 |
| 项目“运行环境” `/projects/:project/environment` | 项目准备材料、按运行机分组的执行环境、当前状态/原因/下一步、验收操作和历史 | 不编辑全局 execution，不自动修环境或安装工具 |
| 项目“配置” | 继续管理原生成并发和项目信息；保留“运行环境”快捷入口 | 不再维护另一份检查入口或准备流程 |
| 项目顶部 | 服务在线情况与运行环境就绪数量，分别显示 | 不把在线或目录查询成功等同于 ready |
| 派发栏 | 用户自动/手动与暂停意图、默认执行方案及其环境阻断 | 不因环境失败修改模式/暂停，不自动换方案 |
| 任务启动面板 | 本次方案及对应环境资格、其他任务阻断、定向准备入口 | 不自动开始验收、重试任务或改变全局默认 |

项目主导航增加“运行环境”，与面包屑、配置快捷入口、顶部链接使用同一名称；保留原路由，不为改名新增兼容路由或搬迁整个 features 目录。全局配置与项目配置的原返回、浏览器后退、未保存草稿保护保持。

## 3. 运行机、执行环境与方案的展示关系

1. 运行机分组来自现有 target：本机为一个组，远端按原 target 标识分组；项目环境页直接显示已加载 target 标识，不为展示另查远端目录；全局配置页沿已有目录名称。不按相同昵称合并不同 target，也不推断物理主机别名。
2. 每个环境卡片仍由后端原 environment_key 标识。执行链路、Agent、权限、入口等参与环境键；仅公开模型及思考强度不同的方案共享环境，跨项目不共享 ready。运行机分组不新增持久对象、环境注册表、别名或第二份摘要规则。
3. 卡片标题显示“Codex 直连”或“Orca · Agent”；同机多个上下文以关联方案名和原环境键短值区分；首版不分析权限/入口差异，也不展开 settings 或凭据。操作仍使用后端完整键。
4. 显示“共用方案：……”及默认方案标记，说明验收通过覆盖本项目的这些方案。生成专用方案不计入环境数。环境为空显示“尚无开发执行方案”，附全局配置入口，顶部不显示难以解释的 `0/0`。
5. 分组以目标为单位，环境以原键为单位；配置页模型方案仍分别保留。配置变化派生出新环境时显示新状态，旧活动继续留在历史中，未结算活动的查看/停止不能因不在当前卡片中消失。

若现有 options 缺少展示所需的目标、链路或 Agent，仅在原只读 DTO 补充由已加载 execution 派生的展示字段；不把完整 settings 或凭据发给浏览器，不允许 Web 重新计算环境键。

## 4. 状态展示与观察有效性

### 4.1 五类事实分别表达

| 事实 | 展示要求 |
| --- | --- |
| 配置保存 | 草稿显示“未保存”；保存成功仅表示文件已保存 |
| 服务加载 | 保存摘要与加载摘要不一致显示“已保存，待重启生效”；一致且已核实时显示“当前服务已加载保存配置”；加载信息缺失显示待核实 |
| 能力目录 | “正在获取能力目录／目录已获取／目录获取失败／使用上次目录／手动填写，目录未确认”；按钮统一为“刷新能力目录” |
| 项目环境 | 使用下一节六阶段及原 ready/not_ready；补充环境原因、下一步和关联方案 |
| 派发 | 自动/手动、暂停为用户意图；环境、依赖、材料等为当前阻断，不能用单个绿色点表达“全部可派发” |

目录可见不证明凭据或实际模型调用已验；项目环境 ready 不承诺所有模型都可调用，也不表示任务依赖等其他前置已满足。配置待重启时，新候选和新验收继续由原配置守卫拒绝，页面明确原因；生成和停止各沿原允许规则，不额外以环境 ready 为前提。

### 4.2 六阶段与操作

保留 `env.View` 的来源和优先级：显式失效优先；原活动未结算显示验收中；无当前活动按材料情况显示未准备或待准备与验收；已结算失败显示阻断；原活动通过后再区分依据读取失败、变化或一致。Web 不从英文诊断猜阶段。

| 原 stage | 用户文案 | 原因与主要下一步 |
| --- | --- | --- |
| unprepared | 未准备 | 列出原材料缺项/读取问题；查看准备要求，必要时生成或更新材料。不能把所有读取错误改写为缺依赖 |
| awaiting_user | 待准备与验收 | 清单可读，尚无当前验收；说明用户在实际执行账号下准备，提供开始验收 |
| verifying | 验收中 | 显示排队、执行、停止待核实等原事实；查看进度、停止原活动，不开启替代验收 |
| ready | 已就绪 | 当前项目环境资格通过；查看通过报告或明确重新验收，说明重新开始即切断旧资格 |
| blocked | 验收阻断 | 显示具体未通过或未核实项；区分已确认不满足要求与检测/结果采集尚未完成，按原原因处理，不一概归因机器故障 |
| stale | 已失效 | 展示显式原因或准备依据变化；处理后重新验收。若原活动仍未结算，仍须展示其进度与停止入口，新验收保持禁用 |

“下一步”只根据结构化阶段及已知事实给出有限建议；原诊断可展开查看，不解析文本推断故障或自动修复。具体动作仍受原能力、配置、目标准入、在线及命令 pending 约束；仅 stage 不足以判断可操作。

### 4.3 查询失败和离线

- 没有成功数据时显示“运行环境状态待核实”或具体查询错误，不用空数组冒充没有环境。
- 同项目、同实例已有数据，后来查询失败或服务离线时，可读缓存但必须标“上次已知状态，当前待核实”，显示最后成功观察时间；顶部计数标为上次结果。不得继续无标记地宣称当前 ready，也不将失败写成环境失效。
- 原查询成功后恢复正常表达。后台正常刷新期间保留最近成功观察，不新增任意 TTL、全局健康状态或数据库字段。
- 新验收、失效及新候选操作在各自所需的当前观察未核实时禁用并说明原因；开始验收不要求旧环境 ready。环境 GET 失败不应连带封死已有独立活动详情可核实的停止入口。停止仍核实原活动 ID/revision、在线和原能力，不依赖 ready。
- 同一 options 查询保持 home/project/instance 作用域、可见性轮询及定向失效；切项目、实例或应用 home 不借用旧计数、活动、命令 pending 或操作草稿。

## 5. 项目环境页面与操作流程

页面按“项目准备材料 → 运行机及环境卡片 → 验收与材料生成历史”组织。同版本的项目准备文档只展示一次；每张卡片提供定位到材料区的入口，环境特定缺项保留在卡片。

### 5.1 材料与用户准备

材料区展示原项目文档、文档中声明的验收脚本路径和来源提交；沿既有材料查询，不新增任意工作区文件读取。提供阅读清单、生成或更新材料入口。沿原本机生成方案选择、生成预览/导出及正常 Git 审阅提交流程；生成成功不是已经应用，未提交材料不授予资格。没有生成方案时说明如何配置。阅读、下载和勾选不写“用户已准备”状态。

### 5.2 卡片内开始与重新验收

1. 点击某卡片的“开始验收”或“重新验收”，只展开该卡片的操作区，移除页面底部独立的全局验收对象选择器。
2. 展示运行机、链路、共用方案、验收覆盖范围及原检查/L2/真实 PR 发布、模型调用等副作用。单方案直接使用该方案；多个方案时预选明确带入的有效方案，否则使用该组默认方案，再否则要求用户选择，不暗中取第一个。
3. 保留每轮超时参数，默认沿原值，输入验证沿后端约束。用户明确提交才发送原 environment_start；payload 仍为 profile_id、round_timeout_seconds、expected_current_revision，外层版本沿原命令语义。
4. 存在未结算原活动时不提供可提交的新验收；其他目标占用由原服务检查，拒绝原因沿原页面命令回执展示。若查询不足以得知 settled，可从原活动摘要消费该事实，必要时只补原 DTO 的只读字段，不建可操作资格状态机。
5. 接受后刷新对应原查询并定位当前活动；回执未知沿原请求对账，不另造 request 或以按钮重试开始。双击不重复提交。重新开始立即失去旧资格的语义保持，失败不得退回历史通过报告。

### 5.3 失效、停止和结果

- “标记失效”置于对应卡片的次要操作，展开后填写原因并显示影响范围“仅当前项目的这个执行环境，含所列共用方案”。environment_key 与 expected_current_revision 来自同一卡片，不使用其他下拉框残留选择。失效不自动停止原 Run。
- 查看/停止绑定原活动 ID/revision，不用当前引用 revision 替代。显式失效、切换配置或活动不再属于当前环境列表时，原历史中仍能查看并按原授权停止未结算活动。
- 卡片只显示简洁结果与下一步。查看当前验收或历史通过报告必须展开并滚动定位所选活动，详情在最近 20 条之外也沿原 ID 查询，不让“历史曾通过”看起来是当前资格。
- 详情先展示同一轮的 checks、完整 L2、验证 PR 发布核实及脚本资源清理、原 Run 收尾；未验证、失败、结果未知分别表达。PR 不写“已合并才通过”；原始 progress/result、Agent 回复、Run ID、来源提交和技术诊断放在折叠详情中。progress 和 Agent final 不作为通过结论。
- 手动刷新、展开、跳转和普通轮询均不发送执行命令、模型请求或外部修复；历史中材料生成与环境验收明确区分。

## 6. 任务到环境的闭环

任务选择执行方案后显示对应运行机/链路、环境阶段与当前原因；原任务依赖和其他 blocker 保留，选中 ready 环境不覆盖其他阻断。派发栏始终显示默认方案，用户模式和环境 blocker 并列；提示去准备时带入默认方案，不自动切换到其他 ready 方案。

定向链接沿原 environment 路由仅带可选 `profile`（本次方案）和 `task`（来源任务）。环境由当前项目 options 内该方案定位，不在 URL 重复携带环境键、候选 ID 或返回地址，不新增页面选择存储。

- 进入后展开并滚动到该方案对应的当前环境，刷新后仍可据 URL 恢复。方案不存在时明确提示原选择已变化，不静默选择另一环境。配置变化后展示该方案当前环境，提交前明确显示当前对象；资格和引用 revision 仍由服务核实。
- 有 task 时提供“返回任务”，回到当前项目 runs 的原任务，通过 `start_profile` 参数恢复本次方案选择，不自动创建候选或提交；不承诺恢复原候选、来源页布局或全部草稿。
- 返回后方案已删除或不可用时显示具体原因，要求显式重新选择。任务不存在时沿原页面提示，不创建替代对象。
- 普通顶部/导航入口不带 task；不同项目、实例不复用旧任务或活动详情。参数仅影响定位，不能构成操作授权，不承载凭据或配置正文。

## 7. 范围与实现边界

主要落点为 Web 的 execution-configs、environment-checks、settings、tasks、runs 和 app 导航；仅在展示确有需要时扩展原 app options 的只读字段。复用当前 Query、Router、命令仲裁及活动详情，不新增通用配置中心、表格平台、前端资格引擎或第二套环境 API。

不修改环境摘要、SQLite 格式、Runner 协议、验收材料、固定提示词、三轮预算、重试/未知/收尾、服务生命周期和自动派发策略。沿 [Worker 生命周期](../../docs/product-design/worker-lifecycle.md) W01–W03 的资格、W08–W16 的原请求和 W18 的结算边界，本次仅调整只读投影、动作位置和页面选择恢复，不新增执行节点或恢复授权。

不部署、不重启或改写安装现场；后续若实现发现必须改模型可见正文、接线或其对应测试/CI，须单列范围并遵守[提示词治理](../../docs/prompt-governance.md)，不得以 UI 文案整理名义顺带修改。

## 8. 验收条件

| ID | 必须证明的成果 |
| --- | --- |
| REU-A01 | 全局配置、项目配置与运行环境职责一致；项目主导航/面包屑/快捷入口同名；原返回、后退、草稿保护仍有效 |
| REU-A02 | 同机不同执行上下文独立卡片、同键模型方案共用、跨项目独立；标题可辨认且不泄露凭据；生成方案不计数；空列表与读取失败分开 |
| REU-A03 | 五类事实分别展示，六阶段保持原优先级；失效且原活动未结算仍可查看/停止；原因不将检测错误误写成机器缺依赖，ready 不承诺模型或所有派发前置 |
| REU-A04 | 首次失败、失败后缓存、离线、恢复、正常后台刷新和项目/实例切换表达正确；待核实不以旧 ready 放行新操作，原停止不被 options 故障连带封死 |
| REU-A05 | 材料仅一处、来源可追溯；生成/导出不授予资格；卡片内方案选择与原命令参数准确，多个方案不隐式任选，超时/重复/占用/回执未知保留原规则 |
| REU-A06 | 失效精确绑定卡片，开始/失效 current revision 与停止 activity revision 分离；历史与当前资格分离，旧未结算活动仍能停止；详情可定位超出列表的报告，结果只验原发布和收尾 |
| REU-A07 | 任务及默认派发阻断定向定位正确；刷新、返回任务和方案恢复有效；无效参数/配置变化不静默换对象；访问页面零新执行，环境不修改用户派发意图 |
| REU-A08 | 受控浏览器覆盖主流程、同机多环境、缓存故障、两个项目切换、返回与键盘定位；窄屏可用，无整体横向溢出，状态不只靠颜色，核心流程自动断言通过 |
| REU-M01 | 后置人工体验：无需口头指导即可区分机器/环境/方案、找到阻断原因及下一步、完成准备与返回任务；参与人及窗口待安排，不能替代 A01–A08 |

方法、最小测试入口、证据和实际状态分别归 Plan 与专属验收。历史原生通过不作为本次 UI 通过证据，本次 UI 验收也不重新授予真实环境 ready。
