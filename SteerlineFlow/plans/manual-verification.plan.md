# 人工核验实施 Plan

实施及验证状态见[专属验收](../testing/acceptance/manual-verification.md)。[Spec](../spec/manual-verification.spec.md) · [测试选择](manual-verification.tests.json)

## 1. 基线与实施顺序

调查基线 `97590c29`。现有候选按固定 Plan 提交读取同名测试安排，Runner 负责发布。PR 查询已有 `head_revision`，尚无草稿字段。先确认固定 Runner 构建的公开契约，再按以下顺序交付。工作区核验启动在 SteerLine 本机实现，独立于 Runner 的开发会话和开发 worktree。[测试安排入口](../../internal/testmanagement/model/inputs.go) · [发布输入](../../internal/runnercontract/input.go) · [PR 查询](../../internal/execution/publication/query.go) · [Runner 生命周期](../../docs/product-design/runner-lifecycle.md)

### P1. 核验 JSON、Plan 生成及候选冻结

1. 实现 Spec v1 的类型、同名路径推导、严格解码和语义校验。复用现有受限 UTF-8、规范 JSON 和固定 Git 文件读取能力，覆盖缺文件、空文件、非普通 Git 对象、重复键和嵌套未知字段。校验器给出字段路径和原因。
2. 为现有 Plan 生成结果 schema 增加可选 `manual_checks` 对象。模型只在任务需要人工判断时生成，并按固定项目材料调查实际启动入口。现有文档写入器校验对象、统一编码并将同名文件与 Plan 同批评审、发布。重生成省略已存在的核验对象时，删除本次文档所拥有的旧伴随文件。人工编写的文档走同一校验器。
3. 修改实际 Plan 生成规则的固定短指令或完整材料时，在 `internal/prompts` 对应文件和组装函数接线。业务层仅传冻结材料和事实。按治理要求审阅实际正文差异、变更前后 UTF-8 字节数、业务原因和验证，独立审核后更新期望样本。 [提示词维护](../../docs/prompt-governance.md)
4. 在候选 W01 预留时读取 Plan 固定提交的伴随文件，与候选和完整发布请求同次保存。测试覆盖 Plan 更新后旧候选仍使用原命令，新候选采用新版本，以及无人工要求的候选正常准备。候选阶段无需解析本机程序或创建核验目录。

### P2. 草稿发布与候选 PR 观察

1. 检查实际固定 Runner 的公开目录、发布输入 schema 和工作流发布结果，核实能否在首次创建时明确请求草稿，并回传或核对平台草稿事实。若缺能力，先在 SteerRunner 完成受支持的发布输入、能力声明和实现，取得合入提交及对应构建再接入。新候选仅使用已声明支持的工作流和 provider，使用实际公开字段。用隔离的 GitHub 目标验证真实创建与查询，无需修改安装版或正式仓库设置。
2. 将草稿意图固定到候选的 Runner 发布输入。扩展 PR 查询类型和支持的适配器，使草稿字段能区分 `true`、`false`、缺失，并提供真实 head 仓库、分支、SHA 和可拉取定位。默认 GitHub 命令 provider、项目初始化模板和示例查询同步。已有无核验要求的候选仍使用现有发布和合并资格。自定义 provider 或其他平台需证明同一契约方可用于含人工核验的候选。
3. 复用候选发布和 PR 观察入口，首次满足身份与草稿条件时持久化一条核验记录。使用唯一约束去重，按实际观察更新 Head 和终态，任务或候选结束时与既有结算一起归档。已有 PR 回执丢失时沿 W16 查询原绑定，观察暂时失败保留诊断。草稿 PR 出现以后，当前 Head 和结论属于核验记录。交付仍走现有 W17。[原发布与收尾](../../docs/product-design/runner-lifecycle.md#报告发布与收尾阶段)

### P3. 本机核验 worktree 和启动生命周期

1. 在应用层实现核验服务，持久化启动意图、实际命令、私有 ref、worktree、端口、原进程身份和退出状态。复用项目目录所有权、Git 执行、路径检查及进程管理原语。用项目、候选 PR 和完整 Head 约束单个活动实例。命令事务先落意图，worker 再执行外部动作。每次尝试使用独立日志目录，worktree、临时目录和日志位于本机受管根下。[路径约定](../paths.md)
2. 服务端验证原 PR 目标后，用 Git 参数数组拉取确定的 PR Head，核对 SHA，再创建 detached worktree。实际运行前再验证目标 HEAD、路径和程序解析。以一次端口分配替换冻结参数，使用受管前台进程树和精简环境启动。为带 URL 的配置提供有界回环探测。实际启动验证覆盖含空格路径、直接程序及显式解释器、变量替换、端口冲突和子进程退出。精简环境需保留本机运行时必须的系统变量，测试确认 PR 和 Runner 认证变量未下传。
3. 实现停止、清理、日志读取和重启对账。对账只核对原意图、受管路径及原进程身份。外部已调用但回执未落库时，保留原目标并据可验证事实结算。确认未运行或资源已清理后，用户可发起新尝试。覆盖部分创建、并发重复点击、运行时版本前移、项目切换、服务退出和脏 worktree。停止须覆盖受管进程树，清理须保留用户变更及历史证据。

### P4. 页面、命令和逐项结论

1. 通过现有项目 API 暴露只读列表、详情和有界日志读取。新增项目范围的核验命令，复用现有 request ID、实例绑定、版本检查、服务端操作者和持久回执。操作包含启动、停止、清理和保存单项结论。浏览器只传目标身份和结论输入，后端从冻结材料解析命令和实际目录。[本地客户端协议](../../docs/product-design/local-client-protocol.md)
2. 用项目 SQLite 保存核验记录、启动尝试和追加结论。PR 观察与结果写入共享项目所有者事务。按核验项、Head、启动尝试和冻结摘要核对来源。使用版本条件防止过期页面覆盖另一位操作者已保存的结果。同请求重放返回原回执。同一 Head 的重验追加新结果。项目关闭或应用重启后历史仍可读取。
3. 在项目侧栏加入「人工核验」，显示待核验、失败待处理和已通过，详情提供旧 Head 与终态历史。执行详情链接到原候选对应核验记录。按任务、PR 和 Head 显示启动进度。Head 变化时保留用户尚未提交的备注并提供「启动最新版本」。全部通过时提供原 PR 链接，Ready 与合并由平台负责人操作。[项目导航](../../web/src/app/app-shell.tsx)
4. 同步正式路径、项目流程和本地客户端协议的新增入口，更新 Plan 编写规范及核验 JSON 的定位。依据实际协议和源码记录可用的 Runner 构建、发布组合与验证范围。

## 2. 测试安排

现有正式 ID 已写入同名测试选择。开发中先跑相关 owner 与 Web 组件定向测试。候选稳定后跑一次固定 L1/L2 和表中受影响合集。Web 生产构建后运行专属浏览器流程，验证任务入口、状态、刷新和操作参数。后续修复按受影响范围补测。[选测与停止条件](../testing.md)

| Spec 条件 | 正式测试 ID 与选择依据 |
| --- | --- |
| MV1 | `l1.minimum` 验证固定模板与项目边界。`go.roadmap` 覆盖既有生成和文档发布所有者，补充可选对象、删旧文件及非法内容回归。 |
| MV2、MV5 | `smoke.delivery` 核对原交付和释放后继。`go.runner-contract` 核对冻结发布输入及 capability。`go.runner-result` 核对草稿观察、发布重放和交付事实。 |
| MV2–MV5 | `go.http` 覆盖新增查询和命令的项目、实例与版本边界。`go.storage` 覆盖结果追加、唯一约束、终态、并发和重启。 |
| MV3、MV4 | 增加专属受控整链，覆盖真实 Git、进程和浏览器，测试条件见专属验收 MV-A3。 |
| MV2、MV5 | `manual-verification.local-codex` 使用支持草稿发布的固定 Runner 构建，验证真实草稿创建、Head 变化及平台 Ready 和合并，测试条件见 MV-A4。 |

MV-A3、MV-A4 是本任务专属验收项。受控场景按测试指南补入分级清单和执行器。真实联验单独精确运行，使用隔离 home、临时项目、独占端口、专属远端 PR 与分支。浏览器及真人步骤、实际 Runner 版本、输出位置和清理事实登记在专属验收。 [测试清单](../testing/test-list.json) · [验收计划](../testing/acceptance/manual-verification.md)
