## 1. 基线与边界

原调查基线为 `40d710fb`，当前实现基于 `07a5c769`。维护业务仍归 `internal/refactoring`，项目运行时管理生命周期，Runner 拥有实际执行和工作区。采用 [#549 的交付契约](../spec/refactoring-agent-delivery.spec.md)，复用首轮只读调查、可写 Runner Final、PR 版本核验和独立合入评审。适配共享容量、计费、并发名额和首次派发资格。当前版本的真实并发需重新取证。

## 2. 实施顺序

### P1　持久状态与项目调度

1. 同步去掉 [SQLite 的唯一活跃索引](../../internal/storage/sqlite/sqlite_store_schema.go)与[写入时的单行动检查](../../internal/storage/sqlite/refactoring.go)。沿项目当前 schema 版本规则固定新定义。保留项目/行动主键、逐条 CAS 和命令 journal 事务。重复提交竞争时，落败方读取原回执并核对正文。将可见的在途状态、已取得项目名额及原 Run 未结算分开建模，优先在现有行动记录上保存入队顺序和占位事实。项目并发默认 3 由维护业务统一提供。
2. 拆分[后台 Tick](../../internal/refactoring/service.go)的选取、推进与补采。分配名额时在同一事务读取占位总数、核对原行动版本并写入占位，多个并发入口也只能取得 3 个名额。只有调度器分配名额。采用有限并发推进有名额的行动，每条最多一个推进者和一个未结算操作。外部 Runner、PR、费用和资格观察有界执行。跨行动短锁只保护状态，逐行动协调 stop 与 submit。单行动慢调用、错误或历史补采不能挡住兄弟行动，诊断按原行动保存。
3. 复用按操作 ID 的共享生成队列与真实 Runner 准入。已占项目名额的行动等待下游容量时保留项目占位，使用结构化等待事实关闭当前计时区间。将推进计时区间和累计值随状态转换原子保存，以原操作时间边界去重，处理重复、迟到和未知观察。分别测试先运行后等待、从等待恢复、停止待结算、离线截断和收尾超预算。名额、预算时钟和总历时分别投影。
4. 等待人工与终态按原操作结算释放占位，答复、停止后交付和冲突续作走同一入队入口。冲突续作派发前重新核验原 PR 与最新持有者，原 PR 已关闭或合并时保留原交付并结清本次续作。停止可原子撤销待发意图，清理对应共享生成队列登记。按 [Runner 生命周期](../../docs/product-design/runner-lifecycle.md)逐条恢复和排空，枚举所有未结算请求及停止义务。重新派发前处理恢复占位。迟到受理沿原请求绑定并结算。已发送且结果未知的操作核实前继续占名额。检查 Stop、Finish、Answer、Conflict 与派发竞争时的原版本、原问题和写者约束。

### P2　环境资格、命令和只读投影

1. 在[维护宿主与读端口](../../internal/app/refactoring.go)增加批量环境选择查询。用原环境键与现有资格来源按运行机分组，用公开的维护能力筛选方案，只返回标识、显示名、链路、模型、默认标记、资格及原因等必要信息。读取同一观察基线，资格未知、门禁关闭和不支持维护分别返回结构化状态。GET 沿现有只读观察，不启动检测或远端检查。
2. 让启动请求携带用户所见环境键、当前资格 revision、所选方案标识及有效配置版本、基线提交和方向版本。对客户端使用不含凭据的配置版本标识。利用原项目基线预留和环境资格依据验证冻结组合，在受理事务复核环境引用。首个可发送意图在原生成准入通过后再做最终复核。环境引用的复核与意图保存使用同一 SQLite 事务，和失效/重新检测明确先后。提交前撤销或失去资格时释放尚未发送的共享队列占位。冻结版本或依据确认已变化时阻断，查询暂时未知时让出名额、按原选择有界复查。目标分支正常前进时复用现有固定提交与当前环境依据对比。首个派发意图落盘后，后继沿冻结授权和原操作准入推进。
3. 扩充列表投影为所有进行中/待答复摘要、历史稳定游标及名额计数。历史按结束时间与 ID 翻页，详情按原行动 ID 直接查询。提供阶段、等待原因、运行环境/方案快照、预算用时、总历时和允许动作。查询从保存事实组装，活动中心复用同一行动的方向、环境、状态及深链。调整应用命令、HTTP 契约及受影响消费者，沿现有版本和请求回执机制。

### P3　侧栏、列表和详情

1. 在[维护页面](../../web/src/features/refactoring-maintenance/refactoring-maintenance.tsx)拆出新建表单和列表/详情。桌面侧栏和窄屏全屏表单复用现有可访问交互。按 Spec 实现环境先选、关联方案、方向原文、基线预览和具体失败提示。将已确认的资格版本与草稿绑定，观察变化后要求确认，查询失败时禁用提交。提交中只锁本草稿，拒绝保留，回执未知沿原操作对账。侧栏仍打开时成功回执进入新详情，关闭后只在原项目刷新列表并显示反馈。按项目、服务实例和提交身份过滤迟到回执。
2. 桌面并排呈现，窄屏列表进入详情，使用 `action=<id>` 表示选择并支持前进、后退和深链。默认选择只执行一次。列表独立轮询，详情只轮询选中记录。历史分页按 ID 合并，行动完成或重新推进后从原分组移除，同时保留选中详情和列表位置。按行动和原问题隔离待提交状态、错误与答复草稿。独立处理三个查询的陈旧或失败，列表失败时仍允许操作当前已核实的在线详情。活动中心显示方向与环境，精确打开原行动。
3. 走查侧栏和详情的键盘焦点、窄屏溢出、阶段文案、容量已满与资格异常。移除现有全页 `working` 门禁，后台占位仍由服务决定。

### P4　验证与交付文档

补齐下表受控及真实用例，使用同名测试选择。完善实际实现对应的产品设计、架构和客户端协议，历史最小闭环 Spec/Plan 及原始报告保留。计划复用原提示词资产和供给路径。实施如果改动提示词正文、接线、资产或对应测试/CI，按[提示词治理](../../docs/prompt-governance.md)给出实际差异、前后字节数、业务原因与验证并完成独立审核。

## 3. 测试安排

开发期按影响定向执行，稳定版本按[测试指南](../testing.md)固定 L1/L2 并执行所选专项。正式命令、环境和通用断言见[机器清单](../testing/test-list.json)，证据目录沿[路径清单](../paths.md)。下面的新增断言接入现有正式场景，实施时同步机器清单、可读分级及 E2E 场景登记。文档阶段沿当前已登记 ID 选择。
