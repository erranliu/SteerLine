## 0. 前置能力验证

主体实施前先独立验证以下两项。记录固定 Runner 构建、真实请求、观察结果和未验边界，结论登记到[专属验收](../testing/acceptance/refactoring-agent-delivery.md)。

1. **Runner 的首轮目录与后续无目录调用。** 用同一固定独立 EXE，先提交带 `generate.directory` 的只读 `generate/1`，目录在整个调用期间固定于启动提交。再提交仅含正式文件材料的 `generate/1`，省略 `directory` 与 `repository`。核对实际权限、文件 manifest、可信原生 Final 与资源结算。若现有公开能力足以承载，两种接线留在本期。若确认必须修改 Runner 公开能力，先单独交付对应前置 Spec。
2. **PR 的 head/base 核验。** 沿现有平台查询入口核对同一 PR 的完整 head 和目标分支 base SHA，覆盖只推进 base、head 保持不变。记录现有 Gitea 与命令型查询的字段来源，以及共享消费者所受影响。若只需查询结果增加字段及本功能校验，留在本期。若必须修改共享查询契约且牵涉其他消费者的行为，再单独交付相应前置 Spec。

2026-11-12 前置探针已完成。固定 Runner 的两种调用均通过；首轮提交的内容固定由宿主提供，后续调用落在独立的空目录。PR 夹具复现了仅 base 变化时当前查询的可见性缺口。实施时为现有查询结果增加可选 `base_revision`，并在维护核验处要求可信 head/base。普通任务查询维持现有字段要求。按本 Spec 的调用边界，两项均留在本期。原始证据和未验范围见[前置能力验证记录](../testing/acceptance/refactoring-agent-delivery.md#前置能力验证)。

## 2. 实施顺序

### P1 · 固定正文、阶段与权限

1. 将 [Spec 正文](../spec/refactoring-agent-delivery.spec.md#2-一级提示词待确认正文)落实为 `internal/prompts/materials/` 下三份一级文件与三份策略文件。通过 prompts 包入口读取，按现有策略枚举只选一段。启动冻结完整正文、方向和策略，缺必要材料时阻断；原请求保留实际字节。短模板只引用正式材料与结果协议，阶段行为由对应一级正文提供。
2. 在启动资格及首轮 prepare 核对固定启动提交和目录来源。能保证内容固定的现有只读快照机制优先复用。若原项目目录可能在调用期间移动或包含未纳入启动提交的修改，使用隔离且固定在该提交的只读工作目录。固定目录的创建、来源和清理由宿主管理，SteerAgent 只获得只读访问。先在固定 Runner 核实实际访问限制和来源契约，无法提供时给出具体阻断。
3. 以首条三级指令的已保存投递事实区分首轮和后续。投递结果未知时先按原号对账。首轮调查已给出充分无改动证据且确认没有可写执行或成果时，保存结论后直接走报告。后续决策与报告用只读 `generate/1` 和正式文件材料，实际请求省略 `directory`、`repository` 及可供浏览的项目路径或工作区授权。以原请求、文件 manifest 和原生 Final 核对结果来源。
4. 从现有操作记录按用途组装有界上下文。后续决策优先取当前指令、关键反馈、未决问题、相关成果摘要和答复；报告按最终版本取关键差异与验证，附全行动的轮次摘要。保留摘要的原操作身份，避免重复携带历史原请求或大段原始反馈。固定材料与必要证据以现有限额校验，超限或缺证记录具体缺口；补证复用原操作记录判断是否有新证据。原始记录保持可查。
5. 改造可写 `execute/1` 的初始化文件，只保留原三级指令、身份和本次执行事实，按用途附加报告原文。移除完整一级规则、二级方向正文、策略正文和历史对话的可写接线。维护可写请求要求派发前核验本轮种子；初始化阻断时按原 Run 停止、封存并记录诊断。保留原 worktree 最新持有者、原请求绑定、停止与用量结算。

### P2 · 结构化人工决策

1. 将决策输出 schema、业务校验、行动问题和答复 DTO 升级到 Spec 的结构。按 Spec 转换表校验每个用途允许的 kind、字段互斥及选项引用，由 worker 映射实际执行用途。核对封存的 Runner `needs_input` 后交回 SteerAgent。由后端生成问题 ID，保存来源操作及恢复用途，CAS 进入等待。
2. 扩展原维护答复路由、事务、查询和页面。展示结构化选项、影响和推荐，绑定 `question_id`、行动版本、选项和补充说明；沿现有命令 journal 去重。答复、结束与停止按同一行动版本仲裁。重启恢复原问题与计时，已等待的行动没有后继投递；恢复时由原阶段重新决策，答复原文和生成的三级指令各自保存。

### P3 · 分离 PR 核验、报告和同步

1. 让发布/冲突执行只交付 PR 事实及最终证据。复用现有平台查询，补齐已支持 provider 的目标分支 base SHA，分别核验版本和同步结果。平台查询的 head/base 为报告绑定，Runner 回传的差异和验证必须能对应这一版本。启动提交保留在原仓库来源字段。受理资格和待核实原因反映缺少可信字段的情况。
2. 把已核验版本及匹配的关键差异交给独立报告 generate。无改动结论走同一报告入口。报告阶段返回缺证项时，复用后续决策和原 worktree 补证，封存后直接回版本核验和报告。由原操作记录识别缺口是否获得新证据。同一缺口无新证据时保存诊断。报告成功时原子保存正文、版本、参考费用快照和同步三级指令。
3. Runner 按已保存请求更新原 PR 正文。同步三级指令引用随附的 PR 身份、版本和报告数据，后端以材料中的绑定为准。同步前使用已认证工具核对 head/base，通过原文字节文件更新，完成后独立核验版本和平台正文与保存原文一致。未知写入只对账原请求与平台事实；明确失败且可重试时复用原报告及指令。
4. 版本变化时停用旧同步绑定，保留原 PR 和旧报告。核验新版本后复用后续成果审计。只有证据适用于新版本才生成新版，需要时补证或重验；确需修改成果时继续原 PR 收尾。反复变化且证据仍无法覆盖时，保存诊断，沿已有维护命令显式继续。手动冲突续作在进入收尾前保存原 PR 最新核验版本，给 SteerAgent 提供该版本与续作事实。由保存事实投影已发布未同步、待复核和已交付状态。
5. 停止、迟到结果及同构建重启遵循 [Runner 调用生命周期](../../docs/product-design/runner-lifecycle.md#跨节点恢复规则)。同步长期产品、架构、现有客户端协议、Runner 接入及提示词治理文档中受本期影响的段落。

### P4 · 提示词独立审核与验证

保留旧资产和代表请求的基线。实施后提交完整正文差异、UTF-8 字节前后值、业务理由和验证，包含替换的短模板、一级/策略材料及实际只读与可写请求的接线。按 [提示词治理](../../docs/prompt-governance.md)核对真实请求、缺材料阻断和黄金样本。请独立审核者复核最终正文、接线和测试变更；黄金样本更新不能代替批准。差异及实际验证登记到专属验收。
